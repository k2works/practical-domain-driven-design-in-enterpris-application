# cargo-tracker フロントエンドアーキテクチャ

## 位置づけ

本書は、[要件定義](../../requirements/cargo-tracker/requirements_definition.md) の画面・帳票モデル（UI-01〜UI-06、RP-01、RP-02）と [ユーザーストーリー](../../requirements/cargo-tracker/user_story.md) の横断受入条件（BR-13）をもとに、画面の提供方式を決める。開発ガイドライン [第 3 章](../../article/03-spring-modular-monolith.md) の受信サービス（ネイティブ Web API：Thymeleaf + htmx）に合わせ、画面を各コンテキストの `interfaces.web` から提供する（ADR-005）。製品は Thymeleaf 3.1・htmx 2.0・Bootstrap 5.3 とし（ADR-006、[技術スタック](tech_stack.md)）、画面ごとの設計は [UI 設計](ui_design.md) で行う。

## 利用チャネル

| チャネル | 利用者 | 対象画面 | 導入段階 |
| :--- | :--- | :--- | :--- |
| 顧客 Web | 荷主担当者、荷受人 | UI-01 顧客予約、UI-04 顧客追跡、RP-01 予約・経路確認書 | MVP（荷受人の直接照会 US-10 は Could） |
| 社内業務 Web | 営業担当者、経路設計者、追跡管理者、データ責任者、カスタマーサポート、システム管理者、監査担当者 | UI-02 社内予約・見積、UI-03 経路設計、UI-05 追跡管理、取込・照合、利用者管理、RP-02 監査証跡 | MVP |
| 現場入力 UI | 荷役作業員 | UI-06 現場入力 | 第 2 段階（オフライン対応が必要なため、方式は第 2 段階の計画時に改めて決める） |

## レンダリング方式

**サーバーが HTML を返し、部分更新にハイパーメディア（htmx 相当）を使う。** クライアント側に業務状態を持つ SPA は作らない（ADR-005）。例外は session の警告で、ブラウザの時計で開き、延長だけを `fetch` で送る（Bolt 32b。下の「session の警告と延長」）。もう 1 つの例外は失効の時の入力の保持で、送信していない入力の写し（入力の控え）をブラウザのそのタブ（sessionStorage）に置き、ログインし直した後にブラウザが戻す（Bolt 32f。下の「入力の控え（Bolt 32f）」）。控えは送信の前の入力の写しで、業務状態の正はサーバーにある（ADR-005 の改訂の経緯）。

| 観点 | サーバーサイドレンダリング + ハイパーメディア（採用） | SPA |
| :--- | :--- | :--- |
| 開示制御（BR-07） | 権限のある項目だけを HTML にする。返していない項目は画面に出ようがない | 画面に出さない項目も API で返さないよう、API 側で別途保証が必要 |
| 社内画面の漏えい | 顧客に返すのは顧客向けの HTML だけ | 社内画面のコードを顧客向けの配信物から除く仕組みが必要 |
| アクセシビリティ（BR-13） | 標準の HTML 要素・フォーム・リンクがそのまま動く。部分更新の箇所だけ通知とフォーカスを扱えばよい | 画面遷移のたびにフォーカス・タイトル・通知を自前で管理する |
| 期待版・冪等性 | フォームの隠し項目で `commandId` と版を往復させる | クライアントの状態管理と API クライアントで共通化する |
| 構成 | バックエンドと同じデプロイ単位。フロントエンドのビルドと配信が不要 | フロントエンドのビルド・配信・バージョン整合が増える |
| 苦手なこと | 高頻度で双方向にやり取りする画面（例: オフラインの現場入力） | — |

MVP の画面は、フォーム入力、一覧・詳細の照会、比較、承認が中心で、高頻度の双方向操作はない。苦手な領域にあたる現場入力 UI は第 2 段階の対象外である。

## 画面の配置

画面は、それを所有するコンテキストの `interfaces.web` に置く（第 3 章 Package structure for interfaces）。画面がコンテキストをまたぐ場合は、主たる操作を持つコンテキストに置き、他のコンテキストの情報はそのコンテキストのクエリから得る。

| 画面 | 所有するコンテキスト |
| :--- | :--- |
| UI-01 顧客予約（輸送条件の下書き・提出・見積りの承認） | 見積り |
| UI-01 顧客予約（本予約の状態・変更・取消しの申請） | 予約 |
| UI-02 社内予約・見積 | 見積り、予約 |
| UI-03 経路設計 | 経路設計 |
| UI-04 顧客追跡、UI-05 追跡管理 | 追跡 |
| 取込・照合 | 外部データ |
| 利用者管理、RP-02 監査証跡 | アクセス・監査 |
| RP-01 予約・経路確認書 | 予約 |

共通のレイアウト、アクセシブルな部品、日時表示は共有の Web 基盤（コンテキストに属さない `shared` の `interfaces.web`）に置く。業務規則は置かない。

### 顧客向けと社内向けの分離

| 項目 | 方式 |
| :--- | :--- |
| URL | 顧客向け（例: `/customer/**`）と社内向け（例: `/staff/**`）で領域を分ける |
| 認可 | 領域ごとに認可規則を設定し、顧客向けの領域では荷主担当者・荷受人の役割だけを許可する |
| レイアウト | 顧客向けと社内向けで別のレイアウトとナビゲーションを使う |
| クエリ | 顧客向けの画面は、顧客向けのクエリ（開示範囲に絞った読み取り）だけを使う |

## 変更操作の共通処理

各画面で実装せず、共有の Web 基盤で共通化する。

1. 変更用のフォームを表示するときに `commandId` を発行し、対象の版とともに隠し項目に入れる。再送時は同じ `commandId` が送られる（ARCH-HO-01）。
2. 期待版の不一致は競合として受け、最新版の内容と差分を表示して再確認を求める。
3. 処理中・完了・失敗・有人確認要（ARCH-HO-02）を区別して表示する。処理中を成功として表示しない。
4. 入力エラーのときは入力値を保持して同じフォームを返し、エラー要約を表示する（BR-13）。

業務規則を画面で判定しない。たとえば見積りの有効判定（BR-10）は、サーバーの判定結果を表示するだけにする。

## アクセシビリティ（BR-13、NFR-ACCESS-01）

WCAG 2.2 AA を目標とし、個々の画面の注意に頼らず共通部品と仕組みで保証する。

| 要求 | 担保する部品・仕組み |
| :--- | :--- |
| キーボード操作、可視フォーカス | 標準の HTML 要素を使う。フォーカス表示を消すスタイルを lint で禁止する |
| 明示ラベル、エラー要約、値の保持 | フォーム部品とエラー要約部品。エラー時は要約へフォーカスを移す |
| 色だけに依存しない状態表示 | 状態バッジ部品（文字とアイコンを必須にする）。予定・実績・確認中を区別する（RQ-03） |
| 非同期更新・確認中への遷移・escalation の通知 | 部分更新した領域をライブリージョンにし、支援技術へ通知する |
| 重要操作の実行前確認 | 確認画面の部品。対象・現在状態・変更内容・影響・実行者・回復手段を必須の項目にする |
| 日時の表示 | 日時表示部品。利用者のタイムゾーンと UTC offset を必ず付ける（BR-10） |
| 帳票（RP-01） | 印刷用のスタイルを持つ HTML として提供する |

検証は、部品単位の自動チェック、主要フローの自動テスト、支援技術を使った手動確認を組み合わせる。配分はテスト戦略（後続工程）で決める。

## 開示制御（BR-07）

権限外の情報を HTML に含めないことで開示を防ぐ。画面上で隠すことを防御にしない。

- 顧客向けのクエリは、荷受人の開示範囲（到着予定、現在状態、主要実績、最終更新時刻）だけを読み取る。
- 参照許可が取り消されたら、次のリクエストで拒否する。既存の session でも対象の予約は表示しない。
- 顧客向けの各画面について、料金・契約条件・書類が HTML に含まれないことを自動テストで確認する。

## 多言語と session の時間制限

| 項目 | 方式 | 根拠 |
| :--- | :--- | :--- |
| 多言語 | 荷受人向けの画面（C-11、C-12）と招待メールは、Spring の MessageSource で日本語と英語を切り替える。言語は利用者の設定、なければブラウザの言語で決める。その他の画面は日本語 | US-10、US-19、レビュー R-10 |
| session の時間制限 | 無操作による失効と発行から 8 時間の上限の 5 分前に警告し、無操作の期限は画面を移らずに延長できる（Bolt 32b。下の「session の警告と延長」）。失効したときは、再認証の後に GET で開いていた業務の画面へ戻す（Bolt 32e。サーバーが失効を見つけたときに要求を覚える。下の「期限の到来の案内のリンクと戻り先」）。送信していない入力は、失効の時にブラウザのそのタブ（sessionStorage）の入力の控えに写し、同じ利用者が同じ画面に戻ったら戻す。送信が拒まれたら、ログインし直した後の画面に案内を出す（Bolt 32f。下の「入力の控え（Bolt 32f）」） | WCAG 2.2.1、US 横断受入条件、レビュー R-15、ACC-06 |

### session の警告と延長（Bolt 32b）

文言とフォーカスの動きは [UI 設計](ui_design.md) の共通部品「session の警告（Bolt 32b）」に置く。

- **置き場所**: 警告の部分（`templates/layout/session-warning.html`）を共通のレイアウト `layout/customer`・`layout/staff` の body の最後に入れ、`/js/session-timeout.js` は警告の部分の中に置く（出す条件を 1 か所にする。Bolt 32b の開発レビュー）。`layout/public` には置かない。CSP（`default-src 'self'`）がインラインのスクリプトを許さないので、外部のファイルにする（`transport-request-form.js` と同じ）
- **残り時間はサーバーが出した秒数から数える**: ログインした画面の応答に、無操作の期限の秒数（`HttpSession.getMaxInactiveInterval()`。今は 1800）と 8 時間の上限までの残りの秒数を、警告の部分の `data-` 属性で出す。ブラウザは残りを問い合わせる定期の request を送らない（問い合わせ自体が無操作の期限を延ばしてしまう）
- **タブの間の同期**: 画面の読み込みと延長の 204 の時刻を「最後の request の時刻」とし、`localStorage` のキー `cargotracker.session.lastRequestAt` に置く。値はミリ秒の時刻だけで、業務データ・利用者の識別子・session ID は置かない（`localStorage` はタブとログインをまたいで残り、利用者を区別しないため。Bolt 32f の入力の控えは sessionStorage に置き、利用者の ID を持つ。下の「入力の控え（Bolt 32f）」）。ログアウトしても消さない（次のログインの画面の読み込みで上書きされる）。無操作の期限は「最後の request の時刻 + 無操作の秒数」、8 時間の期限は「読み込みの時刻 + 8 時間の残りの秒数」とし、早いほうの 5 分前に警告を開く。読み込みにかかった時間だけブラウザの期限がサーバーより遅れないよう、どちらの期限も 10 秒早める。ほかのタブが `localStorage` を更新したら（`storage` のイベント）数え直し、要らなくなった警告を閉じる。`localStorage` を使えないときは、そのタブの時刻だけで数える。ブラウザの「戻る」（bfcache から戻った画面は `storage` のイベントを受け取っていない）とタブを見えるようにしたとき（`pageshow`・`visibilitychange`）も `localStorage` を読み直す
- **延長は htmx でなく `fetch`**: 延長は `POST /session/extend` を CSRF のトークン付きで `fetch` で送る。htmx（XHR）は 302 を黙って追い、A-03 の HTML を 200 で受けるので、失効を見分けられない。`fetch` は `redirect: 'manual'` で 302 を `opaqueredirect` として受けられる。204 なら閉じ、`opaqueredirect`（失効した session は A-03、ログインしていない session は A-01 へ移される）なら期限の到来の案内に替え、それ以外（403・500・通信の失敗）は「延長できませんでした」を示す。警告を開く時刻もブラウザだけの関心で、サーバーの部分を返す request が要らない。よって ADR-005 の「部分更新はハイパーメディアで」の例外にする。警告と延長のためにブラウザが持つのは時刻だけである（業務の入力をブラウザに持つ例外は Bolt 32f の入力の控えだけ）
- **数える request と既知の制約**: 今のテンプレートに部分更新の request（`hx-get`・`hx-post`）はなく、画面の操作はすべて画面の移動である。`SessionLifetimeFilter` は公開の資源（`/js/**` など）でも session を読むので、資源の request でもサーバーの期限は延びるが、資源は画面の読み込みと同時に読まれる。よってブラウザは「画面の読み込み」と「延長」を数えれば足りる。部分更新を足す Bolt で、その request も数える。ブラウザが数えない request（`layout/public` の A-04・エラーの画面、書類のダウンロード）でもサーバーの期限は延びるので、ブラウザの期限はサーバーより早く来ることがある。安全側なので受け入れ、期限の到来の文言は断定しない
- **期限の到来の案内のリンクと戻り先（Bolt 32e）**: 認証の入口の `SessionLifetimeFilter` が、GET で許す一覧（`/customer/**`・`/staff/**`）に当たる request のときだけ戻り先（context path を含む path と query）を request の属性に置き、`SessionTimerAdvice` がそれを `sessionTimer` に足す。警告の部分はそれを `data-return-path` に書き、`session-timeout.js` は期限の到来の案内のリンク「もう一度ログインする」（`data-session-return` の印）の行き先を、同じ origin の path と query に限ってそれにする（戻り先がなければ今どおり `/session-expired`）。戻り先はサーバーが受けた request から作るので、ほかのサイトへは移らない。送信の後の画面（POST で描き直した入力の誤りの画面）には渡さない（送信の URL を開き直すと別の画面か 405 になる）。リンクで開き直したとき、サーバーの session が切れていれば失効の扱いが要求を覚えて A-03 へ移し、ログインし直すと同じ画面に戻る。延長が失効で失敗した後は、失効の扱いがすでに新しい session を作っているので、開き直すと A-01 へ直接移り、ログインの後に同じ画面に戻る。ブラウザの期限が早く来ていて session が生きていれば、その画面がそのまま開く（Bolt 32f から、入力の控えを戻す）。戻り先のためにブラウザが持つのは、サーバーが画面に書いた戻り先の path と query だけである（Bolt 32f から、入力の控えにも同じ戻り先を写す）。Bolt 32f から、戻り先があれば案内のリンクの語を「画面を開き直す」にし、押すと入力を控えに写してから開く（戻り先がなければ「もう一度ログインする」のまま）
- **入力の保持（Bolt 32f）**: 下の「入力の控え（Bolt 32f）」に置く
- **部品の置き場所**: 残り時間をモデルに足す `SessionTimerAdvice`（`@ControllerAdvice`）と延長の `SessionController` は `identity.interfaces.web` に置く。共通のレイアウトの属性を足す前例は `CurrentActorAdvice`（ヘッダーの利用者）で、同じ置き場所にある。session の期限は認証の関心で、8 時間の起点は identity の認証の入口（`SessionLifetimeFilter`）、上限の長さは identity のドメインの `SessionPolicy`（Bolt 33c）にあるので、共有の Web 基盤（`shared`）には置かない（値の受け渡しは [バックエンドのアーキテクチャ](architecture_backend.md)）。`SessionTimerAdvice` が読む request の属性の名前（8 時間の残り・戻り先）は、認証の入口と同じ application 層の `SessionKeys`（`identity.application.internal.session`）の定数を参照する。警告の部分（`session-warning.html`）の A-03 の URL と、共通のレイアウト（`layout/customer`・`layout/staff`）・A-08 の画面の A-08 の URL も、テンプレートに直書きせず `SessionKeys` の URL を使う。画面の層の `SessionUrlsAdvice`（`identity.interfaces.web`、`@ControllerAdvice`）がモデルの `sessionUrls`（`reEnroll` と `expired`）として `SessionKeys` の URL を渡し、テンプレートは `@{${sessionUrls.reEnroll}}`・`@{|${sessionUrls.reEnroll}/later|}`・`@{${sessionUrls.expired}}` で参照する（Thymeleaf のリンク式は制限された式の評価で、静的なクラスを `T(...)` で参照できないため）。表示と振る舞いは変えない（Bolt 33c。それまでは入口と画面の層の 2 つの定数で持ち、一致をテストで守っていた）Bolt 33f から、A-08・A-03 の URL は同じパッケージの `SessionPaths` に分けた（`SessionKeys` は名前だけ）。

### 入力の控え（Bolt 32f）

失効の時に送信していない入力を、ブラウザのそのタブに「入力の控え」として写し、同じ利用者が同じ画面に戻ったら戻す（ACC-06、US の横断受入条件の「未保存の入力は失われず再認証後に再開できる」）。業務の「下書き」（輸送要求の版の状態など）とは別のもので、サーバーには置かない。文言と知らせの振る舞いは [UI 設計](ui_design.md) の共通部品「入力の控え（Bolt 32f）」、利用者の確かめ・捨てる時・個人情報の扱いの決定は ADR-012、業務状態をクライアントに持たない方針の例外は ADR-005 に置く。

- **スクリプト**: `/js/session-input.js` の 1 つのファイルを、ログインした画面（警告の部分 `layout/session-warning` の中）と公開の画面（`layout/public`）の両方で読み、置かれた画面で役割を切り替える。CSP（`default-src 'self'`）のため外部のファイルにする。`/js/**` は公開の URL
- **置き場所とキー**: sessionStorage のキー `cargotracker.session.savedInput` に 1 件の JSON を置く。中身は、利用者の ID、戻り先（正規化したもの）、写した時刻、写した理由（`expired`・`reopen`・`submit`）、公開の画面を経た印（拒まれた印）、欄の値の一覧（フォームの順番・欄の名前・種類・値・ファイルの欄があったか）。sessionStorage はタブごとで、タブを閉じれば消える。1 つのタブに 1 件で、新しく写したら置き換える。sessionStorage を使えないときは何もしない（写さず、戻さない）
- **利用者の鍵**: 警告の部分に `data-user` として、利用者の ID の一方向の値（`SessionTimerAdvice.ownerKey`。`UserId` の SHA-256 の先頭 16 文字、URL で使える Base64）を出す。同じ利用者かどうかだけが分かり、画面に内部の識別子（UUID）を出さない（画面の HTML に UUID を出さない既存の確かめを守る。Bolt 32f の実装で見つけた。理由は ADR-012）。`localStorage`（タブの間の同期）には今までどおり利用者の識別子を置かない
- **写す時**: 期限の到来は `session-timeout.js` が出す CustomEvent `cargotracker:session-expired` で受け、取り消し（ほかのタブの延長や期限のぎわの 204。`unexpire()`）は `cargotracker:session-unexpired` で受けて、期限の到来で写した控えを捨てる（2 つのスクリプトを互いの内部に依存させない）。2 つのイベントは `document` に出し、詳細（`detail`）を持たない。`session-expired` は期限の到来の案内を差し込む直前、`session-unexpired` は案内を取り消した直後に出す。聞き手は入力の控えのスクリプトが DOMContentLoaded で登録するので、警告の部分で `session-input.js` を `session-timeout.js` より前に読む（どちらも defer。期限の到来はタイマーの後なので、登録の前に出ることはない。読み込みの直後に期限を過ぎている画面を足すときは、発火を DOMContentLoaded の後に遅らせる）。「画面を開き直す」は、後から差し込まれる案内の領域でクリックを受けて写してから開く。送信の前は、`main` で POST のフォームの `submit` を受ける（ヘッダーのログアウトと警告の延長のフォームは `main` の外なので写らない）。どれも戻り先（`data-return-path`）のある画面でだけ写す
- **写す欄**: `main` の中の POST のフォーム（`method`・`action` は欄の名前に隠されないよう属性で読む）の、テキスト・数・日付・選択・ラジオ・チェックの欄と `textarea` のうち、初期の値（`defaultValue`・`defaultChecked`・`defaultSelected`）から変えた欄だけ。password・hidden（CSRF のトークンを含む）・ファイル・ボタンは写さない。GET のフォーム（照会）は写さない。変えた欄がなければ写さず、前の控えを残す。拒まれた送信の控えは、ほかの画面の送信では置き換えない
- **戻り先の正規化**: 写すときと比べるときは同じ関数で、戻り先の query から `continue` を除き、それ以外は生の文字列のまま残す（ログインし直して戻った画面の戻り先には `?continue`・`&continue` が入るため。Bolt 32e）。比べる相手は今の画面の `data-return-path` で、`location` でない
- **公開の画面での印**: 印を付ける画面を明示する（opt-in）。送信が拒まれた画面の `main` に `data-session-input="rejected"` を置き、公開のレイアウトで読み込まれたスクリプトは、その印があるときだけ控えに拒まれた印を付ける。置くのは A-03（`identity/session-expired`）、413、CSRF の拒否の 403 である。403 は認可の拒否と CSRF の拒否で同じ画面なので、`SecurityConfiguration` の `AccessDeniedHandler` が `CsrfException` のときだけ request の属性 `sessionInputRejected` を置き、403 の画面がそれを見て印を出す。A-01 と認可の 403 には置かない（公開のレイアウトを使うだけで印を付けると、ログアウトでない 403 や、将来の「届いた送信の結果が公開の画面」の業務で、届いた送信を戻して二重の送信を招く。Bolt 32f の開発レビュー）。A-03 では、控えがあり、戻せる見込みがあるとき（8 時間を過ぎていない、送信が届いた控えでない）だけ一文を足す（文言は UI 設計）。公開の画面では戻さない。8 時間を過ぎた控えは捨てる。ログアウトの後のログインの画面（`/login?logout`）では控えを捨てる（ヘッダー以外の経路でログアウトしたとき）
- **ログインした画面で**: 読み込みの後に、捨てる条件（形が合わない、利用者が違う、写してから 8 時間を過ぎた、送信の控えで印がない（送信が届いた））を見て、当たれば捨てる。残れば、今の画面の戻り先と同じなら戻して知らせ、控えを捨てる。違えば、拒まれた印のある控えについて、案内と「入力していた画面を開く」（控えの戻り先を `sameOriginPath` で同じ origin の path と query に限る。`//`・`/\` で始まる path は拒む。`session-timeout.js` にも同じ確かめがあり、片方だけ直さないよう両方のコメントで指し合う）「入力していた内容を消す」を出す。印がなければ捨てる（ログアウトしていない）。ヘッダーのログアウトの送信で捨てる。イベントの聞き手は戻す前に登録し、戻す処理が失敗しても控えを捨てて画面の初期化を止めない
- **戻し方と順序**: 欄に `.value`・`.checked` で値を入れ（HTML として解釈しない。`innerHTML` を使わない）、`input`・`change` のイベントを出す。画面のスクリプトの初期化の後に戻すため、DOMContentLoaded で戻す（`transport-request-form.js` は head で defer、入力の控えのスクリプトは警告の部分（body の最後）で defer なので、DOMContentLoaded の扱いは画面のスクリプトが先に動く）。C-03 は段階 1 のまま（段階の位置は控えない）
- **知らせの領域**: `layout/customer`・`layout/staff` の `main` の前に空の live region（`aria-live="polite"`・`aria-atomic="true"`。画面の結果の知らせの `role="status"` と区別するため role は付けない）を置いておき、後から文言を入れる。文言は `load` の 500 ms 後に入れる（読み込みの直後の更新は支援技術が捨てることがある）。フォーカスは移さない
- **送信が届いたかの判定**: サーバーに問い合わせない。送信の次に読み込んだ画面がログインした画面なら届いた、送信が拒まれた画面（印のある A-03・CSRF の 403・413）なら拒まれたとみなす。8 時間のぎわで、送信が届いた直後の移動（PRG の GET）が A-03 になると、届いた送信の控えが残り、戻りうる（まれ。既知の課題。ADR-012）
- **既知の制約**: 送信の後に入力の誤りで描き直した画面には戻り先がないので写さない。ほかのタブ・ほかのブラウザでは戻らない。閉じたタブを開き直したとき（ブラウザの復元、タブの複製）には sessionStorage が残ることがある（共用のパソコンではログアウトで捨てる。マニュアル 2.1）。XSS があれば控えも読まれる（SEC-17）
- **取消しの扱い**: 利用を止められた利用者もブラウザでは失効と見分けられず、控えはそのタブに残る。戻るのは同じ利用者がログインし直せたときだけで、止められている間はログインできない。別の利用者がログインすると捨てる（Bolt 32e の「止められた利用者には保持しない」を Bolt 32f の開始準備で変えた。ADR-012）
