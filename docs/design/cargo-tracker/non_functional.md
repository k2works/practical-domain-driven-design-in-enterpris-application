# cargo-tracker 非機能要件

## 位置づけ

本書は、[要件定義](../../requirements/cargo-tracker/requirements_definition.md) の横断品質要求（NFR-AUTH-01〜NFR-PRIVACY-01）を測定可能な目標値にし、各設計書で非機能要件に送った項目に答える。

### 値の扱い

本書の値は、パイロットの規模とこれまでの設計を根拠にした **AI の提案** である。各値に決定者を付け、決定者の承認をもって確定する。承認までは、設計・テスト・運用は提案値を前提に進め、変わったら本書から更新する。

| 状態 | 意味 |
| :--- | :--- |
| 確定 | 要件定義で承認済みの規則（BR-14 など）から決まる値 |
| 提案 | AI の提案。決定者の承認待ち |

要件定義の MVP パイロット境界から、次の規模を前提にする。値は仮定であり、OQ-01（パイロット顧客・航路・案件数）の決定後に見直す。

| 利用者数 | 社内 50 名、顧客 150 名 | 8 役割と荷主担当者・荷受人 |
| 同時利用者（ピーク） | 50 名 | 利用者の 25% |
| 本予約の件数 | 月 300 件 | PV-01 の観測（4 週間または 30 件）を満たし、余裕をとる |

## 可用性と復旧（NFR-AVAIL-01、NFR-RECOVERY-01）

### 稼働時間と SLO

荷主・荷受人はアジアと欧州にいるため、顧客 Web は日本時間の夜間も使われる。

| ID | 項目 | 目標値 | 状態 | 根拠 |
| :--- | :--- | :--- | :--- | :--- |
| AVL-01 | 提供時間 | 24 時間 365 日（計画停止を除く） | 提案 | アジア・欧州の時差 |
| AVL-02 | 月間の稼働率（SLO） | 99.5% 以上（月の停止 約 3.6 時間以内） | 提案 | パイロットとして、Multi-AZ の単一リージョン構成で無理なく達成できる水準。SLA（契約上の約束）にはせず社内の目標とする |
| AVL-03 | 計画停止 | 月 1 回、日曜 02:00〜04:00 JST（欧州の土曜夕方〜夜）。7 日前に画面で告知 | 提案 | ローリングデプロイ（インフラ設計）で通常の配備は停止しない。DB の保守など止める必要があるときだけ |
| AVL-04 | 外部情報の停止時 | 業務は止めず、BR-08 の手動情報と BR-17 の有人案件へ縮退する | 確定 | BR-08、BR-17、BR-18 |

### RPO・RTO

| ID | 項目 | 目標値 | 状態 | 根拠と実現方法 |
| :--- | :--- | :--- | :--- | :--- |
| RCV-01 | RPO（DB） | 5 分 | 提案 | RDS の時点復旧（PITR）で達成できる。本予約の確定が失われると重複予約の原因になる（PV-01）ため、短くする |
| RCV-02 | RPO（外部原本） | 0（失わない） | 確定 | PV-01 の外部原本消失 0 件。S3 のバージョニングと Object Lock（ADR-008） |
| RCV-03 | RTO（AZ の障害） | 15 分 | 提案 | RDS Multi-AZ の自動切替（通常 1〜2 分）と、ECS のタスクを複数の AZ に置くことで達成する |
| RCV-04 | RTO（DB の論理障害、誤操作） | 2 時間 | 提案 | 時点復旧で別のインスタンスへ戻し、切り替える手順（運用要件で手順書にする）。パイロットの DB の規模では時点復旧は 1 時間以内に終わる見込み。月の停止許容（AVL-02 の約 3.6 時間）に収めるため 2 時間とする |
| RCV-05 | RTO（リージョンの障害） | 対象外（パイロット） | 提案 | 別リージョンへの切替は費用に見合わない。バックアップの別リージョン複製だけを行い、復旧は数日を許容する |
| RCV-06 | Multi-AZ | 本番の RDS は Multi-AZ、ECS は 2 つ以上の AZ に分散。ステージングは Single-AZ | 提案 | RCV-03 を満たすため |
| RCV-07 | 復旧後の照合 | DB を戻したら、戻した時点以後に起きたことを DB の外の記録と照合して再処理する。照合に使うのは、外部原本（S3）、本予約の確定・荷主の承認・実績の採用の構造化ログ（commandId・追跡番号などの業務キーを含み、CloudWatch Logs に残る）である。DB の中のイベント発行記録は戻した時点で失われるため使わない | 提案 | RPO 5 分の間に顧客へ示した追跡番号などを復元するため（R-20） |
| RCV-08 | 復旧の訓練 | 本番開始前に 1 回、その後は半年に 1 回、時点復旧の手順を実施して RTO を測る。あわせて、復旧できた最新の時刻を確かめて RPO を実測し、RCV-07 の照合まで行う | 提案 | 手順は使わないと壊れる |

## データ鮮度（NFR-FRESH-01）

| ID | 対象 | 許容範囲 | 超えたときの扱い | 状態 | 決定者 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| FRS-01 | 航海・港湾の採用値 | 最終取得から 24 時間 | 経路候補に「情報が古い」と示し、R-INV-09 の情報不足として扱う | 提案 | 追跡・データ責任者 |
| FRS-02 | 輸送中の追跡（次の予定の実績） | 予定時刻を過ぎ、かつ最後に取り込んだファイルの取得時刻が予定時刻から 36 時間以上たっても実績がない | 追跡を「確認中」（鮮度超過）にし、追跡管理者の一覧に出す | 提案 | 追跡責任者 |
| FRS-03 | 顧客向けの表示 | 最終取得時刻を常に表示する。FRS-02 を超えたら「最新性を保証しない」旨と次回更新日時・担当窓口を示す | — | 確定（US-09、US-10） | — |
| FRS-04 | 承認済み情報源のファイル取込の頻度 | 1 日 1 回以上 | 当日の取込がなければ 11:00 JST に追跡・データ責任者へ通知する（午後に対応できるように） | 提案 | 追跡・データ責任者（OQ-02 の残り） |

パイロットは手動取込（BR-18）のため、鮮度は 1 日単位になる。FRS-02 は取込の周期（1 日）に余裕を足した閾値にし、取込の待ちだけで確認中が乱発しないようにした（レビュー R-12）。KPI-03（状態反映時間）の基準値を測ったうえで、第 2 段階の自動連携で短くする。

## セキュリティ（NFR-AUTH-01、NFR-AUDIT-01）

### 認証（BR-14 と残りの決定）

| ID | 項目 | 値 | 状態 | 根拠 |
| :--- | :--- | :--- | :--- | :--- |
| SEC-01 | 認証方式 | 事前登録したメールアドレス + password + TOTP | 確定 | BR-14 |
| SEC-02 | ロック | 5 回連続失敗で 15 分 | 確定 | BR-14 |
| SEC-03 | session | 無操作 30 分、発行から 8 時間で失効 | 確定 | BR-14 |
| SEC-04 | password の長さ | 12 文字以上、64 文字以下。空白と全角文字を許す | 提案 | NIST SP 800-63B は多要素認証と組み合わせる password に最低 8 文字を求める。業務データを扱うため余裕をとる |
| SEC-05 | password の構成規則 | 文字種の組合せは強制しない。漏えい済みの password の一覧と、よく使われる password の一覧に載っているものは拒否する | 提案 | NIST SP 800-63B の考え方（構成規則より漏えい一覧との照合） |
| SEC-06 | password の定期変更 | 強制しない。漏えいの疑いがあるときだけ変更を求める | 提案 | 同上 |
| SEC-07 | password の保存 | Spring Security の推奨するハッシュで保存する。DelegatingPasswordEncoder の既定の bcrypt（強さ 10、`{bcrypt}` の接頭辞）を使う（2026-10-06 の Bolt 14 の確認ポイント 6。Argon2id は Bouncy Castle が要るため採らない。接頭辞で後から移せる） | 確定 | 平文や可逆な暗号で保存しない |
| SEC-08 | password の回復 | 登録メールアドレスへ 1 回だけ使える再設定リンク（30 分有効）を送る。再設定後も TOTP は必要。再設定は監査記録に残す | 提案 | 多要素を回復の手順でも迂回させない |
| SEC-09 | TOTP の登録 | 初回ログイン時に必須。登録時に一度だけ使える回復コード 10 個を発行する | 提案 | 端末の紛失に備える |
| SEC-10 | TOTP の再登録 | 回復コードを使うか、システム管理者が本人確認（所属企業の管理担当者への確認など、事前に決めた別経路）をしたうえで登録を解除する。解除は監査記録に残し、本人に通知する | 提案 | 管理者による解除を悪用されないよう、本人確認の手順を運用で固定する |
| SEC-11 | ログイン失敗の表示 | どの項目が誤りかを示さない | 確定 | US-18 |

## AI の仮定と要確認

- **規模**: 前提とする規模は要件定義のパイロット境界から推定した値で、実測値ではない。OQ-01 の決定後に見直す。

- **7 年の保持**: 法人の帳簿書類の保存期間を参考にした仮定である。業界規制・契約による要件は確認していない。
- **負荷テストのツール**: 技術スタックに含めていないため、最初の性能テストの Bolt で選定して追加する。
