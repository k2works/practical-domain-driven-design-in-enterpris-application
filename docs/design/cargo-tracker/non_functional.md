### 値の扱い

本書の値は、パイロットの規模とこれまでの設計を根拠にした **AI の提案** である。各値に決定者を付け、決定者の承認をもって確定する。承認までは、設計・テスト・運用は提案値を前提に進め、変わったら本書から更新する。

## 可用性と復旧（NFR-AVAIL-01、NFR-RECOVERY-01）

### 稼働時間と SLO

荷主・荷受人はアジアと欧州にいるため、顧客 Web は日本時間の夜間も使われる。

| ID | 項目 | 目標値 | 状態 | 根拠 |
| :--- | :--- | :--- | :--- | :--- |
| AVL-01 | 提供時間 | 24 時間 365 日（計画停止を除く） | 提案 | アジア・欧州の時差 |
| AVL-02 | 月間の稼働率（SLO） | 99.5% 以上（月の停止 約 3.6 時間以内） | 提案 | パイロットとして、Multi-AZ の単一リージョン構成で無理なく達成できる水準。SLA（契約上の約束）にはせず社内の目標とする |
| AVL-03 | 計画停止 | 月 1 回、日曜 02:00〜04:00 JST（欧州の土曜夕方〜夜）。7 日前に画面で告知 | 提案 | ローリングデプロイ（インフラ設計）で通常の配備は停止しない。DB の保守など止める必要があるときだけ |

### RPO・RTO

| ID | 項目 | 目標値 | 状態 | 根拠と実現方法 |
| :--- | :--- | :--- | :--- | :--- |
| RCV-01 | RPO（DB） | 5 分 | 提案 | RDS の時点復旧（PITR）で達成できる。本予約の確定が失われると重複予約の原因になる（PV-01）ため、短くする |
| RCV-02 | RPO（外部原本） | 0（失わない） | 確定 | PV-01 の外部原本消失 0 件。S3 のバージョニングと Object Lock（ADR-008） |
| RCV-03 | RTO（AZ の障害） | 15 分 | 提案 | RDS Multi-AZ の自動切替（通常 1〜2 分）と、ECS のタスクを複数の AZ に置くことで達成する |
| RCV-04 | RTO（DB の論理障害、誤操作） | 2 時間 | 提案 | 時点復旧で別のインスタンスへ戻し、切り替える手順（運用要件で手順書にする）。パイロットの DB の規模では時点復旧は 1 時間以内に終わる見込み。月の停止許容（AVL-02 の約 3.6 時間）に収めるため 2 時間とする |
| RCV-05 | RTO（リージョンの障害） | 対象外（パイロット） | 提案 | 別リージョンへの切替は費用に見合わない。バックアップの別リージョン複製だけを行い、復旧は数日を許容する |
| RCV-06 | Multi-AZ | 本番の RDS は Multi-AZ、ECS は 2 つ以上の AZ に分散。ステージングは Single-AZ | 提案 | RCV-03 を満たすため |
| RCV-07 | 復旧後の照合 | DB を戻したら、戻した時点以後に起きたことを DB の外の記録と照合して再処理する。照合に使うのは、外部原本（S3）、本予約の確定・荷主の承認・実績の採用の構造化ログ（commandId・追跡番号などの業務キーを含み、CloudWatch Logs に残る）である。DB の中のイベント発行記録は戻した時点で失われるため使わない | 提案 | RPO 5 分の間に顧客へ示した追跡番号などを復元するため（R-20） |
| RCV-08 | 復旧の訓練 | 本番開始前に 1 回、その後は半年に 1 回、時点復旧の手順を実施して RTO を測る。あわせて、復旧できた最新の時刻を確かめて RPO を実測し、RCV-07 の照合まで行う | 提案 | 手順は使わないと壊れる |

## セキュリティ（NFR-AUTH-01、NFR-AUDIT-01）

### 認証（BR-14 と残りの決定）

| ID | 項目 | 値 | 状態 | 根拠 |
| :--- | :--- | :--- | :--- | :--- |
| SEC-01 | 認証方式 | 事前登録したメールアドレス + password + TOTP | 確定 | BR-14 |
| SEC-02 | ロック | 5 回連続失敗で 15 分。password・TOTP・回復コードの誤りを合わせて数え、5 回目の失敗の時刻から 15 分ロックする。ロック中の試行は正しい認証情報でも拒み、数えず期限も延ばさない。0 に戻すのは 2 つの要素がそろったログインの成功だけ（password の段の成功では戻さない）。存在しない利用者、password が正しく利用停止・無効な企業で拒んだとき、利用者の読み出しの DB の誤り、TOTP の登録（A-07）のコードの誤りは数えない。password の段では、ロックは password の照合の後に確かめ、応答の時間でロックが分からないようにする（TOTP・回復コードの段は照合の前に確かめ、時間で分かることを受け入れる。ADR-011 の決定 9）。password の再設定ではロックも失敗の数も変えない（ロック中に再設定しても、ロックが解けるまでは新しい password でもログインできない。完了の知らせはロックの有無を示さない。Bolt 33a）。ロックの解除の操作（システム管理者）は US-16（Bolt 34）で作る（Bolt 32。[ADR-011](../../adr/cargo-tracker/011-mfa-totp.md) の決定 9） | 確定 | BR-14 |
| SEC-03 | session | 無操作 30 分、発行から 8 時間で失効。8 時間の起点は、その session で初めて TOTP または回復コードが通った時刻（`FACTOR_TOTP` が与えられた時刻。TOTP は Bolt 31、回復コードは Bolt 31c）。password の段だけの session は、password を確かめた時刻から 5 分で失効（Bolt 31。ADR-011）。ただし TOTP の登録の途中（A-07 を開いた session）は、登録を始めた時刻から 15 分で失効（認証アプリを入れて QR コードを読む時間を見込む。登録を始めた時刻は password の段の 5 分の中でしか置けず、2 つの要素がそろった後は使わない。Bolt 31b。ADR-011 の決定 6） | 確定 | BR-14 |
| SEC-04 | password の長さ | 12 文字以上、64 文字以下。空白と全角文字を許す。Bolt 33a で、文字数は code point で数え、あわせて UTF-8 で 72 バイト以下にする（bcrypt は 72 バイトを超える password で例外を投げるため。2026-10-15 に human:kakimomokuri が決定）。Unicode の正規化はしない（ログインの照合と同時に直す必要があるので、扱うなら別の Bolt。既知の課題）。画面の文言の数値（12・64・72）は password の方針の定数から描く | 提案 | NIST SP 800-63B は多要素認証と組み合わせる password に最低 8 文字を求める。業務データを扱うため余裕をとる |
| SEC-05 | password の構成規則 | 文字種の組合せは強制しない。漏えい済みの password の一覧と、よく使われる password の一覧に載っているものは拒否する。Bolt 33a で、よく使われる password の一覧を同梱して、大文字小文字を区別せずに照合する（一覧の出典と更新の手順は表の下）。漏えい済みの password の照合（HIBP の k-anonymity API など。外部連携）は W10 で扱う（[#49](https://github.com/k2works/practical-domain-driven-design-in-enterpris-application/issues/49)。2026-10-15 に human:kakimomokuri が決定） | 提案 | NIST SP 800-63B の考え方（構成規則より漏えい一覧との照合） |

SEC-05 のよく使われる password の一覧（Bolt 33a。2026-10-15 に human:kakimomokuri が決定）:

- **出典**: SecLists（MIT License）の `Passwords/Common-Credentials/xato-net-10-million-passwords-1000000.txt`。よく使われる上位 100 万語で、元のデータは xato.net の Mark Burnett が公開したものである。
- **同梱する資源**: `src/main/resources/security/common-passwords.txt`（UTF-8、1 行に 1 語）。出典から 12 文字以上の語を抜き出したもの（約 4.6 万語）。12 文字に満たない語は方針の長さで先に拒むので含めない。
- **資源の隣の説明**: 出典の URL、取得したコミット、MIT の著作権表示、抜き出し方、語数を書く。
- **読み込み**: 起動のときに読み、小文字の集合にする。読めない・空なら起動を止める（照合が黙って空振りしないため）。照合は大文字小文字を区別しない。
- **更新の手順**:
  1. SecLists の取得するコミットを決め、そのコミットの上の出典のファイルを取得する。
  2. 各行を UTF-8 で読み、code point で数えて 12 文字以上の行だけを残す。並びと大文字小文字は変えない（小文字にするのは読み込みのとき）。
  3. 資源を置き換え、資源の隣の説明の取得したコミットと語数を直す。
  4. `check` を流し、一覧の照合のテスト（一覧の 1 語、大文字小文字の違い、1 文字違い）が通ることを確かめる。
- 一覧の定期の更新は自動にしない。漏えい済みの password の照合は W10（#49）で扱う。

TOTP の前提: TOTP はサーバーの時計の正しさに依存し、前後 1 つの時間の窓（±30 秒）を超えるずれは認証の障害になる。アプリケーションの実行環境の時計を NTP で同期する（ECS なら Amazon Time Sync Service）。時計の監視と運用の手順は W10 の運用準備で足す（[ADR-011](../../adr/cargo-tracker/011-mfa-totp.md)、Bolt 13 の持ち込み K-04、Bolt 30）。

## AI の仮定と要確認

- **規模**: 前提とする規模は要件定義のパイロット境界から推定した値で、実測値ではない。OQ-01 の決定後に見直す。
- **EU と日本の十分性認定**: EU と日本の相互の十分性認定（2019 年 1 月発効）を前提にしたが、荷受人の担当者の情報への適用と補完的ルールの扱いは法務の確認が必要である。
- **7 年の保持**: 法人の帳簿書類の保存期間を参考にした仮定である。業界規制・契約による要件は確認していない。
- **負荷テストのツール**: 技術スタックに含めていないため、最初の性能テストの Bolt で選定して追加する。
