# cargo-tracker システムユースケース

## 共通方針

- Intent は、予約から基本追跡までの一貫した顧客価値を、根拠・版・出典・監査証跡とともに提供することである。
- 本書はゲート 2 として、MVP の UC-01〜UC-10、UC-16〜UC-20、および段階横断の UC-15 の主成功シナリオを定義する。

## 機能横断の UI 契約

次の条件は UC-01〜UC-10、UC-16〜UC-20 の人が操作する画面・対話部分、および UC-15 の手動取込・差異確認・復旧照合画面に適用する。UC-15 のバックグラウンド取込処理自体はキーボード・フォーカス条件の対象外だが、その結果を表示・操作する UI には適用する。

- WCAG 2.2 AA を目標とし、キーボードだけで操作でき、可視フォーカス、明示ラベル、エラー要約、色だけに依存しない状態表示を提供する。
- 入力エラー時は入力値を保持し、エラーのある項目、理由、修正方法を示して該当箇所へ移動できるようにする。
- 入力エラー、非同期更新、確認中への状態変化、有人案件の escalation は、視覚表示に加えてスクリーンリーダーなどの支援技術が認識できる方法で通知する。
- 本予約確定、取消し、権限変更、実績訂正、荷受人への共有・取消しは、対象、現在状態、変更内容、影響、実行者を示した実行前確認を要求する。
- 回復可能な操作は取消しまたは再実行の手段を示し、回復不能な操作は実行前確認で明記する。

トレース: BR-13、NFR-ACCESS-01、OQ-07。本契約では列挙した機能条件を判定し、WCAG 2.2 AA 全体の適合判定、画面別の操作順序、文言、支援技術による検証は UI 設計とテスト戦略で具体化する。
- 最小保証として、失敗時も確定済みの業務データを失わず、操作主体と処理結果を追跡可能にする。
- 代替・例外フローはゲート 3 で追加する。画面、API、データベースなどの実装方式は規定しない。

4. アクターが条件を提出する。
5. システムが予約版を審査中として記録する。

## U6 予約管理

### UC-04 予約を確定する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 荷主担当者、営業担当者 |
| 事前条件 | 本予約確定の commit 時刻が有効期限より前である見積り、必須貨物情報、荷主担当者 1 名の承認、承認済み経路版が存在する |
| トリガー | 荷主担当者が見積りと承認済み経路を確認して本予約を申し込む |
| 成功時保証 | 有効な予約版と一意な追跡番号が確定する |
| 最小保証 | 承認前の状態と判断履歴が保持される |
| 測定基準 | 確定所要時間、追跡番号重複 0 件 |
| トレース | BUC-02、RQ-01、RQ-02、RQ-04、BR-01、BR-03、BR-10 |

主成功シナリオ:

1. 荷主担当者が見積り、条件、承認済み経路版を確認する。
2. 荷主担当者 1 名が承認して本予約を申し込む。
3. 営業担当者が見積り、必須貨物情報、荷主担当者 1 名の承認、承認済み経路版を確認する。
4. システムが確定処理の commit 時刻を取得し、その時刻が見積有効期限より前であることを確定と同じ整合性境界で検証する。
5. システムが予約版を確定し、追跡番号を発行する。
6. システムが承認者、確定者、commit 時刻を記録する。

MVP の決定: 荷主内の入力者・承認者は分離せず、荷主担当者 1 名の承認と営業担当者の BR-01 確認で本予約を確定する。荷主内の職務分離は後続段階で再検討する。

### UC-05 予約を変更・取消しする

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 荷主、営業担当者 |
| 事前条件 | 対象予約が存在し、アクターが操作権限を持つ |
| トリガー | 荷主が変更または取消しを申し出る |
| 成功時保証 | 本予約前は新しい輸送要求版または取下げ、本予約後から集荷前は営業承認を伴う新しい予約版または取消しが記録される |
| 最小保証 | 変更前の確定版は改変されず参照できる |
| 測定基準 | 変更処理時間、理由欠落 0 件、版の追跡不能 0 件 |
| トレース | BUC-02、RQ-01、RQ-04、BR-04、OQ-04 |

主成功シナリオ:

1. アクターが対象の輸送要求または本予約と、変更または取消し理由を指定する。
2. システムが本予約・集荷実績の有無と操作権限を確認する。
3. 本予約前の場合、システムが旧版を保持して新しい輸送要求版または取下げを記録する。
4. 本予約後から集荷前の場合、システムが申請を営業承認待ちとして記録する。
5. 営業担当者が影響と業務条件を確認して承認する。
6. システムが新しい予約版または取消しを記録し、必要な再見積り・荷主再承認・再設計を示す。
7. システムが影響を受ける関係者と後続業務へ結果を共有する。

判断表:

| 実行段階 | 変更・取下げ／取消し | 承認 | 結果 |
| :--- | :--- | :--- | :--- |
| 本予約前 | 許可 | 不要 | 新しい輸送要求版、または取下げ |
| 本予約後〜集荷実績採用前 | 許可 | 営業承認が必要 | 新しい予約版、または取消済み |
| 集荷実績採用後 | 通常処理は禁止 | 自動承認しない | 要求を記録し、有人の例外対応へ引継ぎ |

## U2 経路設計

### UC-06 経路候補を算出・比較する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 経路設計者 |
| 事前条件 | 経路設計に必要な見積り済み輸送要求が存在する |
| トリガー | 経路設計者が候補算出を開始する |
| 成功時保証 | 候補、除外理由、情報鮮度を比較できる |
| 最小保証 | 元の輸送要求と既存経路版は変更されない |
| 測定基準 | 候補算出時間、除外理由欠落率、情報鮮度表示率 |
| トレース | BUC-03、RQ-02、RQ-06、BR-02、BR-11 |

主成功シナリオ:

1. 経路設計者が見積り済み輸送要求と基本制約を指定する。
2. システムが利用可能な航海・港湾情報と鮮度を取得する。
3. システムが到着予定時刻が希望到着期限以前、かつ各接続時間が航路別の必要最小接続時間以上となる経路候補を算出する。
4. システムが採用候補と除外候補の根拠を示す。
5. 経路設計者が候補を比較し、検討対象を選ぶ。

### UC-07 例外条件を判断し経路を確定する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 経路設計者 |
| 事前条件 | 比較可能な経路候補が存在する |
| トリガー | 候補に専門判断を要する条件が含まれる、または候補を確定する |
| 成功時保証 | 判断根拠、承認 commit 時刻、参照した外部情報版を伴う経路版が、本予約に利用可能な状態で確定する |
| 最小保証 | 未承認候補は確定経路として利用されない |
| 測定基準 | 根拠欠落 0 件、未承認経路の割当て 0 件 |
| トレース | BUC-03、RQ-06、BR-02、BR-11 |

主成功シナリオ:

1. 経路設計者が候補と例外条件を確認する。
2. 規制、危険品、接続条件などの判断根拠を記録する。
3. 経路設計者が採用候補を承認する。
4. システムが承認の commit 時点で、参照した外部情報版に対する到着期限と必要最小接続時間の適合を再検証する。
5. システムが根拠、承認者、commit 時刻、外部情報版を含む経路版を確定する。
6. システムが確定経路版を本予約の確定条件として提供する。

### UC-08 経路を再設計する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 経路設計者 |
| 事前条件 | 確定済みの経路版が存在する |

| 最小保証 | 旧経路版とそれに基づく実績は保持される |
| 測定基準 | 再設計時間、版関係欠落 0 件 |
| トレース | BUC-03、RQ-02、RQ-06、BR-04、BR-11 |

主成功シナリオ:

1. 経路設計者が再設計の原因と影響対象を確認する。
2. システムが旧経路版を固定し、再設計条件を記録する。
3. 経路設計者が新しい候補を算出・比較する。
4. 経路設計者が変更根拠と採用候補を承認する。
5. システムが新しい経路版を予約へ割り当てる。
6. システムが新旧経路版と影響範囲を関係者へ示す。

### UC-10 主要実績を登録・補正する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 追跡管理者 |
| 事前条件 | 対象予約と実績登録権限が存在する |
| トリガー | 主要実績を受領する、または誤りを認識する |
| 成功時保証 | 出典と登録者を伴う実績または訂正履歴が追跡状態へ反映される |
| 最小保証 | 訂正前の事実と監査履歴は保持される |
| 測定基準 | 出典欠落 0 件、訂正履歴欠落 0 件、反映時間 |
| トレース | BUC-04、RQ-08、BR-05、BR-06 |

主成功シナリオ:

1. 追跡管理者が対象予約と主要実績を指定する。
2. システムが入力元、発生時刻、重複を検証する。
3. 追跡管理者が実績または補正理由を確認する。
4. 採用済みまたは顧客表示済み実績の訂正では、システムが登録者と異なる追跡管理者の承認を要求する。採用前の下書きでは要求しない。
5. システムが新しい記録として実績または承認済み訂正を保存する。
6. システムが予定と実績を再評価して現在状態を更新する。

### UC-20 照会・業務例外を有人対応へ引き継ぐ

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | カスタマーサポート、営業担当者、経路設計者、データ責任者 |
| 事前条件 | 顧客照会へ回答できない、またはパイロットで変更・取消し、再設計、外部停止が発生して自動処理を継続できない |
| トリガー | アクターが担当部門への引継ぎを決定する |
| 成功時保証 | 受付番号、原因、担当、期限、旧版・新版、手動入力出典、顧客連絡、復旧照合、状態遷移が追跡できる |
| 最小保証 | 引継ぎ要求を失わず、未受領・期限超過を検知して上位の運用責任者へ escalation できる |
| 測定基準 | 受付番号欠落 0 件、担当・期限欠落 0 件、有人切替成功率、再問い合わせ率、期限超過件数 |
| トレース | BUC-02〜BUC-04、RQ-03、RQ-05、RQ-08、UC-05、UC-08、UC-09、UC-15、BR-09、BR-17、KPI-02、KPI-04 |

主成功シナリオ:

1. アクターが顧客照会または業務例外、対象予約、原因、参照した出典を確認する。
2. アクターが優先度、担当部門、回答期限、次回更新日時を指定して引き継ぐ。
3. システムが一意な受付番号を発行し、状態を受付済みとして記録する。
4. 必要に応じて旧版・新版、手動入力の出典、顧客連絡要否、復旧照合要否を記録する。
5. 担当者が案件を受領し、状態を対応中へ更新する。
6. 担当者が進捗と次回更新日時を記録し、顧客連絡が必要な場合はカスタマーサポートが共有する。
7. 担当者が回答または復旧照合結果を記録し、必要な顧客回答を行う。
8. システムが回答者、回答時刻、顧客回答履歴、復旧照合結果を保持して案件を終結する。

MVP の決定: 担当が定めた受領期限までに受領しない場合、システムは上位の運用責任者へ escalation し、依頼元へ担当未確定と次回更新日時を示す。具体的な時間値は OQ-06 の運用測定で確定する。

## U4 アクセス・監査

### UC-18 利用者を認証する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 利用者 |
| 事前条件 | 利用者が有効な企業に登録され、利用停止されていない |
| トリガー | 利用者が保護された業務機能の利用を開始する |
| 成功時保証 | 本人確認済みの session が発行され、利用者・企業・認証時刻を追跡できる |

| 測定基準 | 未認証アクセス許可 0 件、利用停止者の認証成功 0 件、認証結果記録率 100% |
| トレース | RQ-11、UC-16、UC-17、BR-14、BR-15、OQ-07 |

主成功シナリオ:

1. 利用者が事前登録メールアドレスと password を提示する。
2. システムがメールアドレスと password を検証し、TOTP MFA を要求する。
3. 利用者が有効な TOTP を提示する。
4. システムが利用者、所属企業、利用状態を確認する。
5. システムが無操作 30 分、最長 8 時間の本人確認済み session を発行する。
6. システムが利用者、企業、認証時刻、認証結果を監査証跡へ記録する。

パイロットの決定: password 回復手順、password 強度、TOTP の登録・再登録手順は NFR-AUTH-01 とアーキテクチャで具体化するが、認証の合否、ロック、session 失効境界は BR-14 を適用する。

### UC-19 荷受人の参照許可を管理する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | 荷主担当者 |
| 事前条件 | 本予約が存在し、荷主担当者が当該予約の共有権限を持つ |
| トリガー | 荷主担当者が荷受人へ追跡情報を共有する、または既存の許可を取り消す |
| 成功時保証 | 指定した荷受人だけが当該予約の到着予定、現在状態、主要実績、最終更新時刻を参照できる、または取消し直後から参照できなくなる |
| 最小保証 | 料金、契約条件、書類、他の予約は開示されず、誤った招待先へ自動的に情報を開示しない |
| 測定基準 | 許可外開示 0 件、取消し後の参照成功 0 件、招待・取消し証跡率 100% |
| トレース | BUC-04、RQ-03、RQ-11、BR-07、OQ-07 |

主成功シナリオ:

1. 荷主担当者が対象予約と荷受人の本人識別情報を指定する。
2. システムが荷主担当者の共有権限と、指定した荷受人が予約の荷受人であることを確認する。
3. システムが予約単位の招待を発行し、開示項目と有効期間を示す。
4. 荷受人が本人として認証され、招待を受け入れる。
5. システムが予約と荷受人の参照許可を有効にし、招待者・受諾者・時刻を記録する。
6. 荷主担当者が許可を取り消した場合、システムが各照会時の認可結果へ即時反映する。

MVP の決定: 許可は予約単位であり、引渡し完了まで荷主担当者が取消しできる。取消し時に認証 session 全体を破棄せず、既存 session からも対象予約を直ちに非開示とする。

### UC-15 外部データを取込み・照合する

| 項目 | 内容 |
| :--- | :--- |
| 主アクター | データ責任者 |
| 支援アクター | 運送会社システム、港湾管理システム |

| トリガー | 選定した提供元から承認済みファイルを受領する |
| 成功時保証 | 原本、冪等性キー、payload、取込履歴、採用値、重複・隔離・差異、復旧照合結果が追跡可能になる |
| 最小保証 | 検証前データは確定情報を上書きせず、最後の採用値を参照できる |
| 測定基準 | 原本追跡率 100%、重複採用 0 件、同一キー・異 payload の上書き 0 件、停止期間原本の未分類 0 件。時間目標は OQ-05 で確定する |
| トレース | BUC-03、BUC-04、RQ-06、RQ-08、BR-08、BR-12、OQ-02、OQ-05 |

3. システムが同一キー・同一 payload を重複として既存結果へ関連付け、同一キー・異 payload を隔離する。
4. システムが新規原本を既存の採用値と照合する。
5. データ責任者が差異と採否を確認する。
6. システムが採用値、原本、判断者、取込履歴を関連付けて記録する。
7. システムが採用値を許可された業務ユースケースへ提供する。

パイロットの決定: 選定した運送会社または港湾の承認済みファイルを手動取込し、外部 API 接続は開始条件に含めない。情報源が 1 件も選定・承認されていない場合は UC-15 を実行可能とみなさず、パイロットを開始しない。

## 精度レベル 3 の AI の仮定

- 「MVP で扱う」とは完全自動化を意味せず、安全な停止、記録、再実行、手動引継ぎを含む。
- 変更・取消しの実行段階、営業承認、予約確定時の役割分担、パイロットの訂正二者確認条件は確定した。変更・取消しの費用・申請期限、保持期間、後続 API の再送間隔などは OQ-04、OQ-05、OQ-07 の残決定に委ねる。
- 外部障害時に古い情報を表示する場合、出典と取得時刻を必ず併記し、最新であると誤認させない。
