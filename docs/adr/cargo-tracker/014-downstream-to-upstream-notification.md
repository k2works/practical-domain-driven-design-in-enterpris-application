# ADR-014: 下流から上流への通知は、下流の listener が上流の公開 API を呼んで行う

上流のコンテキストは下流のコンテキストのイベントを購読しない。下流のコンテキストが自分のイベントを listener で受け、上流の公開 API の冪等な操作を呼ぶ。

日付: 2026-10-08

## ステータス

承認（2026-10-08、human:kakimomokuri が Bolt 19 終了報告の承認で D-71 の AI の推奨の形を採った。ADR の文面は Bolt 20 のステップ 1 で書いた）

## コンテキスト

- 経路設計は見積りのイベント（DE-16）と公開 API（経路条件の照会）に依存する（`routing → quotation :: events・api`。Bolt 17）。見積りは経路設計に依存しない。
- 経路設計が経路を確定すると DE-05 を発行する（Bolt 19）。依頼元の見積りに経路版を割り当てて荷主承認待ちにする（R-INV-11、US-24 AC4）には、見積りがこの事実を知る必要がある。
- ドメインモデルのイベント一覧は「DE-05・DE-07 は下流の事実を上流がイベントで知る形で、上流が下流の公開 API や内部に依存するわけではない」と書いていた。Spring Modulith では、イベントの型を参照することも依存であり、見積りが DE-05 を購読すると `quotation → routing :: events` が加わって循環する。ApplicationModules の検証（ModularityTest）がこれを拒否する（Bolt 19 レビュー D-71、仮説 H3 が成り立たなかった）。
- 予約の DE-07（本予約を確定した → 輸送要求を予約確定済みにする）と、経路設計の DE-06（再設計要 → 見積りの承認を止める）も同じ向きで、同じ問題が起きる。
- イベントの配信は Spring Modulith の発行の記録を経て少なくとも 1 回で、購読側は冪等に処理する（ADR-003）。
- 公開 API の置き場所と形は、Bolt 17 で決めた（上流の `api` パッケージの `@NamedInterface("api")`、戻り値は標準と共有カーネルの型だけ。[バックエンドアーキテクチャ](../../design/cargo-tracker/architecture_backend.md)）。

## 決定

**下流から上流への通知は、下流のコンテキストの listener が自分のイベントを受け、上流の公開 API の操作を呼んで行う。上流は下流のイベントを購読しない。**

| 要素 | 決定 |
| :--- | :--- |
| 依存の向き | 下流 → 上流のまま（例: `routing → quotation :: api`）。上流の `allowedDependencies` に下流を足さない |
| 呼ぶ側 | 下流の `application.internal.eventhandlers` の listener（`@ApplicationModuleListener`）が自分のイベントを受け、`application.internal.outboundservices.acl` の部品を経て上流の公開 API を呼ぶ。listener は発行元のコミットの後に、非同期で、新しいトランザクションで動く。配信の信頼性は下流のイベントの発行の記録が担う（ADR-003） |
| 呼ばれる側 | 上流の `api` パッケージに操作のインターフェースと引数・戻り値の record を置く（照会と同じ置き場所と型の規則）。実装は上流の `application.internal.commandservices` に置き、上流の集約を 1 つ更新する。上流の集約のイベントは、上流の中で発行して上流の中で購読する |
| 冪等 | 上流の操作は冪等にする。同じ業務キー（例: 案件番号と経路版番号）の再実行は何もせず、同じ結果を返す。下流の再配信はそのまま上流の再実行になる |
| 業務の拒否 | 上流が業務の理由で受け付けない（例: 置換済みの見積り）ときは、例外にせず結果の値で返す。下流の listener は警告のログを残して終える（下流の確定は戻さない。結果整合。DE-16 の listener と同じ） |
| 技術の失敗 | 上流の操作が例外を投げたら、listener のトランザクションごと戻り、発行の記録は未完了のまま残って再配信される |
| 適用 | DE-05（経路設計 → 見積り: 経路版を割り当てる。Bolt 20）、DE-06（経路設計 → 見積り: 再設計要の経路版への承認を止める。W6）、DE-07（予約 → 見積り: 輸送要求を予約確定済みにする。W4） |
| 通知の写し | 上流が後で画面に出す下流の情報（例: 割り当てた経路の区間と到着予定）は、呼ぶときに引数で渡して上流が写して持つ。上流は下流に問い合わせない |

### イベントの発行の仕方の基準

Bolt 19 レビュー D-71 で、集約の操作がイベントを「ためる」（見積り・輸送要求の `domainEvents`）か「戻り値で返す」（経路設計案件の `confirm` が DE-05 を返す）かがそろっていないと指摘された。次のようにそろえる。

- 集約の操作がイベントをためるか戻り値で返すかは、集約ごとに選んでよい。1 つの集約の中ではそろえる。
- 発行はアプリケーションサービスが、集約の保存と同じトランザクションの中で行う（`ApplicationEventPublisher`）。リポジトリは発行しない。
- 上流の公開 API の実装（呼ばれる側）も同じで、上流のアプリケーションサービスが上流の集約のイベントを発行する。

### 代替案

| 案 | 却下理由 |
| :--- | :--- |
| 上流が下流のイベントを購読する（ドメインモデルの元の記述） | モジュールの依存が循環し、ApplicationModules の検証が拒否する。循環を許すと、コンテキストを分けて取り出す（ADR-001）ときの切れ目がなくなる |
| イベントの型を共有カーネルに移す | 共有カーネルに業務の意味を持たせない（業務の意味を持たない基本型だけ）。発行の記録は型を完全修飾クラス名で保存するため、移動も避ける（ADR-003） |
| 上流が定期処理で下流の公開 API を問い合わせる（ポーリング） | 上流が下流に依存して同じく循環する。荷主の承認が遅れる |
| 下流が上流の表を直接書き換える | スキーマの所有（ADR-001）を破る |
| 下流が同じトランザクションで上流の公開 API を呼ぶ（listener を使わない） | 1 つのトランザクションで 2 つのコンテキストの集約を更新することになる。上流の失敗で下流の確定が戻る |

## 影響

### ポジティブ

- モジュールの依存の向きが units.md の DAG と一致したまま、下流の事実を上流に伝えられる。ApplicationModules の検証が循環を見張り続ける。
- 配信の信頼性（発行の記録と再配信）と冪等の扱いは、既存のイベントの購読と同じ仕組みで済む。
- 上流は写しを持つため、上流の画面は下流に問い合わせずに描ける。

### ネガティブ

- 上流の公開 API に「操作」が加わり、照会だけだった公開 API が広くなる。操作は冪等で、業務キーを引数に持つものに限る。
- 写した情報は、下流が後で変えても上流には伝わらない。変わる事実（再設計など）は、別のイベントと別の操作で伝える（DE-06）。
- 下流の listener が上流の業務の拒否をログに残すだけのため、拒否が続くと結果整合が崩れたことに人が気づきにくい。ログの監視（運用準備 W10）で拾う。

## コンプライアンス

- ApplicationModules の検証（`ModularityTest`）で循環がないこと、上流の `allowedDependencies` に下流がないことを確かめる。
- ArchUnit で、上流のコードが下流のパッケージを参照しないことを確かめる（見積り → 経路設計。Bolt 20）。
- 上流の公開 API の引数と戻り値は、照会と同じく標準と共有カーネルの型と文字列だけで表す（ArchUnit）。
