# ADR-023: 運用の通知の宛先・業務ホームの一覧・メンテナンス表示

日付: 2026-11-16

## ステータス

採用（2026-11-16、human:kakimomokuri が「推奨で進めて」）。実装は Release 1.1 の頭。

## コンテキスト

- 運用設計（operation.md）は、警告を CloudWatch → SNS → チャット・メール・当番の電話に流し、業務上の未処理は業務ホーム（S-01）に一覧で出すとしている。**運用チャンネルに使うチャットツールは、A 社の標準に合わせて決める（要確認）** のまま未決だった（OP-05）。
- 業務ホーム S-01 は、いまは役割ごとの画面へリダイレクトするだけで、一覧を持たない（W10 で確認）。
- メンテナンス表示（時点復旧の最初の手順 RB-02、計画停止）の仕組みがアプリにない。

## 決定（推奨のとおり）

### 1. 運用の警告の宛先: メールを既定にし、チャットは SNS に足す

- 警告は SNS のトピックに集め、**購読はメール**（運用責任者・データ責任者・追跡管理者の役割別の配布先）を既定にする。宛先の一覧は Terraform の変数にし、値は運用責任者が決める。
- チャットツールは、A 社の標準が決まったら、SNS の購読を足すだけで連携する（アプリを変えない）。決まるまで、チャットなしで運用する。
- 重大（当番の電話）は、パイロットの規模では、メールの重大の件名と、運用責任者の携帯のメールへの転送で代える。当番の体制（OP-05）はパイロット開始の条件のまま。

### 2. 業務ホーム S-01 の一覧: 役割別の「未処理」を少しずつ出す

- S-01 を役割ごとのリダイレクトから、**役割別の未処理の一覧**に変える。最初に出すのは、運用設計の OBS で「業務ホームに出す」と決めたもの: データ責任者（判断を待つ隔離・差異。W10 の警告帯をここへ移す）、追跡管理者（鮮度を超えた追跡 OBS-07）、営業担当者（荷主承認済み・見積り期限間近）、カスタマーサポート（有人確認要・受領期限の超過 OBS-05）。
- 1 回で全部作らず、役割ごとに 1 Bolt ずつ。ログイン後の遷移の仕様（いまのリダイレクト）は、最初の役割の Bolt で、既存の画面を壊さない順序で移す。

### 3. メンテナンス表示: アプリのフィルターと環境変数

- 環境変数（`cargotracker.maintenance.enabled`）が真のとき、ヘルスチェック（管理用のポート）以外のすべての要求に **503 とメンテナンスの案内（Retry-After 付き）** を返すフィルターをアプリに足す。
- 切り替えは、運用タスク `maintenance:on/off` が、今のタスク定義の環境変数だけを変えた版を AWS CLI で登録してサービスを入れ替える（`deploy:rollback` と同じ経路。配備のワークフローはイメージを作り直すので使わない。`desiredCount` を 0 にして止める方法より、利用者に案内を示せる）。（2026-11-28 に改訂。下の「改訂の経緯」）
- 時点復旧（RB-02）の最初の手順は、**ECS の `desiredCount` を 0 にしてアプリを止める**ことのままにする。この表示が止めるのは画面の要求だけで、定期処理とイベントの配り直しは DB に書き続けるため、「書き込みを止める」を満たさない。表示は計画停止に使う。（2026-11-28 に改訂。下の「改訂の経緯」）

## 影響

- どれも W10 では実装しない。Release 1.1 の頭の返済として、小さな Bolt に分けて行う（宛先の変数と SNS、S-01 の最初の役割、メンテナンスのフィルター）。
- 通知の宛先が決まったので、FRS-04（取込がない日の 11:00 JST の通知）・DE-12/30/13 の検知・毒入りイベントの通知を、同じ SNS とメールの経路で実装できる。
