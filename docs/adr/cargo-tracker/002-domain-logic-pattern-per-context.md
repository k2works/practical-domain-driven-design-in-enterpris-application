# ADR-002: ドメインロジックのパターンを境界づけられたコンテキストごとに選ぶ

中核コンテキストは状態保存の集約によるドメインモデルにし、MVP ではイベントソーシングを使わない。

日付: 2026-10-01

## ステータス

承認済み

## コンテキスト

- アーキテクチャ設計ガイドの選択フローでは、「中核の業務領域で監査記録が必要」ならイベント履歴式ドメインモデルと CQRS になる。cargo-tracker の中核コンテキストはいずれも監査証跡を必要とする（NFR-AUDIT-01）。
- 開発ガイドライン第 3 章は、モジュラーモノリスでは「データストアから現在の集約状態を読み込む」状態保存の集約を使い、イベントソーシングは CQRS/ES の実装（第 5 章、Axon Framework）で扱うとしている。
- 第 2 章の追跡コンテキストでは、TrackingActivity 集約が HandlingEvent エンティティの列を持つ。状態保存のまま、事実の列を集約の中に持つ形である。
- コンテキストごとに「何が真実か」は違う。
  - 追跡: 現在状態は主要実績から導出する（インセプションデッキ 解決方針）。訂正は新しい実績で行い（BR-05）、順序が逆転した実績は保留し（BR-06）、完了後の遅延実績も原本を残す（BR-16）。
  - 見積り・経路設計・予約: 業務が「版」という概念を明示的に持つ（予約版、見積り、経路版。BR-04、BR-16）。版の履歴がそのまま監査の材料になる。
  - アクセス・監査、外部データ: 一般・補完の領域で、規則は単純か手続き的である。
- 初版の草案は追跡をイベント履歴式 + CQRS としていた。開発ガイドラインと突き合わせ、追跡の要件は第 2 章の形（実績の列を持つ状態保存の集約）で満たせると判断した。

## 決定

**ドメインロジックのパターンを境界づけられたコンテキストごとに選び、MVP ではイベントソーシングを使わない。**

| コンテキスト | パターン |
| :--- | :--- |
| 見積り、経路設計、予約 | ドメインモデル（状態保存の集約）。版を不変にし、変更は新しい版の追加で表す |
| 追跡 | ドメインモデル（状態保存の集約）。主要実績を追記専用のエンティティとして持ち、現在状態は集約の中で実績から導出する |
| アクセス・監査 | 単純なモデル。監査証跡は追記専用 |
| 外部データ | トランザクションスクリプト + Inbox・隔離・照合（ADR-004） |

すべてのコンテキストで、状態を変える操作は集約がドメインイベントを生成し、アクセス・監査コンテキストが監査証跡に記録する。

### 代替案

| 案 | 却下理由 |
| :--- | :--- |
| 追跡だけをイベント履歴式 + CQRS にする（初版の草案） | 訂正・保留・遅延実績は、実績を追記専用のエンティティとして持てば状態保存でも表せる。イベントストア・プロジェクション・結果整合の負担に見合う利点が MVP にはない。第 3 章のモノリス実装とも食い違う |
| 全中核コンテキストをイベント履歴式にする | 見積り・経路設計・予約は版の概念で監査要件を満たせる |
| 全コンテキストをトランザクションスクリプトにする | 中核の規則（BR-01、BR-10、BR-11 など）がサービス層に散らばり、貧血モデルになる（第 3 章「ドメインの豊かさ」）。Golden dataset による検証も難しくなる |

## 影響

### ポジティブ

- 全中核コンテキストが同じ流儀（状態保存の集約、4 パッケージ構成）になり、理解と実装が揃う。
- 追跡の照会は集約の状態を読むだけで済み、結果整合の遅れがない。
- 第 3 章の実装例をそのまま手本にできる。

### ネガティブ

- 実績の件数が非常に多くなると、追跡集約の読み込みが重くなる。第 2 段階のリアルタイム追跡で問題になれば、照会用の読み取りモデルの追加か、CQRS/ES への移行を別の ADR で判断する。
- 過去の任意時点の状態を再現するには、版や実績の記録から組み立てる必要がある。

## コンプライアンス

- ドメインモデル設計で、各コンテキストの集約がこの ADR に沿っていることをレビューする。
- 追跡の主要実績、各集約の旧版、監査証跡に更新・削除がないことをテストで確認する。
