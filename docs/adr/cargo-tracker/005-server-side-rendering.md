# ADR-005: 画面はサーバーサイドレンダリングとハイパーメディアで提供する

顧客 Web と社内業務 Web は、各コンテキストの `interfaces.web` がサーバーで描画した HTML で提供する。

日付: 2026-10-01

## ステータス

承認済み

## コンテキスト

- MVP の利用チャネルは顧客 Web（荷主担当者、荷受人）と社内業務 Web（A 社の 7 役割）で、外部の API 利用者はいない（BR-18、OQ-05）。
- BR-07 は、荷受人に料金・契約条件・書類・他の予約を開示しないこと、参照許可の取消し後は既存 session でも参照できないことを求める。PV-01 は権限外開示が 1 件でもあればパイロット中止とする。
- BR-13 は WCAG 2.2 AA を目標とし、エラー要約、値の保持、非同期更新の通知、重要操作の実行前確認を求める。
- 開発ガイドライン第 3 章は、受信サービスとして REST API と、Thymeleaf + htmx によるネイティブ Web API を示している。
- MVP の画面は、フォーム入力、一覧・詳細の照会、比較、承認が中心で、オフライン対応や高頻度の双方向操作はない（現場入力 UI は第 2 段階）。
- 初版の草案は SPA（顧客アプリと社内アプリの 2 つ）としていた。開発ガイドラインと突き合わせ、見直した。

## 決定

**画面は、所有するコンテキストの `interfaces.web` がサーバーサイドで描画した HTML で提供し、部分更新にはハイパーメディア（htmx 相当）を使う。SPA は作らない。**

- 顧客向けと社内向けで URL の領域・認可規則・レイアウトを分ける。
- 変更用のフォームは `commandId` と対象の版を隠し項目に持つ（ARCH-HO-01）。
- MVP では REST API を作らない。外部の利用者が現れた時点で `interfaces.rest` を追加する。
- テンプレートエンジンと部分更新のライブラリは技術スタック選定で決める。第 3 章の Thymeleaf + htmx を第一候補とする。

### 代替案

| 案 | 却下理由 |
| :--- | :--- |
| SPA + REST API（初版の草案） | 開示制御を API の応答項目で別途保証し、社内画面のコードを顧客向けの配信物から除く仕組みが要る。画面遷移ごとのフォーカス・通知を自前で管理する必要がある。フロントエンドのビルド・配信が増える |
| SPA と SSR の併用（画面ごとに選ぶ） | 2 つの方式の部品・テスト・認可の仕組みを維持することになる。MVP に SPA が必要な画面はない |

## 影響

### ポジティブ

- 権限のある項目だけを HTML にするため、返していない情報は画面に出ようがない（BR-07、PV-01）。
- 標準の HTML 要素とフォームがそのまま動き、アクセシビリティを部品で担保しやすい（BR-13）。
- アプリケーションが 1 つのデプロイ単位に収まり、フロントエンドの配信基盤が要らない（ADR-001）。

### ネガティブ

- 情報量の多い比較画面（UI-03 経路設計）で操作性が足りない可能性がある。UI 設計のプロトタイプで確かめる。
- 第 2 段階の現場入力 UI（オフライン対応）には向かない。そのときは別の方式を改めて判断する。
- 外部の利用者向けの API が必要になったら、別に REST API を設計する必要がある。

## コンプライアンス

- 顧客向けの各画面について、料金・契約条件・書類が HTML に含まれないことを自動テストで確認する。
- 主要フローの自動テストと支援技術による手動確認で、BR-13 の要求を確認する。
