# ADR-001: モジュラーモノリスを採用する

バックエンドを 1 つのデプロイ単位とし、境界づけられたコンテキストごとのモジュールで境界を守る。

日付: 2026-10-01

## ステータス

承認済み

## コンテキスト

- インセプションデッキの解決方針は「ドメイン境界に沿って責務を分離するが、物理的なサービス分割は後続のアーキテクチャ設計で判断する」としている。
- MVP には 6 つの Unit（U1〜U6）があり、units.md は Unit をデプロイ単位とは定めていない。
- MVP は予約・経路設計・基本追跡の縦の流れを通すウォーキングスケルトンで、Unit 間のやり取りが多い（予約確定には見積りと経路版の両方が必要）。
- チームは小規模で、分散システムの運用（サービスごとのデプロイ、ネットワーク障害、分散トレース、サービスごとの DB 運用）を負う余力がない。
- 一方で、版・証跡・開示制御の規則が多く、コンテキストの境界が崩れると規則の置き場所が曖昧になる。
- 開発ガイドライン第 2 章・第 3 章は、Cargo Tracker を境界づけられたコンテキストごとのモジュールを持つモジュラーモノリス（単一デプロイ、集中 DB）として実装し、DDD による「真のモジュラリティ」からマイクロサービスへ移行できるとしている。

## 決定

**バックエンドを 1 つのデプロイ単位（モジュラーモノリス）とし、境界づけられたコンテキストをモジュールとして分ける。**

- モジュールは見積り、経路設計、予約、追跡、アクセス・監査、外部データの 6 つ（Unit と 1 対 1）。
- モジュール間は公開 API（入力ポート）とドメインイベントだけで連携する。内部クラスと他モジュールのテーブルを参照しない。
- データベースは 1 つで、モジュールごとにスキーマと DB 利用者を分け、他スキーマへの権限を与えない。
- 各モジュールは第 3 章の interfaces / application / domain / infrastructure の 4 パッケージで構成する。
- 境界の違反はアーキテクチャテスト（ArchUnit 相当）で CI において検出する。ドメイン層がフレームワークに依存しないことも同じテストで固定する（第 3 章）。

### 代替案

| 案 | 却下理由 |
| :--- | :--- |
| マイクロサービス | 第 2 章のマイクロサービス構成は、第 4 章以降で扱う移行先として残す。MVP では小規模チームに分散システムの運用負荷がかかる。MVP では Unit 間のやり取りが多く、ネットワーク越しにすると ARCH-HO-02 の部分成功の扱いがすべての呼び出しに広がる |
| 境界を設けない単一のモノリス | 版・開示・冪等性の規則がコンテキストをまたいで散らばる。第 2 段階でコンテキストを切り出す選択肢がなくなる |
| サーバーレス（関数単位） | 集約の不変条件とトランザクション境界が関数に分散する。ローカルでのテストが難しい |

## 影響

### ポジティブ

- デプロイ・監視・障害対応が 1 系統で済む。
- コンテキスト間の同期呼び出しが関数呼び出しになり、ネットワーク障害を考えなくてよい。
- モジュール境界とイベント連携を守っておけば、負荷や組織の都合で後からサービスとして切り出せる。

### ネガティブ

- 1 つのモジュールの不具合や負荷が全体に波及しうる。
- 境界は規律とテストで守るしかなく、怠ると単一のモノリスに劣化する。
- モジュールごとに別の言語や実行基盤を選べない。

## コンプライアンス

- アーキテクチャテストで、モジュール間の依存が公開 API とイベントだけであることを検査する。
- DB の権限設定で、各モジュールの DB 利用者が自スキーマ以外に触れないことを確認する。
