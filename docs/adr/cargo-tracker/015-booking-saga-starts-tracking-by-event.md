# ADR-015: 予約サガは状態を予約に持ち、追跡の開始は追跡が DE-07 を購読して行う

予約サガの状態（処理中・完了・失敗・有人確認要）は予約の 1 か所に置く。追跡の開始は、予約が追跡を呼ぶのではなく、追跡の listener が DE-07（本予約を確定した）を購読して行い、結果を予約の公開 API で返す。

日付: 2026-10-08

## ステータス

承認（方針は 2026-10-08 に human:kakimomokuri が W4 の開始準備で決めた。ADR-003 の改訂は 2026-10-08 に Bolt 23 の開始準備で決めた。文面は Bolt 23 の終了報告の承認で確かめる）

## コンテキスト

- ADR-003 の決定 3 は、予約サガを「状態を永続化したサガが中央で進めるオーケストレーション型」とし、補足の決定で「予約サガの業務上の再試行は、サガがコマンドで直接呼ぶ」とした。コレオグラフィ型は「状態が各コンテキストに散ると、完了・処理中・有人確認要を 1 か所で判断できない」として採らなかった。
- 追跡（U3）は予約（U6）の予約と追跡番号に依存する（[Unit 定義](../../requirements/cargo-tracker/units.md) の依存 `U3 → U6`）。予約は追跡の上流である。
- ADR-014 は「上流は下流のイベントを購読せず、下流の公開 API に依存しない」と決めた。予約のサガが追跡の公開 API を呼ぶと `booking → tracking` が加わり、追跡が予約に依存する `tracking → booking` と循環する。Spring Modulith の検証（ModularityTest、AT-03）がこれを拒否する。
- W4 の開始準備の整合性検証で、バックエンドアーキテクチャの予約サガの図（「追跡開始コマンドを送る」）がこの循環を作ることが分かった。

## 決定

| 要素 | 決定 |
| :--- | :--- |
| 依存の向き | `tracking → booking`（`api`・`events`）だけ。予約は追跡に依存しない |
| サガの状態 | 予約の `application.sagas` の予約サガが、処理中・完了・失敗・有人確認要を `booking_saga` に永続化する。本予約の確定と同じトランザクションで「処理中」を作る。画面は予約サガの状態だけを見て、処理中を完了と表示しない |
| 追跡の開始 | 追跡の `application.internal.eventhandlers` の listener が DE-07 を受け、追跡を開始する（追跡記録を作り、経路版の区間を予定として採用する）。開始の結果（開始した・業務の理由で開始できない）を予約の公開 API（`booking :: api`）で返し、予約サガを完了または失敗にする |
| 冪等 | 追跡の開始は予約 ID で冪等にする（同じ予約の DE-07 の再配信は何もしない）。予約の公開 API も、同じ予約の同じ結果の再通知は何もしない |
| 再試行 | 追跡の開始の技術の失敗は、イベントの発行の記録の再配信（RTY-01）が担う。予約サガは追跡を呼ばないので、別の再試行の仕組みを持たない（同じ処理を 2 つの仕組みで再試行しない、という ADR-003 の補足の決定の理由は保つ） |
| 有人確認要 | 予約サガは、処理中のまま一定時間を超えたもの（RTY-02 の値で決める）を定期処理で有人確認要にし、BR-17 の有人案件の起票を依頼する。定期処理は ShedLock で 1 インスタンスに限る（ADR-003）。作るのは W8（US-20）と W10（定期の再配信） |
| ADR-003 の改訂 | 決定 3 の「サガが中央で進める」を「サガが状態を中央で持ち、後続はイベントで動く」に改める。補足の決定「再試行の担い手」の「予約サガの業務上の再試行は、サガがコマンドで直接呼ぶ」を「予約サガの後続（追跡の開始）の再試行はイベントの再配信が担い、サガは処理中の滞留で有人確認要にする」に改める |

### 代替案

| 案 | 採らない理由 |
| :--- | :--- |
| 予約のサガが追跡の公開 API を呼ぶ（ADR-003 のまま） | `booking → tracking` が加わり、追跡が予約に依存する向きと循環する。追跡が予約に依存しないように、必要な値をすべてコマンドの引数で渡す形もあるが、Unit の依存の向き（U3 → U6）と ADR-014 を改めることになり、予約が下流の追跡を知る |
| 状態も各コンテキストに散らすコレオグラフィ型 | ADR-003 が退けた理由（完了・処理中・有人確認要を 1 か所で判断できない）がそのまま当たる。この ADR は状態を予約に残すので、その理由は当たらない |
| 予約と追跡を 1 つのトランザクションで更新する | コンテキストが互いの表に触れ、ADR-001 の境界が崩れる（ADR-003 の代替案と同じ） |

## 影響

### ポジティブ

- 依存の向きが ADR-014 と Unit の依存にそろい、ModularityTest で守れる。
- 予約は追跡を知らずに確定でき、Bolt 23 で予約を作り、Bolt 25 で追跡を作る順に進められる。
- 状態は予約の 1 か所にあり、画面と監視は予約サガだけを見ればよい。

### ネガティブ

- 予約サガは後続を自分で呼ばないので、「なぜ進まないか」の手がかりは追跡の側のイベントの発行の記録（未完了の配信）にある。監視（OBS-04）は予約サガの処理中の滞留と、発行の記録の未完了の件数の両方を見る。
- 定期の再配信（W10）までは、追跡の開始の技術の失敗は起動し直すまで再配信されない（ADR-014 と同じ）。

## コンプライアンス

- ModularityTest で `booking` が `tracking` に依存しないことを確かめる（`tracking` を作る Bolt 25 から）。
- 予約サガの状態の遷移は予約の中の単体テストで、追跡の開始から予約サガの完了までは PostgreSQL の統合テストで確かめる（Bolt 25）。
