# ADR-016: 予約は commit 時刻を渡して見積りの公開 API で確定に使えるかを確かめる

見積りの有効性の判定（BR-10、Q-INV-06）は見積りの 1 か所に置く。予約は commit 時刻を渡して見積りの公開 API に照会し、確定に要る写しか、使えない理由を受け取る。

日付: 2026-10-08

## ステータス

承認（方針は 2026-10-08 に human:kakimomokuri が W4 の開始準備で決めた。文面は Bolt 23 の終了報告の承認で確かめる）

## コンテキスト

- BR-10: 予約確定の commit 時刻が見積有効期限より前のときだけ有効で、同時刻以後は失効。B-INV-02（予約）と Q-INV-06（見積り）が同じ規則を述べている。
- 予約（U6）は見積り（U1）の下流で、見積りの公開 API とイベントに依存してよい（ADR-001・ADR-014）。
- Bolt 11 レビュー R-19 は、見積りに「予約確定に使えるか（commit 時刻）」を置き、予約から見積りの判定をどう問い合わせるか（公開 API か有効期限の写し）を ADR で決めるとした。
- 見積りはすでに、荷主の承認で割り当てた経路の写し（経路版と区間）を持つ（ADR-014、Bolt 20）。

## 決定

| 要素 | 決定 |
| :--- | :--- |
| 判定の置き場所 | 見積りの 1 か所（Q-INV-06）。予約は有効期限の比較を持たない |
| 照会 | 見積りの公開 API（`quotation :: api`）に、業務番号と見積り番号と commit 時刻を渡す（2026-10-08 の Bolt 23b で見積り ID から改めた。画面の URL に内部の ID を出さない D-4 のため。呼び出し元は予約だけ）。見積りが承認済みで commit 時刻が有効期限より前のときだけ、確定に要る写し（輸送要求 ID・版、業務番号、見積り ID、荷主企業、荷受人、貨物区分・要約、荷主承認者と承認時刻、割り当てた経路版）を返す。それ以外は理由（失効・未承認・置換済み・見つからない・再設計要）を値で返す（ADR-014 の「業務の拒否は結果の値で返す」。再設計要は Bolt 37e で足した） |
| commit 時刻 | 予約の確定のトランザクションの中で、見積りへの照会の直前に `Clock` から取った時刻とする。同じ値を見積りへの照会に渡し、`booking_version.committed_at` に記録する（判定と記録を同じ値にする）。DB の実際のコミットはその後になるが、業務上の commit 時刻はこの値と定める。Bolt 37e2 から、確定用の照会が見積りの行のロックを待つことがある。commit 時刻はロックの待ちの前に取るので、待った分だけ実際のコミットより前になる。待ちは上限（下の「本予約の確定と印・置換の競合」）で抑え、業務上の commit 時刻はこの値のままとする |
| 照会の時点 | 確定の POST の同じトランザクションで照会する。確定の画面（S-09）の表示のための照会は参考で、確定の可否は POST の照会で決める。Bolt 37e2 から、POST は見積りの行をロックする確定用の照会（`BookableQuotationQuery.findForConfirmation`）を使い、S-09 の GET は今の照会（`find`。ロックしない）を使う。S-09 の GET は `@Transactional(readOnly = true)` で、read-only では `FOR UPDATE` を使えないため |
| 経路版 | 予約は経路設計（`routing`）に問い合わせず、見積りが割り当てた経路の写しを使う。再設計要・旧版の経路版の拒否（B-INV-05、Q-INV-10）は見積りの側で止める。DE-06 は経路設計の中の listener が受けて見積りの公開 API（再設計要の伝達）を呼び（ADR-014）、見積りはその経路版を割り当てた見積りに再設計要の印を付けて、荷主の承認と確定の照会を拒否する（再設計要は Bolt 37e、listener は Bolt 37e2。旧版は US-08） |
| 写しの扱い | 予約は確定の後に見積りへ問い合わせ直さない。予約版は不変で（B-INV-08）、確定の時点の写しを持つ |
| 本予約の確定と印・置換の競合 | Bolt 37e2 で決めた。確定用の照会は、見積りの行を（輸送要求 ID・見積り番号）で単表から最初に `SELECT ... FOR UPDATE` で読み（`flushCache="true"`）、そのあと今の照会と同じ判定と写しを返す（照会の結果の形は変えない）。入力ポートの操作は `@Transactional(propagation = MANDATORY)` で、ロックは本予約の確定のトランザクションが終わるまで持つ。照会が先に行を押さえれば、印を付ける更新（DE-06）と再見積りの置換は確定のコミットまで待ち、予約は残る（R-INV-07）。印を付ける更新か置換が先に行を押さえれば、確定用の照会はそのコミットまで待ち、キャッシュを使わずに新しい行を読んで拒否する（同じトランザクションでその前に見積りを読んでいても）。ロックの照会には待ちの上限（`timeout`。JDBC の問い合わせの時間切れで、H2 と PostgreSQL の両方で効く）を付け、時間切れは例外のまま上げる（本予約の確定は既存の例外の画面）。上限の値は Bolt 37e2 のステップ 5 で決めてここに書く |

### 代替案

| 案 | 採らない理由 |
| :--- | :--- |
| 予約が有効期限の写しを DE-04（荷主の承認）などで受けて自分で判定する | 規則の写しが 2 か所になり、置換・再見積りの反映が遅れる。予約が見積りのイベントを購読して状態を持つ必要がある |
| 経路設計に公開 API を作り、予約が経路版の状態を直接確かめる | 予約の依存に `routing` が加わる。見積りがすでに割り当てた経路の写しを持ち、再設計要は見積りの側で止められる |
| 確定用の照会で見積りの行を共有ロック（`FOR SHARE`）で読む（Bolt 37e2） | 排他（`FOR UPDATE`）にすると同じ見積りの確定どうしも直列になるが、同じ見積りの予約は 1 件（B-INV-11）で確定どうしは貨物予約の UK でぶつかるので、直列にしても失うものがない。H2 で `FOR SHARE` が使えるかを確かめていない（`FOR UPDATE` は identity の前例で H2 と PostgreSQL の両方で流れている） |
| 見積りの版を照会の結果に含め、確定で期待版として渡す（Bolt 37e2） | 予約は見積りの集約を書かないので、期待版を照らす書き込みが予約の側にない。照らすには、確定のトランザクションの終わりに見積りの版をもう一度読むか、見積りの行を書く操作を公開 API に足すことになり、照会と同じ時点の守りにならないか、予約が見積りを書く形になる。公開 API の結果（`BookableQuotationResult.Bookable`）にも項目が増える |

## 影響

### ポジティブ

- 期限の規則と境界のテスト（1 分前・同時刻・1 分後）は見積りの側の 1 か所で済む。
- `booking` の依存は `quotation :: api` だけになる。

### ネガティブ

- 照会は見積りの行を読むだけでロックしないため、照会と予約の保存の間に、別のトランザクションで見積りが置換される（再見積り）か、経路の再設計要（DE-06。W6）で承認・確定を止められると、止める前の見積りで確定し得る。置換は営業担当者の操作で、確定と同時に起きるのはまれ。B-INV-11（1 つの見積りから予約は 1 件）は貨物予約の UK で守る。Bolt 37e2 で、本予約の確定（POST）を確定用の照会（見積りの行のロック）に変え、この競合（再見積りとの競合を含む）はロックで待つようにした。S-09 の GET の照会は今もロックしないが、確定の可否は POST で決める。
- DE-06 との競合を厳密に防ぐ方法（照会で見積りの行を `FOR SHARE` で読む、または見積りの版を照会の結果に含めて確定で期待版として渡す）は、DE-06 を作る W6 で決める（Bolt 23 の既知の課題）。決着（Bolt 37e2）: 確定用の照会で見積りの行を `FOR UPDATE` で読む（決定の「本予約の確定と印・置換の競合」。採らなかった 2 つの案は代替案）。
- 確定用の照会のロックは、予約のトランザクションが見積りのコンテキストの行を押さえる、コンテキストの境界をまたぐロックである。同じ DB の中のモジュラーモノリスだから成り立つ。コンテキストを別のサービスに分ける（統治分割。ADR-001）ときは、見積りの側で確定を受け付ける操作（予約の確保）か期待版の照合に置き換える。
- 本予約の確定は、印を付ける更新か置換が見積りの行を押さえている間、待ちの上限まで待つ。時間切れは例外の画面になり、営業担当者はやり直す。commit 時刻は待ちの前に取るので、待った分だけ実際のコミットより前になる。
- ロックの順の規則: 確定用の照会は見積りの 1 行だけを単表から押さえる。複数の見積りの行を書く側（印を付ける入力ポート）は照会の順（`ORDER BY transport_request_id, quotation_no`）で書く。ロックの照会は最初の読み込みにし、組み立ての読み込みはその後にする（MyBatis のセッションのキャッシュ）。この順を変えるとデッドロックか古い読み込みになり得るので、PostgreSQL の並行の統合テストと変異で守る。

## コンプライアンス

- 見積りの API の単体テストで、境界の 3 点（1 分前・同時刻・1 分後）を確かめる。
- ArchUnit と ModularityTest で、`booking` が `routing` に依存しないこと、予約のコードが見積りの有効期限を比較しないことを確かめる。
- PostgreSQL の並行の統合テスト（`OverlappingTransactions`。後の接続が先の接続を待っていることを `pg_blocking_pids` で確かめる）で、確定用の照会の後の印を付ける更新が確定のコミットまで待つこと、印を付ける更新の後の確定用の照会が印のコミットまで待って再設計要で拒否すること（同じトランザクションでその前に見積りを読んでいる形も）を確かめる（Bolt 37e2）。
- 予約の腐敗防止層と本予約の確定・S-09 の GET の単体テストで、確定（POST）は確定用の照会を、S-09 の GET は今の照会を使うことを確かめる。確定用の照会のロック・`flushCache`、予約の腐敗防止層が確定で今の照会を使う変異を当てて落ちることを確かめる（Bolt 37e2）。
- H2 で確定用の照会が流れることを、dev（H2）の起動と本予約の確定で確かめる（Bolt 37e2）。
