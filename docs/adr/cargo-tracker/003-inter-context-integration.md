# ADR-003: コンテキスト間は冪等コマンド・永続化したドメインイベント・オーケストレーション型のサガで連携する

コンテキストをまたぐ処理を、分散トランザクションなしに安全に再実行できる形にする。

日付: 2026-10-01

## ステータス

承認済み

## コンテキスト

- ARCH-HO-01: Unit 間の変更コマンドは command ID、対象 ID、期待版を持つ。同じ command の再実行は同じ結果を返し、期待版の不一致は上書きせず競合とする。
- ARCH-HO-02: Unit をまたぐ処理は完了・処理中・失敗・有人確認要を区別し、後続が未完了の状態を成功と表示せず、安全に再処理できる情報を残す。
- PV-01 は重複予約が 1 件でも出たらパイロット中止とする。
- BR-17 は、変更・取消し、再設計、外部停止が起きたら自動処理を止め、有人案件へ引き継ぐとする。
- 開発ガイドライン第 3 章は、BC 間の非同期通知をアプリケーションイベントの発行と、コミット後（AFTER_COMMIT）の購読で行う。発行元がロールバックしたときに購読側が動かないことは保証されるが、コミット後・購読前にプロセスが止まるとイベントは失われる。第 3 章もこの取りこぼしをメトリクスで数えて気づく、としている。
- 第 1 章・第 2 章は、複数コンテキストをまたぐ業務の流れをサガとしてモデル化し、コレオグラフィ型とオーケストレーション型があるとしている。第 3 章のモノリス実装ではサガを使っていない。

## 決定

**コンテキスト間の連携を次の 3 つの仕組みで行う。**

1. **冪等コマンドと期待版**: 変更コマンドに `commandId` と `expectedVersion` を持たせる。各コンテキストは処理済みコマンドを記録し、同じ `commandId` には同じ結果を返す。集約の版を楽観ロックに使う。
2. **永続化したドメインイベント**: 第 3 章と同じくアプリケーションイベントとして発行する。購読は Spring Modulith の `@ApplicationModuleListener`（発行元のコミット後に、非同期で、購読側の新しいトランザクションで処理する）で行う。発行したイベントと配信の完了状態を発行元と同じトランザクションで保存し、未完了の配信を起動時と定期処理でやり直す（Transactional Outbox と同じ効果）。再配信の定期処理は ShedLock で 1 インスタンスに限る。受信側は冪等に処理し、イベントが持つ発行元の集約の版より古いものは適用しない。
3. **オーケストレーション型のサガ**: 複数コンテキストにまたがる業務の流れ（MVP では予約サガ: 予約確定 → 追跡開始）は、状態（処理中・完了・失敗・有人確認要）を永続化したサガが中央で進める。MVP では自動補償をせず、進められないときは BR-17 の有人案件を起票する。

再試行の回数・間隔・timeout の値は非機能要件（RTY-01〜03）で決める。実装方式は Spring Modulith のイベント発行記録とする（ADR-006）。

### 補足の決定（2026-10-01 の分析成果物レビューで追加）

| 項目 | 決定 | 理由 |
| :--- | :--- | :--- |
| 購読方式 | `@ApplicationModuleListener` を使い、同期の `@TransactionalEventListener(AFTER_COMMIT)` は使わない | 同期の AFTER_COMMIT では、購読側の書き込みがコミットされない |
| 再試行の担い手 | イベントの配信の失敗はイベント発行記録の再配信が担う。予約サガの業務上の再試行は、サガがコマンドで直接呼ぶ | 同じ処理を 2 つの仕組みで再試行すると、回数と監視の閾値が食い違う |
| 複数インスタンスの排他 | 再配信と予約サガの再試行の定期処理は ShedLock で 1 インスタンスに限る | Spring Modulith は再配信の排他を提供しない |
| イベントの型 | 各コンテキストの `events` パッケージに置き、移動しない | イベント発行記録は型を完全修飾クラス名で保存するため、移動すると未完了のイベントを復元できない |
| 有人確認要の見え方 | 予約サガの状態を業務ホームの一覧の正とし、有人案件の起票はそれに追加して行う | 追跡の開始と同じ原因で起票も失敗しうる |

### 補足の決定（2026-10-02 に human:kakimomokuri が承認した D-1 で追加）

| 項目 | 決定 | 理由 |
| :--- | :--- | :--- |
| イベントの表し方 | ドメインイベントは、注釈 `@DomainEvent` を付けた record で表す。共有カーネルに `DomainEvent` インターフェース（`occurredAt`）を置かない | 一律の発生時刻は、業務の語彙の時刻（提出時刻・提示時刻）と二重になる。技術上の発生時刻と ID は、Spring Modulith のイベント発行記録（`publication_date`、`id`）が持っている |
| 型の保証 | 注釈では型を保証できないため、ArchUnit で両方向に固定する。`@DomainEvent` の付いたクラスは `domain.events` の record であり、`domain.events` のトップレベルのクラスは `@DomainEvent` の付いた record である | 注釈の付け忘れと置き場所の誤りを機械で検出する |
| 業務キー | 各イベントは、受信側の冪等性のキーになる業務キーを持つ（DE-01 なら輸送要求 ID と版番号） | 共通のイベント ID を持たないため、受信側は業務キーで重複を吸収する |
| 持てる型 | イベントは Java の標準と共有カーネルの型だけを持つ。イベント専用の値は record の入れ子にする | イベントの形は保存される契約であり、ドメインモデルのリファクタリングで保存済みのイベントを壊さない |

### 代替案

| 案 | 却下理由 |
| :--- | :--- |
| 第 3 章のとおり AFTER_COMMIT の購読だけにする | コミット後・購読前にプロセスが止まるとイベントが失われ、ARCH-HO-02 の「安全な再処理」と PV-01 を満たせない。同期の AFTER_COMMIT では購読側の書き込みもコミットされない |
| 1 つのトランザクションで複数コンテキストを更新する | 同じ DB なので技術的には可能だが、コンテキストが互いのテーブルに触れることになり ADR-001 の境界が崩れる |
| メッセージブローカーを導入する | MVP は単一プロセスで足りる。第 3 章も Messaging Integration は分散構成（第 4 章）で導入するとしている |
| コレオグラフィ型のサガにする | 予約サガは「完了・処理中・有人確認要」を 1 か所で判断して画面に示す必要がある。状態が各コンテキストに散ると判断できない |
| Saga で自動補償する | 補償の業務規則（変更費用・期限）が未決（OQ-04）。BR-17 は有人対応を求めている |

## 影響

### ポジティブ

- 二重送信・再送があっても重複予約・二重登録が起きない。
- 途中で失敗しても、どこまで完了したかが記録に残り、再処理できる。
- 第 4 章（EDA）・第 5 章（CQRS/ES）へ移るときも、イベントとサガの契約はそのまま使える。

### ネガティブ

- イベントの反映は結果整合になる。画面は「処理中」を正しく表示する必要がある。
- 処理済みコマンド・イベントの配信記録・サガの状態を保存する表が増える。保持期間と掃除の方針が要る。
- 未完了の配信や「処理中」で止まったサガを監視する必要がある。

## コンプライアンス

- 同じ `commandId` を 2 回送っても結果が 1 つになることを統合テストで確認する。
- イベントの購読前にアプリケーションを止めて再起動しても、イベントが失われず二重処理もされないことを統合テストで確認する。
- 可観測性で、未完了の配信件数と滞留時間、止まったサガの件数を監視する。
