## 判断と学び

- 試行の記録は、記録すること自体が副作用になる。CSRF の守りのない GET で書くと、記録の信頼性を他人に崩させる。監査は状態を変える操作（守られた POST）に結び付ける
- 存在を隠す 404 は、本文だけでなく処理の量（読み出し・書き込み）もそろえないと、時間から漏れる
- MockMvc はエラーの画面を描かないので、エラー画面どうしの比較は画面の層で行う

### ふりかえり（KPT）

- Keep
  - 開始準備の 2 つの検証で、共通の 404 の画面がないこと、`REQUIRES_NEW` の前例の誤り、二重の書き手を着手前に見つけた
  - 書き手の表を計画に置いたので、レビューで記録の場面を議論しやすかった
- Problem
  - 計画で GET の記録を決めたとき、CSRF と時間の差の観点を検討しなかった
  - 区別できないことのテストを MockMvc で書き、空振りに気づかなかった
- Try
  - T-144: 監査の記録を足す計画では、記録する操作が CSRF で守られているか（GET か）と、記録の有無で応答の時間が変わるかを確認ポイントに挙げる
  - T-145: エラー画面の本文を比べるテストは画面の層（または実際のサーバー）で書き、MockMvc では状態コードと副作用だけを見る

### 既知の課題（後に持ち込む）

- テストの準備でシステム管理者を作ると割り当てが自動で入る（`UserAdministrationSecurityIntegrationTest`・`UiUsers`）。作る順序に依存し、準備が見えにくい
- 照会の `list` は管理者でないと空、`detail` は 403 で、扱いがそろっていない（URL の規則で先に 403 になるので、利用者には見えない）
- SpotBugs の `EI_EXPOSE_REP2` の除外の列挙が 1 件増えた（34c）
- 確定の POST は、範囲外のときだけ監査を書くので応答の時間が少し違う（CSRF で守られた管理者の操作に限る）
- Bolt 34 からの既知の課題（`User.changeRoles`、`RoleChangeResult` の共用、照会の射影の置き場所、監査記録の DB の権限）と 33c〜33f からの既知の課題は変わらず
