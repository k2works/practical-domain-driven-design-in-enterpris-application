### 計画からの変更

- ローカルのファイルシステムの保存（`LocalFileSystemRequiredDocumentStorage`）を、ステップ 3 からステップ 2 に前倒しした。アプリの起動に書類の保存の部品が要るため。
- フォームのファイルの入力欄と書類の誤りの文言を、ステップ 4 からステップ 2 に前倒しした。誤りの文言の表と、項目と画面の入力の対応を確かめる既存のテストが求めるため。
- D-20 で必要書類を必須から外したので、`ShipmentTermsInputTest` の「すべて空なら全項目の不足」の期待から、書類の 3 項目を外した。
- 1 件 10 MB を超える書類をエラー要約で示すため、multipart の上限を送信の合計（55 MB）にそろえた。合計が上限を超えたときは、コントローラーに届く前に例外が起きるので、エラー要約ではなく 413 の案内の画面を出す（`UploadLimitAdvice`）。

| # | 仮説 | 結論 | 根拠 |

## 判断と学び

### 設計への反映（反映済み）

- ユーザーストーリー: US-01 の決定に D-20（任意、形式と容量と件数、閲覧できる人、出し直しでの引き継ぎ、複製は R1.0）
- ドメインモデル: 用語 6 つ（必要書類、書類の添付、書類の種類、書類の形式、書類の受付規則、書類の保存）、Q-INV-01 から必要書類を外した、Q-INV-16、必要書類の段落
- データモデル: `required_document` の 4 列と制約、追記専用の一覧、ファイルの中身の置き場
- UI 設計: C-03 の書類の入力、必要書類の取得の URL、エラー要約の例、ファイルの入力欄
- 手順書: 必要書類の任意の添付と、書類の保存先（`cargotracker.document-storage.base-dir`）

### 人の決定（本報告の承認の場で）

- **ウイルスの検査**: この Bolt では入れていない（形式を 3 つに絞り、中身で判定し、`attachment` と `nosniff` で返すまで）。検査が動くまでパイロットで書類の添付を使わないことを、パイロット開始の条件に足した（2026-10-03 に human:kakimomokuri が決定）。方式は運用準備（W10、#28）で決める。リリース計画のパイロット開始の条件と W10 に書いた

### 既知の課題

| 課題 | 影響 | 扱い |
| :--- | :--- | :--- |
| ファイルを保存した後に DB の保存が失敗すると、ファイルが残る | 保存先に参照されないファイルがたまる | S3 の実装（W10）のときに、ライフサイクルの規則か片付けのジョブを決める |
| 送信の合計が 55 MB を超えたときは、エラー要約でなく 413 の案内の画面になる | 入力はブラウザの「戻る」で戻すしかない | まれなので MVP ではこのままにする |
| 取得できるのは現在の版の書類だけ | 前の版で差し替えた書類は開けない（いまは差し替えがないので起きない） | 書類の削除・差し替えの Bolt で見直す |
| 引き継いだ書類の削除・差し替えがない | 誤った書類を出すと、出し直しでも残る | 後の Bolt |
| ウイルスの検査がない | 社内の端末の感染のおそれ | パイロット開始の条件に足した（上の「人の決定」）。W10 で方式を決める |
| 書類の一覧の表とリンクのスタイルを画面ごとに書いた | 共通の部品がない | UI の骨格（#36）で共通の CSS に移す（Try T-18） |
