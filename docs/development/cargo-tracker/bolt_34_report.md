## 判断と学び

- 規則の組合せ（職務分離）だけを見ると、操作する人と操作される人が同じ種類のとき（システム管理者どうし）の穴を見落とす。権限を変える機能は「誰が誰に何を付けられるか」を操作者と対象の組で確かめる
- どの選び方でも必ず拒まれる入力の欄は、拒否の文言で説明するより、出さずに理由を示すほうが読み手に優しく、マニュアルの説明も減る
- 画面の層の受入シナリオで、エラー要約の中のリンクの色がコントラストの検査に当たった。既存の部品の形（S-09）に揃えるのが早い

### 既知の課題（後に持ち込む）

- `User.changeRoles` は判定を通さずに呼べる（呼ぶ側の規律に頼る）。判定の結果を引数に取る形を、34b の利用停止で同じ形が増えるときに検討する
- `RoleChangeResult` を確かめる呼び出しと変える呼び出しで共用し、届かない枝を例外で埋めている
- 照会の射影（`UserSummary`・`UserDetail`）を集約のポート `UserRepository` で受けている（前例 `BookingSummary` と同じ）。照会専用のポートに分けるかを 34c か W10 で検討する
- SpotBugs の `EI_EXPOSE_REP2` の除外がクラスの列挙で増え続ける（34c）
- 監査記録の UPDATE・DELETE を DB の権限で止めていない（運用の準備で）
- 33c〜33f からの既知の課題（全画面の `@ControllerAdvice`、印の知らせの写し、`new UtcInstant(x)`、Bolt 32f の画面の層の揺れ、#49）は変わらず
