## Bolt ゴール

営業担当者が差し戻した見積依頼を、荷主が自社の見積依頼の一覧（C-02）で見つけ、詳細（C-04）で差戻しの理由と不足事項を読み、編集（C-03）で直して出し直せる。出し直すと業務番号は変わらずに版 2 が審査中になり、営業の受付一覧（S-02）に版 2 として並ぶ。他社の見積依頼は、一覧にも詳細にも編集にも出ない。

### 確かめたい仮説

| # | 仮説 | この Bolt で分かること |
| :--- | :--- | :--- |
| H1 | Bolt 5 で作った再提出の入力ポート（`ShipmentTermsInput` を受け取る `resubmit`）を、提出と同じフォームと変換器から書き換えずに呼べる | Bolt 5 のリスク「再提出は画面がないため利用者の流れとして確かめられない」への対策が効いたか |
| H2 | C-04 の「いま誰の対応待ちか」を、輸送要求の状態だけから決められる（状態ごとの対応表） | 進み具合の表示に、状態のほかの情報（担当営業など）が要るか |
| H3 | 承認ゲートを業務のルール以外でまとめても、終了報告の承認で人の変更依頼や見逃しの誤りが増えない | ゲートの密度を下げてよいか（Release 0.1 の残りの Bolt に使えるか） |

## 設計（この Bolt の範囲）

### ドメインモデル

集約の操作は足さない。荷主の一覧のための照会と、読み取りモデルの項目を足す。

```plantuml
@startuml
title 輸送要求（Bolt 6 で足す照会と読み取りモデル）
interface "輸送要求のリポジトリ\n(TransportRequestRepository)" as Repo {
  + findByNumber(業務番号, 荷主企業) 【既存】
  + findSummariesByShipper(荷主企業) 【新規】
  + findUnderReviewSummaries() 【既存・社内用】
}
class "輸送要求の一覧の行\n(TransportRequestSummary)" as Sum <<読み取りモデル>> {
  業務番号
  版番号
  状態 : TransportRequestStatus 【新規】
  最初の提出時刻
  現在の版の提出時刻
  出発地・目的地
  希望到着期限
  貨物種別
}
class "輸送要求\n(TransportRequest)" as TR <<集約ルート>> {
  + 再提出する(輸送条件, 提出者, 提出時刻) 【Bolt 5】
  + reviewRecords()
}
Repo ..> Sum
Repo ..> TR
note right of Repo
  荷主の照会は必ず荷主企業で絞る（Q-INV-08、R-02）。
  社内用の照会（ForStaff・UnderReview）は荷主の画面で使わない
end note
@enduml
```

> 注（設計への反映。ステップ 1 で反映する）: 次は計画を書いた時点でドメインモデルになかった。
>
> - リポジトリの荷主企業の一覧の照会（`findSummariesByShipper`）と、読み取りモデル `TransportRequestSummary` の状態の項目
> - 荷主に見せる審査記録の範囲: 差戻しの理由と不足事項は見せ、審査の確定の根拠は見せない（確認ポイント 2）

### 状態遷移

状態と遷移は Bolt 5 のまま変えない。荷主の画面から見た「いま誰の対応待ちか」を状態に対応させる（仮説 H2）。

```plantuml
@startuml
title 輸送要求の状態と、荷主の画面の「いま誰の対応待ちか」
[*] --> 審査中 : 提出する
審査中 --> 見積り作成中 : 審査を確定する
審査中 --> 下書き : 差し戻す
下書き --> 審査中 : 再提出する（C-03 の編集、版 + 1）
審査中 : A 社の対応待ち（営業担当者が審査しています）
下書き : お客様の対応待ち（差戻しの理由を確かめ、直して出し直してください）
見積り作成中 : A 社の対応待ち（営業担当者が見積りを作成しています）
@enduml
```

### データモデル

表と列は変えない（スキーマの変更なし）。荷主企業の一覧は、既存の索引 `ix_transport_request_shipper_status`（`shipper_company_id`, `status`）で絞り、版 1 と現在の版を結合して読む。

```plantuml
@startuml
title Bolt 6 で読む表（変更なし）
entity "quotation.transport_request" as tr {
  * id : UUID <<PK>>
  --
  * request_number <<UK>>
  * shipper_company_id 【荷主企業で絞る。索引あり】
  * status
  * current_version_no
  * version 【楽観ロック。再提出の UPDATE】
}
entity "quotation.transport_request_version" as trv {
  * transport_request_id <<PK,FK>>
  * version_no <<PK>>
  --
  （再提出で版 2 以降を INSERT。Bolt 5）
}
entity "quotation.review_record" as rv {
  （差戻しの理由・不足事項を読む）
}
tr ||--|{ trv
trv ||--o{ rv
@enduml
```

### 画面遷移

```plantuml
@startuml
title 荷主の再提出（Bolt 6 の範囲）
[*] --> C02 : GET /customer/transport-requests
C02 : 見積依頼の一覧（自社だけ）
C02 : 業務番号、版、状態（いま誰の対応待ちか）、出発地 → 目的地、提出時刻

C04 --> C03E : [下書き] 編集（新しい版）

C03E --> C04 : POST /customer/transport-requests/{業務番号}/versions\n（PRG、「版 2 を出し直しました」）
C03E --> C03E : [入力の誤り] 入力を残してエラー要約
C03N : GET /customer/transport-requests/new（Bolt 4）
C03N --> C04 : POST /customer/transport-requests\n（PRG、「提出しました」。完了画面を統合）
@enduml
```

## AI の仮定

- C-02 の並びは、最初の提出時刻の新しい順にする（荷主は最近の依頼から探す）。件数が少ないうちはページ分けをしない。
- 荷主の画面の状態の表示名: 審査中は「審査中（A 社の対応待ち）」、下書きは「差戻し（お客様の対応待ち）」、見積り作成中は「見積り作成中（A 社の対応待ち）」とする。営業の画面の表示名（「差戻し（下書き）」）は変えない。
- 編集の画面は、Bolt 4 の C-03 のテンプレートとフォームを使い回し、見出しと送り先と「出し直すと版 N になります。業務番号は変わりません」の案内だけを変える。
- 出し直しの検証は提出と同じ（`ShipmentTermsInput`）。希望到着期限は、出し直す時刻より後でなければならない（版 1 の期限が過ぎていれば直してもらう）。
