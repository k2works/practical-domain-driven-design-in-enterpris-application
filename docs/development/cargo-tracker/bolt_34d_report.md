## 判断と学び

- 「すぐ消さない」決定の副作用は、逆向きの操作（再開）で現れた。状態を 2 値で持つ操作では、往復（停止 → 再開）の後に何が残るかを計画の段で確かめる
- 停止は「入れなくする」だけでなく、停止の前に配った鍵（再設定のリンク、既存の session）を無効にするかを同時に決める必要があった
- 値の検証（400）を範囲の判定より先にすると、範囲外の試行が記録から漏れる。記録を伴う守りは、入力の解釈より先に置く

### 既知の課題（後に持ち込む）

- 停止の確定の時に相手が処理中の request は最後まで動く（request ごとの確かめの作り。隙は 1 回分）
- 詳細に停止の理由・停止した人・時刻を示さない（監査記録にだけ残る）。一覧のキャプチャに停止の例がない
- 停止する相手の担当の案件の引き継ぎ（W6 の担当案件と一緒に検討する）
- 34c に送ったもの: 判定を通さずに呼べる `changeRoles`・`changeStatus`、`RoleChangeResult` の共用、判定の前半の写し、controller の分割と詳細の描画の部品化、利用状態の名前の写し、役割の領域の見出し、セキュリティの統合テストの login の写し
- Bolt 34b からの既知の課題（範囲外の POST の時間の差、テストの割り当ての暗黙の準備ほか）は変わらず。34d の確定にも同じ形がある
