### 支援技術の手動確認の手順

確認用に、無操作の期限を短くして起動する（例: `SPRING_SESSION_TIMEOUT=6m` を付けて `./gradlew bootRun`。警告は 1 分後に開く）。NVDA と Chrome（または Firefox）、できれば VoiceOver と Safari で行う。

1. **開いたときの読み上げとフォーカス**: 見積依頼の作成画面の入力欄にフォーカスを置いて待つ。警告が開いたら、「まもなくログアウトします、ダイアログ」と本文が読まれ、「ログインを延長する、ボタン」にフォーカスが来るか
2. **閉じ込めと Esc**: Tab と Shift+Tab で 2 つのボタンの間だけを巡るか。Esc で閉じた後、開く前の入力欄にフォーカスが戻り、値が残っているか
3. **延長の成功**: 「ログインを延長する」で、画面が移らず、入力値が残り、フォーカスが元の欄に戻るか
4. **延長の失敗**: 開発者ツールでネットワークをオフラインにして延長を押す。「延長できませんでした」が読まれるか。もう一度押して、2 回目も読まれるか
5. **残りの分**: 開いたまま 1〜2 分待ち、数字の書き換えで読み上げが割り込まないか
6. **期限の到来**: 開いたまま期限まで待つ。案内（「ログアウトした可能性があります」）が読まれるか（NVDA と VoiceOver の両方。VoiceOver は差し込んだ alert を読み落とす報告がある）。Tab で背後の入力欄を巡り、フォーカスを受けた要素が案内に隠れないか
7. **表示**: 幅 320 CSS px（または 400% の拡大）で、ダイアログが横にはみ出さず、ボタンが押せるか

## 計画からの変更

- 骨組み（H2）は仮のダイアログでなく本物の部分とスクリプトで流した（最初の UI テストで時計が効くことを確かめた）
- 警告の文言は HTML の `data-` 属性に置き、スクリプトは `{minutes}` を置き換えるだけにした（文言を UI 設計とテンプレートの 1 か所に保つ）
- 空の `role="alert"` の領域を常に置くと既存のシナリオ（`confirm_booking_ui`）の `getByRole(ALERT)` が 2 つに当たったので、期限が来たときに要素を差し込む形にした
- `th:replace` は `th:if` より先に評価されるので、レイアウトの条件を外側の `th:block` に置いた（`@WebMvcTest` で 162 件落ちて見つけた）
- マニュアルの警告は 2.2 でなく新しい節 2.5 にした（議題 3）。期限の到来の案内の文言から「操作がなかったため」を外した（ステップ 1）
- 延長の後の `close` のイベントが次の警告を止めていたので、利用者が閉じた（「閉じる」・Esc）ときだけ同じ期限で開かない扱いにした

## 判断と学び

- 延長の URL に本体を書かず「フィルターを全部通ったこと」を延長の意味にしたので、CSRF・認証・利用者の確かめ・上限の判定を延長のために書き直さずに済んだ。代わりに、それぞれの経路を統合テストで 1 つずつ確かめた（無操作で失効した session の延長は、CSRF のトークンのない拒否で A-03 になる）
- 画面の層のテストの「〜が閉じる」「〜が出ていない」は、初めから出ていなくても通る。違反を入れて落ちないシナリオがあったことで気づいた
- 共通のレイアウトを変えると、`@WebMvcTest` のように advice の一部しか読まない描画の全部に効く。画面の層のテストだけでは気づかない

### ふりかえり（KPT）

- Keep
  - 延長の URL の経路を、実際のブラウザと同じく画面の HTML から CSRF のトークンを取って確かめた
  - 違反を入れて、空振りしていたシナリオを見つけた（T-117）
  - レビューを 5 つの観点で並べ、利用者に見える文言と支援技術の指摘を、報告の前に直した
- Problem
  - 共通のレイアウトを変えた後、`uiTest` だけを流して `check` を後にしたので、`@WebMvcTest` の 162 件の失敗に遅れて気づいた
  - UI テストの機能の絞り込み（環境変数）が効かず、1 回の確かめに毎回 9 分かかった
  - 最初の文言（「操作がないため」）は、実装が数えるものと利用者の言葉がずれていた
- Try
  - T-119: 「〜が閉じる」「〜が出ていない」のような否定の確かめは、先にそれが出ていることを確かめてから行う
  - T-120: 共通のレイアウト・共通の部品を変えたら、画面の層のテストより先に `check`（`@WebMvcTest` の描画を含む）を流す

### 既知の課題（後に持ち込む）

- `localStorage` の時刻は利用者を区別しない（別のタブで別の利用者がログインし直すと、古いタブの時刻もそろう。業務データは置かないので実害は小さい）
- 差し込んだ `role="alert"` が VoiceOver で読まれるか（議題 1 の手動確認で確かめる。読まれなければ差し込みを遅らせる）
- `role="dialog"` と `alertdialog` のどちらにするか（手動確認の結果で決める）
- ブラウザが数えない request（書類のダウンロード、`layout/public` の画面）でブラウザの期限が早く来る。部分更新（htmx）を足す Bolt では、その request も数える（architecture_frontend）
- 別のタブでログインし直した後の古いタブの延長は 403 が続く（文言で「画面を開き直す」に導く）
- 画面の層の時計は実時間で流れる（`pauseAt` していない）。「1 分未満」の表示、`localStorage` を使えないとき、別のタブの延長による同期は確かめていない
- マニュアルのキャプチャは全ページで撮るので、ビューポートの外のフッターが暗くならない
- 8 時間のシナリオは DB の属性の直接の書き換えに頼る（Spring Session の `FlushMode`・`SaveMode` を変えると見直す）
- `SessionTimerAdvice` は範囲を指定しない `@ControllerAdvice`（`CurrentActorAdvice` と同じ）。共通のレイアウトの属性を足す advice が増えたら、置き場所を見直す
- 静的資源の request でも 8 時間の残りを置き、利用者の確かめの SQL が走る（W10 の性能の評価で 32c の指摘と一緒に見る）
- テストの JVM のメモリ不足（CI で 1 回）。続けて出たら、テストの JVM のメモリを見直す
