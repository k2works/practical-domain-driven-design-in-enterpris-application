## 判断と学び

- 規則の一覧を手で写すと、足し忘れは黙って通る。実際のモジュールを基準に一致を確かめる規則にすると、足し忘れが落ちる。ただし手書きの規則そのものの写しは別に守る必要がある
- 原本の「消さない補償」は、保存先が DB の間はトランザクションの巻き戻りと関係する。ポートの約束だけでは守れず、保存の実装とアプリケーションサービスの順序で決まる
- RFC 4180 では、改行を含む値と閉じ忘れを文字だけでは見分けられない。推測で読み直さず、範囲を示して人に判断させる

### ふりかえり（KPT）

- Keep: ステップごとの承認ゲートで、許可リストの範囲・行 3 の Red・解析の誤りの理由を、その場で人に諮って決めた。2 つの検証で、補償の形（ADR-010 の消す補償は使えない）と依存の宣言の原則の食い違いを、実装の前に見つけた
- Problem: 解析の境目（閉じ忘れの後、ヘッダーの誤り、空行、誤りの後の立ち直り）を、計画の状態の組み合わせの表で数え切れず、開発レビューで見つけた。サブエージェントがステップ 1 で T-204 にまた触れた
- Try: T-228: 解析器の状態の組み合わせの表には、各誤りの「後」に来る入力（改行を含む値、空行、ファイルの終わり）の行を置く。T-227（W6 の締めで PROJECT.md の決まりに「空のコマンドも流さない」を足すか）は W7 の締めで諮る
