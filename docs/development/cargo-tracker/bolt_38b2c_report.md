# Bolt 38b2c 終了報告 - 利用者の招待の発行（identity の側）と、招待の用途の規則

## 承認の議題（T-36。先に確かめてほしいこと）

システム管理者が利用者を登録したら、登録のコミットの後に招待のトークン（24 時間・1 回だけ）を発行し、招待のメールを送るようにしました。登録の画面はまだない（38b3）ので、利用者から見える振る舞いは変わりません。

| # | 確かめてほしいこと | 見る場所 |
| :--- | :--- | :--- |
| 1 | **DE-25 と発行の流れ（構造）**: 登録のサービスが、利用者・役割・監査を書いた後に同じトランザクションで DE-25 `UserRegistered`（登録の ID・利用者の ID・時刻だけ）を出す。拒否と重複のロールバックでは残らない。招待のハンドラーがコミットの後に受け、`USER_INVITATION` のトークンを発行して、ACL で通知の公開 API に送る | `UserRegistrationService`、`UserInvitationMailEventHandler` |
| 2 | **発行の共有の部品と 1 分の抑え**: 再設定と招待のハンドラーは、package-private の `PasswordResetTokenIssuance` に発行の手順を任せる（占有 → 再配信 → 抑え → 有効か → 前の未使用の無効化 → 発行）。抑えを数えるかは用途の値 `throttlesRepeatedIssue()`（`RESET` だけ）。再設定の振る舞いは変わらず、変わったのは発行しなかったときの INFO のログの文（「{用途} のトークンを発行しなかった（理由）: 契機 {}」）とロガーの名前だけ | `PasswordResetTokenIssuance`、`PasswordResetTokenPurpose` |
| 3 | **セキュリティ**: リンクの平文・トークン・メールアドレスは、表・発行記録・ログに残らない（行 2）。`IssuedLink` の `toString` はリンクとアドレスを伏せる。登録の後に止められた利用者と、企業が無効になった利用者には発行しない（行 5）。送れなくても例外にせず、出口は A-05 | 行 2・5・6 のテスト |
| 4 | **ArchUnit の規則（T-205）**: `PasswordResetTokenPurpose.USER_INVITATION` を参照してよいのは、招待のハンドラーだけ。名前の見張りと組にした。38b4 の A-06 の出し分けは、定数を外から参照せず、enum のメソッドで問い合わせる（release_plan の 38b4 の行に書いた） | `LayerArchitectureTest` |
| 5 | **受け入れるか決めてほしいこと（開発レビューの L6）**: 送れずに未完了で残った DE-25 は、アプリの再起動の後に配り直される（`republish-outstanding-events-on-restart`）。その間に本人が A-05 で password を設定していても、利用者は有効なので、招待をもう一度送り、未使用の再設定のトークンを無効にする。推奨は、この Bolt では受け入れて既知の課題とし、38b4 の開始準備で DE-25 の古さ（例: 登録から 24 時間を超えたら発行しない）で止めるかを諮ること | 既知の課題 |

## 判断と学び

- 抑えのような「順序に依存する判定」を共有するときは、どの段の後に見るかも共有の部品に含める。呼ぶ側の前に置くと、占有の外で判定することになり、同時の要求を直列にできない
- メールの到着は、送ったトランザクションのコミットより先に起きる。届いたメールから表を読むテストは、先にハンドラーの完了（発行記録の完了）を待つ
- 規則で定数の参照を禁じるときは、その定数で出し分けたくなる次の Bolt（ここでは 38b4）を先に探し、問い合わせの形を決めておく
