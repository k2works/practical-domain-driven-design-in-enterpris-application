## 判断と学び

- 拒否を共通の文言にすると、利用者は何を直せばよいか分からない。理由ごとに欄の誤りで示し、直す行動を文に書く
- 変異で「欄を取り違えても落ちない」テストの穴を見つけた。パラメーターのテストは、期待する値の組み合わせまで縛らないと空振りする

### ふりかえり（KPT）

- Keep: 計画の時点で、0 件になったときの示し方（2 つの決まりのぶつかり）を見つけて決めた。開発レビューのユーザー代表の視点で、接続が切れる場合のマニュアルの欠けを見つけた。サブエージェントは heredoc を 1 度も使わなかった（39b2 から 8 本続けて）
- Problem: 私の指示（0 バイトの受入シナリオを作る）が計画と食い違った（担当が計画に合わせた）
- Try: T-244: パラメーターのテストは、入力と期待する出力の組み合わせ（どの欄にどの文言）まで縛る

### 既知の課題（後に持ち込む）

- 39c3: 要確認と注記（受信記録の行の範囲の列、注記の並び、要確認を DB から復元する照会と `requiresReview()` の一致、ファイルの誤りの「どうすればよいか」、0 バイトのファイル・種別の違うファイルが隔離 1 になる受入シナリオ、誤りの理由を表の列で持つか）。開始準備で再分割が前提
- 行 2（40 MiB を超え 55 MB 以下）は MockMvc で流すので、Tomcat の multipart の上限を通っていない（設定を変えたときに気づけない）
- `PilotReadiness.NO_APPROVED_SOURCE` を public にした（理由を返すメソッドの方が型に意図が残る）
