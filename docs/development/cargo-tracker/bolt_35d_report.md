## 判断と学び

- 時刻の前後で事実を代わりに見るときは、その順をだれが守るかを確かめる。別のコンテキストの時計で付いた時刻は、自分の集約が守る順ではない。集約が自分で守る順（回答は提示の後）を探すと、同じ事実をより頑丈に見られた
- 同じ画面の 2 か所に案内を置くときは、役割（すること・事実）を先に決める。組み合わせの表で文言を行ごとに決めても、上下の 2 つの欄の重なりは表の 1 行の中に隠れる
- 選び方の条件（どの輸送要求の状態で見積りから選ぶか）を SQL と画面の両方に書くと、片方だけを直す余地が残る。読み取りモデルは値を返すだけにして、選び方は 1 か所に置く

### ふりかえり（KPT）

- Keep
  - 開始準備の 2 つの検証が組み合わせの表の抜け（予約確定済みの後、非同期の間）を見つけ、計画で塞いだ
  - 判定（再承認か・失効か）を集約と読み取りモデルで共有し、C-02 と C-04 がずれない
  - 変異 39 個がすべて落ちた。画面の層のシナリオは非同期を待たずに通る
- Problem
  - 計画の判定（経路の確定の時刻）の前提を、だれが守る順かまで確かめずに採った
  - 組み合わせの表の行ごとのテストを、輸送要求の状態を合わせずに既存のテストに任せ、行 1・3 が抜けた
  - 同じ画面の 2 か所の文の重なりを、計画の段階で見なかった
- Try
  - T-162: 時刻の前後で事実を代わりに見る判定は、その順をだれ（どの集約・どのコンテキストの時計）が守るかを書く。自分の集約が守る順を使う
  - T-163: 状態の組み合わせの表を作ったら、行ごとに、表の条件（輸送要求の状態を含む）をそろえたテストを 1 本ずつ置く。既存のテストで済ませない
