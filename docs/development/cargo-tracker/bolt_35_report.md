## 判断と学び

- 上流の規則が拒むので通常の流れでは届かない守りは、受入テストで上流の規則の外の状態を作って確かめる。上流の内部の部品に触るステップは上流の側に置けば、予約は本物の公開 API を通ったまま確かめられる（AT-05 に当たらない）
- 開いたときと送ったときで同じ表示を出すなら、送ったときは判定した結果を画面に渡す。照会し直した結果だけに頼ると、2 つの判定がずれたときに理由のないまま操作が繰り返される
- 下流が「解釈しない写し」として持っていた値を業務の判定に使い始めたら、上流の公開 API にその値の集合を約束として書く

### ふりかえり（KPT）

- Keep
  - 業務ルール層のシナリオの Red（特殊貨物が本物の公開 API を通って確定されてしまう）から入り、サービス・集約・規則の順に内へ進めた。判定の順を変異で確かめた
  - 2 つの整合性検証で、受入テストの部品の前提の誤り（予約のステップから見積りを置けない）と規則の取り違え（`DomainArchitectureTest` は他の BC のドメインへの依存を止めない）を着手前に見つけた
- Problem
  - 計画で「特殊貨物の状態は開発環境で作れない」と書いたが、開発データの SQL で作れた（事実を確かめずに書いた）
  - 確定のサービスに分岐を足して Checkstyle の複雑度に当たり、`check` で初めて気づいた
  - 送ったときの表示を照会し直した結果に任せ、判定した結果と表示の結び付きをレビューで指摘された
- Try
  - T-154: 「作れない」「できない」と計画に書く前に、作る手段（開発データ・テストの部品・設定）を探して確かめる
  - T-155: 開いたときと送ったときで同じ表示を出す画面では、送ったときは判定した結果を画面に渡す形を計画の設計の約束に書く
