## 計画から変えたこと

- 39d の行 7 を契約のテストに上げる分（行 16）を計画の承認の場で 39d2b に送った（見積りを約 4 時間 05 分にするため）。件数が減ったときの示し方（行 15）は開始準備の決定 (8) で 39d2b に送ってある
- 判断の画面の行き先（404・判断済み）は、判断のサービスに足した `refusalOf(UUID)` が決める。画面はポートを直接呼べないため。GET と POST で同じ定めを使う（クラス図にないメソッド）
- メモリの受信記録のリポジトリに、判断のリポジトリを受けないコンストラクタも残した（受入シナリオの組み立てを変えないため）
- 判断の画面に、S-16 と同じ共通部品のエラー要約を足した
- 39d の UI のステップ「ページ送りのリンクを開く」を、Shift+Tab で画面の終わりから戻る書き方に直した（1 ページに 100 個の「判断する」が増え、Tab の上限の 80 回を超えたため）
- 判断の画面のキャプチャは新しいシナリオを作らず、12.2 の既存のシナリオの続きで撮った。形式の誤りの判断の画面はキャプチャにしなかった（項目表で「この図には写っていません」と書いた。12.1 の前例）
- マニュアルに「送り直した原本は再び隔離になり判断し直せる」とは書かなかった（39d4 で確かめるまで書かない）

## 判断と学び

- 判断の記録のような追記専用の事実は、集約を持たない record とポートで足りる。同時の判断は表の一意制約に任せ、違反を例外に写して「判断済み」の文に変える
- 同じ規則を 2 つの層で守ると、片方に当てた変異はもう片方の守りに隠れる。変異は守りの置き場所ごとに当てる（Bolt 39c4 の学びの繰り返し）

### ふりかえり（KPT）

- Keep: 計画の承認の場で見積りの超過を後の Bolt に送り、目安の中に収めた。マニュアルの担当が、送り直しが重複になるおそれという業務の穴を、実装の文の突き合わせの中で見つけた
- Problem: 担当のサブエージェントが標準入力を待つコマンド（heredoc と `python -`）をまた 1 回流した（ステップ 2。すぐ止め、書き込みはない。39c4 から 4 本続いた）。マニュアルの担当が、触らない決まりの `.claude/agent-memory` に 1 行を足し、すぐに消した
- Try: T-247（フックで heredoc と `python -` を拒む）を W7 の締めで最初に諮る。触らないファイルもフックで守る案を T-247 に含める
