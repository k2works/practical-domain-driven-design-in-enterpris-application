## 判断と学び

- 期待結果を区分の要約（例の表）と全体（案件のデータ）の 2 か所に持つと、片方を直し忘れる。要約のステップで両方を照らすと、食い違ったままでは緑にならない
- 境界の案件は、境界の両側（ちょうどと 1 分）を 1 つの案件に入れないと、許容時間や比べ方の誤りを落とせない
- 並べ方を 2 か所（探索と集約）で持つと、片方を外す変異は区別できない（等価の変異）。どちらで守るかを決めておく

### ふりかえり（KPT）

- Keep: 開始準備で分け方・G-04・CI の上限・「区間」を人に諮って決めた。案件のデータを 1 か所に置き、受入シナリオと集約の単位のテストで共有した。本体を変えずに v0 の期待結果が通ることを確かめた
- Problem: 計画の G-06 が境界の案件になっておらず、G-01 に同時刻の候補がなかった（開発レビューで分かった）。シナリオアウトラインの変異の判定を XML の名前でしたので、はじめ V5 を「生き残り」と誤って出した
- Try:
  - T-195: 境界を確かめる代表案件は、境界の両側（ちょうどと外側）を同じ案件に入れる
  - T-196: シナリオアウトラインの変異は、Cucumber の結果（`cucumber.json`）の feature と行で判定する（XML の名前は「Example #n」だけで feature を区別できない）
