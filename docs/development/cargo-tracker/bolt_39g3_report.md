## 判断と学び

- 見込みと最終取得時刻を現在状態と同じところで導くと、「採用の実績が変わったときだけ動く」が型の外に出ず、DE-13 と保持のみの経路を個別に守らなくて済む（行 11・13）
- 導出しない経路があるときは、変異のテストの組で「その経路の後に導出が走る」手順を入れないと、導出の中の条件の変異が生き残る（M6）
- 画面の層の航海は遠い未来なので、遅れの実績は今より後になり手入力で登録できない。前提で予定をずらすと、固定の日付を実の時計と比べずに遅れを示せる
- SonarQube はテストのラムダの中の複数の呼び出しを違反にする。引数を先に作ってからラムダに入れる

### ふりかえり（KPT）

- Keep: 守る既存のテストを Red の前に流した（39g2 の Try）。状態の組み合わせの表の行をテストの名前に付け、変異 11 個がすべてどこかの行で落ちた。変異のスクリプトは落ちたテストの名前で判定し、起動の失敗と分けた
- Problem: 標準入力につなぐ形のコマンド（`python - --version`）を 1 回打った（議題 4）。計画の変異の行の見込みに、導出しない経路と保存の層の違いを入れていなかった（M6・M8・M9）
- Try: Bash のコマンドは必要な部分だけを打ち、`python` に `-` を付けない（T-247 のフックで拒む）。変異の一覧を書くときに、変異が効く層とそこを通るテストの組を 1 行ずつ確かめる
