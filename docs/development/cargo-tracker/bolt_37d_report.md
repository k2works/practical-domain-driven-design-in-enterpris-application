## 判断と学び

- 振る舞いの前に、状態の記録とスキーマと保存を準備として分けると、データベースの承認ゲートを振る舞いの判断から切り離せ、既存のテストの期待値が変わらないことで準備の正しさを確かめられた（Bolt 37b の前例）
- 「再設計要は確定の記録を持つ」のような、状態の意味から出る不変条件は、記録の項目を足すときに一緒に書き出す。計画の段階では項目の有無だけを見て、状態どうしの関係を見落とした
- 検査を足すたびにコンストラクターの循環的複雑度が上がる。T-175 を Bolt 37c で立てたのに、この Bolt では switch だけを数え、if の連なりを数えなかった

### ふりかえり（KPT）

- Keep
  - 開始準備の 2 つの検証が、仮説の誤り（列を読むテストがある）と半日を超える見積りを着手の前に見つけ、Bolt を分けられた
  - まだ流していないマイグレーションに、レビューの指摘（CHECK）を同じファイルで足せた（push の前にレビューした）
  - 変異で、保存の表の条件と読み戻しの誤りが統合テストで落ちることを確かめた
- Problem
  - 経路版のコンストラクターの循環的複雑度を、`check` を流すまで気づかなかった（T-175 の数え方が switch だけだった）
  - SonarQube の「`record` という変数名」の指摘を 3 か所で受けた
- Try
  - T-176: T-175 を広げる。値オブジェクトやエンティティに検査を足すときは、そのコンストラクターの分岐（if・`&&`・`||`・三項）を数え、10 を超えそうなら検査をメソッドに切り出してから足す
  - T-177: `record` は Java の制限付きの識別子なので、変数名に使わない（`redesign`・`confirmation` など意味の名前にする）
