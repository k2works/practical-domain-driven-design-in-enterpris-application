### 作ったもの

- S-02: 「予約の確定待ち」の表（荷主が承認した見積りを有効期限の近い順に。経路、荷主の承認、有効期限。前は「…の本予約の確定へ」、失効は「…の見積りを開く」）。経路設計中・荷主承認待ちの表に経路の確定の時刻（未確定は凡例つきの「—」）
- S-09 本予約の確定（`/staff/bookings/new?transportRequest=…&quotation=…`、`POST /staff/bookings`）: 確定条件の表、「この表示は開いた時刻での確認です」、確認の項目（対象・変更内容・影響・回復手段）、「契約条件と照合した」のチェックと「本予約を確定する」。欠けた条件はエラー要約
- S-24 予約の詳細（`/staff/bookings/{追跡番号}`）: 追跡番号、業務番号、状態、予約版 1（確定時刻・経路・貨物）、追跡の開始（処理中を完了と出さない）
- 見積りの公開 API: 照会の鍵を業務番号と見積り番号に、結果に荷主の承認時刻
- 予約の照会 `BookingQueryService`（開いた時刻での参考の判定、確定済みの判定、予約サガの状態）
- テスト: 画面の単体テスト、予約の照会の単体テスト、PostgreSQL の統合テスト（予約の確定待ち、見積りの予約の有無）、セキュリティの統合テスト、画面の層のシナリオ `features/ui/confirm_booking_ui.feature` 3 本

## 判断と学び

### 既知の課題（後の Bolt に持ち込む）

- **Bolt 24**: 確定済みの判定（処理済みコマンドか既存の予約の照合）を見積りの照会より前に置き、確定済みの通知に既存の追跡番号と S-24 への導線を付ける（AC4）。S-09 のフォームにコマンド ID を足す
- **Bolt 25**: S-24 の「追跡の開始: 完了」を人が確かめる入口（S-10 の最小の一覧か、S-02 の結果からの導線）を決める。`booking :: api` と予約サガの遷移
- **人の判断（未決）**: 承認の後に失効した見積りの再見積りの規則（議題 5。画面の暫定の案内は承認済み）。Bolt 24 の開始準備で扱いを確かめる
- **社内の画面の共通の部品**: エラー要約へのフォーカス（S-07・S-09）

### ふりかえり（KPT）

- Keep
  - すべてのステップで、骨組みを置いて Red を本命のアサーションで確かめてから実装した（Bolt 23 の Problem を直せた）
  - 3 つの観点の開発レビューで、画面の行き止まり（承認済みの見積りは再見積りできない）を push の後すぐに見つけた
- Problem
  - 失効の案内の文言を、遷移先で本当に再見積りできるかを確かめずに書いた（画面の層のシナリオもリンクの有無までで止まっていた）
  - T-55 を守らず、整形の前の行の形で置換のスクリプトを書き、1 回やり直した
  - 既存の CSRF のテストの形を確かめずにテストを書き、1 回やり直した
  - 開発レビューの対応を、`check` だけで `uiTest` を流さずに push し、CI の画面の層のジョブを 1 回赤にした（`86cf224`。`abcc1e4` で直した）
- Try
  - T-70: 画面の欄の値を確かめるステップ（`hasText`）がある欄には、案内の文を足さずに欄の外に置く。開発レビューの対応の後も、push の前に `uiTest` を流す（AI、次の Bolt から）
