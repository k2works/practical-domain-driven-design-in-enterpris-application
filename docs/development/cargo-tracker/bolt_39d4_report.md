## 判断と学び

- 業務の判断の推奨は、受入条件の文と突き合わせる。初稿の (p) は「値が同じなので害がない」で書いたが、AC3 に「採用値を重複生成せず」とあった
- 巻き戻しを確かめるテストは、テスト自身のトランザクションの外から読む。`@Transactional` のテストの中では、例外が出ても巻き戻ったことを証明できない

### ふりかえり（KPT）

- Keep: 39d2 から持ち越した「送り直すと一覧に戻らないおそれ」を、着手前にコードで確かめて 2 つの検証でも追い直した。2 つの検証の意見が分かれた (p) は、受入条件を根拠に片方を選んだ
- Problem: 担当が標準入力に関わるコマンドの禁止を 3 回破った（`cat > /dev/null`、スクリプトの中の `< /dev/null`、待ちのループの `read`。どれも固まらず害はなかった）。文章の指示だけでは止まらない
- Try: T-247 を W7 の締めで最初に諮る（heredoc・`python -`・`cat >`・`< /dev/null` を拒むフック）

### 既知の課題（後に持ち込む）

- 39e・39g: 同じ情報版で値が違う組と同じ値の組のイベントの扱い、採用した値がまだ反映されない文の削除、誤って採用したときの道の位置づけ
- 39h: 外部版をまたいで採用中の値と矛盾する原本は差異
- W7 の締め: テストの完全修飾名（115 か所と数え方の外の 93 か所）
- W8: 判断済みの一覧と却下の理由を読む手段、`decision.html` のエラー要約の共通化
- W10: 一覧の描画の切り分け、負けた採用のログ
