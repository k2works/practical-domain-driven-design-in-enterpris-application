## 判断と学び

- 枠組みは「どこで投げた例外か」で扱いを変える。利用者の読み出しの例外は包んで失敗へ倒すが、照合の後の確認の例外は包まない。計画の時点では同じ段の読み出しを 1 つに見ていた。前提を特性テストで先に固めてから扱いを決める（T-108）と、計画の段で気付けた。
- 失敗のイベントは例外のクラス名の完全一致で選ばれ、親の型の対応は使われない。新しい例外の経路を足すときは、イベントが出ることを統合テストで確かめる（監査記録が 0 件のテストで見つけた）。
- 検出器を使う読み戻しは、入力（ランダムな秘密）によって揺れる。素の画像なら検出をしない読み方を選ぶ。1 回の緑では揺れが直った証拠にならないので、繰り返して確かめる。

  - 同時実行のテストは、後の操作が待つことを確かめてから先をコミットする形にそろえた（T-100）
  - 見張りの違反を 5 つ入れて落ちることを確かめた（T-88・T-112）
- Problem
  - 計画にあったリスナーと照合の後の確認の単体テストを、統合テストで足りると見て後回しにし、レビューで指摘された
  - 表全体を数える確かめを書き、ほかのテストの行で通る形になっていた
  - 計画の確認ポイント 8 の前提（同じ段の読み出しは同じ扱い）を、枠組みの振る舞いで確かめずに決めていた
- Try
  - T-113: 監査記録などの共有の表の件数は、テストの前後の差か、そのテストの利用者で絞って確かめる
  - T-114: 枠組みが例外をどう扱うかに頼る確認ポイントは、開始準備で特性テストの形にして確かめてから決める

### 既知の課題（後に持ち込む）

- Bolt 32c: ADR-012 の見直しの 3、AC6 の request ごとの役割の確認、Bolt 31d から送った低の指摘
- 議題 4・5 の判断（予告の後の一文、ログインの監査をサービスに寄せるか）
- 「5 回」「15 分」の画面の文言と `LockPolicy` の重複（文言と方針が一致することを確かめるテストか、モデルの属性で渡すか）
- ロックの規則が `LoginFailure` とマッパーの SQL に二重にある（Bolt 30 からの意図的な負債。契約テストが一致を守る）。`login_failure` の表の注釈（COMMENT）を次に表を変えるときに直す（Bolt 34 の持ち込み）
- 回復コードのログインで、回復コードの消費と `LOGIN_SUCCEEDED`・回数の戻しが別のトランザクション（Bolt 31c から）。IA-INV-08 の範囲を文書ではっきりさせる
- `LoginAttemptService` などの `@Service` と `@Bean` の二重の定義、ログインの監査の書き込みの経路が 2 つ（議題 5）
- 統合テストの独自の Spring のコンテキスト（`@MockitoSpyBean` と独自の時計）が増えた。32c の「3 つの統合テストの時計の設定」と合わせて整理する。テストの JVM の途中の終了が再び出たら、メモリを調べる
- 画面の層のロックのシナリオで、5 回の誤りのたびに axe の検査をしている（1 回目だけで足りる）
- 存在する利用者と存在しない利用者の失敗で DB の往復の回数が違う（bcrypt に比べて小さいので受け入れる）。W10 の性能・攻撃の評価で計測項目に入れる
- S-02 の受入テスト（WAF の規則のテスト）の置き場所を W10 の開始準備で決める
- マニュアル（Bolt 33b）: 2.1 のログインの手順を 2 段階（A-02・A-07・回復コード）に書き直し、ロックの予告と「ログインに成功するまでの誤りを、password・認証コード・回復コードを合わせて数える」を足す。付録 B の Q1-1 に「5 回続けて誤った」の行を足す
