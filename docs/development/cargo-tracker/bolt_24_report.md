## 判断と学び

### 既知の課題（後の Bolt に持ち込む）

- **Bolt 25**: 送り直しの文言「追跡の開始を待っています」は、追跡の開始が完了した後の再送では事実と合わなくなる（確認ポイント 9）。S-24 に後から戻る入口（S-10 の最小の一覧か導線）。`afterMigrate` の権限の付与の一覧に `tracking` を足す（A-11）
- **人の判断（未決）**: A-1（ADR-001 の例外）、A-2（追記専用と RET-06）、SonarQube の S8445、D-85（承認の後に失効した見積りの再見積り。W6 の開始準備）
- **エラーの画面**: 400・404 の業務の画面（U-3、Bolt 23b の P-7）
- **AT-04**: マッパーの SQL が自スキーマだけを参照する検査（A-10）
- **社内の画面の共通の部品**: お知らせとリンクのまとまり、フラッシュ属性の名前、エラー要約とお知らせへのフォーカス（A-6・U-2、Bolt 23b の U-3）

### ふりかえり（KPT）

- Keep
  - 開始準備の 2 つの検証で、計画の中心の約束（見積りの照会より前に確定済みを判定する）が今の鍵では成り立たないことと、置き場所が層の規則に必ず違反することを、着手の前に見つけた
  - 同時実行を、ラッチでそろえた本物の PostgreSQL のトランザクションで確かめ、3 回流して安定を確かめた
  - スキーマの承認ゲートで、停止フックに何度促されても止まった（T-67）
- Problem
  - ステップ 2 で `BookingRow` に列を足したのに、マッパーの結果の対応を足さず、ステップ 3 の最初の Red がコンテキストの読み込みで落ちた（本命のアサーションではなかった）
  - 画面の層のシナリオを画面の実装の後に書き、Red を確かめなかった（T-39）
  - heredoc の Python の文字列の `\\n` が改行になり、図と Java の文字列を 2 回壊した（Edit で直した）
  - 停止フックが承認待ちの間に何度も同じ指摘を出し、同じ返事を繰り返した
- Try
  - T-71: 行の型（`*Row`）に列を足したら、同じステップでマッパーの XML の結果の対応と INSERT・SELECT の列もそろえ、コンテキストを読み込むテストを 1 本流す（AI、次の Bolt から）
  - T-72: 画面の層のシナリオは、画面の単体テストと同じステップで先に書き、骨組みで落ちることを確かめる。DB を使うために後に回すときは、計画にその旨と Red を確かめる時点を書く（AI、次の Bolt から）
  - T-73: エスケープを含む編集（`\n`、`\"`）は heredoc の Python に入れず、スクラッチパッドのファイルか Edit で当てる（AI、次の Bolt から）
