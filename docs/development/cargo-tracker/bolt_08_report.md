### 計画からの変更

- 入口の一覧はテンプレートにせず、静的なファイルのまま Bootstrap と共通の CSS を読むようにした（コントローラを足さずに済む。AI の仮定からの変更）。
- 既存の C-03 のシナリオ（キー操作の提出、誤りの直し、特殊貨物、書類、出し直し）は、期待する結果を変えずに、段階を進める操作を足した。特殊貨物のシナリオで「提出ボタンが使えない」ことは、提出ボタンのある確認の段階まで進んでから確かめる。

### UI-HO-04 の所見（AI の観察。合否は本報告の承認の場で人が触り、この形で残すと決めた）

- 1 つのフォームの中で段階を切り替えるので、選んだ書類は段階を行き来しても残る（シナリオ「確認の段階から前の段階に戻って直しても選んだ書類が残っている」）。
- 段階を移ると見出しへフォーカスが移り、次の Tab で段階の最初の入力に届く。キー操作だけで 4 段階を進めて提出できた。
- 提出の誤りは、エラー要約のリンクで誤りのある段階が開く。ただし、提出した直後に開くのは最初の誤りの段階だけで、2 つの段階に誤りがあると、もう 1 つの段階はリンクから開く必要がある。
- 確認の段階の入力のまとめは、ファイル名と選んだ選択肢の表示名を出す。値は `textContent` で入れ、HTML として解釈しない。
- 段階ごとの検証はしないので、誤りは確認の段階から提出するまで分からない（確認ポイント 3 の決定どおり）。

### 既知の課題

| 課題 | 影響 | 扱い |
| :--- | :--- | :--- |
| 段階ごとの検証がない | 誤りは確認の段階から提出するまで分からない | R1.0 の下書き保存のときに、段階ごとの保存と検証を決める |
| 2 つの段階に誤りがあると、提出の直後に開くのは最初の段階だけ | もう 1 つの段階はエラー要約のリンクから開く | 承認の場で今の形のまま残すと決めた。段階ごとの検証とあわせて R1.0 の下書き保存の Bolt で見直す |
| 表を狭い画面で時系列のリストに切り替えていない | 狭い画面では表を横にスクロールする | 一覧が増えてから（UI 設計「画面幅」） |
| ログアウト、役割に応じたナビ、利用者のタイムゾーンでの窓口の案内 | 仮の表示 | 認証（US-18）と利用者管理（US-16） |
| htmx は読み込むだけで、まだ使っていない | — | 一覧の絞り込みなどを作る Bolt で使う |
