# Bolt 38b2 終了報告 - 利用者の登録のサービスと監査（使えないハッシュ、範囲外の記録）

## 承認の議題（T-36。先に確かめてほしいこと）

システム管理者が管理範囲の企業に利用者を登録するサービスを作りました。画面がないので、普通の利用者から見える振る舞いは変わりません（画面は 38b3、招待のメールは 38b2b）。

| # | 確かめてほしいこと | 見る場所 |
| :--- | :--- | :--- |
| 1 | **判定の順と拒否**: 操作者 → 企業の有無 → 管理範囲 → 企業の有効性 → 表示名 → 登録の判定 → 重複のメールアドレス。「ない」と「範囲外」は別の値（38b3 の画面が同じ応答にする）、範囲外の無効な企業は範囲外として扱う、重複は値で返す（同時の登録は一意制約の例外をトランザクションの外で値にする） | `UserRegistrationService`、`UserRegistrationRefusal` |
| 2 | **範囲外の記録（構造）**: 確定（`register`）で範囲外の企業へ登録しようとしたときだけ、その試行（`ADMIN_SCOPE_DENIED`、対象は企業）を別のトランザクションで書く。`check` は書かない。外側のトランザクションの中では例外にする（合流すると記録が消えるため）。ArchUnit の規則は変えていない。**「書き手は 1 か所」を守る規則はない**（規則が守るのは記録のサービスへの依存だけ）。`AuditRecord.adminScopeDeniedCompany` を呼ぶ部品を登録のサービスに限る規則を足すか、決めてほしい（開発レビューの指摘。規則の追加は人に諮る） | architecture_backend の S-20 の画面の構造の段落 |
| 3 | **セキュリティ**: 使えないハッシュ（乱数の平文を bcrypt にして捨てる。照合は常に一致せず時間も同じ）。ログインの道の try を `EmailAddress.of` だけに狭め、読めない利用者の行のときだけ監査の理由が `SERVICE_ERROR` になる（開始準備で受け入れた差） | `BcryptUnusablePasswordHashIssuer`、`CargoUserDetailsService` |
| 4 | **監査**: `USER_REGISTERED`（対象は新しい利用者・版 0・変更後は役割の名前。メールアドレスと表示名は書かない） | `AuditRecord.userRegistered` |

## 判断と学び

- 「存在を示さない」は、前例どおり値を分けたまま応答で守ると、記録の取り違えがない（同じ値にして印を持たせる案は、名前と意味が食い違う）
- 一意制約の例外を値にするときは、トランザクションの外で捕まえる。中で捕まえると、続けて書く道で中断したトランザクションを踏む
- 「書き手は 1 か所」と書くときは、規則が何を守っているか（依存か、呼び出しか）を文書に書く（T-153 の再確認）

### ふりかえり（KPT）

- Keep: 2 つの整合性検証で、ArchUnit の規則に当たる設計（範囲外の記録の書き手）を計画の段階で見つけ、人に諮れた。変異 10 個がすべて落ちた
- Problem: 計画で「書き手は 1 か所」と書いたが、規則がそれを守っているかを確かめなかった（開発レビューで分かった）
- Try:
  - T-205: 「書き手は 1 か所」「呼び手は 1 か所」と書くときは、それを守る ArchUnit の規則（依存か呼び出しか）を計画の確認ポイントに挙げ、ないなら足すかを諮る

### 既知の課題（後に持ち込む）

- 「書き手は 1 か所」を守る規則がない（議題 2 の決定による）
- 書式文字や NBSP だけの表示名（38b3 の開始準備で諮る）
- 外側のトランザクションに合流したときの rollback-only（38b3 の画面は `@Transactional` の外で呼ぶ）
- 既にいる利用者の行が読めないと登録の判定が 500 になる（データの不整合を外へ出す方針）
- 範囲外のときだけ記録で応答時間が違う（Bolt 34b の既知の課題。#50、38e）
