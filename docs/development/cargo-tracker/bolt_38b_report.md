## 判断と学び

- 承認の値は、同じ集約の実体（役割の変更）なら判定した実体で縛れるが、別の集約は ID で持つ。前例の形を写すときは、持つものが同じ集約かを確かめる
- 用途の値に期限を持たせると、用途で分ける switch が要らず、期限の誤りは用途の値の 1 か所の変異で捕まえられる

### ふりかえり（KPT）

- Keep: 2 つの整合性検証で、承認の値の置き場所（入れ子・private）と用語集の整合テストの見落としを計画の段階で直せた。変異 8 個がすべて落ち、改行も変えなかった
- Problem: 用語集の整合テストの「最初の語」が「。」までの句だと知らず、新しい値の Javadoc を「（Bolt 38b。…）」で始めた（開発レビューで分かった）。シェルの heredoc の中の Python が途中で切れ、スクリプトのファイルを 2 回作り直した
- Try:
  - T-203: `@ValueObject`・`@AggregateRoot` の新しい型の Javadoc は「用語集の名前。…」で始める（最初の「。」までが用語集の名前と一致すること）
  - T-204: 複数行のスクリプトは heredoc でなく Write でファイルにする（規則の再確認。heredoc の中に別の heredoc や引用符の多い Python を入れない）

### 既知の課題（後に持ち込む）

- 職務分離の枝は今の規則では到達しない（規則が広がったときのための守り）
- ログインの道（`CargoUserDetailsService.findUser`）は、役割 0 件の利用者の例外を「見つからない」に吸い込む（今も同じ。try を `EmailAddress.of` だけに狭めることを 38b2 以降の候補にする）
