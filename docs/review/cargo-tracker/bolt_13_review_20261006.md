## 総合評価

次の点は 2 つの視点とも評価した。

- 本体と分けた Gradle プロジェクトで学習テストを書き、本体の依存と CI に触れていない（確認ポイント 1・2）。
- RFC 6238 の試験ベクトルで 3 つの候補を同じ入力のまま比べ、骨組みを先に置いて Red を記録した（T-37）。
- 資料の少ない振る舞い（結果のトークンの型が `toBuilder()` を宣言しないと要素が合わさらない、要素の権限の発行時刻がシステムの時計で決まる）を見つけ、ADR に残した。
- password と TOTP の失敗を `AuthenticationFailureBadCredentialsEvent` の 1 か所で数え、監査記録（IA-INV-08）を書く箇所とそろえた。
- 時計を注入し、TOTP・ロック・最長 8 時間の判定を決定的に確かめた。
- 「開発環境では TOTP を飛ばす」案を退け、開発と本番で認証の流れをそろえた。

一方、ADR の主張のうち 3 つは、実装に穴があるかテストの裏付けがなかった（tester）。

1. 最長 8 時間を、期限切れの session に TOTP だけを送って延ばせた（プローブで再現）。
2. ロックと最長 8 時間の境界が「同時刻」の 1 点だけで、ロックの回数・期間・最長の時間・窓を変えるミューテーションがすべて残った。
3. ADR が採る (b) `java-otp` が、2 段階のログインの流れで一度も動いていなかった（流れは (a) の実装の上）。

加えて architect は、開発環境の入力済みの守りが「設定の値があるか」の 1 層だけであること、`identity` への置き方と仮の主体の置き換えの順が ADR にないこと、TOTP の段で session の ID を変えていないことを高とした。

方式（Spring Security 7 の要素の権限で 2 段階のログインを組み、TOTP の生成は小さなライブラリに任せる）は 2 つの視点とも維持できると評価した。
