# cargo-tracker Bolt 21 開発成果物レビュー（2026-10-08）

## レビュー対象

- Bolt 21 の変更（`git diff 9fc50d0f..7097c244`）。KPI 計測記録の最初の提示時刻とリードタイム（`KpiObservation`）、DE-03 の listener（`KpiObservationEventHandler`）、表の列と条件付きの更新、S-22 の前身の画面、デモのサンプル、設計文書（KPI-INV-01〜03、`kpi_observation`、S-22、US-21 の D-11）
- 観点として、listener が記録できないときの扱い、届く順の入れ替わり、テストダブルの忠実さ、日時表示の写し、PV-01 の判定の材料としての使いやすさを必ず含めた

## 総合評価

仮説 H1（見積りの公表された言語だけで KPI を作れる）と H2（条件付きの更新で再配信と順序の入れ替わりを吸収できる）は成り立った。`identity` の依存の宣言は変わらず、見積りのコードに差分はない。いちばん早い提示時刻の規則は、集約・SQL の条件・表の制約で守られている。この 3 つは契約テストでメモリと MyBatis の両方に効く。TDD は 3 ステップとも Red → Green の順にコミットされている。

一方で、次の 3 つの問題があった。

- listener が 2 つの欠けを同じ扱いにしていた。1 つは届く順の遅れで直る欠け（提出の記録がない）、もう 1 つは再配信しても直らない欠け（提示時刻が提出時刻より前）。後者は起動のたびに失敗を繰り返す毒入りのメッセージになっていた。
- テスト用のメモリのリポジトリが保存している実体を返していた。このため、listener が保存を呼ばなくても単体テストと受入テストが通る状態だった。
- 利用者の視点では、未提示の行に提出からの経過時間がなかった。長く待たされている案件が見えず、W9 の 90 パーセンタイルの扱いも誤りやすい。

指摘の数: 高 7、中 17、低 19（5 視点の合計。重なりを含む）。

### D-79 の詳細（listener の 2 つの欠けを分ける）

- 提出の記録がない DE-03: 今のまま警告のログを残して例外を投げ、発行の記録を未完了に残して再配信を待つ。
- 提示時刻が提出時刻より前の DE-03: 再配信しても直らないため、ERROR のログを残して捨てる。ADR-014 の「再配信しても変わらない不正な依頼は例外にしない」と同じ考え方にした。
- 集約に問い合わせ `precedesSubmission` を足した。listener は例外を制御の流れに使わない。これで try の範囲が広すぎる問題と、例外の原因が落ちる問題もなくなった。
- 例外の文言は `UtcInstant` ではなく `Instant` を示す。

### D-81 の詳細（足したテスト）

| テスト | 足したこと |
| :--- | :--- |
| 契約テスト | 同じ時刻、提出時刻と同時刻（DB の制約の境界）、読み出した記録を変えても保存するまでは変わらない |
| MyBatis の制約のテスト | 1 秒前にした |
| 配信の統合テスト | 最初の提示時刻を見積りの提示時刻と、リードタイムを差と、値で照合する。提出の記録がない DE-03 の発行の記録が失敗のまま残り、`IncompleteEventPublications` の再配信で記録できる |
| listener のテスト | ログの輸送要求 ID と理由を確かめる |
| 表示の値のテスト | 日付をまたぐ日時（14:59Z・15:00Z）、期間の `PT59M59S`・`PT1H` |
| デモのサンプルのテスト | 番号を明示した集合で選び、見積りの提示時刻と値で照合する |

### D-82 の詳細（画面）

- 未提示の行の表示を「未提示（提出から 52 時間 10 分）」の形にした。コントローラーは Clock を使う。
- リードタイムの列の「—」の読み上げは「算出しない」にした。
- 表の下に、「—」の意味と、暦の経過時間であることの凡例を置いた。
- 期間の書式の static メソッドの名前を `formatDuration` に変えた。record の部品 `leadTime` との多重定義をなくすため。

### D-83 の詳細（直した文書）

- `user_story.md`: D-11 を「AI の判断。終了報告で人の承認を待つ」と明記した。
- `domain_model.md`:
  - KPI-INV-01 の冒頭の「有効な」を「最初に提示した見積り（経路方針を含む）」に書き直した。
  - 見積りごとの提示時刻は `quotation.quotation.presented_at` に残るので、取消しを作るときに終点を出し直せる、と書いた。利用者の視点の「提示の履歴を残す」には、表を変えずにこれで応える。
  - KPI-INV-03 に D-79 を書いた。
  - DE-01・DE-03 の購読者の欄を「提出時刻」「最初の提示時刻」に結び付けた。
- `data_model.md`: 追跡を KPI-INV-03 まで広げた。Bolt 21 より前の提示は記録されていないこと、`db/dev-data` のシードはスキーマの所有の例外であることを書いた。
- `ui_design.md`: S-22 の前身の記述を直した。
- Javadoc: 集約から SQL の条件への対応を書いた。表示のタイムゾーンが固定であることを書いた。
- 計画: Markdown の崩れとステップ 4 の時刻を直した。
- 受入シナリオ: 表記を直した。範囲外（取消し）と、再配信のシナリオの役割を書いた。

### D-84 の詳細（後の Bolt と人の判断に回したもの）

- **日時表示と期間表示を 1 か所に集める**（計画の確認ポイント 7 の条件に達した。3 つ目の写し）
  - 置き場所の候補は 3 つある。
    - A: `shared` の名前付きインターフェース
    - B: `platform` の Web の部品
    - C: Thymeleaf の式オブジェクト
  - 推奨は B。理由は、共有カーネルが表示の関心で変わらないこと。
  - いつやるかと置き場所は人が決める。推奨は次の Bolt の最初のリファクタリング。
- **W9（S-22 の本体）に回すもの**
  - 監査担当者の認可
  - 週次の値と基準値
  - PV-01 の母集団を見分ける列（荷主企業・航路・状態）
  - 期間での絞り込みと、未提示を上に出す並び
  - 日時の短い形
  - 週末をまたいだ件数
  - 未提示の輸送要求の週次の集計の扱い（営業責任者に確かめる）
- **未完了の発行の件数を確かめる手段**（W10 の監視）
  - パイロットの計測の前に前倒しするかは人が決める。
  - 前倒しする理由: 記録に失敗した輸送要求は「未提示」と見分けられず、KPI-01 の母集団から黙って欠けるため。
- **開発戦略の「Bolt ごとのアプローチの決め方」の見直し**（計画の確認ポイント 12）
  - 人が決める。
  - 推奨は、規則から外れるときに計画の「アプローチ」欄に理由を必ず書く形。
- **そのほかの低い指摘**
  - 受入シナリオの動詞（「求める」と「算出する」）をそろえる。
  - MyBatis の null の変換の対称性。
  - `.gitattributes` で Java の改行を LF に固定する。
  - 非同期の listener の例外がログに 2 回出ること（W10 の監視で決める）。
  - 利用者ごとのタイムゾーン。
  - 基準値も暦の経過時間で測ることを、測る担当者に文書で伝える（パイロット開始の条件）。
