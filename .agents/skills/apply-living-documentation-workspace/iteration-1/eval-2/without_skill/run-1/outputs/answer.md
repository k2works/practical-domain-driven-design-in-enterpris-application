# 注文受付から DB 保存までの新メンバー向けドキュメント方針

## 結論

コードが頻繁に変わるなら、「処理の詳細を手で書き写した文書」は作らないでください。数週間で嘘になります。次のように分けるのがよいです。

1. **変わりにくい「地図」だけを手書きする**（1 ページ。全体像、読む順番、用語、設計意図）
2. **変わりやすい「詳細」はコードとテストから生成・参照する**（シーケンス図、API 仕様、スキーマ、クラス一覧）
3. **文書が古くなったら CI で気づける仕組みにする**

## 1. 手書きするもの（寿命が長い情報）

- 注文処理の全体像: 受付 → 検証 → ドメイン処理 → 永続化の 4〜5 ステップ程度の粒度
- 各ステップの入口となるクラス・ファイルへのリンク（行番号ではなくシンボル名で参照）
- 「なぜこの構造か」: 設計判断、ADR へのリンク
- ユビキタス言語（注文、受注、明細などの用語）
- 読む順番とデバッグの入り口（どのテストを動かせば流れを追えるか）

粒度を粗くするほど陳腐化しません。メソッド名や引数まで書くと壊れます。

## 2. 生成・参照するもの（変わりやすい情報）

| 情報 | 方法 |
| :--- | :--- |
| API 仕様 | OpenAPI をコード（アノテーション）から生成 |
| DB スキーマ・ER 図 | マイグレーションや実 DB から自動生成（SchemaSpy など） |
| 処理の流れ | 受入テスト／統合テストを「実行可能な仕様」とし、テスト名・Given-When-Then を読ませる。必要ならトレースやテストから PlantUML のシーケンス図を生成 |
| クラス・依存関係 | ArchUnit や依存関係ツールで生成 |
| 用語・役割 | コード上の注釈（ドメインの役割を示すアノテーションや KDoc/Javadoc）から用語集を生成 |

「注文を受け付けて保存する」シナリオは、**エンドツーエンドのテスト 1 本**を新メンバーの教材にするのが最も陳腐化しにくい方法です。動かなくなればテストが落ちるので、嘘が残りません。

## 3. 陳腐化を防ぐ運用

- 手書き文書は**コードと同じリポジトリ**に置き、PR のチェックリストに「文書への影響」を入れる
- 文書内のコード参照はリンク切れ検査（シンボル・パスの存在確認）を CI で行う
- 生成物は CI で毎回再生成し、手で編集しない
- 手書き文書に最終確認日（verified）と担当を付け、一定期間過ぎたら見直しを促す
- 新メンバーが文書どおりに進めて詰まった箇所は、そのまま修正対象にする（オンボーディングを文書の検証に使う）

## 4. 進め方（最小から始める）

1. 全体像の 1 ページ（手書き）と、代表的な E2E テスト 1 本を用意する
2. API 仕様とスキーマ図の自動生成を CI に載せる
3. 新メンバーに実際に使ってもらい、足りない所だけ足す

## 避けること

- 処理手順をコードの逐語的な説明として長文で書く
- 行番号や詳細なシグネチャを手書き文書に埋め込む
- 手で描いたシーケンス図を保守し続ける（生成できるものは生成する）

要点は、**人が書くのは「意図と地図」、機械が書くのは「現在の事実」** という分担です。
