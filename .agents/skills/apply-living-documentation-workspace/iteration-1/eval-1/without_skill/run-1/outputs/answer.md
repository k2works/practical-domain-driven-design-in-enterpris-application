# テーブル定義書と ER 図の進め方

## 結論

DDL（db/migrations）がすでにある以上、手で書くのは避け、DDL を唯一の情報源（Single Source of Truth）にして生成するのがよいです。手書きは DDL と必ず乖離し、「変更を楽に安全にできる」状態を損ないます。

## 方針

1. 構造情報は生成する。テーブル名・カラム・型・NULL 制約・PK/FK・インデックスは、稼働中の DB またはマイグレーションから自動生成します。
2. 人が書くのは生成できない知識だけにする。テーブルや列の業務上の意味、なぜその設計か、ステータス値の意味、集約や境界づけられたコンテキストとの対応を書きます。
3. 意味情報は DDL 側に持たせる。`COMMENT ON TABLE/COLUMN`（または DB が対応する同等機能）で、新しいマイグレーションとして追加します。これで生成物に意味が自動で載ります。
4. ER 図は PlantUML または Mermaid のテキストで生成する。画像を手で描かず、生成した `.puml`/`.md` を docs/design に置きます。
5. CI で再生成して差分を検出する。マイグレーションを変えたのにドキュメントが古いままになることを防ぎます。

## 最初にやること

1. 現状把握として、マイグレーションを空の DB に適用して最新スキーマを作る（Docker で使い捨て DB を起動）。
2. ツールを 1 つ選んで試す。候補は次のとおりです。
   - SchemaSpy、tbls（スキーマから Markdown のテーブル定義書と ER 図を一括生成）
   - SchemaCrawler、dbdocs など
   - プロジェクトの DB と言語に合うものを優先する
3. 出力先を docs/design 配下（例: `docs/design/db/`）に決め、生成コマンドをタスク化する（npm script や gulp タスクなど。使い捨てスクリプトを作らない）。
4. 1 回生成して結果を確認し、足りない意味情報（コメント）を洗い出す。
5. COMMENT を追加するマイグレーションを作る。DB スキーマ変更にあたるため、適用前に人の承認を得る。
6. 生成物のうち手書き部分（業務ルール、状態遷移の補足）だけを別の節または別ファイルに分け、生成物と混ぜない。
7. 再生成と差分チェックを CI に入れる。

## 注意点

- 生成物は手で編集しない。編集箇所は生成元（DDL の COMMENT）に戻す。
- テーブル数が多い場合、ER 図は全体 1 枚ではなく、集約・サブドメイン単位に分割すると読めます。
- ドメインモデルや論理データモデル（概念レベル）は設計意図の文書なので、これは手で書く価値があります。物理定義（テーブル定義書）と役割を分けてください。

## 要点

構造は DDL から生成、意味は COMMENT で DDL に持たせる、概念設計だけ人が書く。最初の一歩は、使い捨て DB にマイグレーションを流して tbls などで出力を試すことです。
