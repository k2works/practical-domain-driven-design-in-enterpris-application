## Living Documentation 適用結果

- 操作: triage → automate（必要なら augment）
- 対象: docs/design/ のテーブル定義書・ER 図（DDL は db/migrations に存在）
- 判断: **手で書かない。生成する**
  - 根拠: 権威ある情報源は DDL（db/migrations）。テーブル構造は頻繁に変わり、DDL から機械的に取り出せる。手書きの複製はマイグレーションのたびに古くなり、AI に渡すコンテキストも汚す。
- 作成・更新: （助言のみ。リポジトリは変更していない）
- 検証: 下記「進め方」の 4 と 5
- 要確認: 下記

## 方針

### 1. triage の結論

1. 価値のある知識か。テーブル構造は多くの人に関係するので価値はある。ただし「構造そのもの」は DDL にすでにある。
2. すでに成果物の中にないか。DDL にある。複製しない。
3. 機械的に取り出せ、かつ頻繁に変わるか。取り出せるし変わる。したがって**生成する**。

つまり「手書きの定義書・ER 図」は作らず、DDL を正（権威ある情報源）にして、そこから生成します。生成物は捨てて作り直せるキャッシュ扱いで、新しい真実の源にしません。

### 2. 生成するもの（4 ステップ）

「範囲を選ぶ → 目的でフィルタ → 射影 → 出力形式に変換」で進めます。

- **範囲**: db/migrations（または、マイグレーション適用後の実スキーマ）
- **フィルタ**: 1 つの図に 1 つのストーリー、5〜9 要素。全テーブルを 1 枚に描くとアンチパターンです。コンテキスト・業務領域ごとに分けて描きます。
- **射影**: テーブル、カラム、型、制約、FK、コメントを抽出します。
- **出力**: テーブル定義書は Markdown。ER 図は PlantUML か Mermaid で、差分管理できるプレーンテキストにします。

### 3. 人が書くのは「意図」だけ（augment）

DDL に表れない「なぜ」だけを補います。

- テーブル・カラムの役割や業務上の意味は、`COMMENT ON` や DDL コメントに書き、それを生成物に取り込みます。別文書に書きません。
- 設計判断の理由や却下した代替案は ADR（`creating-adr`）に残します。
- 外在的な情報（所有者など）は付けません。説明が難しいテーブルや読みにくい図は、名前や設計を直す合図です。

## 最初にやること

1. **手作業で小さく試す。** 1 つの業務領域（5〜9 テーブル）を選び、DDL から図と定義書を出してみます。IDE のデータベースツールや、スキーマ抽出のワンライナーで十分です（tbls や SchemaSpy などはその後でよい）。読み手に価値があるかを確かめてから、専用ツールや CI に進みます。
2. **読み手・目的・核心メッセージを 1 つずつ決める。** 例: 新メンバーが主要な業務領域のデータ構造を把握する。
3. **PROJECT.md を確認する。** 生成ツールやタグ名、公開先がプロジェクト固有に決まっていれば、そちらを正とします。
4. **入口と更新トリガーを決める。** README や docs/design の index から 1 本のリンクで辿れるようにします。マイグレーション変更時にビルド／CI で再生成します。
5. **生成物に元へのリンクと生成日／版を付ける。** 公開物を直接編集させず、DDL を直す運用にします。

## 仕上げの点検（check）

- 手作業で更新している一覧・図が docs/design に残っていないか。
- 生成が CI で再現でき、DDL との不一致が検出できるか。
- 図が 5〜9 要素に収まり、線が交差しすぎていないか。
- 生成物を `apply-docs-structure`（配置）と `apply-okf`（来歴・index・log）で整える。公開・Lint は `operating-docs`。

## 要確認（人の判断が必要）

- 生成ツールの選定（新しい外部ツール導入は確認必須）。
- ER 図を分割する単位（業務領域の切り方）。
- 自動化（CI 公開）まで進めるか。手作業での試行結果を見て決めます。
- 手書きの設計意図（コメント）を DDL に追記するのは、スキーマ変更を伴うため承認を得てから行います。
