# Living Documentation 適用

ドキュメントを「知識を伝えるプロセス」として扱い、**書く量を減らしながら信頼できる状態を保つ**ための判断と仕上げの工程。原則の正は次の 3 ガイド。

- `docs/reference/LivingDocumentation導入ガイド.md` — 全体像・4 原則・各パターン
- `docs/reference/ダイナミックキュレーション導入ガイド.md` — 安定した基準で少数を選ぶ
- `docs/reference/ガイドツアー・サイトシーイング導入ガイド.md` — 見どころの案内

同じディレクトリに `PROJECT.md` があれば必ず読む（生成ツール・タグ名・公開先など本プロジェクト固有の事情はそこにある）。食い違えば `PROJECT.md` を正とする。

## なぜ毎回適用するのか

手書きの複製は、元（コード・設定・テスト）が変わるたびに古くなる。古い文書は読み手を誤らせ、AI-DLC では**AI に渡すコンテキストそのものを汚す**（成果物は契約であり、コンテキストである）。だから「書く前に探す」「書くなら根拠だけ」「重複させるなら検証を付ける」を、文書を 1 つ作るたびに繰り返す。守るのは 4 原則：Reliable（同期している）・Low effort（変更時の追加作業が小さい）・Collaborative（会話優先、チームで所有）・Insightful（実態を映し設計を改善させる）。

## 5 つの操作

変化の速さでアプローチを選ぶ。速く変わる知識ほど、人が書かず機械に任せる。

| 操作 | いつ | 要点 |
| :--- | :--- | :--- |
| **triage** | 文書を書く**前** | 書く／リンクする／生成する／書かない、のどれかを決める |
| **augment** | コードに意図が足りない | 本質的な知識だけ、コードに近い場所に、機械が読める形で補う |
| **curate** | 読み手に少数だけ見せたい | 安定した基準で動的に選ぶ。マップ・ツアー・模範例 |
| **automate** | 頻繁に変わり、成果物から抽出できる | 用語集・図・一覧を生成する |
| **check** | 仕上げ | 陳腐化の芽（手作業の一覧・直接参照・過剰なタグ）を点検 |

### triage：書く前に判断する

次の順で問い、最初に当てはまったものを採る。

1. **価値のある知識か？** 長く役立つ・多くの人に関係する・重要でクリティカル、のいずれでもなければ**書かない**。対話や根本原因の修正（命名・設計の改善）で済むなら、そちらを選ぶ。デフォルトは書かない
2. **すでに成果物の中にないか？** コード・テスト・DDL・設定・ADR・コミット履歴・既存のリファレンスにあれば、**リンクする**。複製しない
3. **成果物から機械的に取り出せるか？** 取り出せ、かつ頻繁に変わるなら**生成する**（automate へ）。DDL → ER 図・テーブル定義書、コード → 用語集・依存図、テスト → シナリオ一覧
4. **変わらない知識か？** ビジョン・原則・判断の理由のように安定していれば**書く**。ただし意図・根拠・却下した代替案に絞る（augment へ）
5. **やむを得ず重複させるか？** 不一致を検出するテストやチェックを必ず用意する（Reconciliation）

**権威ある情報源を先に決める。** 同じ知識が複数箇所にあるとき、変更が最も正確に反映される場所（多くはコード・DDL）を正とし、他はそこから導く。統合した結果（生成物）を新しい真実の源にしない。いつでも捨てて作り直せるキャッシュとして扱う。

**書きにくさは設計のシグナル。** 説明が難しい、図が交差だらけになる、用語集が読めない、といった状態は、文書ではなく名前や設計を直す合図。

### augment：足りない意図だけを補う

コードは「どう」を語るが「なぜ」を語らない。補うのは意図・判断・根拠に限る。

- **本質的（intrinsic）な知識だけ付ける。** 要素を消せば知識も消えるもの（役割・性質・判断理由）はよい。所有者・配置先のような外在的な知識は付けない。変更のたびに保守が要るため
- **根拠は 4 点セット**で残す：その時点の文脈／問題・要件／選んだ解決策と理由／却下した代替案と理由。記録は変更を怖がらせず、後押しする。置き場所は ADR（`creating-adr`）、変更単位の意図はコミットメッセージ（`git-commit`）、コード上の役割はアノテーション（`アノテーション導入ガイド.md`）
- 推測で先回りして書かない。実際に作ったものについて、必要になった時点で書く（just-in-time）。同種の判断が繰り返されるなら、原則を 1 回だけ書いて各所から参照する
- 大半に当てはまる性質は付けず、**例外だけ**に付ける
- 規約（命名・パッケージ構成）で分類を表せるなら規約を使い、静的解析で守らせる。元ファイルに触れないときだけサイドカーを使う（最後の手段）

### curate：少数を動的に選んで見せる

最初に**読み手・目的・伝えたい核心メッセージを 1 つずつ**決める。1 文書 1 メッセージ。そのうえで手法を選ぶ。

| 目的 | 手法 | 上限の目安 |
| :--- | :--- | :--- |
| ドメインの中心概念を示す | コアのハイライト | 主要な概念に限定 |
| 真似してほしい書き方を示す | 模範例（弱点も書く。目的は会話のきっかけ） | チーム合意の少数 |
| 全体の見どころを順序なしで示す | サイトシーイング・マップ | 5〜7 個、最大 10 個 |
| 処理の流れを追わせる | ガイドツアー（name・description・rank） | 1 本あたり数ステップ |
| 振る舞いを読み手別に説明する | シナリオダイジェスト（タグで絞る） | 読み手ごと |

選択基準は**安定したもの**（フォルダ構成・命名規約・タグ・リンクレジストリ・ツールの出力）にする。クラス名や URL の名指し列挙はリネームで壊れるので使わない。抽出は**まず IDE の検索から**始め、価値が確かめられてから生成スクリプト・CI 公開へ進む。手順・実装例・落とし穴の詳細は `references/curation.md`。

### automate：生成する

Living Document は 4 ステップで作る：**範囲を選ぶ → 目的でフィルタする → 関係する内容を抽出する（射影）→ 出力形式に変換する**。

- 用語集：クラス名・メソッド名・列挙値からドメイン用語だけを**選択的に**抽出する（技術的なものは除く）。境界づけられたコンテキストごとに分ける。読みにくければコードの名前を直す（用語集はコードの質へのフィードバック機構）
- 図：**1 つの図に 1 つのストーリー**、5〜9 要素。すべてをリバースエンジニアリングで描かない。プレーンテキスト（PlantUML・Mermaid・DOT）で差分管理できる形にする
- 自動化の前にまず手作業で試し、手間に見合うか判断する。生成物には元へのリンクを付け、公開物を直接編集させず元を直させる

詳細（Living Glossary・Living Diagram・ランタイムドキュメンテーション）は `references/automation.md`。

### check：陳腐化の芽を点検する

- 手作業で更新している一覧・目次・図が残っていないか
- 名前や URL を直接指定した参照が残っていないか
- 重複した知識に不一致を検出する仕組みがあるか
- タグ・アノテーションを付けすぎていないか（マップは最大 10）
- 生成物がビルド／CI で更新・公開されるか。入口（README 等）から 1 本のリンクで辿れるか
- 新メンバーに実際に歩いてもらい、迷った箇所を直したか

## 導入の進め方（小さく始める）

1. **新規作業から**適用する。既存全体を一度に直さない
2. 目的 1 つ・基準 1 つ・タグ 5〜10 個以内で動かし、効果を確認してから広げる
3. 反応を見て、模範例・マップ・ツアー・生成へ順に進める

## 他スキルとの連携

本スキルは「何を書くか／書かないか／どう取り出すか」を決める。他の工程は既存スキルに任せ、**複製しない**。

| 場面 | 使うスキル |
| :--- | :--- |
| 判断の根拠を残す | `creating-adr` |
| 変更の意図を残す・CHANGELOG | `git-commit`、`developing-release` |
| 配置先の判断 | `apply-docs-structure` |
| フロントマター・index・log | `apply-okf` |
| 設計書・図の公開、Lint | `operating-docs` |
| 判断と学びの記録 | `creating-journal` |
| 実装中に役割・用語・画面知識をコードへ持たせる | `developing-backend`、`developing-frontend` |

典型的な流れ：文書を書こうとする → triage で「生成する」「リンクする」を先に検討 → 書くなら `apply-docs-structure`（配置）→ 作成 → `apply-okf`（来歴）。本プロジェクトの成果物との対応表は `references/project-mapping.md`。

## 完了報告

```markdown
## Living Documentation 適用結果

- 操作: triage / augment / curate / automate / check
- 対象: <文書・コード・読み手>
- 判断: 書く / リンク / 生成 / 書かない — <根拠（権威ある情報源・変化の速さ）>
- 作成・更新: <ファイル・タグ・生成スクリプト>
- 検証: <重複の不一致検出・生成の再現性・上限数の遵守>
- 要確認: <タグ名や基準のチーム合意、自動化に進むかの判断、など>
```
