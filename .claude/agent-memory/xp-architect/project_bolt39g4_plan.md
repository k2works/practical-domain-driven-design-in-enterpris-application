Bolt 39g4 は FRS-02 を「判定の時刻 >= 次の予定の実績の予定時刻 + 36h（ちょうどは超過）」と読み、確認中にせず S-11・S-12 で読むときに示す提案（業務の判断 (aq)〜(as)、台帳 D-133〜D-135、前の決定の変更 (19)〜(21)。(21) は FRS-02 の条件と「鮮度」の定義の変更で、R-12 の理由と取込停止時の振る舞いが逆になる）。リファクタリング（対応づけを Schedule に出す）は Red の前に置く（Java では Red のテストがコンパイルを止める。検証で指摘）。`tracking_record.next_expected_at` を足して保存値で S-11 を判定する（スキーマ）。航海の採用値（DE-12）で動く見込みと根拠の表示は 39g4b に分け、優先だけ (at)/D-136 で先に決めた（到着の実績 > 遅れの見込みと最後の区間の航海の到着予定の遅い方）。

**Why:** 確認中から出る道は US-13 だけ（D-124）で、時刻で変わる状態は定期の処理が要る。追跡は取込の時刻を持たない。DE-12 の分は listener・索引・順の規則（D-105）の置き場所・PERF-06 の直列が未決で、鮮度と触る場所が重ならない。

**How to apply:** 39g4b の開始準備では上の技術の未決 5 点を必ず諮る。`LatestEstimateRule` の対応づけを `Schedule` に出すリファクタリングを先に分けた（見込みと次の予定の実績で写しを作らない）。既存の行は NULL のままなので配備前に件数を確かめる。S-11 の上限 50 件より古い鮮度超過は見えない（W10 で絞り込み）。[[project-bolt39g3-plan]]
