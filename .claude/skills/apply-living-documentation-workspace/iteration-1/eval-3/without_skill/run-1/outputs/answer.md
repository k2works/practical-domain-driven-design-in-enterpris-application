# 手書きの用語集がコードとずれる問題への対処

## 原因

用語集とコードが別々の場所にあり、二重管理になっていることが原因です。コードを変えても用語集を直す仕組みがありません。人の注意に頼る運用は必ず破綻します。

## 方針

用語の正本（Single Source of Truth）をコードに一本化し、用語集はそこから生成するか、ずれを自動検出します。

## 具体策

1. **コード側に定義を持たせる（Living Documentation）**
   - クラス・型・列挙に、ドメイン上の意味を KDoc / Javadoc / docstring で書きます。
   - 独自アノテーション（例：`@DomainTerm(name="受注", definition="…")`）を付けると、機械的に抽出しやすくなります。
   - 命名自体をユビキタス言語に揃えます。コードの識別子が用語になっている状態を目指します。

2. **用語集を自動生成する**
   - アノテーションやドキュメントコメントを走査し、Markdown を生成するスクリプトを作ります。例は Dokka、javadoc doclet、ts-morph、Python の ast などです。
   - CI で毎回生成し、`docs/` に出力するか公開します。手では編集しません。
   - 生成物に「自動生成・直接編集禁止」と明記します。

3. **ずれを CI で検出する**
   - 生成した用語集と、コミット済みの用語集の差分があればビルドを失敗させます。
   - 用語集にある用語がコードに存在しないこと（陳腐化）、主要なドメイン型が用語集にないこと（漏れ）を検査します。
   - アーキテクチャテスト（ArchUnit など）で、ドメイン層の公開型には用語定義を必須にする方法もあります。

4. **コードに現れない用語の扱い**
   - 業務上の概念のうち、コードに対応しないものだけを手書きの補足ファイルに分けます。
   - 補足ファイルは、自動生成の用語集に結合して出力します。
   - 手書き部分は最小限にし、レビュー時にコード変更とセットで確認する PR チェックリストを置きます。

5. **運用ルール**
   - ドメインモデルを変更する PR では、用語の定義も同じ PR で更新します。
   - 「説明の変更がコードと同じ場所にある」状態にしておくと、レビューで漏れに気づけます。
   - 定期的に、用語と実装の乖離を点検する日を設けます。

## 導入の進め方

1. まず中核の集約・エンティティ・値オブジェクトだけを対象にします。
2. 小さく生成スクリプトを作り、CI に組み込みます。
3. 効果を確認してから、対象範囲を広げます。

## まとめ

手書きの用語集をなくすことが目的ではありません。コードを正本にし、用語集をその派生物にします。そうすれば、ずれは起きにくくなり、起きても CI で検知できます。
