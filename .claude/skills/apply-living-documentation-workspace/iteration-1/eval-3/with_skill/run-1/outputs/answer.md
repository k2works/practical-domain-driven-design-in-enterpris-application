# ドメインモデル用語集がコードとずれる問題の直し方

## 結論

**手書きの用語集を直すのではなく、手書きをやめて、コードから生成する（Living Glossary）** のが解決策です。ずれの原因は書き方や運用の甘さではなく、「同じ知識をコードと用語集の 2 か所に人手で持っている」という構造にあります。構造を変えない限り、頑張っても再びずれます。

## 判断の根拠（triage）

| 問い | 答え |
| :--- | :--- |
| 価値のある知識か | はい。ユビキタス言語は長く役立ち、チーム全体に関係する |
| すでに成果物の中にあるか | はい。クラス名・メソッド名・列挙値がドメイン言語そのもの |
| 機械的に取り出せ、頻繁に変わるか | はい。用語はコードの変更のたびに増減・改名される |

したがって判断は「生成する」です。権威ある情報源は**コード**とし、用語集はそこから導くキャッシュとして扱います。生成物を新しい真実の源にしてはいけません。いつでも捨てて作り直せる状態にします。

## 進め方

### 1. 範囲とフィルタを決める

- すべてのコードがドメインに関係するわけではないので、ドメイン用語だけを**選択的に**抽出します。アノテーションやパッケージ規約（例：`domain` 配下）で対象を絞ります。
- `toString()`・`equals()`・技術的なフィールド・インフラ層のクラスは除外します。
- **境界づけられたコンテキストごと**に用語集を分けます。同じ語でも文脈で意味が違うため、1 枚にまとめません。

### 2. 定義文はコードの近くに置く

コードから取り出せるのは「名前」までで、「その言葉が何を意味するか」という定義文は人が書く必要があります。ただし置き場所は用語集ではなく、**コードのコメントやアノテーションの説明**にします。

- 付けるのは本質的な知識（役割・意味・判断理由）だけにします。所有者や配置先のような外在的な情報は付けません。
- 大半に当てはまる性質は付けず、例外だけに付けます。
- 用語が「なぜ」その名前になったかという重要な判断は ADR（`creating-adr`）に残し、用語集からはリンクします。

### 3. 生成して公開する

1. まず手作業で 1 つのコンテキストについて抽出し、読み手にとって価値があるか確かめます。IDE の検索やワンライナーで足りるか先に試します。
2. 価値が確認できたら生成スクリプトにし、**ビルド／CI で更新・公開**します。
3. 生成物には元コードへのリンクと生成日／版を付けます。
4. 公開された用語集を**直接編集させません**。誤りがあれば元のコード（名前や説明）を直します。
5. README などの入口から 1 本のリンクで辿れるようにします。

具体的なツール（アノテーション処理、ソース解析、スクリプト言語）はプロジェクトの言語に依存するため、`PROJECT.md` があればそれに従い、無ければチームで決めてください。

### 4. 読みにくければコードを直す

生成した用語集が読みにくい、意味不明な語が並ぶ、という場合は、用語集ではなく**コードの名前や設計の問題**です。用語集はコードの質へのフィードバック機構として使います。コードが宣言的で、ドメイン言語で書かれているほど、用語集も良くなります。

### 5. やむを得ず手書きを残す部分があるなら

どうしても手書きが残る場合（コードに現れない概念など）は、不一致を検出する仕組み（Reconciliation）を用意します。たとえば、用語集に載る用語がコードに存在するかを確かめるテストや CI チェックです。検出なしの重複は、また必ずずれます。

## 小さく始める

- 既存の用語集全体を一度に置き換えず、**新規・変更するコンテキスト 1 つ**から始めます。
- 効果を確認してから他のコンテキストへ広げます。
- 実装中にドメインモデルへ役割や用語を持たせる作業は `developing-backend` の Living Documentation の実践と連動します。

## 点検項目（check）

- 手作業で更新している用語の一覧が残っていないか
- 生成がビルド／CI に組み込まれ、更新が自動か
- 用語集から元コードへ辿れるか
- 用語集を直接編集する運用になっていないか

## Living Documentation 適用結果

- 操作: triage → automate（augment を併用）
- 対象: ドメインモデルの用語集（読み手：開発者・業務担当者・AI）
- 判断: 生成する。根拠は、権威ある情報源がコードであり、変化が速く、機械的に抽出できるため
- 作成・更新: なし（助言のみ）
- 検証: 手書き部分があれば用語とコードの不一致を検出するチェックを用意する
- 要確認: 抽出の基準（アノテーションかパッケージ規約か）、生成ツールの選定、コンテキストの分け方のチーム合意、最初に着手するコンテキスト
