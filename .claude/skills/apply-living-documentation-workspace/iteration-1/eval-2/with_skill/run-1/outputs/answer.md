# 新メンバー向け「注文受付から DB 保存まで」の案内：推奨方針

結論：**手書きの処理説明書は作らず、コードに付けた少数のタグから「ガイドツアー」を生成する**のがよいです。コードが頻繁に変わるため、手書きの複製はすぐ古くなります。古い案内は新メンバーを誤らせ、AI に渡すコンテキストも汚します。

## 1. triage：書く前の判断

| 問い | 判断 |
| :--- | :--- |
| 価値のある知識か | はい。多くの新メンバーに関係し、全体像の理解に直結する |
| すでに成果物の中にあるか | 処理の流れ自体はコード（入口から保存まで）にある。複製しない |
| 機械的に取り出せ、頻繁に変わるか | はい。したがって**生成する** |
| 変わらない知識か | 「なぜこの設計か」の根拠は比較的安定している。これだけ ADR に書く |

権威ある情報源はコードです。ツアー文書は生成物であり、いつでも捨てて作り直せるキャッシュとして扱います。直接編集はさせず、直すときはコード側のタグや説明を直します。

## 2. curate：ガイドツアーで案内する

- 読み手は新メンバー、目的はオンボーディング、核心メッセージは「注文が届いてから DB に保存されるまでの流れ」の 1 つに絞ります（1 文書 1 メッセージ）。
- 節目の要素だけを選びます。例として、受付の入口（API や受信リスナー）、入力の検証、ドメインの注文処理、永続化（リポジトリ）の 4〜6 ステップ程度です。全部を載せるとノイズになります。
- 各ステップに name、description、rank を付けます。
  - name：ツアー名（例：注文受付〜保存）
  - description：このツアーの文脈での意味と「次に何が起きるか」（API の使い方説明とは別）
  - rank：10, 20, 30 の 10 刻み。途中に追加しても番号が崩れない
- 選択は**安定した基準**（タグ・フォルダ構成・命名規約）で行い、クラス名や URL の名指し列挙はしません。リネームで壊れるためです。
- 補助として、全体の見どころを順序なしで示すサイトシーイング・マップ（5〜7 個、最大 10）を添えるのも有効です。

## 3. 小さく始める

1. **まず IDE の検索から**始めます。タグ（アノテーションやコメントタグ）を重要な数か所だけに付け、検索で一覧が得られるか確認します。
2. 価値が確かめられたら、タグ付き要素を走査して name でグルーピングし、rank 順に並べて Markdown に連結するスクリプトを作ります。各ステップのタイトルはソースへのリンクにします。
3. ビルド／CI で生成・公開まで自動化し、README から 1 本のリンクで辿れるようにします。生成を最初から作り込まないことが重要です（走査実装は複雑化しやすい）。
4. 変更のたびにツアーが最後まで通るか CI で確認します。

## 4. augment：書くのは根拠だけ

コードに無い「なぜ」だけを補います。設計判断の理由は ADR（`creating-adr`）、変更の意図はコミットメッセージに残します。処理手順の逐語的な説明はコードの複製になるので書きません。

## 5. check：陳腐化を防ぐ点検

- 手作業で更新する一覧や図が残っていないか
- クラス名・URL の直接参照が残っていないか
- タグの付けすぎ（マップは最大 10）がないか
- **新メンバーに実際に歩いてもらい、迷った箇所を直す**。歩きにくい箇所は文書ではなく、名前や構造を直す合図です

## 6. 要確認（チームで合意する点）

- タグ名（例：`GuidedTour` のように 1 つに統一）と付与ルール
- ツアーに含める節目の要素（4〜6 個）
- 生成スクリプトへ進むタイミング（IDE 検索で価値を確認してから）
- 公開先と入口（README からのリンク）

## 補足

手書きの Markdown だけで済ませる場合、コードが頻繁に変わるなら保守負担が大きく、最終手段です。やむを得ずブックマーク形式（タイトル・短い説明・場所へのリンク）の手作業一覧にするなら、リンク切れや不一致を検出するチェックを必ず付けてください。
