## 1. Living Document の作り方

記述対象と同じペースで進化する文書。手作業では維持できないので、変更のたびに生成する。

1. **範囲を選ぶ**：ソースコード管理など、データの保管場所から
2. **目的に沿ってフィルタする**
3. **関係する内容を抽出する**（射影）
4. **出力形式に変換する**：Markdown・図・HTML・PDF

変換が複雑なら中間モデルを連鎖させる。1 つの図やリストは **5〜9 項目程度**に収める。生成物には元へのリンクと生成日／版を付け、公開物を直接編集させず元を直させる。

## 2. Living Glossary

ユビキタス言語の用語集をコード自身から生成する。クラス名・メソッド名・列挙値はドメイン言語の一部だから。

- すべてのコードがドメインに関係するわけではない。アノテーション等で**選択的にフィルタ**する
- `toString()`・`equals()`・技術的なフィールドは除外する
- 境界づけられたコンテキストごとに用語集を分ける
- 成功条件は**コードが宣言的であること**。コードが良いほど用語集も良くなる
- 用語集は目的ではなく、**読みにくければ名前やコードを直すきっかけ**（コードの質へのフィードバック機構）

手書きの用語集とコードがずれる問題は、「手書きを直す」のではなく「手書きをやめて生成する」で解く。人が書く必要があるのは、コードに表れない定義文（意図）だけで、それはコードのコメントやアノテーションの説明に置いて抽出する。

## 3. Living Diagram

**1 つの図に 1 つのストーリー**（One diagram, one story）。情報過多の図は、情報がない図と同じくらい役に立たない。リバースエンジニアリングで全部描くのはアンチパターン。

作り方は Living Document と同じ：スキャン → 関連部分をフィルタ → 意味ある情報を抽出 → レイアウト → レンダリング。出力は PlantUML・Graphviz（DOT）・Mermaid などのプレーンテキスト。

| 図の種類 | 特徴 | 使いどころ |
| :--- | :--- | :--- |
| ナプキンスケッチ | 使い捨て | 一時的な会話 |
| 独自ツールの図 | 見た目は良いが差分管理が難しい | 避ける |
| プレーンテキストの図 | 差分管理しやすい | 長く使う図 |
| コード駆動の図 | リファクタリングに強い | 長く使う図 |
| Living Diagram | コードから自動生成 | 頻繁に変わる構造 |

見やすさ：軸に意味を持たせる／近さ＝類似、包含＝特殊化とレイアウトに意味を持たせる／サイズ・色に意味（重要度・深刻度）を持たせる／線が 1 本でも交差するなら複雑すぎる可能性。

代表例：

- **ヘキサゴナルアーキテクチャ図**：ドメインを中心に、依存が外→内の一方向であることを示し、違反は赤で強調
- **ビジネスドメイン概要図**：パッケージに宣言したドメイン間の関係から生成
- **コンテキスト図**：外部アクターを宣言し、許可リストと組み合わせて想定外の依存を検知

Living Diagram はコードをありのままに映し、設計の質について正直にする。**不都合な真実に気づく**ことが価値の一つ。

DDL → ER 図・テーブル定義書は単一情報源からの公開の典型。手で ER 図を描かず DDL（権威ある情報源）から生成する。

## 4. 単一情報源からの公開と整合性検証

- **Single-Source Publishing**：知識は 1 か所に置き、そこから文書を生成して公開する（1 つの Markdown から HTML・PDF、DDL からテーブル定義書）。公開物にバージョンと最新版へのリンクを付ける
- **Reconciliation（整合性検証）**：やむを得ず複数箇所に置く知識は、不一致を自動テストで検出する。BDD のシナリオとステップ定義、前提を確かめるカナリアテスト、外部公開した契約（列挙値・API スキーマ）の変更検知テスト
- **Consolidating Dispersed Facts**：分散した事実（あるインターフェースの全実装、依存関係、クラス階層）は自動で集めて再構成する。結果は**キャッシュ**であり、真実の源にしない

## 5. ランタイムドキュメンテーション

質問に答えられるものはすべてドキュメントとみなせる。

- **生きたサービス図**：分散トレーシング（Trace/Span/Parent ID の伝搬）を集約するとサービス依存グラフになる
- **Visible Workings**：「この結果はどう計算したか」に実行時に答えられるようにする。説明責任が要る領域で有用
- **Visible Tests**：テスト出力をドメイン固有の図として可視化する。探索段階では図を眺め、後からアサーションにしていく
- **イベントソーシングのテスト**：Given（過去のイベント）／When（コマンド）／Then（新しいイベント）がそのままシナリオ。コマンドは命令形、イベントは過去形で命名すれば BDD フレームワーク無しで読める
- **Introspectable Workings**：決定木・ワークフロー・設定など内部の動きを見せたい対象は、各要素がコラボレータを返す仕組みで再帰的に走査できるようにする。最低限、設定に基づいて動く処理は設定を表示できるようにする

## 6. 自動化に進む前の判断

- まず手作業で作ってみて、読み手に価値があるか確かめる（効果の薄い自動化は保守コストだけ残す）
- 最初は IDE 検索やワンライナーで足りるか確認する。専用ツールは必要になってから
- 生成物の入口（README 等）と更新トリガー（ビルド／CI）を先に決める
- 生成が難しい・図が読めない場合は、ドキュメントではなく設計の問題として扱う
