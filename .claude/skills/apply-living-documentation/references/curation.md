## 1. 動的キュレーションの導入ステップ

固定のリストは変更に追従できず陳腐化する。**安定した基準**で選び、編集上の判断（何を伝えるか）だけを人がメタデータで表し、抽出と公開はツールに任せる。

1. 読み手と目的を 1 つに絞る（新メンバーのオンボーディング、業務担当者への説明、設計レビューなど）
2. 核心メッセージを 1 つ決める（「ここが核心」「ここを真似して」「ここから読んで」）
3. 選択基準を決める。命名規約・フォルダ構成で足りるか、専用タグが要るか
4. 重要な少数だけにタグを付ける
5. 抽出する。まず IDE の検索、次に走査スクリプト
6. ビルド／CI で生成・公開を自動化する
7. コードにない意図・背景を説明文で補う
8. チームで見直す。何を模範例・コアとするかは合意で決める

最初のゴール：1 目的・1 基準・タグ 5〜10 個以内で動く状態。

安定した基準の例：フォルダ構成、命名規約（`Repository` で終わる型）、タグ・アノテーション、リンクレジストリ、ツールの出力。**避ける**：特定のクラス名や URL の名指し列挙。

## 2. 手法の使い分け

| 手法 | 目的 | メタデータ例 | 目安 |
| :--- | :--- | :--- | :--- |
| コアのハイライト | 中心概念を示す | `@CoreConcept` | 主要概念に限定 |
| 模範例 | 真似してほしい良いコード | `@Exemplar(pros, cons)` | チーム合意の少数 |
| サイトシーイング・マップ | 見どころを順序なしで | `@KeyLandmark` `@MustSee` | 5〜7、最大 10 |
| ガイドツアー | 流れを順序付きで | `@GuidedTour(name, description, rank)` | 1 本あたり数ステップ |
| シナリオダイジェスト | 振る舞いを読み手別に | `@keyexample` `@nominalcase` `@wip` | タグで絞る |

選び方：全体像を掴ませたい → コア → マップ／書き方を伝えたい → 模範例／流れを追わせたい → ツアー／業務担当者に説明・進捗報告 → シナリオダイジェスト。**最初は 1 つだけ**試す。

模範例は完璧でなくてよい。弱点があれば理由を書く。目的はコピペではなく、ペア／モブプロやレビューでの会話のきっかけ。

## 3. サイトシーイング・マップの作り方

1. **見どころを選ぶ**：「ここを理解すれば全体が分かる」場所をチームで 5〜7 個（最大 10）に絞る。決めにくいほど価値がある
2. **タグ名を決める**：汎用名を 1 つ（`KeyLandmark`・`MustSee`・`PointOfInterest`・`CoreConcept`）。目的別に乱立させない
3. **付ける**：選んだ要素だけに。理由は説明文に書く
4. **一覧を生成する**：IDE 検索、またはスクリプトでタグ付き要素を集める
5. **入口に置く**：README や Wiki からリンクする

タグの付けすぎはコードを標識だらけにする。控えめに。コードが頻繁に変わりタグ検索が使えない場合のみ、ブックマーク形式（タイトル・短い説明・場所へのリンク）の手作業一覧を許容するが、保守負担が大きいので最終手段。

## 4. ガイドツアーの作り方

処理の入口から出口まで、見どころを順にたどる 1 本の物語。

| パラメータ | 役割 |
| :--- | :--- |
| name | どのツアーのステップか（1 本だけなら省略可） |
| description | **このツアーの文脈での意味**と「次に何が起きるか」。API の使い方説明（Javadoc）とは別 |
| rank | 並び順。**10, 20, 30… の 10 刻み**にして途中追加できるようにする |

手順：題材の流れを 1 本選ぶ（例：外部から届いたデータが処理され DB に保存されるまで）→ 節目の要素だけ選ぶ（全部載せるとノイズ）→ name・description・rank を付ける → name で分類し rank で並べて Markdown に連結する（各ステップのタイトルはソースへのリンク）→ 最初から最後まで歩いて分かりにくい箇所を直す。

歩いて分かりにくければ、それは構造の分かりにくさのシグナル。文書でなく設計の改善につなげる。

## 5. 実装の最小形

言語非依存の考え方：**タグを定義 → コードに付与 → 走査して出力**。

```java
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface PointOfInterest { String value() default ""; }

@GuidedTour(name = "Quick Developer Tour",
            description = "The MQ listener which triggers a full chain of processing",
            rank = 10)
public class FuelCardTxListener { ... }
```

C# は属性（Attribute）、TypeScript などはコメントタグや decorator、Markdown/文書ではタグ（`@keyexample` 等）で同じことができる。複数プロジェクトで共有するならタグ定義は専用の場所に置く。

生成の流れ：ソースを走査してタグ付き要素を集める → ツアー名でグルーピングし rank 順に並べる → 名前・コメント・description を取り出す → Markdown に連結（ソースへのリンク付き）→ CI で実行し公開。

生成実装は複雑化しがち（アノテーション走査・型探索で「毛深く」なる）。**まず IDE 検索で価値を確認し、必要になってから作り込む。**

## 6. 落とし穴と対策

| 落とし穴 | 対策 |
| :--- | :--- |
| 名前・URL の直接参照で陳腐化 | 安定した基準で間接的に選ぶ |
| 見どころ過多でマップの意味が薄れる | 5〜7（最大 10）に絞る |
| タグでコードが汚れる | 控えめに。説明は引数か生成側に持たせる |
| 全部載せてノイズになる | 1 文書 1 メッセージ。目的外は載せない |
| 説明がコードの複製になる | ツアーでの意味と次に起きることを書く |
| ツアーの番号が崩れる | 10 刻みで rank |
| 模範例で意見が割れる／複製され改善が止まる | 演習で合意し、弱点も書き、目的を会話のきっかけと明記 |
| タグ名がばらばらで検索できない | 名前を先に決めて統一 |
| 生成物が更新されない | ビルド／CI で生成〜公開まで自動化 |
| 誰も読まない | README など入口からリンクし、オンボーディングで実際に歩く |

運用：新メンバーに歩いてもらい迷った箇所を直す／大きな変更後にツアーが最後まで通るか CI で確認／長くなったらテーマ別に分割／完全版と要約版を分ける。

## 7. チェックリスト

導入前：

- [ ] 読み手と目的を 1 つに絞った
- [ ] 核心メッセージを 1 文で言える
- [ ] 選択基準は名前・URL の直接指定ではない
- [ ] タグ名と付与ルールをチームで合意した
- [ ] 上限（マップ 5〜7／最大 10、ツアー数ステップ）を決めた

導入後：

- [ ] IDE 検索でタグ付き要素の一覧が得られる
- [ ] ツアーがステップ順に生成され、各ステップからコードへ飛べる
- [ ] 抽出・公開がビルド／CI で自動化されている
- [ ] 手作業の一覧が残っていない
- [ ] 入口（README 等）からリンクされ、新メンバーのフィードバックを反映した
