    cargo-tracker UI 設計¶

    位置づけ¶

    本書は、フロントエンドアーキテクチャ の引継ぎ AF-02（画面ごとの遷移、レイアウト、文言、帳票）と、ドメインモデル の引継ぎ DM-02（画面ごとのコマンド・クエリ、開示範囲ごとの表示項目）に答える。2026-10-01 の 分析成果物レビュー を受けて、業務の順序（R-01）と利用者の業務上の穴（R-09〜R-16、R-27、R-28、R-30、R-33）を反映した。

    前提 出典 UI への影響
    画面はサーバーサイドレンダリングとハイパーメディアで提供する ADR-005 1 画面 = 1 URL。部分更新は一覧の絞り込み、状態の更新、確認の領域、session の警告に限る。session の警告はサーバーに部分を求めず、ブラウザの時計で開き、延長だけを fetch で送る（Bolt 32b。下の「部分更新を使う箇所」）。失効の時の入力の控えはブラウザのそのタブだけで扱う（Bolt 32f。ADR-005 の例外。下の「入力の控え（Bolt 32f）」）
    顧客向けと社内向けで URL の領域を分ける ADR-005 /customer/** と /staff/** で別のレイアウト・ナビゲーションにする
    業務の順序 要件定義 エンドツーエンド業務フロー 審査 → 見積りと経路方針の提示 → 荷主の回答 → 詳細経路設計 → 荷主の承認 → 本予約
    横断受入条件（BR-13、WCAG 2.2 AA） user_story.md 共通部品（エラー要約、確認の領域、状態バッジ、日時表示、通知領域、session の警告）で担保する。session の警告のうち、失効の前の警告と延長は Bolt 32b、再認証の後に開いていた画面（GET で開いた業務の画面）への復帰は Bolt 32e、送信していない入力の保持（入力の控え）と送信の後の失効は Bolt 32f で作る
    荷受人の開示範囲 BR-07 荷受人向けの画面は到着予定・現在状態・主要実績・最終更新時刻だけを表示する
    言語 US-10、US-19 荷受人向けの画面（C-11、C-12）と招待メールは日本語と英語。その他は日本語
    Bootstrap 5.3、htmx 2.0、Thymeleaf ADR-006 部品は Bootstrap を基に作り、色だけで状態を示す部品は使わない

    現場入力 UI（UI-06）は第 2 段階のため本書の対象外とする。

    システムメタファー¶

    輸送の情報を 旅程表 にたとえ、顧客 Web と社内業務 Web で同じ語彙を使う。

    旅程表のたとえ 画面の語 ドメインの概念
    時刻表 予定 確定した経路版の区間（当初の予定）
    通過記録 実績 採用した主要実績
    時刻表の改訂 最新の見込み 実績と採用値から見込む最新の到着時刻
    照合中の札 確認中 予定と実績の矛盾、順序の逆転、鮮度超過
    旅程表の版 経路版 経路の確定・再設計で増える版
    参照した時刻表の号（○月号） 参照した航海情報の版 参照情報版（R-INV-02。経路の判定のときに参照した航海の情報の版。データでは航海の採用情報版と呼ぶが、主要実績の「採用」とは別の語。値はそのまま示す。Bolt 29c）

    画面では「予定」と「実績」を常に並べて区別し、「確認中」のときは何が分かっていて何が分かっていないかを分けて示す（UI 設計の原則）。

    画面のオブジェクト¶

    ガイドのオブジェクト指向 UI に従い、利用者が操作する「モノ」をドメインモデルの集約から選ぶ。各オブジェクトに一覧（コレクションビュー）と詳細（シングルビュー）を持たせ、操作は詳細の画面に置く。

    オブジェクト 集約（ドメインモデル） 一覧 詳細 主なアクション 利用者
    見積依頼（輸送要求） 輸送要求 ○ ○ 下書き作成・更新、複製、提出、取下げ、審査確定、差戻し 荷主担当者、営業担当者
    見積り 見積り 輸送要求の詳細に含める ○ 算出、社内承認、提示、荷主の回答（詳細経路設計へ進む・辞退・相談）、荷主の承認 営業担当者、荷主担当者

    認証とアカウント¶

    A-02 の誤り・再利用（回復コードの誤り・使用済みを含む。Bolt 31c）では、password の要素を捨てて A-01 に戻し、「認証コードまたは回復コードが正しくないか、すでに使われています。もう一度ログインして、認証アプリに表示された新しいコードか、まだ使っていない回復コードを入れてください。」を示す。password を知った者が 1 つの session で TOTP を試し続けられないようにするため（ADR-011 の K-02）。password・TOTP・回復コードの誤りを合わせて数え、5 回続いたら 15 分ロックする（Bolt 32。ADR-011 の決定 9）。ロックは画面の遷移でなく内部の状態なので、遷移図には置かない（状態はドメインモデルのログインの失敗の状態遷移図）。ロック中は password の段も認証コードの段も誤りと同じ経路と文言にし、2 つの誤りの文言に一般の予告「続けて 5 回誤ると、15 分ログインできなくなります。」を足す（TOTP・回復コードの誤りも数えるので、予告を見ないままロックされないように）。ロックの有無と解ける時刻は示さない（AC2）。TOTP を登録していない利用者は、A-02 を経て A-07 に移り（Bolt 31b。Bolt 31 では登録の案内に送っていた）、登録して回復コードを保存した後、A-02 で TOTP を入れてログインを終える（ログイン → A-02 → 未登録なら A-07 → 回復コードの保存 → A-02 → ホーム）。登録は TOTP の要素を与えない（ADR-011 の決定 6）。認証アプリを使えない利用者は、A-02 の「認証アプリを使えない場合」を開いて回復コードを 1 つ入れ、ログインを終える（Bolt 31c。ADR-011 の決定 7）。回復コードで通ると A-08 に移る（Bolt 33b。ADR-011 の決定 10）。A-08 で認証アプリを登録し直すと新しい回復コード 10 個を受け取り、「続ける」で開いていた画面か役割のホームに着く。「後で登録する」を選ぶと同じ行き先に着き、印がある間（再登録の完了、ログアウト、session の失効まで）は業務の画面に知らせが出る。入口は回復コードでログインした印だけで、認証コードでログインした利用者は A-08 を開けない（機種を変えるときも回復コードでログインする。マニュアルの付録 B）。password の段だけの session は 5 分で失効し、A-03 に移す（A-02 を開いたまま放置した session を残さない）。A-07 を開いた session だけは、登録を始めてから 15 分を上限にする（認証アプリを入れて QR コードを読む時間を見込む。SEC-03）。

    ログインした画面（遷移図のホーム）では、失効の 5 分前に警告し、延長しても画面を移らない（Bolt 32b。共通部品の「session の警告（Bolt 32b）」）。警告のまま期限を過ぎると、画面を移らずに期限の到来の案内を出す。案内のリンクの行き先は、GET で開いた業務の画面ならサーバーが渡した戻り先（その画面）、ほかの画面（送信の後の画面など）なら A-03 にする（Bolt 32e）。Bolt 32f から、戻り先があればリンクの語を「画面を開き直す」にし、押すと入力を控えに写してから開く。戻り先がなければ「もう一度ログインする」のままにする。戻り先を開き直したときにサーバーの session が切れていれば、失効の扱いが要求を覚えて A-03 へ移し（A-03 の問い合わせ先の案内を通す）、ログインし直すとその画面に戻る。延長が失効で失敗した後は、失効の扱いがすでに新しい session を作っているので、開き直すと未認証の要求として A-01 へ直接移る（A-03 を通らない）が、要求は覚えるので、ログインの後はその画面に戻る。ブラウザの期限が早く来ていて session が生きていれば、その画面がそのまま開き、控えた入力を戻して知らせる（Bolt 32f）。

    送信（POST）の前にも入力を控えに写す（Bolt 32f）。サーバーの session が切れていた・CSRF のトークンが合わなかったなどで送信が拒まれた画面（A-03、CSRF の 403、413）で拒まれると、その画面が控えに「拒まれた」印を付ける（公開の画面でも、A-01 と認可の 403 は印を付けない。ログアウトでも送信の失敗でもないため）。ログインし直した後の画面（送信は覚えないので役割のホーム。Bolt 32e）の戻り先は控えと違うので、main の前に「送信できなかった入力があります。」と「入力していた画面を開く」「入力していた内容を消す」を出す。「入力していた画面を開く」で送信した画面を開くと入力が戻る。送信が届いた（送信の次にログインした画面が開いた）なら控えを捨てる。文言と捨てる時は共通部品の「入力の控え（Bolt 32f）」に置く。

    TOTP の端末を失い回復コードもない場合は、システム管理者が S-20 で事前に決めた別経路の本人確認をしたうえで登録を解除し、本人は次回のログインで A-07 から登録し直す（SEC-10）。

    password を忘れた利用者は、A-01 の「password を忘れた場合」から A-05 を開いて登録メールアドレスを送る（Bolt 33）。A-05 は公開の画面で、ナビゲーションの対象外にする（ログインした画面のナビにも出さない）。送った後は登録の有無にかかわらず A-01 に戻して同じ知らせを出し、メールは登録された有効な利用者にだけ届く。メールのリンクを開くと、トークンを確かめて session にトークンの ID だけを置き、トークンのない URL の A-06 へ移す（Bolt 33a）。使えないリンクは、理由によらず同じ無効なリンクの案内にする。A-06 は password の要素を与えず、設定したら A-01 に戻して新しい password と TOTP でログインし直す。その利用者のほかの端末の session は、次の操作で A-03 になる（ADR-011、ADR-017）。

    A-01 ログイン¶

    Bolt 14 の A-01 は、メールアドレス・password・「ログイン」と、ログインできない場合の問い合わせ先の案内だけにする。「password を忘れた場合」（A-05 へのリンク）は Bolt 33 で足す。ログインの誤り（role="alert"）と再設定の依頼の後に出す知らせ（role="status"）は、どちらも見出しの直下（欄の上）に示す。知らせの文言は A-05 の節に置く。Bolt 33a で、再設定の完了の知らせ（/login?reset-completed のときだけ。role="status"。印 reset-completed がなければ出さない。T-124）を同じ位置に足す。文言は A-06 の節に置く。password と認証コードの欄は貼り付けとパスワード管理ツールを妨げない。autocomplete="username"・"current-password"・"one-time-code" を付ける（WCAG 3.3.8）。

    開発環境（dev プロファイル）では、開発体験を優先し、A-01 のメールアドレスと password を既定の開発用の利用者で入力済みにする（2026-10-06 に human:kakimomokuri が決定）。入力済みにするのは dev プロファイルの設定があるときだけで、既定の設定（ステージング・本番を含む）では入力済みにしない。値は開発用の利用者の固定の値で、本物の秘密を使わない。既定の設定で入力済みにならないことをテストで守る。Bolt 14 では cargotracker.dev-login.accounts[n].role・email・password（application-dev.properties。開発用の荷主担当者 2 人と営業担当者 1 人。経路設計者は Bolt 17、追跡管理者（tracking-manager@dev.cargo-tracker.example）は Bolt 26 で足した）を入れ、最初の利用者で A-01 を入力済みにし、A-01 の下に「開発用の利用者でログイン（開発環境だけ）」として利用者ごとのボタン（例: 「営業担当者でログイン（sales@dev.cargo-tracker.example）」）を出して、選んでそのままログインできるようにする（2026-10-06 に human:kakimomokuri が決定）。dev の外または staging・prod と一緒にこの設定があれば起動を失敗させる（ADR-011 の決定 3、ADR-012）。A-02（認証コード）は、開発用の利用者に固定の TOTP の秘密を持たせ、dev プロファイルのときだけその時点のコードを入力済みにする。TOTP を飛ばさず、開発環境でも 2 段階のログインを通す（2026-10-06 に human:kakimomokuri が承認。Bolt 13 の確認ポイント 7）。Bolt 31 で、cargotracker.dev-login.accounts[n].totp-secret（Base32。利用者ごとに別）を足し、利用者ごとのボタンで password の段を通った後、A-02 をその時点のコードで入力済みにして出す（「確認」を押す 1 回が増える）。コードは設定の固定の秘密だけから作り、利用者の表の秘密は復号しない（ADR-011 の決定 3）。同じ利用者で 30 秒以内に入り直すと、同じコードの再利用として拒否され A-01 に戻る（本体の再利用の拒否は開発環境でも変えない）。デモでは、入り直す前に次の 30 秒の刻みを待つ。

    A-02 認証コードの入力¶

    Bolt 31 の A-02 は、6 桁の数字の欄と「確認」だけにする。欄には autocomplete="one-time-code"・inputmode="numeric" を付け、貼り付けとパスワード管理ツールを妨げない（WCAG 3.3.8）。誤り・再利用は A-01 に戻して上の文言を示す（拒否の種類は監査記録の理由 INVALID_TOTP・TOTP_REUSED にだけ残す）。Bolt 32 で、ロック中も誤りと同じく A-01 に戻して同じ文言を示すことにし、文言に一般の予告「続けて 5 回誤ると、15 分ログインできなくなります。」を足した。ロック中の案内と解ける時刻は示さない（AC2。監査記録の理由 LOCKED にだけ残す。ADR-011 の決定 9）。

    Bolt 31c で、回復コードの欄を足した（ADR-011 の決定 7）。

    • 「認証アプリを使えない場合」は <details> で、中に別のフォーム（name="recoveryCode"、autocomplete="off"、inputmode は付けない）と「回復コードで確認」を置き、同じ POST /login/totp に送る。欄の形で TOTP と取り違えない。JavaScript も CSP の変更も要らない
    • 回復コードは大文字・前後と中の空白・ハイフンなしの 8 文字・全角（IME で入れたまま）でも受け付ける（正規化。手で書き写したコードを打ち直させない）。形が合わなければ照合せずに拒む。欄の説明は「半角の数字と a〜f の英字で 8 文字。大文字、空白、ハイフンはあってもかまいません。」で、使い方の文とあわせて aria-describedby で読み上げる。spellcheck="false"（Bolt 31c の開発レビュー）
    • 誤り・使用済み・形の違い・両方の欄がある送信は、TOTP の誤りと同じく A-01 に戻して上の文言を示す（拒否の種類は監査記録の理由 INVALID_RECOVERY_CODE にだけ残す）
    • これまで A-02 にあった「認証アプリを使えない場合は…お問い合わせください」（SEC-10 の経路）は、<details> の中の回復コードの欄の下に「回復コードもない場合は…」として移す
    • 登録の直後の案内（「認証アプリを登録しました。…」）は、session に登録を始めた時刻があるときだけ示す。TOTP・回復コードが通ったら登録を始めた時刻を消すので、ログインを終えた後に A-02 を開き直しても出ない（Bolt 31b のレビュー 13）
    • Bolt 33b から、回復コードが通ったら A-08 へ移す（下の A-08 の節）。A-02 の文言は変えない（「使った回復コードは二度と使えません」は再登録の後も事実で、再登録で残りの回復コードも置き換わることは A-08 で示す）

    A-05 password の再設定の依頼¶

    Bolt 33 の A-05 は、メールアドレスの欄（autocomplete="email"。貼り付けとパスワード管理ツールを妨げない。WCAG 3.3.8）と「再設定のリンクを送る」と「ログインに戻る」（A-01 へのリンク）だけにする。欄の誤りは欄の下に示し、aria-describedby で結ぶ（A-07 のコードの誤りと同じ形）。誤りのときは title に「エラー: 」を付け（「エラー: password の再設定の依頼 - cargo-tracker」）、欄に autofocus を付ける（読み上げはラベル・無効・説明の順）。

    入力 A-05 の文言
    空（前後の空白だけを含む） 「メールアドレスを入力してください。」
    形式の誤り（EmailAddress が受け付けない値） 「メールアドレスの形式が正しくありません。例: user@example.com」

    形の誤りでは入れた値を残す。形が正しければ、登録の有無にかかわらず /login?reset-requested に移し、A-01 に次の知らせを出す（role="status"。ログインの誤りの文言とは別の位置）。

    password の再設定の依頼を受け付けました。

    入力したメールアドレスが登録されていて、ご利用いただける状態であれば、再設定のリンクをそのアドレスへ送ります。

    • リンクの有効期限は 30 分で、1 回だけ使えます。
    • 数分たっても届かない場合は、迷惑メールのフォルダを確かめてから、もう一度依頼してください（前にリンクを送ってから 1 分以内の依頼では送りません。新しいリンクを送ると、前のリンクは使えなくなります）。
    • それでも届かない場合は、荷主の方は担当営業に、社内の方はシステム管理者にお問い合わせください。

    知らせが出る場面と、事実と合うか（Bolt 32f の Try T-123）:

    場面 実際に起きること 知らせの各文が事実と合うか
    登録された有効な利用者 依頼のコミットの後にトークンを発行し、リンクを送る（応答は送信を待たない） 合う。送るのは応答の後なので「送ります」とし、「送りました」と断定しない
    登録のないメールアドレス 監査（UNKNOWN_USER）だけで、送らない 合う（「登録されていて…であれば」の条件に当たらない）。届かないので、最後の問い合わせ先の文で次の行動を示す
    止められた利用者 監査（SUSPENDED）だけで、送らない 合う（「ご利用いただける状態であれば」の条件に当たらない）。止めたことは示さない（IA-INV-09）
    所属企業の無効 監査（COMPANY_INACTIVE）だけで、送らない 合う（同上）
    前にリンクを送ってから 1 分以内の繰り返し 依頼の監査は残るが、ハンドラーが発行も送信もしない（1 分の起点は前の発行）。前のリンクは使えるまま 合う（括弧の「前にリンクを送ってから 1 分以内の依頼では送りません」）。1 分を過ぎてから依頼し直すと新しいリンクを送り、前のリンクは使えなくなる（括弧の「新しいリンクを送ると、前のリンクは使えなくなります」）
    送信の失敗（SMTP の誤り） 通知は FAILED になり、届かない 合う（「届かない場合は…もう一度依頼」で回復できる。送れなかった依頼は利用者が依頼し直す）
    ログイン済み・password の段の session で A-05 を開いた 同じ A-05 を出し、入力したアドレスで扱う。session の利用者は変えない。戻った A-01 は、ログイン中も知らせとログインの欄を出す 合う（知らせは入力したアドレスについて述べ、session の利用者に触れない）
    印のない /login 依頼していない 知らせを出さない（T-124）

    依頼の後に A-01 で知らせを読んだ利用者がそのままログインできるよう、A-01 のほかの部分（欄・ログインの誤りの文言・問い合わせ先の案内）は変えない。

    A-06 password の再設定¶

    Bolt 33a の A-06 は、見出し「password の再設定」、説明（上の 3 つの条件）、「新しい password」と「新しい password（確認）」の 2 つの欄、「password を設定する」、「ログインに戻る」（A-01 へのリンク）だけにする。2 つの欄には autocomplete="new-password" を付け、貼り付けとパスワード管理ツールを妨げない（WCAG 3.3.8）。条件の数値（12・64・72）は password の方針の定数から描き、文言に数字を書き写さない。欄の誤りは A-05 と同じ形にする（欄の下に示して aria-describedby で結ぶ。誤りのときは title に「エラー: 」を付け（「エラー: password の再設定 - cargo-tracker」）、誤りの欄に autofocus を付ける）。誤りを示すときは、2 つの欄に入れた値を応答に書き戻さない（空で示す。A-01 が password を残さないのと同じ）。

    A-07 認証アプリの登録¶

    A-07 は、登録の画面と、登録を保存した応答で示す回復コードの保存の画面の 2 つからなる（Bolt 31b）。初めの設計は回復コードを登録の前の同じ画面に示していたが、それだと平文の回復コードを登録の途中の session（Spring Session JDBC の表）に置くことになるため、登録の後の 2 つ目の画面に分けた（Bolt 31b 計画の確認ポイント 4）。

    登録の画面:

    • QR コードはサーバーが作るインラインの SVG で、role="img" と代わりの文「認証アプリで読み取る QR コード」を付ける。色は fill の属性で付け、style は使わない（CSP）
    • キーは Base32 を 4 文字ずつ区切って示す。QR コードと同じく秘密と同じ重さの値なので、応答は Cache-Control: no-store にし、session・記録には置かない。再読み込みやタブを 2 つ開いても、登録の途中は同じキーを示す
    • コードの欄は autocomplete="one-time-code"・inputmode="numeric"（A-02 と同じ）
    • コードの誤りは同じ画面にエラー要約で示し、同じキーで示し直す（認証アプリに登録済みのキーを使い続けられる）。password の要素は捨てない。誤りは失敗の回数に数えない（Bolt 32 で決めた。登録は認証のイベントを経ず、登録の誤りは自分の秘密の確かめで、他人の要素の推測にならない。ADR-011 の決定 9）
    • 「ログインの画面に戻る」はログアウトの POST（A-02 と同じ）

    回復コードの保存の画面（登録の POST の応答）:

    • 回復コードは 10 個で、形は 1a2b-3c4d（8 文字の 16 進を 4 文字ずつハイフンで区切る）。一度だけ示し、どこにも保存しない（ハッシュだけを保存する。SEC-09）。応答は Cache-Control: no-store
    • 「回復コードを安全な場所に保存した」は画面の必須のチェック（required）。サーバーは確かめない（回復コードは登録の時点で保存済みなので、確認は利用者への促し）
    • 「ログインを続ける」は A-02 への GET のフォーム。A-02 で、登録に使ったコードか次のコードを入れてログインを終える
    • 登録の画面と同じ期限の時刻（「… までに、続けてログインを終えてください」）を示す。登録を始めた時刻は A-02 で TOTP または回復コードが通るまで残る（通ったら消す。Bolt 31c）
    • 再読み込み（登録の POST の再送）は、登録済みとして A-02 へ移す（回復コードはもう示さない）
    • 回復コードは A-02 の「認証アプリを使えない場合」で使う（Bolt 31c。上の A-02 の節）

    A-08 認証アプリの再登録¶

    A-08 は、回復コードでログインした利用者が認証アプリを登録し直す画面と、完了の POST の応答で示す新しい回復コードの保存の画面の 2 つからなる（Bolt 33b。US-18 AC9、SEC-10、ADR-011 の決定 10）。A-07 と同じ形にし、秘密の発行のポート（TotpSecretIssuer）と QR コードを A-07 と共用する（A-08 は A-07 のサービス TotpEnrollmentService を呼ばない。途中の暗号文の扱いは部品 TotpProvisioningStarter に、回復コードの発行は RecoveryCode.issueSet に寄せ、2 つのサービスが使う。Bolt 33d）。A-02・A-07・A-08 のコードの欄の pattern（[0-9]{6}）と maxlength（6）は、画面がモデル codeDigits で渡す TOTP の桁数（TotpCredential.DIGITS）から描く（Bolt 33d。見出し・前文・説明の「6 桁」の文言はテンプレートに残す。表示は変えない）。A-08 の URL は、共通のレイアウトの知らせのリンクと A-08 の画面のフォームの送信先ともに、application 層の SessionPaths の URL を使う（Bolt 33c で SessionKeys に置き、Bolt 33f で分けた）（画面の層の SessionUrlsAdvice がモデルの sessionUrls.reEnroll として渡し、テンプレートは @{${sessionUrls.reEnroll}} で参照する。Bolt 33c。表示と振る舞いは変えない）。A-07 との違いは、2 つの要素がそろった session のログインした画面のレイアウト（layout/customer・layout/staff）に置くこと、「後で登録する」があること、ログインの手続きでなく登録し直しなので「ログインの画面に戻る」がないこと（期限の文言はある）、の 3 つである。ログインした画面なので session の警告（共通部品）は出る。印の知らせ（共通部品）は A-08 には出さない（同じことを画面の本文が言う）。Bolt 33f から、A-07 の「始めてから 15 分」・A-08 の「開いてから 15 分」・A-03 の「ログインから 8 時間」・回復コードでログインした印の知らせの「15 分」・session の警告の「ログインから 8 時間」も、画面の層がドメインルール SessionPolicy の期間を書いてモデルで渡し、テンプレートに数値を書かない（文の途中はインライン式（[[...]]）で描き、警告は属性 data-lifetime-message の値を th:data-lifetime-message で描く。表示は変えない）。

    • 見出しと title は「認証アプリの再登録」（title は「認証アプリの再登録 - cargo-tracker」）
    • QR コード・キー・コードの欄は A-07 と同じ（インラインの SVG に role="img" と代わりの文、キーは 4 文字ずつ、欄は autocomplete="one-time-code"・inputmode="numeric"）。応答は Cache-Control: no-store。再読み込みやタブを 2 つ開いても、途中は同じキーを示す（途中の暗号文と開いた時刻を session に置く。平文の秘密は置かない）
    • 期限の時刻は開いた時刻から 15 分で、日時表示の共通部品で示す（再読み込みでは延ばさない）。期限を過ぎてから送った場合は下の文言で示し直す。画面は自動では変わらない。期限を過ぎた途中の値（暗号文・開いた時刻）は、GET で始め直すときに捨てて新しいキーと期限にする

    • 「後で登録する」は別のフォームの POST（/account/authenticator/later。CSRF のトークン付き）で、印を確かめてから（印がない・期限を過ぎていれば役割のホーム）、印を残して覚えた要求の画面か役割のホームへ PRG で移す。リンクにしない（GET は状態を変えない）
    • 「登録し直すと、前の認証アプリのコードと、残っている回復コードは使えなくなります。」は、完了するまで前のものが使えることも含めて事実と合う（置き換えるのは新しいコードを確かめた時点。ADR-011 の決定 10）

    新しい回復コードの保存の画面（完了の POST の応答）:

    • A-07 の回復コードの保存の画面と同じ形（見出し「回復コードの保存」、10 個、形 1a2b-3c4d、説明の文、Cache-Control: no-store、「回復コードを安全な場所に保存した」は画面の必須のチェック）。違いは、1 文目を「認証アプリを登録し直しました。前の回復コードは使えなくなりました。」にすること、期限の時刻がないこと、ボタンを「続ける」にすること

    入力の控え（Bolt 32f）¶

    失効の時に送信していない入力を失わないための部品である（US の横断受入条件の「未保存の入力は失われず再認証後に再開できる」、ACC-06）。仕組み（置き場所、キー、スクリプトの順序）は フロントエンドのアーキテクチャ の「入力の控え（Bolt 32f）」、捨てる時と利用者の確かめの理由は ADR-012 に置く。

    用語: 「入力の控え」は、送信していない入力をブラウザのそのタブに写したものである。業務の「下書き」（輸送要求の版の状態、C-03 の下書き保存、追跡の下書き実績）とは別のもので、サーバーには保存せず、業務状態の正でもない。画面・マニュアル・設計文書では「控え」「控える」と言い、「下書き」と言わない。「控える」はシステムが写すことにだけ使い、利用者が自分で入力を写し取ることは「書き写す」「メモする」と言う（Bolt 32f の開発レビュー。同じ画面で 2 つの意味にしない）。

    場面 振る舞い
    写す時 警告の期限の到来の案内を出したとき、「画面を開き直す」を押したとき、業務の画面の POST のフォームを送信する前。戻り先（data-return-path）のある画面でだけ写す
    写す欄 main の中の POST のフォーム（method の属性で見分ける）の、テキスト・数・日付・選択・ラジオ・チェックの欄と textarea のうち、初期の値から変えた欄だけ。password・hidden（CSRF のトークンを含む）・ファイル・ボタンは写さない。GET のフォーム（照会）は写さない。変えた欄がなければ写さず、前の控えを残す。控えは 1 つのタブに 1 つで、新しく写したら置き換える。ただし、拒まれた送信の控えは、ほかの画面の送信では置き換えない（案内から開くか消すまで残す）
    戻す 同じ利用者が、控えと同じ戻り先の画面を開いたら、自動で欄に値を入れ（HTML として解釈しない）、知らせを出し、控えを捨てる。C-03 は段階 1 から開く（「段階入力」の表）
    送信が拒まれた場合 送信が拒まれた画面（A-03、CSRF の 403、413。main の data-session-input="rejected"）が控えに「拒まれた」印を付ける。A-01 と認可の 403 は印を付けない（画面ごとに明示する。公開のレイアウトを使うだけでは付けない）。ログインし直した後の画面（役割のホームなど）の戻り先が控えと違えば、案内「送信できなかった入力があります。」を出す。「入力していた画面を開く」で控えの戻り先を開くと入力が戻る。期限の到来・「画面を開き直す」で写した控えも、A-03 を経ていれば同じ案内を出す
    捨てる時 戻したとき、送信が届いたとき（送信の控えで、拒まれた印がないままログインした画面が開いた）、「戻した入力を消す」・「入力していた内容を消す」、利用者が違うとき、写してから 8 時間を過ぎたとき（ログインした画面か公開の画面を開いたときに確かめる）、ログアウト（ヘッダーの「ログアウト」の送信、ログアウトの後のログインの画面 /login?logout）、期限の到来が取り消されたとき（期限の到来で写した控え）、拒まれた印がないまま戻り先と違うログインした画面を開いたとき（ログアウトしていない）、形の合わない控え。タブを閉じれば消える
    保持しないもの 送信の後に入力の誤りで描き直した画面（戻り先がない。この画面のまま期限が来た入力は控えない。期限の到来の案内は「もう一度ログインする」のまま、本文で控えるよう促す）、ほかのタブ・ほかのブラウザでの戻し、ファイル（選び直す）。sessionStorage や JavaScript を使えないときは何もしない
    知らせ・案内 文言 ボタン・リンク

    • フォーカス: 知らせ・案内を出してもフォーカスは移さない（読み込んだ画面の最初の位置のまま）。「戻した入力を消す」・「入力していた内容を消す」を押すとボタンは無くなるので、フォーカスは領域（tabindex="-1"）に移し、消した後の文言を読ませる。中身の更新とフォーカスで 2 回読まれないよう、差し替える間だけ aria-live を止める

    • 「入力していた画面を開く」の行き先: 控えの戻り先を、同じ origin の path と query に限って使う（sameOriginPath。//・/\ で始まる path はほかの origin を指すので拒む）。ブラウザで path の前方一致の判定はしない
    • 「まだ送信していません」: 送信が届いたかは、送信の次に開いた画面がログインした画面か公開の画面かで見分ける。8 時間のぎわで、送信が届いた直後の移動（PRG の GET）が A-03 になると、届いた送信の入力が戻りうる（まれ）。文言は断定のままにし、既知の課題として ADR-012 に書き、マニュアルで一覧を確かめるよう補う。版（hidden）は写さないので、控えてから戻すまでにほかの人が同じものを更新していると、戻した入力をそのまま送ると更新を上書きしうる。「内容を確かめてから送信してください」で補い、既知の課題として ADR-012 に書く

    回復コードでログインした印の知らせ（Bolt 33b）¶

    回復コードでログインし、A-08 で「後で登録する」を選んだ利用者に、認証アプリを登録し直すよう促す部品である（US-18 AC9、SEC-10、ADR-011 の決定 10）。残りの回復コードが少ないときの案内は作らず、この知らせで再登録を促す（残りの数の案内は #47）。

    文言は印の状態で 2 つに分ける（画面の層の RecoveryLogin.stateOf が NONE・ACTIVE・EXPIRED を返す。NONE では出さない。15 分はドメインルール SessionPolicy の印の期間で、属性の名前は SessionKeys にある。Bolt 33c で寄せた。文言は変えない）:

    印の状態 出す条件 文言
    ACTIVE 印の利用者が今の主体で、回復コードでログインしてから 15 分未満 「回復コードでログインしました。認証アプリを登録し直してください。」とリンク「認証アプリを登録し直す」（A-08）
    EXPIRED 印の利用者が今の主体で、回復コードでログインしてから 15 分を過ぎた 「回復コードでログインしてから 15 分を過ぎたため、この画面からは認証アプリを登録し直せません。登録し直すには、いったんログアウトして、回復コードでログインし直してください。」（リンクなし。A-08 を開いても役割のホームへ移るので、リンクを置かない）
    • 出す画面: ログインした画面のレイアウト（layout/customer・layout/staff）のすべての画面。A-08 には出さない（画面の本文が同じことを言う）。公開の画面（layout/public）には出さない
    • 出す条件: session に回復コードでログインした印（利用者の ID とログインした時刻）があり、印の利用者の ID が今の主体と同じとき。15 分を過ぎたかで上の 2 つの文言を選ぶ。印は A-08 の完了・ログアウト（session と一緒に消える）・password の段の成功（同じ session での利用者の切り替え。認証の入口が 2 つの属性をどちらも消す）で消えるので、そのときから出ない。15 分を過ぎても印は消さない（EXPIRED の案内を出すため）
    • 印の期限の理由: 「後で登録する」の後も印が session の最大 8 時間残ると、session を盗んだ者や離席中の端末に触れた者が、password なしで認証アプリを登録し直せる（一時的な乗っ取りが、続く乗っ取りになる）。印はログインの直後だけ有効という受け入れの前提を守る（2026-10-15 の開発レビューで human:kakimomokuri が決定。ADR-011 の決定 10）
    • 位置と読み上げ: ヘッダーの後、main の前（入力の控えの知らせの領域の前）に、alert alert-warning の見た目の静的な案内として置く。live region にも role="alert" にもしない（画面を開くたびに読み上げさせない。急ぎの知らせでない）。フォーカスは移さない。リンクの名前「認証アプリを登録し直す」は文脈なしで行き先が分かる（WCAG 2.4.4）
    • 閉じる操作: 置かない（印がある間は毎回出す。消すには登録し直すかログアウトする）
    • 文言の場面: 上の A-08 の節の場面の表の「後で登録する」「回復コードでログインしてから 15 分を過ぎた」「後で登録してログアウトした・session が失効した」「同じ session で別の利用者に切り替えた後」の行。印のない利用者（認証コードでログインした）には出ない

    隠し項目（commandId）の欠け・形の誤り 400（利用者が入れる値ではないため、項目のエラーにしない。Bolt 24） 開き直して再操作
    業務規則による拒否（失効、古い版、集荷後の変更など） 拒否の理由と、代わりにできること（再見積り、新しい版、有人案件） 案内に従う
    権限なし・他社のデータ A-04。対象の存在の有無を推測できる情報を出さない。存在しない番号と同じ応答にする。試行は監査記録に残る 戻る
    session の失効が近い 無操作の失効の 5 分前の警告と延長の操作。8 時間の上限の 5 分前は、延長できないことと送信を促す警告（Bolt 32b。共通部品「session の警告」） 延長（8 時間の警告では送信してから再ログイン）
    session の延長の失敗（403・500・通信の失敗） 警告の中に「延長できませんでした。もう一度お試しください。ログアウトしても、入力中の内容はこのタブでログインし直すと戻ります。」（Bolt 32f。入力を控えられない画面では「…続けて失敗する場合は、入力中の内容を書き写してから画面を開き直してください。」）。失効とは分ける（Bolt 32b） もう一度延長
    警告の期限の到来 モーダルでない案内（role="alert"）。画面を移らず、入力を画面に残す（Bolt 32b）。GET で開いた業務の画面ではリンク「画面を開き直す」で、入力を控えに写してからその画面を開き直す（Bolt 32e・32f）。戻り先がなければ「もう一度ログインする」（A-03 へ） 「画面を開き直す」。ログインし直すと入力が戻る（戻り先がなければ、入力を自分で控えてから A-03 へ）
    再設定のリンクが使えない（期限切れ・使用済み・新しいリンクを送った後・存在しない。A-06 の送信での利用停止・所属企業の無効を含む） A-06 の無効なリンクの案内。どの理由かを示さない（Bolt 33a） 「password の再設定を依頼し直す」（A-05）
    session の失効・利用停止・所属企業の無効化・ほかの端末での password の再設定（Bolt 33a） A-03 の再認証の案内。業務データを表示しない。無操作・8 時間の失効では、ログインし直すと GET で開いていた業務の画面に戻る（Bolt 32e）。送信の後・利用停止・所属企業の無効化の後は役割のホームに着く。そのタブに入力の控えがあれば、同じ利用者がログインし直すと戻る（Bolt 32f） 再ログイン
    送信が拒まれた（session の失効、CSRF のトークンの不一致の 403、413） A-03・403・413。送信の前に写した入力の控えに拒まれた印を付ける（認可の 403 は付けない）。ログインし直した後の画面に「送信できなかった入力があります。」と「入力していた画面を開く」「入力していた内容を消す」（Bolt 32f） 「入力していた画面を開く」で入力を戻し、確かめてから送信し直す
    役割の取消し 取り消した役割の URL は A-04（Bolt 32c。次の request から）。残した役割の画面は使える 戻る、問い合わせ
    非同期処理の遅れ・失敗 「処理中」のまま表示し、有人確認要になったら受付番号を示す 有人案件で対応
    外部情報の停止・鮮度超過 最終採用値・取得時刻・最新性を保証しない旨・次回更新・担当窓口 有人窓口
    メールの送信失敗 画面の通知一覧（C-16）に同じ内容を表示する 画面で確認
    予期しないエラー 何が完了していて何が未完了かを示し、要求 ID を表示する 再操作または問い合わせ（要求 ID を伝える）

    部分更新を使う箇所¶

    ADR-005 のとおり、画面全体の遷移を基本とし、部分更新は次に限る。

    箇所 使い方 アクセシビリティ
    一覧の絞り込み 絞り込み条件の変更で一覧の表だけを更新する 件数の変化を通知領域で知らせる
    経路候補の再算出 候補の表だけを更新する 更新が終わったときに 1 回通知する
    非同期処理の状態 「処理中」の間だけ状態の部分を問い合わせ（非機能要件の間隔）、完了・有人確認要で止める 状態が変わったときだけ通知する
    確認の領域 詳細画面の中に確認の領域を開く フォーカスを確認の領域へ移し、戻るで元のボタンへ戻す
    session の警告 失効の 5 分前に警告を開く。サーバーに部分を求めず、ブラウザの時計で開き、延長だけを fetch で送る（htmx でない。htmx は 302 を黙って追い、失効を見分けられない。Bolt 32b。フロントエンドのアーキテクチャ） 警告を支援技術に通知し、延長のボタンへフォーカスを移す（8 時間の警告は「閉じる」）。閉じたら開く前のフォーカスに戻す

    AI の仮定と要確認¶

    • 本予約を確定する人: US-04 の受入条件に従い、本予約の確定は営業担当者が社内業務 Web（S-09）で行う。荷主は見積りへの回答（C-05）と、見積りと経路の承認（C-17）を行う。
    • 本予約と船腹の確保: 確認書（C-13）と予約の詳細（C-07）に「本予約は A 社との輸送条件の確定であり、船腹の確保は運送会社の確認後に表示する」と示す。船腹の確保を画面で扱うかは業務責任者に確認する（R-28）。
    • KPI の照会者: S-22 は監査担当者の画面とした。プロダクト責任者が使う場合の役割は OQ-07 の残項目で扱う。
    • 荷主・社内の画面の言語: 英語は荷受人向けの画面と招待メールだけとした。荷主の担当者が欧州にいる場合の英語対応は、パイロット顧客（OQ-01）が決まった後に判断する。
    • 画面イメージの値: 画面イメージの企業名・番号・金額・時刻は説明用の架空の値である。
