    ADR-012: 認証の主体は共有カーネルの型にし、password の段を Spring Security の form login と Spring Session JDBC で作る¶

    US-18 の password によるログインと session を、Spring Security 7 の form login と Spring Session JDBC で作る。ほかのコンテキストは、共有カーネルに置く認証の主体の型だけを受け取り、Spring Security の型にも identity にも依存しない。

    日付: 2026-10-06

    ステータス¶

    承認（2026-10-06、human:kakimomokuri が Bolt 14 の終了報告の承認で採用した。Bolt 14 の確認ポイント 2・3 の方針）

    コンテキスト¶

    • US-18 の password の段（AC1 の password と session、AC2、AC4、AC5）を Bolt 14 で作る。TOTP・ロック・再設定・権限の取消し（AC6）は W5（Bolt 14 計画）。
    • これまで、提出者・回答者・審査者・承認者は、設定の仮の主体（ProvisionalActorProperties）で決めていた。quotation の 4 つの controller が使う。
    • identity は quotation :: events に依存する（KPI 計測記録が DE-01・DE-03 を購読する）。quotation が identity に依存すると循環する（Bolt 13 レビュー D-48）。
    • アクセス・監査は単純なモデルで、認証の仕組みは実績のある部品に任せる。認証の成功・失敗は、同じ request の中で同期に監査記録に書く（IA-INV-08）。
    • TOTP の方式は ADR-011（提案）で、W5 で採否を決める。password の段は、TOTP の採否と独立に決まる。
    • 開発環境では A-01 を入力済みにする（2026-10-06 の人の決定）。

    決定（案）¶

    1. 認証の主体の型¶

    • 共有カーネル（shared）に、認証された利用者 AuthenticatedActor（利用者 ID・企業 ID・役割（1 つ以上）・表示名・企業名）と役割 Role（BR-15 の 8 役割）を置く。
    • quotation の controller は、引数に AuthenticatedActor を書くだけでこの型を受け取る。identity の引数の解決（AuthenticatedActorArgumentResolver）が Spring Security の主体から作って渡すため、@AuthenticationPrincipal も使わない。Spring Security の型（UserDetails、Authentication）と identity には依存しない（ArchUnit で確かめる。Bolt 14 の実装で、注釈も Spring Security の型であるため引数の解決にした）。
    • Spring Security の主体は identity の型（CargoUserDetails。UserDetails を実装する）で、session（Spring Session JDBC）に直列化できる値だけを持ち、actor() で AuthenticatedActor を作る。
    • 置き換えの順は ADR-011 の決定 4 に従う（型を足す → 認証を入れる → controller を 1 つずつ置き換える → ProvisionalActorProperties を消す）。

    2. 認証の構成¶

    • SecurityFilterChain は identity.infrastructure.config に置く。/customer/** は SHIPPER、/staff/** は SALES の役割を求める。静的な資源と /login・/session-expired・/password-reset（A-05。password の再設定の依頼。Bolt 33）と /password-reset/*（再設定のリンクを開く /password-reset/{トークン} と A-06 の /password-reset/new。Bolt 33a。33a までは準備中の仮の画面。ADR-017 の決定 6）は認証なしで開ける。Bolt 33a で公開の URL を /password-reset/* と確定した。/password-reset/new も 1 段で含まれ、new はトークン（43 文字の URL 安全な Base64）と重ならないので、/password-reset/** は採らない（要らない深い path まで公開しない。/password-reset/x/y が公開でないことを統合テストで確かめる）。判定は認可と同じ PathPatternRequestMatcher のままにする。公開の URL（PUBLIC_PATHS）は SessionRevalidationFilter の確かめと失効の時に要求を覚える動きの対象外になる。
    • form login（GET・POST /login）と DaoAuthenticationProvider を使う。利用者の読み出し（UserDetailsService）は identity に置き、利用停止の利用者と無効な企業の利用者を、理由付きで認証の失敗にする（IA-INV-09）。画面の文言はすべて同じにする（SEC-11）。
    • password は DelegatingPasswordEncoder の既定（bcrypt、{bcrypt} の接頭辞。SEC-07）。
    • session の固定化を防ぐため、ログインで session ID を付け替える（Spring Security の既定の ChangeSessionIdAuthenticationStrategy）。CSRF は同期トークン（既定）。
    • 認可は request ごとの今の役割で判定する（Bolt 32c で改めた。Bolt 14 から 32 まではログインの時点の役割）。認証済みの request ごとに利用者・役割・企業を DB から読み、主体を作り直して差し替える（SEC-12・IA-INV-04・AC6。下の「W5 で見直すこと」の 3）。取り消した役割の URL は A-04（権限なし）になる。
    • 応答のヘッダーは X-Frame-Options: DENY、X-Content-Type-Options: nosniff、CSP default-src 'self'。Cookie は HttpOnly・SameSite=Lax、dev の外で Secure。

    3. session¶

    • Spring Session JDBC で、platform スキーマの spring_session・spring_session_attributes に置く（DDL はベンダーごと）。
    • 無操作 30 分は session の期限（MAX_INACTIVE_INTERVAL）で判定する。期限は spring.session.timeout で決める（server.servlet.session.timeout は Spring Session に効かないことを、既定と違う値のテストで確かめた）。
    • 発行から 8 時間の上限は、ログインのときに session の属性（固定の名前）に置いた認証時刻と、アプリケーションの Clock で比べるフィルターで判定する。Bolt 31 から、8 時間の起点（AUTHENTICATED_AT）はその session で初めて TOTP が通った時刻にし、password の段だけの session は password を確かめた時刻（PASSWORD_VERIFIED_AT）から 5 分で失効させる（ADR-011 の決定 2）。フィルターは要素の数で上限を選ぶ。このフィルターは認証の処理より前に置く（Bolt 13 の Try T-40）。認証済みなのに認証時刻がない session も失効させる（fail-closed。ログインの時刻を置かない認証の経路を足しても上限が外れない）。
    • 役割とホームの対応はルートのコントローラーの 1 か所に置き、ログインの後もルートを通す。画面のまだない役割は A-04 にする。

    • 印はログインから 15 分だけ有効にする（2026-10-15 の Bolt 33b の開発レビューで human:kakimomokuri が決定）。印が session の最大 8 時間残ると、session を盗んだ者や離席中の端末に触れた者が、password なしで認証アプリを登録し直せるため。画面の層（RecoveryLogin.stateOf）は NONE・ACTIVE・EXPIRED の 3 つに分け、15 分を過ぎた EXPIRED では A-08 を開かせず（役割のホームへ）、業務の画面にリンクのない案内を出す。15 分を過ぎても印は消さない（案内を出すため）。
    • 同じ session での利用者の切り替え（T-102）: 回復コードでログインした後にログアウトせずに別の利用者の password を通すと、password の段の成功（LoginSuccessHandler）が印の 2 つの属性をどちらも消す（登録の途中の属性を消すのと同じ場所）。画面の層も、印の利用者の ID が今の主体と同じときだけ印として扱う（二重に守る）。印は再登録の完了でも消え、ログアウトと失効では session と一緒に消える。
    • 属性の名前は、Bolt 33b では認証の入口（identity.infrastructure.security の定数のクラス。Bolt 33c で名前と期間を SessionKeys・SessionPolicy に移して消した）と画面の層（RecoveryLogin）に同じ値の定数を置き、一致をテストで守っていた（画面の層は infrastructure に依存できない。前例は登録の途中の暗号文）。Bolt 33c で、ほかの 4 組と A-08 の URL（6 組目）とまとめて SessionKeys に、15 分の期間を SessionPolicy に寄せた（下の項目）。
    • Bolt 33c から、session の属性の名前と期間の置き場所を次の 2 つにする（2026-10-15、Bolt 33c の開始準備の決定 1・2 と決定 2 の (5) で human:kakimomokuri が決定）。振る舞いは変えない。
    • 名前（SessionKeys）と URL（Bolt 33f から SessionPaths）: application 層の SessionKeys（identity.application.internal.session）。層をまたいで共有する session の属性の名前 6 つ（ログインの時刻、password を確かめた時刻、登録を始めた時刻、登録の途中の秘密、回復コードでログインした印の利用者と時刻）、request の属性の名前 2 つ（8 時間の残り、戻り先）、A-08 の URL、A-03 の URL（/session-expired）を置く。ふるまいは持たない。値は Bolt 33b までの文字列を変えない（動いている session の属性が読めなくならない。値を固定するテスト SessionKeysTest で守り、2 つの定数の一致を守るテストは要らなくなるので消す）。画面だけが使う名前（A-08 の途中の 2 つ）は画面の層に残し、テストの URL の写しは仕様として文字列のまま残す。パッケージは開発ガイドライン第 3 章の置き場所にないので、人の決定として書く。認証の入口からの参照は決定 6 の例外に足す。Bolt 33f から、URL 2 つは同じパッケージの定数だけのクラス SessionPaths に分け、SessionKeys は名前だけを持つ（2026-10-16、Bolt 33f の開始準備の決定 1）。URL（遷移先）の関心を application 層に置く理由: 認証の入口（infrastructure。移す先）・合成ルート（公開する URL とメールに書く URL）と画面の層（リンク・フォームの送信先・受ける URL）が同じ値を参照し、内側の層から画面の層への依存を作らないため。static final String の定数はコンパイル時に参照先に埋め込まれるので、層の規則（ArchUnit）には定数の参照が見えない。規則で守れないことを承知の上で、意図した依存の向きを設計の約束として保つ。合成ルートが画面の層の PasswordResetController.URL を参照していた前例（Bolt 33）も、同じ向きにそろえて SessionPaths に寄せた。名前と URL はクラスで分けたので、関心はクラスで見分けられる（Bolt 33c の議題 4 (b) への答え。Bolt 33f の開始準備の決定 7 と開発レビューの決定。human:kakimomokuri が決定）。
    • 期間: ドメインルール SessionPolicy（identity.domain.model.rules。LockPolicy と並べる）。2 つの要素がそろった session の 8 時間、password の段の 5 分、登録の途中の 15 分、回復コードでログインした印の 15 分、再登録の 15 分を Duration の定数で持つ。Bolt 33c では期間だけを持ち、期限の判定は今の置き場所のままにした。Bolt 33e から、期限の判定 isExpired（ちょうどの時刻は期限切れ。時計を持たない純粋な関数）も持ち、判定していた 4 か所が使う（2026-10-16、Bolt 33e の開始準備の決定 2 で human:kakimomokuri が決定）。Bolt 33f から、期限の時刻 deadline も持ち、画面に示す期間の文言もこの期間から描く。
    • 採らなかった案: 名前と URL もドメインに置く（session と request の属性の名前は HTTP の関心で、業務の知識ではない）、画面の層に置いて入口から参照する（interfaces はどの層からも参照されない規則に例外が要る）、2 つの定数とテストのまま残す（同じ値を 6 組持ち、組が増えるたびにテストを足す）。

    4. 監査¶

    • ログインの成功・失敗・ログアウトを、Spring Security のイベントの listener から、同じ request の中で identity.audit_record（追記だけ）に書く。失敗の理由（BAD_CREDENTIALS・UNKNOWN_USER・SUSPENDED・COMPANY_INACTIVE）は記録にだけ残す。
    • 存在しないメールアドレスでの失敗は、操作者を空にして記録し、メールアドレスは残さない。
    • Bolt 33 から、password の再設定の依頼（A-05）を PASSWORD_RESET_REQUESTED で記録する。書くのは依頼のアプリケーションサービス PasswordResetRequestService で、依頼と同じトランザクションで書く（IA-INV-08）。有効な利用者は SUCCESS（理由なし）、止められた利用者は FAILURE・SUSPENDED、所属企業の無効は FAILURE・COMPANY_INACTIVE、登録のないアドレスは FAILURE・UNKNOWN_USER（操作者を空にし、アドレスを残さない）。理由は AuthenticationRejection の値を使う。繰り返し（1 分以内）で送らなかったことは記録しない。監査と送信の記録は結ばない（AUD-02 の対象の列は使う Bolt で足す。ADR-017）。
    • Bolt 33a から、password の再設定の完了を PASSWORD_RESET_COMPLETED（成功だけ。操作者に利用者と企業）で記録する。書くのは PasswordResetCompletionService で、トークンの使用・password の更新と同じトランザクションで書く。
    • Bolt 33b から、認証アプリの再登録の完了を TOTP_RE_ENROLLED（成功だけ。操作者に利用者と企業）で記録する。書くのは TotpReEnrollmentService で、TOTP の秘密の置き換え・回復コードの発行し直しと同じトランザクションで書く。
    • 監査記録の書き込みに失敗したら、ログインも失敗にする（IA-INV-08 の同期の書き込み。fail-closed）。
    • 権限外のアクセスの試行の記録（ADMIN_SCOPE_DENIED）は、Bolt 34b から controller の確定の POST で AdministrationScopeDenialService が単独で書く（GET では書かない）。
    • W5 のロックの失敗の数え方は、この listener が失敗・成功のイベントをアプリケーションのサービス LoginAttemptService に写す形にする。数えるのと、その監査記録を書くのはサービスの 1 つのトランザクションで、listener は数えない。数えない拒否と password の段の成功は listener が監査記録に直接書く（Bolt 32。下の「W5 で見直すこと」の 5。ADR-011 の決定 9）。Bolt 34c の決定で、この書き手の分け方を今のままにした（listener が直接書くのは数え方に関わらない 1 文の記録、数え方と結び付く記録とロック中の試行はサービス。書き手の表と理由は ADR-011 のステータスの Bolt 34c の決定）。Bolt 32 から、ロックしたときに ACCOUNT_LOCKED を書き、ロック中の試行を理由 LOCKED、利用者の読み出し（loadUserByUsername）の DB の誤りを理由 SERVICE_ERROR で記録する（どちらも数えない）。
    • Bolt 31 から、操作を PASSWORD_VERIFIED（password の段の成功）と LOGIN_SUCCEEDED（2 つの要素がそろった）に分ける。TOTP の失敗は利用者と理由（INVALID_TOTP・TOTP_REUSED）で記録する（下の「W5 で見直すこと」の 1）。Bolt 31b から TOTP の登録を TOTP_ENROLLED で、Bolt 31c から回復コードの使用を RECOVERY_CODE_USED（LOGIN_SUCCEEDED と 2 行）で記録し、回復コードの拒否は理由 INVALID_RECOVERY_CODE で記録する（ADR-011 の決定 7）。Bolt 31d から、TOTP を登録していない利用者の TOTP の送信を理由 TOTP_NOT_ENROLLED で記録する（今までは INVALID_TOTP。利用者への応答は変えない。ADR-011 の決定 8）。Bolt 32c から、request ごとの確かめで session を捨てたときに SESSION_REVOKED（結果 FAILURE、理由 SUSPENDED・COMPANY_INACTIVE・UNKNOWN_USER、操作者は session の主体の利用者 ID と企業 ID）を書く。書くのはアプリケーションのサービス SessionRevalidationService で、監査を直接書く入口の経路は増やさない。役割が変わっただけのときは書かない。

    6. 層の規則 D-5 の認証の例外（Bolt 31）¶

    • 認証の入口のパッケージ（identity.infrastructure.security。Spring Security の provider・listener・成功と失敗のハンドラー・フィルター・拒否の例外）から、identity.application.internal.commandservices だけを参照してよい。例外の範囲は入口だけである（Bolt 31d で決めた）。暗号の部品（AesGcmSecretCipher・Base32・BcryptRecoveryCodeHasher・JavaOtpTotpCodeGenerator・RandomRecoveryCodeGenerator・RandomTotpSecretIssuer）は Bolt 31c まで同じパッケージにあり、例外がパッケージ全体にかかっていた（Bolt 31 の開発レビューで挙がり、Bolt 31b では秘密の発行と回復コードの生成の実装を名指しして application に依存しない規則で守りを補った）。Bolt 31d で暗号の部品を identity.infrastructure.crypto に分け、既存の規則（合成ルートと入口の外の infrastructure は application に依存しない）が crypto にかかるようにし、名指しの規則をパッケージの規則に置き換えた。足した規則は「crypto は security に依存しない」だけである。保存した要素を読めないときは crypto が UnreadableCredentialException（ドメインの例外）を投げ、入口が捕まえる（ADR-011 の決定 8）。Bolt 31c の回復コードの provider（RecoveryCodeAuthenticationProvider）も入口で、RecoveryCodeVerificationService（commandservices）を呼ぶので、この例外の範囲に収まる。合成ルートの外の infrastructure は application に依存しない規則（D-5）の狭い例外で、サガの例外（infrastructure.persistence から application.sagas）と同じ書き方で LayerArchitectureTest に足し、理由を because に書く。例外の外は落ちることを、違反を入れて確かめる。
    • 理由: provider と listener は Spring Security が呼ぶ入口で、interfaces の層に置けない。業務の判断（TOTP の照合の結果を写し、刻みを使う。照合そのものは Bolt 31d から TOTP の資格）はアプリケーションのサービス（TotpVerificationService）に置き、入口は結果を認証の成否に直すだけにする。
    • Bolt 32 のロックの数え方（下の「W5 で見直すこと」の 5）も同じ形にする（2026-10-13、Bolt 31 の整合性検証の指摘への回答で human:kakimomokuri が決定。バックエンドのアーキテクチャ）。入口の監査のリスナー（AuthenticationAuditListener）・照合の後の確認の部品（LockAwareUserDetailsChecker）・TOTP と回復コードの provider は、LoginAttemptService（commandservices）を呼ぶので、この例外の範囲に収まる（Bolt 32）。
    • request ごとの確かめ（下の「W5 で見直すこと」の 3）も同じ形にする。入口のフィルター SessionRevalidationFilter は SessionRevalidationService（commandservices）を呼び、結果を session と主体に写すだけにする。判定（User#authenticationRejection）と SESSION_REVOKED の書き込みはサービスに置く。利用者と企業はドメインのポート UserStandingRepository（identity.domain.model.aggregates）で 1 回で読み、実装は identity.infrastructure.persistence に置く。この例外の範囲に収まり、新しい例外は要らない（Bolt 32c の計画の承認）。
    • ロックの判定 LoginAttemptService#isLocked は問い合わせだが commandservices に置く。認証の入口から呼ぶため、入口から呼べるのは commandservices だけという例外の範囲に収める（例外を queryservices に広げない）。登録済みかの問い合わせ isEnrolled を queryservices に移した Bolt 31b の前例は、入口から呼ばず画面の層だけが呼ぶ問い合わせだったためで、矛盾しない（Bolt 32 の計画の承認）。
    • Bolt 33c から、入口が参照してよい application 層に identity.application.internal.session（SessionKeys。Bolt 33f から URL の SessionPaths も同じパッケージ）を足す（2026-10-15、Bolt 33c の開始準備の決定 3 で human:kakimomokuri が決定）。LayerArchitectureTest の規則「認証の入口はidentityのコマンドサービスだけに依存してよい」の許可を commandservices.. と session.. にし、because に「session の属性の名前を認証の入口と画面で共有するため（Bolt 33c）」を足す。
    • 理由: session と request の属性の名前と A-08・A-03 の URL は、認証の入口（置く・読む・移す）と画面の層（読む・リンクに書く）の両方が使う。画面の層は infrastructure に依存できず、interfaces はどの層からも参照されないので、両方から参照できる置き場所は application 層になる。
    • 上の「例外を queryservices に広げない」と矛盾しない理由: SessionKeys・SessionPaths（Bolt 33f）はふるまいを持たない名前と URL（public static final String の定数）だけで、問い合わせも業務の判断も持たない。入口がこれを参照しても、業務の判断を入口に持ち込まない。queryservices を入口から呼べないようにしたのは、問い合わせ（業務の状態を読むふるまい）を入口に持ち込まないためで、その方針は変えない。
    • 例外の外（入口から queryservices、ほかの infrastructure から session）は落ちる。ほかの規則に当たったら止めて諮る（T-125）。

    代替案¶

    案 採らない理由
    主体の型を identity に置き、quotation から参照する quotation → identity → quotation :: events が循環する
    controller が Authentication を受け取り、利用者 ID を取り出す 業務の層の外側とはいえ、認証の方式が quotation に入る。TOTP の段（要素の権限）を足すときに quotation の変更が要る
    session を Servlet のコンテナのメモリに置く 複数のコンテナ（W10 の ECS）で session を共有できない。利用停止の即時の失効を DB の削除でできない
    送信（POST）の後の失効では、Referer の画面を覚えて戻す（Bolt 32e） Referer は利用者の側で変えられ、オープンリダイレクトの入口になる。送信の後の画面は送信の URL のまま描き直しており、開き直すと別の画面か 405 になる。送信の後の失効は Bolt 32f で、ブラウザが送信の前に戻り先を持つ
    入力の控えをサーバーの session や表に置く（Bolt 32f） 送信していない業務の入力をサーバーに残すことになる。無操作の失効では失効した session から利用者が分からず、戻す相手を確かめられない。ADR-005 の例外がブラウザより広くなる
    入力の控えを localStorage に置く（Bolt 32f） タブとブラウザの終了をまたいで残り、ほかのタブにも出る。共用のパソコンに個人情報が長く残る
    覚えた要求を利用者に結び付ける（Bolt 32e） 無操作の失効では、失効した session から利用者が分からない。8 時間の上限だけ結び付けると振る舞いが分かれる。別の利用者は認可で拒まれ、データは見えない
    認可を request ごとに DB で確かめるのも今入れる 利用者を止める操作（US-16）がなく、効き目を確かめられない。AC6 と一緒に W5 で入れる（Bolt 32c で入れた。DB の値を変えて確かめる）

    影響¶

    ポジティブ¶

    • quotation の controller の変更は引数の型の置き換えで済み、TOTP の段を足しても quotation は変わらない。
    • 仮の主体がなくなり、提出者・承認者などに本当の利用者が記録される。

    ネガティブ¶

    • session は JDK の直列化で DB に置く。Role の定数の改名・削除、CargoUserDetails の移動や項目の変更、Spring Security の版の更新、W5 の要素の権限の追加で、配備の前の session が復元できなくなる。互換を壊す変更を配備するときは、配備の手順で platform.spring_session の行を消し、利用者にログインし直してもらう（W10 の運用手順書に書く）。復元の失敗を無効な session として扱う変換は、W5 の要素の権限を足すときに検討する（Bolt 31 では、要素の権限を足しても配備の前の session は復元でき、password の段の時刻がないので期限の判定で A-03 に送る形になった。復元そのものが失敗する変更の変換は入れていない。ADR-011 の決定 2）。Bolt 32 のロックでは、互換を保つため CargoUserDetails に項目を足さず、ロックの状態を session に写さない（ADR-011 の決定 9）。

    • 未認証の request（ログインの画面の CSRF のトークン、失敗の後のメールアドレス）でも session の行ができる。作られる速さの上限（レート制限）は、W10 の WAF の送信元ごとの流量の規則で扱う（利用者ごとのロックでは抑えられない。Bolt 32 の開始準備で S-02 とあわせて決めた。SEC-20、リスク台帳）。

    • Bolt 32c まで、利用停止しても既存の session は最長 8 時間使えた（パイロットの前で本番の利用者はいない）。Bolt 32c で request ごとに確かめるようにして解消した。その代わりに、認証済みの request ごとに 1 回の SQL が増える。キャッシュは入れない（入れると AC6 の「次の request から」が崩れる）。W10 の性能の評価で計測する（PERF-01・02）。

    • 既存のテスト（controller の単体テスト、画面の層のシナリオ）にログインの準備が要る。
    • Bolt 32e から、失効の後に同じブラウザで別の利用者がログインすると、前の利用者が開いていた画面の URL へ移る（役割の違いは A-04、他社の業務番号は見つからない扱い。URL の path は見える）。覚えた要求を利用者に結び付けないため。共用の端末はログアウトしてから離れる運用で補う。
    • ステージング・本番の利用者を作る手段は、利用者の管理（US-16）まで無い。
    • Bolt 32f から、送信していない入力（個人情報を含みうる）がブラウザのそのタブに最長 8 時間残りうる。XSS があれば読まれる。閉じたタブの復元で残ることがある。8 時間のぎわで届いた送信の入力が戻り、二重に送信されうる（上の決定 3 の Bolt 32f の項目の既知の課題）。

    1. @EnableMultiFactorAuthentication を入れると、password の段でも認証の成功のイベントが出る。監査の操作を「password を確かめた」と「ログインした」に分ける（Bolt 31）。
    2. 認可の条件（hasRole）に要素の権限を加える（Bolt 31）。全体の注釈で業務の URL に 2 つの要素を求めるので、URL ごとの規則は役割だけのままにし、要素の欠けた主体で業務の URL を開けないことを全 URL で確かめる。
    3. request ごとの DB の確かめ（SEC-12・AC6）は、利用者 ID から主体を作り直して差し替える形にし、問い合わせを 1 回にまとめる（決めた。2026-10-14、Bolt 32c の計画の承認で human:kakimomokuri が決定。Bolt 32 の開始準備で 32 から送った）。
    4. 入口のフィルター SessionRevalidationFilter（identity.infrastructure.security）を SessionLifetimeFilter の直後に置く。認証済みの主体（CargoUserDetails）を持つ request だけで、SessionRevalidationService#revalidate(UserId, CompanyId) を呼ぶ。password の段だけの主体（A-02・A-07 の途中）にもかけ、止められた利用者に TOTP・回復コードの段を続けさせない。
    5. 読み出しはドメインのポート UserStandingRepository（利用者と所属企業の組 UserStanding を返す）で 1 回。実装は identity.app_user と identity.company を内部結合し identity.user_role を外部結合する 1 つの SQL で、役割の数だけ出る行を 1 人の User にたたむ。
    6. サービスは今のドメインの規則（User#authenticationRejection(company)）で判定する。利用者が見つからなければ UNKNOWN_USER。拒否なら SESSION_REVOKED を 1 つのトランザクションで書く。フィルターは session を捨て、セキュリティのコンテキストを消して A-03 に送る。
    7. 拒否でなければ、フィルターが今の役割・表示名・企業名で CargoUserDetails を作り直し、今の Authentication を toBuilder() で主体と ROLE_ の権限だけ替える。要素の権限（FACTOR_PASSWORD・FACTOR_TOTP）は残す。新しいセキュリティのコンテキストに入れ、session には保存しない（毎回作り直すので古い役割は戻らない）。A-02・A-07 が通ったときは、認証のフィルターが差し替えた後の主体で session に保存する。この振る舞いは特性テストで固定した（Bolt 32 の Try T-114）。
    8. 誤りは fail-closed にする。読み出しの DB の誤り、監査の書き込みの誤り、役割が 0 件の利用者（データの不整合）は、session を捨ててから 500 にする。

    10. 引数の解決で、TOTP まで済んでいない主体を渡さない（決めた。2026-10-13、Bolt 31c の計画の承認で human:kakimomokuri が決定）。
