    ADR-018: 再見積りの提示で輸送要求を荷主承認待ちへ戻し、届く順の入れ替わりは楽観ロックでぶつけて守る¶

    荷主の承認の後に失効した見積りを再見積りして提示したら、DE-24 で輸送要求を予約待ちから荷主承認待ちへ戻す。輸送要求を進める・戻す listener は、輸送要求を読んでから見積りを読み、DE-04 と DE-24 は進めなくても輸送要求を書いて版を上げる。置換済み・失効の見積りの DE-21・DE-04 は輸送要求を進めない。

    日付: 2026-10-19

    ステータス¶

    採用（方針は 2026-10-19 に human:kakimomokuri が Bolt 35b2 の開始準備で決め、文面を同日に Bolt 35b2 の終了報告の承認で確かめた）

    コンテキスト¶

    • D-85（2026-10-11）: 荷主の承認の後に失効した見積りは、承認済みの経路版を引き継いで再見積りし、荷主の再承認を受ける。Bolt 35b で見積りの側を作り、新しい見積りは提示で荷主承認待ちに直行する（DE-03 を出し、DE-21 は出さない）。輸送要求は予約待ちのまま残る
    • 輸送要求の状態は、見積りのイベント（DE-03・DE-16・DE-21・DE-04）と予約の通知（DE-07）を受けた別のトランザクションで、先の状態へだけ進め、戻さない（Bolt 12 レビュー R-04）。listener は同じ輸送要求を並行して更新し得るので、楽観ロックの競合は読み直してやり直す。やり直しが安全なのは、先へだけ進める冪等な操作だから（Bolt 22。TransportRequestProgression）
    • 戻す操作を足すと、この安全の根拠が崩れる。届く順が入れ替わると次のずれが起きる
    • 荷主の再承認（DE-04）が DE-24 より先に処理されると、DE-24 が後から荷主承認待ちへ戻し、承認済みの見積りなのに輸送要求が荷主承認待ちで止まる
    • 再見積りで旧版になった見積りの DE-21・DE-04 が戻しの後に届くと、新しい見積りが未承認のまま輸送要求が予約待ちへ進む
    • 輸送要求は「どの見積りのための状態か」を持たない。見積りの状態に失効・置換済みを書くのは再見積りだけ（期限による失効は状態を書き換えない）
    • 2 つの集約を 1 つのトランザクションで更新しない（ドメインモデル）。H2 と PostgreSQL には方言差があり（ADR-007）、見積りのコンテキストの業務番号の採番の mapper は共通の構文で書いている（TransportRequestNumberCounterMapper.xml）。採番の mapper が SELECT ... FOR UPDATE を使わないのは、UPDATE の行ロックで採番を直列にできるからで、方言だからではない。SELECT ... FOR UPDATE は identity の mapper（PasswordResetTokenMapper.xml の利用者の行のロック）で H2 と PostgreSQL の両方で流れている（Bolt 37e2 で直した。下の改訂の経緯）

    決定¶

    要素 決定
    戻しのイベント 新しいドメインイベント DE-24 QuotationPresentedForReapproval（再見積りを荷主の再承認待ちにした）。経路を持つ見積りの提示で、DE-03 の後に出す。属性は見積り ID・見積り番号・輸送要求 ID・版番号・提示時刻
    輸送要求の操作 荷主承認待ちへ戻す操作。同じ版で、予約待ちなら荷主承認待ちに戻し、それより手前なら荷主承認待ちに進める（ほかのイベントの遅れ）。荷主承認待ちなら変えない。予約確定済みは変えない（D-87。US-05）。操作は見積りを知らない
    読む順 輸送要求を進める・戻す listener は、輸送要求を読む → イベントの見積りを読む → 判定して進める・戻す → 保存する（楽観ロック）。輸送要求を先に読むので、見積りを読んだ後にほかの listener が輸送要求を書けば、保存がぶつかる。競合したら輸送要求と見積りを読み直して判定し直す（READ COMMITTED で、相手のコミットを読む）
    進めなくても書く DE-04 の listener は、輸送要求がすでに予約待ちに届いていても保存して版を上げる。DE-24 の listener は、見積りが荷主承認待ちなら、輸送要求がすでに荷主承認待ちでも保存する。こうして、先に読んで後から書く側が必ずぶつかり、読み直して見積りの今の状態に合わせる
    DE-24 の判定 見積りが荷主承認待ちのときだけ戻す。承認済みなら変えない（その見積りの DE-04 が進める）。見つからない・置換済み・失効・荷主承認待ちでないなら変えず警告のログ
    置換済み・失効の見積りのイベント DE-21・DE-04 の listener は、イベントの見積りに置換済み・失効の記録があれば輸送要求を進めず、警告のログを残す（DE-04 の書き込みもしない）
    部品の形 判定の口（QuotationGate）と「届いていても書く」の指定を TransportRequestProgression に置き、読む順をその中に閉じる。指定を持たない呼び手（DE-03・DE-16・DE-07）は今のまま
    守りが成り立つ条件 判定が読む見積りの状態を変える操作の後には、必ず輸送要求を書く listener が続く（荷主の承認の後の DE-04、再見積りの提示の後の DE-24。どちらも届いていても書く）。判定に新しい見積りの状態を使うとき（荷主の辞退、D-86）は、その状態の変化の後に輸送要求を書く listener を用意する

    確かめる差し込みの順¶

    順 結果
    DE-24 が輸送要求と見積り（荷主承認待ち）を読んだ後に、再承認と DE-04 の書き込みが入る DE-24 がぶつかり、読み直すと承認済みで戻さない。予約待ち
    DE-04 が輸送要求を読んだ後に、DE-24 の戻しが入る DE-04 がぶつかり、読み直して予約待ちへ進める
    旧版の DE-04 が輸送要求と旧版（まだ置換されていない）を読んだ後に、再見積り・提示・DE-24 が入る DE-24 は荷主承認待ちに届いていても書くので、旧版の DE-04 がぶつかり、読み直すと旧版は失効で進めない。荷主承認待ち
    旧版の DE-04 が DE-24 の戻しの後に届く 旧版の失効の記録で進めない。荷主承認待ち
    旧版の DE-04 が輸送要求と旧版を読んだ後に、再見積りだけがコミットし（まだ提示していない）、旧版の DE-04 が書く 再見積りは輸送要求を書かないのでぶつからず、輸送要求は予約待ちへ進む。提示の後の DE-24 で荷主承認待ちに戻る。提示までの間の予約待ちは再見積りの前と同じ状態なので、一時的なずれとして受け入れる（Bolt 35b2 のレビュー）

    代替案¶

    案 採らない理由
    DE-24 の listener が見積りの行を SELECT ... FOR UPDATE で読み、戻すまで荷主の承認を待たせる 読む順と「進めなくても書く」と置換済み・失効の見積りの判定で、ロックを足さずに上の差し込みの順をすべて守れる（ポジティブ）。荷主の承認を DE-24 の listener の終わりまで待たせる必要がない。注（Bolt 37e2 で直した）: 当初の理由は「方言の構文を入れる（ADR-007）」と「2 つの集約の行を 1 つのトランザクションで押さえる」だった。SELECT ... FOR UPDATE は identity の前例で H2 と PostgreSQL の両方で流れるので、方言は理由にならない。押さえるのは見積りの 1 行で、書くのは輸送要求の集約 1 つなので、2 つの集約を書く形にもならない（Bolt 37e2 の本予約の確定用の照会も、押さえるのは見積りの 1 行で書くのは予約の集約である。ADR-016）
    輸送要求に「どの見積りのための状態か」を持たせる列を足し、イベントの見積りと照合する スキーマを変える。Bolt 35b の決定 (4)（引き継ぎ元の列を足さない）と同じく、見積りの状態から辿れる
    隙間は受け入れて台帳に載せ、警告のログで見つける 承認済みの見積りなのに輸送要求が荷主承認待ちで止まると、営業の業務ホームと荷主の表示が誤り続け、直す操作がない

    影響¶

    ポジティブ¶

    • スキーマもロックも足さずに、届く順の入れ替わりで状態がずれない
    • 置換済み・失効の見積りのイベントで輸送要求が進まない（Bolt 35b のレビューの指摘）
    • 守りは TransportRequestProgression の 1 か所に閉じ、差し込むテストで確かめられる

    ネガティブ¶

    • DE-04・DE-24 の再配信のたびに、状態の変わらない輸送要求の書き込みが 1 回増える
    • 守りは読む順に依存する。順を変えると破れるので、Javadoc と差し込むテストと変異で守る
    • 「置換済み・失効の記録 = 再見積りで旧版になった」は、今のコードでは再見積りだけが状態を書くので成り立つ。荷主の辞退（US-24 AC2。Q-INV-09「辞退した見積りは失効する」）を作るときは、辞退した見積りのイベントの扱いを見直す
    • 輸送要求は先へだけ進めるという前提（R-04）は、DE-24 だけが例外になる。ほかの進める操作は今のまま
    • 守りは READ COMMITTED（同じトランザクションの中の読み直しが相手のコミットを読む）と、版の合わない UPDATE が 0 行になること、0 行の UPDATE の後に MyBatis の 1 次キャッシュが古い見積りを返さないことに頼る。分離レベルを REPEATABLE READ 以上に上げると、競合が直列化の失敗の例外に変わり、読み直しの形が変わる

    コンプライアンス¶

    • 輸送要求の戻す操作と見積りの DE-24 の発行を単体テストで確かめる
    • 上の差し込みの順を、輸送要求の読み込みの後と見積りの読み込みの後に差し込むテストで確かめる。1 つ目の順は PostgreSQL の統合テストでも確かめる（READ COMMITTED と MyBatis のキャッシュの前提）
    • 戻す条件・読む順・判定の呼び直し・進めなくても書く・置換済み・失効の見積りの判定に変異を当てて落ちることを確かめる
    • 業務ルール層の受入シナリオで、再見積りの提示で荷主承認待ち、再承認で予約待ち、戻しの後の旧版の DE-04 で荷主承認待ちのままを確かめる

    改訂の経緯¶

    • 2026-10-23: Bolt 37e2 で、代替案「DE-24 の listener が見積りの行を SELECT ... FOR UPDATE で読む」の採らない理由と、コンテキストの方言差の記述を直した。SELECT ... FOR UPDATE は identity の前例で H2 と PostgreSQL の両方で流れ、押さえるのは見積りの 1 行で書くのは別の集約 1 つなので、「方言」と「2 つの集約」は理由にならないため。Bolt 37e2 で本予約の確定用の照会に FOR UPDATE を使う（ADR-016）。決定（DE-24 の listener はロックしない）は変えない（Bolt 37e2 計画 の確認ポイント 5。human:kakimomokuri が承認）
