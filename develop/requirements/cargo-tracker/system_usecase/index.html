    cargo-tracker システムユースケース¶

    共通方針¶

    • Intent は、予約から基本追跡までの一貫した顧客価値を、根拠・版・出典・監査証跡とともに提供することである。
    • 本書はゲート 2 として、MVP の UC-01〜UC-10、UC-16〜UC-20、および段階横断の UC-15 の主成功シナリオを定義する。

    機能横断の UI 契約¶

    次の条件は UC-01〜UC-10、UC-16〜UC-20 の人が操作する画面・対話部分、および UC-15 の手動取込・差異確認・復旧照合画面に適用する。UC-15 のバックグラウンド取込処理自体はキーボード・フォーカス条件の対象外だが、その結果を表示・操作する UI には適用する。

    • WCAG 2.2 AA を目標とし、キーボードだけで操作でき、可視フォーカス、明示ラベル、エラー要約、色だけに依存しない状態表示を提供する。
    • 入力エラー時は入力値を保持し、エラーのある項目、理由、修正方法を示して該当箇所へ移動できるようにする。
    • 入力エラー、非同期更新、確認中への状態変化、有人案件の escalation は、視覚表示に加えてスクリーンリーダーなどの支援技術が認識できる方法で通知する。
    • 本予約確定、取消し、権限変更、実績訂正、荷受人への共有・取消しは、対象、現在状態、変更内容、影響、実行者を示した実行前確認を要求する。
    • 回復可能な操作は取消しまたは再実行の手段を示し、回復不能な操作は実行前確認で明記する。

    トレース: BR-13、NFR-ACCESS-01、OQ-07。本契約では列挙した機能条件を判定し、WCAG 2.2 AA 全体の適合判定、画面別の操作順序、文言、支援技術による検証は UI 設計とテスト戦略で具体化する。 - 最小保証として、失敗時も確定済みの業務データを失わず、操作主体と処理結果を追跡可能にする。 - 代替・例外フローはゲート 3 で追加する。画面、API、データベースなどの実装方式は規定しない。

    U1 輸送要求・見積り¶

    UC-01 輸送条件を下書き・提出する¶

    項目 内容
    主アクター 荷主担当者、営業担当者
    事前条件 利用者が所属企業の予約を作成できる
    トリガー 新しい輸送の相談を開始する
    成功時保証 必須条件を含む輸送要求版が審査中となり、提出者と時刻が記録される
    最小保証 下書きは失われず、未提出であることを識別できる
    測定基準 入力負担、再入力率、必須項目不足による差戻し率。目標値は OQ-01、OQ-06 で確定する
    トレース BUC-01、RQ-01、BR-01

    主成功シナリオ:

    1. アクターが輸送条件の下書きを開始する。
    2. 荷主、荷受人、貨物仕様、発着地、希望日を記録する。
    3. システムが必須条件と企業権限を検証する。
    4. アクターが条件を提出する。
    5. システムが輸送要求版を審査中として記録する。

    UC-02 輸送条件を審査・差し戻す¶

    項目 内容
    主アクター 営業担当者
    事前条件 審査中の輸送要求版が存在する
    トリガー 営業担当者が審査対象を選ぶ
    成功時保証 条件が見積り可能と判断され、審査履歴が残る
    最小保証 元の輸送要求版と既存審査履歴は保持される
    測定基準 審査時間、差戻し率。目標値は OQ-01、OQ-06 で確定する
    トレース BUC-01、RQ-04、BR-01

    主成功シナリオ:

    1. 営業担当者が審査中の輸送要求版を確認する。
    2. 契約条件、貨物仕様、必要書類を照合する。
    3. 見積りに必要な条件がそろっていると判断する。
    4. システムが判断者、時刻、判断根拠を審査履歴へ記録する。
    5. 輸送要求版が見積り作成可能な状態になる。

    UC-03 見積りを作成・提示する¶

    項目 内容
    主アクター 営業担当者
    事前条件 輸送条件が審査済みである
    トリガー 営業担当者が見積り作成を開始する
    成功時保証 料金根拠、利用者のタイムゾーンと UTC offset を明示した有効期限、経路方針を伴う見積りが提示される
    最小保証 未確定の見積りが顧客承認対象にならない
    測定基準 見積りリードタイム、根拠欠落率。目標値は OQ-06 で確定する
    トレース BUC-01、RQ-01、RQ-04、BR-01、BR-10

    主成功シナリオ:

    1. 営業担当者が審査済み輸送条件を確認する。
    2. 料金構成と経路方針を作成する。
    3. システムが料金根拠と UTC の時点で保存する見積有効期限の存在を検証する。
    4. 営業担当者が見積りを確定する。
    5. システムが見積有効期限を利用者のタイムゾーンへ変換し、タイムゾーンと UTC offset を明示して荷主へ提示する。

    U6 予約管理¶

    UC-04 予約を確定する¶

    項目 内容
    主アクター 荷主担当者、営業担当者
    事前条件 本予約確定の commit 時刻が有効期限より前である見積り、必須貨物情報、荷主担当者 1 名の承認、承認済み経路版が存在する
    トリガー 荷主担当者が見積りと承認済み経路を確認して本予約を申し込む
    成功時保証 有効な予約版と一意な追跡番号が確定する
    最小保証 承認前の状態と判断履歴が保持される
    測定基準 確定所要時間、追跡番号重複 0 件
    トレース BUC-02、RQ-01、RQ-02、RQ-04、BR-01、BR-03、BR-10

    主成功シナリオ:

    1. 荷主担当者が見積り、条件、承認済み経路版を確認する。
    2. 荷主担当者 1 名が承認して本予約を申し込む。
    3. 営業担当者が見積り、必須貨物情報、荷主担当者 1 名の承認、承認済み経路版を確認する。
    4. システムが確定処理の commit 時刻を取得し、その時刻が見積有効期限より前であることを確定と同じ整合性境界で検証する。
    5. システムが予約版を確定し、追跡番号を発行する。
    6. システムが承認者、確定者、commit 時刻を記録する。

    MVP の決定: 荷主内の入力者・承認者は分離せず、荷主担当者 1 名の承認と営業担当者の BR-01 確認で本予約を確定する。荷主内の職務分離は後続段階で再検討する。

    UC-05 予約を変更・取消しする¶

    項目 内容
    主アクター 荷主、営業担当者
    事前条件 対象予約が存在し、アクターが操作権限を持つ
    トリガー 荷主が変更または取消しを申し出る
    成功時保証 本予約前は新しい輸送要求版または取下げ、本予約後から集荷前は営業承認を伴う新しい予約版または取消しが記録される
    最小保証 変更前の確定版は改変されず参照できる
    測定基準 変更処理時間、理由欠落 0 件、版の追跡不能 0 件
    トレース BUC-02、RQ-01、RQ-04、BR-04、OQ-04

    主成功シナリオ:

    1. アクターが対象の輸送要求または本予約と、変更または取消し理由を指定する。
    2. システムが本予約・集荷実績の有無と操作権限を確認する。
    3. 本予約前の場合、システムが旧版を保持して新しい輸送要求版または取下げを記録する。
    4. 本予約後から集荷前の場合、システムが申請を営業承認待ちとして記録する。
    5. 営業担当者が影響と業務条件を確認して承認する。
    6. システムが新しい予約版または取消しを記録し、必要な再見積り・荷主再承認・再設計を示す。
    7. システムが影響を受ける関係者と後続業務へ結果を共有する。

    判断表:

    実行段階 変更・取下げ／取消し 承認 結果
    本予約前 許可 不要 新しい輸送要求版、または取下げ
    本予約後〜集荷実績採用前 許可 営業承認が必要 新しい予約版、または取消済み
    集荷実績採用後 通常処理は禁止 自動承認しない 要求を記録し、有人の例外対応へ引継ぎ

    U2 経路設計¶

    UC-06 経路候補を算出・比較する¶

    項目 内容
    主アクター 経路設計者
    事前条件 経路設計に必要な見積り済み輸送要求が存在する
    トリガー 経路設計者が候補算出を開始する
    成功時保証 候補、除外理由、情報鮮度を比較できる
    最小保証 元の輸送要求と既存経路版は変更されない

    MVP と後続段階の境界¶

    領域 MVP で保証する範囲 後続段階
    入力・権限 必須項目検証、企業間分離、荷受人の予約単位参照許可、権限違反の拒否と記録 権限体系の高度化は OQ-07 の残項目確定後
    変更・並行処理 版保持、競合検知、古い版による上書き防止 自動調停は行わない
    外部データ 限定情報源の原本保持、冪等処理、順序・差異・復旧照合 税関直接連携、対象情報源の拡大
    追跡 予定と主要実績、出典、鮮度、訂正履歴 荷役イベント自動同期、リアルタイム通知、例外案件管理
    例外対応 安全な停止、理由記録、受付番号付き有人引継ぎ、担当受領、期限・次回更新、顧客回答、終結 自動検知・通知と高度な例外案件管理
    精算 見積り根拠を保持 引渡し・料金照合・精算確定

    精度レベル 2 の AI の仮定¶

    • カスタマーサポートは UC-09 を社内担当者として利用し、予約の代理確定・変更は行わない。
    • 未決の数値、訂正承認条件、保持期間は確定値として扱わない。荷受人の開示範囲は BR-07 の決定を適用する。
    • 税関システムは MVP の UC-15 の支援アクターに含めない。
    • 各シナリオは業務目的と観測可能な結果を記述し、UI や通信方式を規定しない。

    精度レベル 3 の承認事項¶

    ID 判断案 理由
    G3-D1 必須項目、企業権限、重複、並行更新、版競合を MVP で扱う 誤った予約・開示・上書きを防ぐための最低限の安全性である
    G3-D2 外部データの timeout、再送、重複、順序逆転、復旧照合を MVP で扱う 基本追跡の出典と鮮度を保証する前提である
    G3-D3 変更・取消し、再見積り、再設計、実績訂正を MVP で扱う 現実の輸送変更を版履歴なしで運用できないためである
    G3-D4 自動通知、例外案件管理、荷役イベント自動同期を第 2 段階へ送る MVP の基本追跡を超えるためである
    G3-D5 税関直接連携と対象情報源の拡大を後続へ送る OQ-05 の契約・責任分界が未確定である
    G3-D6 引渡し・精算確定を第 3 段階へ送る MVP の予約・経路・基本追跡の価値検証後に実施するためである

    精度レベル 3 の AI の仮定¶

    • 「MVP で扱う」とは完全自動化を意味せず、安全な停止、記録、再実行、手動引継ぎを含む。
    • 変更・取消しの実行段階、営業承認、予約確定時の役割分担、パイロットの訂正二者確認条件は確定した。変更・取消しの費用・申請期限、保持期間、後続 API の再送間隔などは OQ-04、OQ-05、OQ-07 の残決定に委ねる。
    • 外部障害時に古い情報を表示する場合、出典と取得時刻を必ず併記し、最新であると誤認させない。
