    Bolt 23b 終了報告 - 本予約の確定の画面（US-04 AC1・AC2、#10）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt23b）により、計画の承認から終了報告の前まで、承認ゲートで止まらずに進めた。止まらなかったゲートごとの判断を次に置く。表の変更はない（T-67 は当たらない）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 画面の設計のゲート（ステップ 1）: S-09・S-24・S-02 の文言と構成、ADR-016 の照会の鍵を業務番号と見積り番号に改めた改訂 人の決定（確認ポイント 3・4・7）のとおり。UI 設計の S-09 の図を「画面そのものを確認の領域」に直した UI 設計 の S-02・S-09・S-24 の行、ADR-016 の改訂の経緯
    2 モジュールの境界のゲート（ステップ 2）: 見積りの公開 API の照会と確定のコマンドを業務番号と見積り番号で受ける形に変えた 呼び出し元は予約だけ。booking の依存は変わらず、quotation は booking に依存しない（S-02 から S-09 へは URL だけでつなぐ）。ModularityTest 緑 quotation.api.BookableQuotationRequest、ConfirmBookingCommand
    3 確定の画面の Red／Green・認可・画面のゲート（ステップ 3・4） Red を実行して失敗を確かめてから実装した（Bolt 23 の Problem を繰り返していない）。認可は既存の /staff/** の規則のまま、セキュリティの統合テストで確かめた 計画のステップ 3・4 の結果
    4 計画からの変更: 見つからない見積りは S-02 に戻さず 404 にした（C-17 など既存の画面と同じ）。業務番号の形の判定を予約から外し、見積りの公開 API の「見つからない」に任せた（開発レビュー） 予約に業務番号の形の写しを持つと、採番の形が変わったときに予約だけが黙って 404 を返す BookingController
    5 ドメインの判断が要る: 荷主の承認の後に失効した見積り（承認済み）は、いまの規則（Quotation.requoteRejection が詳細経路設計に進んだ見積りの再見積りを拒む）では再見積りできない。画面が「再見積りしてください」と案内すると行き止まりになるので、文言を「再見積りが必要です」に、S-02 の入口を「…の見積りを開く」にし、「再見積りは、まだ画面で操作できません。扱いは担当者で相談してください」と示した US-04 AC2 の「失効と再見積りの必要性が示される」は満たす。再見積りの規則（経路を設計し直すか、承認済みの経路を引き継ぐか）を変えるのはドメインの判断なので人に諮る。どの Bolt で扱うか決めてほしい 開発レビュー P-1、S-02 の予約の確定待ちの表
    6 開発レビューの対応の範囲。直したもの 15 件、後に回したもの 9 件（下の「開発レビュー」） 画面の行き止まり、エラー要約の漏れ、表から行が落ちる不具合、境界のテスト、文言は、この Bolt の目的そのものなので直した。Bolt 24・25 の振る舞いに要るものは既知の課題にした 開発レビュー
    7 #10 は開いたまま、画面の結果をコメントする（クローズは Bolt 25） 計画どおり #10

    仮説の結論¶

    # 仮説 結論
    H1 業務番号と見積り番号で S-09 を開けば、予約は見積りの公開 API だけで確定条件を示せる 成り立った。URL に内部の ID はなく、booking の依存は増えていない。荷主の承認時刻を公開 API の結果に足した
    H2 S-09 の表示（参考）と POST の判定（commit 時刻）を分けて示せば、表示の後に失効しても迷わない 成り立った。画面の層のシナリオで、開いた後に期限を過ぎた見積りは送っても確定せず、S-02 に「再見積りが必要です」と示された。ただし再見積りの操作そのものがまだない（議題 5）

    開発レビュー¶

    プログラマー（テスターの観点を含む）、アーキテクト、インタラクションデザイナー（ユーザー代表の観点を含む）の 3 つの観点で行った。

    # 指摘 重大度 対応
    P-1 失効した行の「再見積りへ」と「再見積りしてください」の先で再見積りできない（承認済みの見積りは再見積りを拒む） 高 文言と入口を直し、規則は議題 5 で人に諮る
    P-2 / U-2 貨物の要約が空のまま送るとエラー要約に出ない 中 直した（Red を確かめてから。「必須貨物情報: …」の項目）
    P-6 輸送要求が経路設計中のまま見積りが承認されると、S-02 のどちらの表にも出ない 中 直した（予約の確定待ちに経路設計中も含める。統合テストに足した）
    P-4 / U-1 ナビの「予約」が 405 になる 中 当たらない。セキュリティの統合テストで 200（準備中の画面）を確かめた。S-24 に後から戻る入口がないことは既知の課題
    P-5 失効の境界（同時刻・1 秒前）を S-02 で確かめていない 中 直した（T-38）
    A-中2 / P-12 予約が業務番号の形を写して持つ 中 直した（見積りの公開 API の「見つからない」に任せる）
    U-4 / P-11 エラー要約の項目の形（「表示名: 文言」）とチェックの aria-describedby 中 直した
    U-6 S-24 の「commit 時刻」が業務の言葉でない。完了の知らせ方がない 中 直した（「確定時刻」、「完了したらこの画面に表示します。画面を更新して確かめてください。」）
    U-11 確認の項目の「影響」と「回復手段」が重なる 低 直した（「集荷前なら変更・取消しを申請できます」）
    P-8 / A-低2 予約サガが欠けると原因の分からない 500 低 直した（不変条件の違反と分かる例外）
    P-9 失効の判定の写し 低 直した（QuotationViews.isExpired を共有）
    A-低1 層の図に照会から腐敗防止層への矢印がない 低 直した
    S-1〜8 SonarQube の新しい指摘 8 件（レコードのパターン、名前のない変数、文字列の定数、使わない変数、アサーションの順） — 直した
    A-中1 / P-3 / U-7 確定済みの判定が見積りの照会の後にある（確定後に失効した見積りを開くと「期限切れ」と出る。確定済みに S-24 への導線がない） 中 後に回す（Bolt 24 の AC4 で、処理済みコマンドか既存の予約の照合を見積りの照会より前に置く）
    U-3 エラー要約にフォーカスが移らない 中 後に回す（S-07 も同じ。社内のレイアウトの共通の部品で直す）
    U-1 確定の後に S-24 へ戻る入口がない 高 後に回す（確認ポイント 7 のとおり Bolt 25 で S-10 の最小の一覧か導線を決める）
    P-7 入力の形の誤りで 404 と 400 が混ざる 低 後に回す
    U-8・U-9・U-10・U-12 お知らせの句点、追跡番号の区切りの表示、満たした条件の表記、状態の列の重なり 低 後に回す（画面の文言をそろえる Bolt で）
    A-低3〜5 読み取りモデルが集約を包む、照会の結果の型が 3 段で同じ形、一覧の読み取りモデルがドメイン層に増える 低 後に回す（Bolt 25・W11 で投影や照会専用のポートを ADR で諮る）

    判断と学び¶

    既知の課題（後の Bolt に持ち込む）¶

    • Bolt 24: 確定済みの判定（処理済みコマンドか既存の予約の照合）を見積りの照会より前に置き、確定済みの通知に既存の追跡番号と S-24 への導線を付ける（AC4）。S-09 のフォームにコマンド ID を足す
    • Bolt 25: S-24 の「追跡の開始: 完了」を人が確かめる入口（S-10 の最小の一覧か、S-02 の結果からの導線）を決める。booking :: api と予約サガの遷移
    • 人の判断（未決）: 承認の後に失効した見積りの再見積りの規則（議題 5。画面の暫定の案内は承認済み）。Bolt 24 の開始準備で扱いを確かめる
    • 社内の画面の共通の部品: エラー要約へのフォーカス（S-07・S-09）

    ふりかえり（KPT）¶

    • Keep
    • すべてのステップで、骨組みを置いて Red を本命のアサーションで確かめてから実装した（Bolt 23 の Problem を直せた）
    • 3 つの観点の開発レビューで、画面の行き止まり（承認済みの見積りは再見積りできない）を push の後すぐに見つけた
    • Problem
    • 失効の案内の文言を、遷移先で本当に再見積りできるかを確かめずに書いた（画面の層のシナリオもリンクの有無までで止まっていた）
    • T-55 を守らず、整形の前の行の形で置換のスクリプトを書き、1 回やり直した
    • 既存の CSRF のテストの形を確かめずにテストを書き、1 回やり直した
    • 開発レビューの対応を、check だけで uiTest を流さずに push し、CI の画面の層のジョブを 1 回赤にした（86cf224。abcc1e4 で直した）
    • Try
    • T-70: 画面の欄の値を確かめるステップ（hasText）がある欄には、案内の文を足さずに欄の外に置く。開発レビューの対応の後も、push の前に uiTest を流す（AI、次の Bolt から）
    • T-69: 画面が次の行動を案内する文言（「…してください」）を書くときは、その行動の画面と規則が今あるかをコードで確かめ、画面の層のシナリオは案内の先まで進める（AI、次の Bolt から）
