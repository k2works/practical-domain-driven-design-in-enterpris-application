    Bolt 33b 終了報告 - 回復コードによる TOTP の再登録（US-18 AC9）と #13 のクローズ¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-15 に、確認ポイント 1〜16 を推奨どおりとして承認を受けた（363a0965f）。/goal Bolt33b の下で、ステップ 1〜6 の承認ゲートで止まらずに進めた。層・モジュールの規則には当たらなかった。開発レビューで人の判断が要る指摘が 1 つ出たので諮った（議題 3）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 止まらなかった承認ゲート: ステップ 1（設計文書）、2（部品の付け替えと資格の置き換え。セキュリティ・構造）、3（再登録のサービス。セキュリティ）、4（画面。画面・セキュリティ）、5（マニュアル）、6（終了報告の前の直し） Red を確かめてから実装した（契約テスト・単体テスト・統合テスト・画面の層。例外は議題 5）。変異の確かめ: 刻みの使用の秘密の条件を外すと 5 件、置き換えの秘密の条件を外すと 4 件が落ちた（T-112）。決定の順（確かめた後に置き換え、確定の後に失効）と実装を突き合わせた（T-129） 「ステップの結果」「指標」
    2 計画からの変更（セキュリティ。人に諮らずに変えた）: 再登録の置き換えを、計画の「利用者の行を占有する」から「再登録の前に読んだ秘密のままのときだけ置き換える条件付きの更新」に変えた。あわせて、同じ秘密で二度送った場合（二度押し・別のタブ）は照合の前に「ほかの画面で先に登録し直していた」（Superseded）として、置き換えも回復コードの発行し直しもしない 占有は「同時の 2 つの再登録で回復コードを 2 回発行する」ことを防げるが、二度押しは防げなかった（先の確定の後に後が来ると、占有を取り直して置き換えてしまう）。秘密の条件付きの更新は、刻みの使用（決定 5）と同じ形で、同時でも順でも 1 つだけが通る。暗号文は IV が毎回乱数なので同じ値に戻らない（ABA が起きない）。app_user の占有と順序を共有しないので結合も小さい。同時のテスト（後の更新が先の行ロックを待つことを pg_stat_activity で確かめる）と単体テストで確かめた ADR-011 の決定 10、data_model の totp_credential
    3 開発レビューで人が決めたこと（2026-10-15、human:kakimomokuri）: 回復コードでログインした印に 15 分の期限を付ける。過ぎたら A-08 を開けず、業務の画面の知らせはリンクのない「いったんログアウトして、回復コードでログインし直してください」に変わる セキュリティのレビュー（中）: 「後で登録する」の後も印が session の最大 8 時間残ると、session を盗んだ者や離席中の端末に触れた者が、password なしで認証アプリを登録し直せる（一時的な乗っ取りが続く乗っ取りになる）。再認証なしを受け入れる前提（印はログインの直後だけ有効）を守る。A-08 の 15 分（開いた時刻から）より印の 15 分（ログインから）が先に来るので、サービスの期限切れの分岐は画面からはほぼ届かない守りになった UI 設計の A-08 と共通部品の知らせ、ADR-011 の決定 10
    4 W6・W10 に送ったもの: #47 に、回復コードの経路でも本人へメールで知らせること、残りの回復コードの案内。#49 に、ほかの session の失効の失敗の扱い、失敗の試行の監査、覚えた要求の絶対 URL と逆プロキシの Host の確認 T-89（後に回したものは Issue にする）。どれも計画の確認ポイント 4・13 と SEC-10 の回復コードの経路の範囲の外 #47・#49
    5 TDD の抜け: UserSessionRevoker.revokeOthers のテストは実装と同じ書き換えで足し、先に Red を確かめていない。監査の失敗で全体が戻る統合テストと、印の単体テストは、開発レビューの後に足した見張りのテストで、最初から緑だった 振る舞いはそれぞれ統合テストで確かめている。Red を確かめなかったことを記録する 計画の更新履歴
    6 33c の範囲: 開発レビューで、A-08 の URL の組（6 組目）、HttpSessionRequestCache の一本化、A-07 と A-08 の途中の暗号文と回復コードの発行の重複、認証の結果のトークンに経路を持たせること、revokeOthers の session の ID の値オブジェクトを足した どれも振る舞いを変えない直しで、33c（構造）に入る。33c の開始準備で範囲と時間を見直す release_plan の 33c の行
    7 #13 のクローズと SP: 終了報告の承認の後に #13 をクローズし、US-18 の残りの SP 6 を数える（AC9 の管理者の経路と本人への通知は #47） 開始準備の決定 2 の (8) release_plan の W5

    仮説と結論¶

    # 確かめたこと 結論
    1 刻みの使用に秘密の一致を足し、置き換えを読んだ秘密のままのときだけにすれば、古い秘密で照合した要求も、同時の再登録も、置き換えの後に通らない 支持。後の更新が先の行ロックを待って 0 件になることを PostgreSQL で確かめた
    2 回復コードの発行し直しを置き換えと同じトランザクションにすれば、古い回復コードは置き換えの後に通らない 支持。回復コードによるログインの消費が、消えた行の行ロックを待って 0 件になる
    3 回復コードでログインした印で A-08 へ導き、「後で登録する」を許しても、印をログインの直後だけ有効にすれば、再認証なしの再登録を受け入れられる 支持（開発レビューで印に 15 分の期限を付けた後）

    開発レビュー¶

    プログラマー、テスター、アーキテクト、セキュリティ、テクニカルライターの 5 つの観点で行った（git diff 363a0965f..52cc550db）。高の指摘はなかった。

    # 観点 重要度 指摘 対応
    1 セキュリティ 中 印に期限がなく、「後で登録する」の後も 8 時間、password なしで再登録できる 人の決定（議題 3）。15 分の期限
    2 プログラマー・アーキテクト・セキュリティ 中 「続ける」は GET のフォームで、覚えた要求の query が消える POST（/account/authenticator/continue）で受けてサーバーが redirect する。query を保つテスト
    3 プログラマー 中 監査の失敗で全体が戻ることを、どのテストも確かめていない spy で監査を失敗させる統合テスト（TotpReEnrollmentRollbackIntegrationTest）
    4 テスター 中 同時の再登録の待ちを 500 ms で見ていて bcrypt の時間で空振りしうる。先の回復コードが残ることを見ていない pg_stat_activity のロック待ちで確かめ、先の回復コードが使えることを足した
    5 テスター 中 印を消す 2 つの守りのどちらかを外しても通る。画面の 15 分・再送の分岐のテストがない。ほかの端末が生きていることを先に見ていない session の属性の消去、印の単体テスト（RecoveryLoginTest）、印の期限、完了の後の再送、ほかの端末の事前の確かめを足した
    6 アーキテクト 中 文書の「秘密の発行と QR を共用する」が事実と違う（共用はポートと EnrollingUser だけ） 文書を直し、重複の寄せ方を 33c に送った
    7 アーキテクト 低 計画に「利用者の行の占有」などの古い記述が残る 計画を実装に合わせた（議題 2）
    8 プログラマー 低 「後で登録する」が印を確かめない、期限を過ぎた途中の値を GET が使い続ける、AtomicReference<Boolean>、用語集に Superseded がない 直した
    9 テクニカルライター 中・低 「後で登録したまま次のログインでも認証アプリのコードは使えない」が事実と違う、A-02 の 5 分の起点、機種を替える（前のものも使える）人の行がない、付録 B の Q1-1 の見出しと行の順、中断の場面、用語集の認証コード 直した
    10 アーキテクト・プログラマー 低 A-08 の URL の組、HttpSessionRequestCache の一本化、重複の寄せ方、認証の結果に経路、session の ID の値オブジェクト、始めたときの秘密を条件にする 33c に送った（議題 6。Bolt 33c の開始準備で、TOTP の部品の整理は 33d に分けた。Bolt 33d の開始準備で、認証の結果に経路と session の ID の値オブジェクトは → 33e）。始めたときの秘密は、失効が成功する限り後の端末の session が消える。振る舞いが変わる直しなので #49 に送った（Bolt 33c の開始準備の決定 6、2026-10-15、human:kakimomokuri）
    11 セキュリティ 中・低 失効の失敗が警告のログだけ、失敗の監査、覚えた要求の絶対 URL #49（議題 4）

    • 置き換えの仕組み（議題 2）と印の期限（議題 3）

    判断と学び¶

    • 計画の「占有で直列にする」は、同時の 2 つは防げても、順に来る二度押しを防げなかった。条件付きの更新の条件に「読んだ値のまま」を入れると、同時と順の両方を 1 つの仕組みで扱える
    • 再認証なしの経路を受け入れる判断は、「その経路がいつまで有効か」と組で決める。計画の段階では印の期限を確認ポイントに挙げていなかった
    • 変更の影響を受ける既存のテストを探すとき（T-122）、1 つのクラスだけを見て、ロックのテストの回復コードのログインの期待を見落とした。recoveryCode で grep すれば見つかった
    • 変異の確かめで git checkout を使い、まだコミットしていない XML の変更を戻してしまった（控えから戻した）
