    Bolt 25 終了報告 - 追跡の開始と予約サガの成功の経路（US-04、ADR-015、#10）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt25）により、計画の承認から終了報告の前まで、スキーマを除く承認ゲートで止まらずに進めた。止まらなかったゲートごとの判断と、人の判断が要る設計の論点を次に置く。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 計画の verify: 計画は確認ポイントへの回答（2026-10-09）と /goal Bolt25 を承認として進めた。計画の verify（okf_apply.py verify --by human:kakimomokuri）は人の名前で検証を記録する操作のため実行していない Bolt 23b・24 と同じ Bolt 25 計画
    2 スキーマの承認（ステップ 2。T-67 のとおり止めた）: 停止フックの指摘の末尾に y が付いて届いたものを、マイグレーションの承認として受け取って進めた。人の入力として正しかったか確かめてほしい。承認を待つ間、停止フックは同じ指摘を 10 回あまり繰り返したが、承認がないまま進めなかった Bolt 24 の議題 2 と同じ形で、Bolt 24 では人が承認として認めた V20261009130000__create_tracking.sql、afterMigrate__grant_app_user.sql
    3 設計文書・モジュールの境界・新しい注釈・Red／Green・画面のゲート（ステップ 1・3・4・5） どれも計画の確認ポイントの決定（2026-10-09、human:kakimomokuri）と設計文書のとおり。Red を確かめなかったテストは下の「T-39 の記録」に書いた 計画のステップ 1〜5 の結果
    4 計画からの変更（人の判断が要る）: 層の規則の例外を合成ルートにも広げた。確認ポイント 21 の決定は「腐敗防止層から他のコンテキストの interfaces.api を参照してよい」だった。合成ルート（infrastructure.config）が公開 API の bean を腐敗防止層に渡すところで規則が落ちたため、例外の対象に合成ルートを足した（開発レビュー A-3）。代わりの案は、(b) 例外を「呼ぶ側と呼ばれる側の最上位パッケージが異なる」に絞る、(c) 「他のコンテキストの interfaces.api の型をコンストラクタの引数に持つのは腐敗防止層だけ」の見張りの規則を足す 応用の部品（腐敗防止層）は部品探索の対象外なので、合成ルートが組み立てるしかない。見積りの公開 API を使う予約・経路設計の合成ルートも同じ形（quotation.interfaces.api は層の規則の外なので規則に当たらなかった） LayerArchitectureTest、architecture_backend.md「公開 API の置き場所と形」
    5 計画からの変更: 公開 API の実装（インバウンドアダプター）は <コンテキスト>.interfaces.api.internal に置き、部品探索で拾う（画面のコントローラーと同じ）。「アダプターは誰からも型で参照しない」見張りの規則を足した（開発レビュー A-4） 合成ルートは層の規則で interfaces の実装を参照できない。名前付きインターフェースが子のパッケージを含むかに左右されないため architecture_backend.md、LayerArchitectureTest
    6 人の判断が要る（A-1）: 予約サガが失敗・有人確認要（W8）のときに遅れて届いた追跡の開始の結果は、例外にせず NotCompleted(SAGA_NOT_IN_PROGRESS) を返し、状態を変えない形にした。代わりの案は、(b) 有人確認要 → 完了の遷移を業務として認める（遅れて成功した場合） 例外にすると、再配信しても直らない失敗が配信の記録に残り続ける（Bolt 21 の毒入りのメッセージと同じ型）。業務の判断（有人確認要の後に完了にしてよいか）は W8 で有人確認要を作るときに決め直せる BookingSagaCommandService、ADR-015
    7 既知の制約（記録）: Bolt 25 の前に確定した予約は、追跡の listener ができる前に DE-07 の配信を終えているので、追跡の開始が起きない（再配信の対象もない）。デモ環境は再起動のたびに初期状態に戻る（手順書）ので、Bolt 25 の配備の再起動で Bolt 23・24 の予約は残らない。ステージング・本番はまだない（W10）。本番の運用が始まった後に同じことを起こさないよう、W8 で有人確認要を作るときに「予約 ID を指定して追跡の開始を起こし直す管理用の操作」を要るかどうか決める（開発レビューの懸念） 手順書の「再起動すると…開発用の企業と利用者だけになります」 手順書 heroku_demo_setup.md、計画の確認ポイント 19
    7b 人の指示による変更（終了報告の後、2026-10-09）: 「api は interfaces 以下に配置するルールを追加して quotation にも適用する」により、公開 API を <コンテキスト>.interfaces.api 以外に置かない規則（PublicApiArchitectureTest）を足し、見積りの quotation.api を quotation.interfaces.api に移した。見積りの 4 つのアプリケーションサービスは公開 API を実装するのをやめ、アプリケーションやドメインの型で結果を返す。公開 API の型への変換は quotation.interfaces.api.internal のアダプターが担う。既存のサービスのテストは、アダプター越しに同じアサーションで確かめる形に移した 層の規則（アプリケーション層はインターフェース層を参照しない）のため、予約・経路設計と同じ形にした。名前付きインターフェースの名前は api のままなので、予約・経路設計の allowedDependencies は変わらない PublicApiArchitectureTest、quotation.interfaces.api.internal、architecture_backend.md
    8 開発レビューの対応の範囲（下の「開発レビュー」） 正しさ（例外が listener とサービスから漏れる 2 経路）、テストの補強、文言、契約の Javadoc は直した 開発レビュー
    9 #10 は終了報告の承認の後にクローズし、US-04 の AC3・AC5（W6）の Issue を新しく作る 計画の確認ポイント 14 #10

    作ったもの¶

    • tracking モジュール: 追跡記録（TrackingRecord、@CoreConcept）・予定・予定区間・追跡番号（コンテキスト固有）・追跡状態・追跡の予約状態、DE-22 追跡を開始した、tracking スキーマ（tracking_record・scheduled_leg）と MyBatis の実装
    • 追跡の開始: DE-07 の listener が経路設計の公開 API（routing.interfaces.api.RouteVersionLegQuery）から確定した経路版の区間を引いて予定として採用し、追跡記録の保存と同じトランザクションで DE-22 を発行する。DE-22 の listener が予約の公開 API（booking.interfaces.api.TrackingStartNotification）で予約サガを完了にする（別のトランザクション。ADR-014 の形）
    • 冪等: 追跡記録は予約 ID で一意（uk_tracking_record_booking）。予約サガは処理中のときだけ期待版で完了にする。予約の値の写しや区間が規則に合わない DE-07、処理中でない予約サガへの通知は、例外にせず警告のログで終える
    • DE-07 に荷主・荷受人の企業 ID（null 可）。区間は載せない（payload を小さく保つ）
    • S-09 の確定のお知らせから「追跡の開始を待っています。」を外し、S-24 に「追跡の開始: 完了」。処理中のときだけ、自動では変わらないことと開き直すリンクと問い合わせ先を示す
    • 検査: AT-04（マッパーの SQL が自分のスキーマだけを参照する）、「予約・経路設計は追跡に依存しない」、公開 API の形の検査を interfaces.api に、アダプターを誰も型で参照しない、業務のスキーマの GRANT の漏れ

    仮説の結論¶

    # 仮説 結論
    H1 DE-07 に企業 ID だけを足し、区間は経路設計の公開 API で引けば、payload を小さく保ったまま確定した経路版の区間を予定にでき、依存は Unit の DAG のとおりになる 成り立った。DE-07 の JSON は 4,000 文字に収まり、ModularityTest は通った。経路設計の「確定した候補」の探索を経路設計案件の操作にし、DE-05 の listener と公開 API で同じ操作を使うようになった
    H2 追跡記録の予約 ID の一意制約と、処理中のときだけ完了にする操作で、DE-07・DE-22 の再配信でも追跡記録 1 件・予約サガ完了 1 回になる 成り立った。PostgreSQL の統合テストで、配信し直しても追跡記録・予定区間の件数と予約サガの版が変わらないことを確かめた。同時の配信の負けた側は一意制約か楽観ロックの例外のまま戻り、再配信（再起動のとき）で既存の記録を見つけて何もしない

    開発レビュー¶

    プログラマー（テスターの観点を含む）、アーキテクト、インタラクションデザイナー（ユーザー代表の観点を含む）の 3 つの観点で行った。

    # 指摘 重大度 対応
    P-1 / A-2 区間の写しの到着の検査と追跡番号の形の検査が try の外で、listener から例外が漏れる（再起動のたびに同じ失敗を繰り返す） 高 直した（予定・追跡番号の組み立てをまとめて警告のログで終える。テスト 2 件を足し、Red を確かめた）
    P-2 企業 ID の片方だけが null の DE-07 を確かめていない 高 直した（テスト 2 件。今の実装で最初から通った）
    P-3 / A-1 予約サガが失敗・有人確認要のときに、遅れて届いた結果で例外になる 高（A-1）・中（P-3） 直した（SAGA_NOT_IN_PROGRESS。議題 6）
    U-1 / U-2 案内が「自動で表示します」と「更新してください」を混ぜている。処理中のまま終わらないときの出口がない 高 直した（「この画面は自動では変わりません。…しばらくしても処理中のままなら、システム管理者にお問い合わせください。」）
    P-4 再配信の確かめで @ApplicationModuleListener の bean を直接呼ぶと、非同期の代理で別スレッドになりうる 中 直した（代理を外した本体を同期で呼ぶ）
    P-5 同時の通知の負けた側の例外の単体テストがない 中 直した（今の実装で最初から通った）
    A-3 層の規則の例外が「他のコンテキストの」「腐敗防止層に渡すだけ」を表していない 中 人に諮る（議題 4）
    A-4 interfaces.api.internal が名前付きインターフェースの外であることを確かめていない 中 直した（アダプターは誰も型で参照しない規則）
    A-5 / P-8 AT-04 の検査が拾えない形（カンマ結合、USING、修飾のない表名など） 中・低 既知の限界として test_strategy.md の AT-04 の行に書いた
    U-3 / U-4 更新をブラウザーの機能だけに頼っている。案内が欄と結び付いていない 中 直した（「CT… の予約の詳細を開き直す」のリンク、aria-describedby）
    U-5 状態の変化を live region で伝えない意図が書かれていない 中 直した（ui_design.md の S-24 の行）
    P-9 / A-9 NULL 可の列と集約の必須が食い違い、NULL の行で原因の分からない例外になる 低 直した（原因の分かる例外。テストで Red を確かめた）。列を NOT NULL にするかは主要実績を作る Bolt 26 で決める
    A-6 / A-7 通知の追跡番号・開始時刻を使っていないのに「照合に使う」と書いた。楽観ロックの例外が契約に書かれていない 低 直した（Javadoc と data_model.md の完了の時刻）
    A-8 DE-07 の null 可の属性に終わりの条件がない 低 直した（domain_model.md の DE-07 の行）
    P-6 / P-7 / P-10〜P-12 メモリのリポジトリの例外の型、警告のログの二重、complete() の版の名前、画面の層の待ちのループ、listener がアプリケーションサービスを持たない 低 後に回す（P-12 は主要実績の取り込みが入る Bolt 26 で判断）
    U-6 / U-7 「処理中（追跡の開始を待っています）」の冗長、「完了」の後の次の行動 低 後に回す（U-6 は Bolt 25b、U-7 は荷主の照会の Bolt 27）
    A-10 受入の配線が本番の合成ルートを写している 低 後に回す（本番の配線は統合テストが確かめている）

    T-39 の記録（Red を確かめなかったテスト）¶

    • Keep
    • 開始準備の 2 つの検証で、2 つのコンテキストを 1 つのトランザクションで更新する形と、区間を DE-07 に載せる形の問題を、着手の前に見つけた

    • Problem

    • 画面の層のシナリオの正規表現に Pattern.quote を使い、Playwright が JavaScript の正規表現に変えるため一致しなかった
    • 組み立ての例外の範囲（try の外の検査）を、開発レビューまで見落とした
    • Try
    • T-74: listener の「再配信で直らない欠けは警告のログで終える」を書くときは、イベントの値から値オブジェクトを作る呼び出しをすべて同じ try に入れ、値オブジェクトごとの不正な値のテストを 1 件ずつ書く（AI、次の Bolt から）

    • T-76: 状態の列挙の値ごとに、遅れて届いたイベントや通知で例外にならないかを表にする（T-57 の拡張。AI、次の Bolt から）
