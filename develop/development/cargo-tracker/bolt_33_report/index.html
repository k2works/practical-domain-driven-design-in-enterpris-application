    Bolt 33 終了報告 - 通知モジュールの新設と password の再設定の依頼（US-18 AC8 の前半）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-15 に、確認ポイント 1〜19 を推奨どおりとして承認を受けた（00d4533）。/goal Bolt33 の下で、ステップ 1〜6 の承認ゲートで止まらずに進めた。ただし、開発レビューで人の判断が要る指摘が 4 つ出たので、ステップ 6 で止めて諮った（議題 3）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 止まらなかった承認ゲート: ステップ 1（設計文書と ADR-017）、2（通知モジュール。モジュールの境界・スキーマ・外部連携）、3（トークンと依頼。セキュリティ・スキーマ）、4（画面。画面・セキュリティ）、5（マニュアル） 各ステップの先頭に表を置き、単体テスト・統合テストの Red を確かめてから実装した。変異の確かめは 3 つ: 利用者の行の占有を外すと同時の発行のテストが、1 分の判定を外すと繰り返しのテストが、ハンドラーを同期のリスナーにすると応答の時間のテストが落ちた（T-112・T-117） 「ステップの結果」「指標」
    2 計画からの変更: (a) 送信のポートを application.internal.outboundservices から domain.model.aggregates に移した（ステップ 2 で層の規則に当たった。人に諮らずに動かした。議題 3 の (1) で決め直した）。(b) リンクの path を /password-reset/{トークン} に決めた（33a の A-06 はこれに合わせる）。(c) CSRF のトークンのない送信は計画の「403」でなく、既存の扱いのとおり A-03 に移る（誤ったトークンは 403）。(d) Mailpit をテストの共通の組み立てから分け、要るテストだけで起動する (a) 技術のポートはドメインに置く前例（RecoveryCodeHasher など）に合わせた。規則の例外は足していない。(b) A-05 と同じ URL の下に置き、公開の URL の範囲を /password-reset/* の 1 段にとどめる。(c) どちらも依頼を処理しないことを監査で確かめた。(d) 開発レビューの指摘（全統合テストのコンテキストでコンテナが起動していた） 計画の更新履歴、ADR-017
    3 開発レビューで人が決めたこと（2026-10-15、human:kakimomokuri）: (1) 外部の技術のポートはドメインに置く前例を規則にする（CLAUDE.md のガードレールに足した）。(2) SMTP の送信はハンドラーのトランザクションと利用者の行の占有の中のまま、接続・読み・書きのタイムアウト（各 5 秒）を入れ、保証を at-least-once と ADR-017 に書く。(3) 33a まで仮の A-06 を公開する（トークンを読まず session に覚えず、「準備中」と Referrer-Policy: no-referrer だけ）。(4) 応答時間の差・発信元ごとの抑止・爆撃の 1 日の上限・デモのログのリンクは W10 に送る (2) 送った後、コミットの前に落ちると、届いたリンクは使えず、再配信で 2 通目が送られることがある（まれ。利用者は新しいリンクを使える）。(3) 公開しないままだと、未認証でリンクを開いたときにトークン付きの URL が session の表に保存され、平文を残さない SEC-08 に反した ADR-017 の決定 3・4・6 と既知の課題、CLAUDE.md
    4 W10 に送ったもの: #49 を作った（応答時間の差、発信元ごとの抑止と監査の発信元、爆撃の上限、SES と送信元の認証、保持の期間、再試行とバウンス）。#48 に、dev のメールの守りも確認の範囲に含めるようコメントした T-89（後に回したものは Issue にする） #48・#49
    5 CI の MkDocs の配備の失敗（人の指摘）: ER 図の対象のスキーマの一覧（ops/scripts/design_docs.js）に notification がなく、schemaspy:generate が止めていた（c7afe12 から 88ca89c までの 3 回）。一覧に足し（e935546）、配備が成功したことを確かめた 計画が挙げたスキーマの一覧は 3 か所（権限・マッパー・コメント）で、4 か所目の ER 図の対象を知らなかった。data_model.md の記述を 4 か所に直した（Try T-126） data_model.md の notification の表
    6 デモ環境の Config Vars（人の作業）: deploy:demo:setup の Config Vars に CARGOTRACKER_PUBLICBASEURL を足した。Heroku への反映は heroku login が要るので、人が npx gulp deploy:demo:setup を実行してほしい。反映するまで、デモ環境のログに出るリンクは http://localhost:8080 を指す 外部の環境への操作で、ログインが対話のため heroku_demo_setup.md の「2. 初回のセットアップ」
    7 マニュアルの公開: 2.6 は依頼までの手順と、「リンクを開くと『この画面は準備中です』と示される」ことを書いて公開した（33a で A-06 の手順に替える） 仮の A-06 を公開したので、計画の「33a と同じ日に公開する」前提は要らなくなった マニュアル 2.6、付録 B の Q1-6

    仮説の結論¶

    # 仮説 結論
    H1 公開 API と ACL で、通知の部品を identity に持たずに、層とモジュールの規則を例外なしで守れる 支持（ただし送信のポートは計画の置き場所でなくドメインに置いた。議題 2 の (a)）。アーキテクチャのテストは例外なしで緑。Mailpit にメールが届く
    H2 依頼の応答は判定と監査とイベントだけにし、発行と送信をモジュールのイベントのハンドラーに移せば、応答がそろい、待たず、発行記録に平文が残らない 支持。送信を 3 秒遅らせても応答は先に返る（同期のリスナーにすると落ちる）。発行記録・通知の記録・表に平文がない。登録の有無で数 ms の差は残る（#49）

    開発レビュー¶

    プログラマー、テスター、アーキテクト、セキュリティ、テクニカルライター（インタラクションデザイナーを含む）の 5 つの観点で行った（git diff a3ae011..f49fd55）。高の指摘は 7 件で、すべて直したか人が決めた。

    # 観点 重要度 指摘 対応
    1 プログラマー・アーキテクト・セキュリティ 高 SMTP にタイムアウトがなく、送信がトランザクションと利用者の行の占有の中で無期限に待ちうる。送った後にコミットが落ちると 2 通目が出る 人の決定（議題 3 の (2)）。タイムアウト 5 秒、at-least-once を ADR-017 と Javadoc に書いた。結果を書けなくても例外にしない
    2 アーキテクト 高 層の規則に当たってポートを人に諮らずに動かした（CLAUDE.md のガードレールに反する） 人の決定（議題 3 の (1)）。前例を規則にし、CLAUDE.md に足した
    3 セキュリティ 高 33a まで、リンクを開くとトークン付きの URL が session の表に保存される 人の決定（議題 3 の (3)）。仮の A-06 を公開した。テストで session の Cookie が作られないことを確かめた
    4 テスター 高 メールはハンドラーのコミットの前に届くので、メールを待った直後に表を読むと不定に落ちる 表を読む前に発行記録の完了を待つようにした（test_strategy にも書いた）
    5 テスター 高 否定の確かめが非同期のハンドラーより先に走り空振りする。サービスの判定を外しても落ちない。ハンドラーの再確認を確かめていない 否定の依頼を先に出し、最後の有効な依頼が届いてから確かめる順にした。止めた利用者の DE-23 が 0 件であることでサービスの判定を、ハンドラーを直接呼ぶテストで再確認を確かめた。画面の層のシナリオも同じ順にした
    6 セキュリティ・プログラマー 中 失敗の理由とログに、SMTP の応答の宛先のアドレスやトークンが残りうる。ログが 2 か所 理由からリンク・トークン・メールアドレスを伏せ、ログは通知の側に寄せた
    7 テスター 中 Mailpit が全統合テストのコンテキストで起動する。応答の時間のテストが最初の要求の準備で遅れうる。ハンドラーの経路の送信の失敗、使ったトークンを無効にしないことを確かめていない MailpitConfiguration に分けた。計る前に GET で温めた。2 つのテストを足した
    8 テクニカルライター 中 1 分の起点（前の依頼でなく前の発行）、「もう一度依頼すると前のリンクが使えなくなる」（1 分以内では成り立たない）、メールの「認証アプリのコード」（回復コードの利用者に合わない）が事実とずれる。A-01 の知らせが長い。A-05 の誤りに気づきにくい。マニュアルの手順と本文の説明が事実とずれる 文言を直した（UI 設計・画面・メール・マニュアル）。知らせを段落と箇条書きにし、A-05 の誤りで title に「エラー: 」を付けて欄にフォーカスを置く
    9 セキュリティ 中・低 応答時間の差、発信元ごとの抑止、爆撃の上限、デモのログのリンク 人の決定（議題 3 の (4)）。#49
    10 プログラマー・セキュリティ 低 公開の base URL が userinfo とループバック（127.0.0.1・::1）を拒まない。監査の工場メソッドの Optional の引数。リンクの path の 2 か所の重複。理由の切り詰めがサロゲートの途中で切れる 拒むようにした。工場メソッドを受け付けた・受け付けなかったの 2 つに分けた。path は合成ルートからコントローラーの定数で渡す。code point で切る
    11 アーキテクト 中・要判断 W9 の宛先のモデル（利用者でない宛先、recipient_user_id の NOT NULL と UK、種類ごとの公開 API か汎用か） ADR-017 の既知の課題に書き、W9 の開始準備で決める

    計画からの変更¶

    • 送信のポートの置き場所（議題 2 の (a)、議題 3 の (1)）

    • 依頼のサービスは UserRepository.findByEmail と CompanyRepository で読み、同じ User#authenticationRejection で判定した

    判断と学び¶

    • 層の規則に当たったときに置き場所を動かすのは、前例があっても設計の判断で、/goal の下でも止めて諮る。前例を規則にするかは人が決める
    • 非同期のハンドラーが外部に送るものは、DB の確定より先に外から見える。テストは送られたものを見た後でも、DB を読む前にハンドラーの完了を待つ
    • 新しいスキーマを足すときの一覧は、計画の 3 か所のほかに ER 図の対象があった。「スキーマの名前を並べた一覧」を grep で探してから足す

    既知の課題（後に持ち込む）¶

    • 送信は at-least-once（送った後、コミットの前に落ちると 2 通目が出ることがある。ADR-017）
