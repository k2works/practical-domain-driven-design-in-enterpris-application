    Bolt 32f 終了報告 - 失効の時の入力の保持（ACC-06）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-14 に、確認ポイント 1〜13 を推奨どおりとして承認を受けた（de7d472）。/goal Bolt32f の下で、ステップ 1〜5 の承認ゲートで止まらずに進めた。止めて諮る条件（5.5 時間を超える見込み、送信が拒まれた場合の案内が書けない）には当たらなかった。支援技術の手動確認（ステップ 5 の承認ゲート）は、2026-10-15 の終了報告の承認とあわせて人が済ませた（議題 6）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 止まらなかった承認ゲート: ステップ 1（設計文書）、2（Red）、3（Green。画面・セキュリティ）、4（マニュアル）、5（レビューと報告） Red（足したシナリオと期待を直したシナリオの 16 件が、狙いの理由で落ちる）を確かめてから Green にした。T-120 に従い check を先に流した。送信の前に写す処理を外す変異で送信の 2 シナリオが落ちることも確かめた（T-112） 「ステップの結果」「指標」
    2 計画からの変更（セキュリティ・画面）: (a) data-user は利用者の ID（UUID）そのものでなく、一方向の値（SessionTimerAdvice.ownerKey。SHA-256 の先頭 16 文字）にした。(b) 知らせの領域は role="status" でなく、role のない aria-live="polite" にした (a) 画面の HTML に UUID を出さない既存の確かめ（BR-07）が落ちた。同じ利用者かどうかが分かれば足りる。塩のない決定的な値なので、秘匿ではなく仮名化であることを ADR-012 に書いた。(b) 既存の画面の getByRole(STATUS) が 2 つに当たって落ちた。画面の結果の知らせと区別するため ADR-012 の決定 3、計画の変更の記録
    3 開発レビューで変えた設計（セキュリティ・データ）: 「拒まれた」印を付ける画面を、公開のレイアウトの一律から画面ごとの明示（main の data-session-input="rejected"）に変えた。対象は A-03・413・CSRF の拒否の 403 で、A-01 と認可の 403 には付けない。403 の画面は 1 つなので、SecurityConfiguration の AccessDeniedHandler が CsrfException のときだけ request に印を置く アーキテクトの指摘。一律に付けると次の問題が起きる。認可の 403 の後に「ログアウトの前に入力していた内容があります」が出る。将来「届いた送信の結果が公開の画面」の業務ができると、届いた送信を戻して二重の送信を招く。レイアウトを共有する画面が増えるたびに意味が変わる architecture_frontend.md の「公開の画面での印」、ADR-012、SecurityConfiguration.markingCsrfRejection
    4 文言の決定（開発レビュー）: 案内は「送信できなかった入力があります。」にした（理由を言わない）。リンクとボタンは「入力していた画面を開く」「入力していた内容を消す」にした。戻した知らせは「前に入力していた内容を戻しました。…」にした。利用者が自分で写すことは「書き写す」と言い、「控える」はシステムの写しにだけ使う テクニカルライターとインタラクションデザイナーの指摘。以前の文言は、CSRF の 403・413・session が生きたままの開き直しで事実と合わなかった。「画面を開く」「消す」は、リンクとボタンの一覧で文脈なしに意味が取れない。「控えてから」は同じ画面で 2 つの意味になる ui_design の「入力の控え（Bolt 32f）」、マニュアル 2.4・2.5・付録 B
    5 受け入れた既知の課題 次の 3 つは、どれも知らせの「内容を確かめてから送信してください」と、マニュアルの「一覧で確かめる」で補う。
    (a) 8 時間のぎわの二重の送信（確認ポイント 7。確かめるシナリオはない）
    (b) 戻した入力による上書き（版を写さない。開発レビューのアーキテクトの指摘）
    (c) 期限の到来の後に入力した分は控えに写らない（pagehide では写さない。ログアウトの送信と区別する必要があるため）    		 ADR-012、マニュアル 2.5
    6 人による支援技術の手動確認（2026-10-15 に済み）: NVDA＋Chrome か VoiceOver＋Safari で、下の「支援技術の手動確認の手順」を行ってほしい 知らせを読ませる時機（load の 500 ms 後）、消した後のフォーカスと 2 回の読み上げは、自動の axe では確かめられない 下の手順
    7 取消しの決定の変更（開始準備で決めた）: 32e の「止められた利用者には保持しない」を、「控えはそのタブに残るが、戻るのは同じ利用者がログインし直せたときだけ」に変えた ブラウザでは取消しの A-03 と失効の A-03 を見分けられない。止めたことは画面に示さない ADR-012、release_plan

    仮説の結論¶

    # 仮説 結論
    H1 戻り先のある画面で、期限の到来・開き直し・送信の前に変えた欄を sessionStorage に写せば、同じ利用者が同じ画面に戻ったときに戻せる 支持。次の場合に、出発地と貨物種別が戻ることを画面の層で確かめた。
    ・期限の到来の後にサーバーの session も切れた場合（A-03 を経てログインし直す）
    ・session が生きたまま開き直した場合
    ・延長が失効で失敗した後に A-01 を経る場合
    ・7 時間 59 分たった場合
    H2 送信の次の画面で拒まれたかどうかが分かれば、サーバーに問い合わせずに、届いた送信を戻さず、拒まれた送信だけ案内できる 条件付きで支持。session の失効と CSRF の 403 で拒まれた送信は案内から戻り、届いた送信は戻らない（同じ画面に戻る場合も含む）。ただし、印を付ける画面を明示しないと誤判定する（議題 3）。8 時間のぎわは見分けられない（議題 5 の (a)）

    開発レビュー¶

    プログラマー、アーキテクト、テスター、テクニカルライター、インタラクションデザイナーの 5 つの観点で行った（git diff 641b575..8a0537d）。高の指摘は 7 件（テクニカルライター 3、テスター 3、インタラクションデザイナー 1）で、すべて直した。

    # 観点 重要度 指摘 対応
    1 テクニカルライター 高 8 時間のぎわの二重の送信の注意がマニュアルにない 2.5 と付録 B に「一覧で確かめてから送信」を書いた
    2 テクニカルライター 高 「控える」が、システムの写しと利用者の書き写しの 2 つの意味になっている 利用者の行為を「書き写す」にし、用語の規則に足した
    3 テクニカルライター 高 CSRF の 403・413 でも「ログアウトの前に」と出て、事実と合わない 「送信できなかった入力があります。」にし、付録 B の原因の欄を直した
    4 テスター 高 「送信が届いたら控えが残らない」は、規則を外しても落ちない 送信が届いて同じ画面に戻る場合のシナリオを足し、変異で落ちることを確かめた
    5 テスター 高 CSRF のトークンを写さない確かめが空振りしている 値を変えてから確かめる形にした。同値の変異であることが分かったので、指標とテスト戦略に書いた
    6 テスター 高 案内の「消す」を押すシナリオがない 足した（消した後に開いても戻らない）
    7 インタラクションデザイナー 高 「戻した入力を消す」の後に、貨物種別の案内と提出の aria-disabled が残る 戻した欄に change を出し、貨物種別のシナリオで確かめた
    8 アーキテクト 中 公開のレイアウトで一律に印を付ける推論は広すぎる 画面ごとの明示にした（議題 3）
    9 アーキテクト 中 sameOriginPath が // と /\ をサーバーの firewall に頼って通している 2 つのファイルで拒むようにした
    10 アーキテクト・テスター 中 公開の画面で 8 時間を確かめず、A-03 の一文が戻らない控えでも出る 公開の画面でも 8 時間を過ぎた控えを捨て、戻せる見込みがあるときだけ一文を出す。一文が出ないシナリオを足した
    11 プログラマー 中 形の合わない控えで初期化が壊れる。拒まれた控えが、ほかの画面の送信で上書きされる 形を確かめ、聞き手を戻す前に置き、戻す処理を try で囲んだ。拒まれた控えは上書きしない
    12 プログラマー・アーキテクト 中 延長の失敗の文言と期限の到来の文言で、選ぶ条件が違う 1 つの条件（戻り先と利用者の鍵がある）にした
    13 インタラクションデザイナー 中 読み込みと同時の live region の更新が落ちやすい。「ログアウトの前の」が事実と合わない。段階入力でどこに戻ったか分からない。期限の到来の案内が「ログインし直した後」を前提にしている 知らせを load の 500 ms 後に入れた。理由を言わない文言にした。「すべての段階に戻しました。…」を足した。「開いた画面に戻します（ログインを求められたら…）」にした
    14 テスター 中 控えが残っていないことを 1 回だけ読む。否定の確かめが、領域がなくても通る 待って確かめるようにした。否定の前に領域があることを確かめるようにした
    15 テクニカルライター 中 ログアウトで消えるのはヘッダーのボタンでだけ、そのタブだけ。「8 時間で消える」が不正確。描き直した画面からの送信の例外。取消しの利用者 マニュアル 2.1・2.4・2.5 を直した
    16 アーキテクト 低 利用者の鍵は仮名化である。イベントの契約。捨てる時の列挙が 3 つの文書で違う ADR-012・architecture_frontend・ui_design をそろえた。利用者の鍵の単体テストを足した
    17 各観点 低 ボタンの名前、method・action の DOM clobbering、消した後の 2 回の読み上げ、/login?logout、テストの名前とコメント 直した

    判断と学び¶

    • 「どの画面を経たか」をレイアウトという構造上の位置で暗に決めると、レイアウトを共有する画面（認可の 403）の意味まで変わる。印は、意味を持つ画面に明示して置く
    • 「変えた欄だけを写す」は、hidden の欄では初期の値が値に追随するので、許す一覧と 2 重に効く。変異の確かめで、テストが見分けられないことが分かった
    • 知らせの文言は、出る場面をすべて並べてから決める。最初の「ログアウトの前の」は、session が生きたままの開き直しと CSRF の 403 で事実と合わなかった

    ふりかえり（KPT）¶

    • Keep
    • 開始準備で文言の場面（送信の後、写す時、捨てる時、リンクの語）を人に決めてもらったので、実装の途中で止まらなかった
    • 5 つの観点のレビューで、構造の推論の広さ（印）と支援技術の時機を報告の前に直した
    • 変異の確かめで、空振りするテストと同値の変異を見分けた
    • Problem
    • 知らせの文言を、主な場面（ログアウト）だけで決めた
    • 印を公開のレイアウトに一律に置いた
    • Try
    • T-123: 知らせ・案内の文言を決める前に、それが出る場面（原因の違い、session の生死）を表にし、すべての場面で事実と合うかを確かめる
    • T-124: 「この画面を経た」で振る舞いを変えるときは、レイアウトでなく画面に印を明示する。印の有無の対をテストにする

    既知の課題（後に持ち込む）¶

    • 8 時間のぎわの二重の送信（受け入れた。確かめるシナリオはない）
    • 戻した入力による上書き（版を写さない。受け入れた）
    • 期限の到来の後に入力した分は、控えに写らない（pagehide では写さない）
    • JS の単体の層がなく、入力の控えの規則は E2E だけで確かめている。radio・checkbox は貨物種別で確かめた。select・同じ名前の欄・GET のフォームを写さないこと・8 時間ちょうどの境界は確かめていない。画面の層のテストの時間が問題になったら、page.setContent で固定の HTML を置く層を作る
    • sameOriginPath が 2 つのファイルに重複している（両方のコメントで指し合う。ビルドの仕組みを入れるときにまとめる）
    • 社内の画面のフォームで写して戻す道は、画面の層で通っていない（同じ部品を通る）
    • 利用者の鍵は仮名化（秘匿が要るなら HMAC）
    • 共用のパソコンで、閉じたタブの復元で控えが戻ること（PRV-01 は「提案」のまま。管理・コンプライアンス責任者の確認を待つ）
    • 32e から持ち越した、要求の属性の名前の 3 組の重複（33b）

    支援技術の手動確認の手順（議題 6。人が行う）¶

    準備: dev で起動し（./gradlew bootRun）、荷主（dev のアカウント）でログインする。期限の到来を待つ間は、ブラウザの開発者ツールで時計を進めるか、30 分待つ。NVDA＋Chrome または VoiceOver＋Safari で、各項目を 2〜3 回試す。

    1. 戻したことの知らせ: C-03 で段階 1〜2 に値を入れる（貨物種別は「一般」以外）。期限の到来の案内が alert として読まれることを確かめてから、「画面を開き直す」を押す。開き直した直後に、操作をしなくても「前に入力していた内容を戻しました。…すべての段階に戻しました。…」が読まれるか。読み込みの読み上げと重なって落ちないか
    2. フォーカスの位置: 1. の後、フォーカスが知らせに奪われていないか。Tab の順は「ヘッダー → ナビ → 戻した入力を消す → main の先頭」か。閲覧モードで上から読むと、知らせが main の前に読まれるか
    3. 戻した値の追随: 段階の一覧で段階 2 と確認の段階へ移り、戻した値が欄と要約にあるか。貨物種別の案内が読まれ、提出が「使用不可」と読まれるか
    4. 「戻した入力を消す」: Enter で押す。フォーカスが知らせの領域へ移り、「戻した入力を消しました。」が 1 回だけ読まれるか。フォーカスの枠が見えるか。貨物種別の案内が消え、提出が使えるようになるか
    5. 送信が拒まれた場合の案内: 送信の前に別のタブでログアウトしてログインし直す（CSRF のトークンが替わる）。そのうえで C-03 を送信すると 403 になる。次に見積依頼の一覧を開き、「送信できなかった入力があります。」が読まれるかを確かめる。リンクの一覧（NVDA の Insert+F7、VoiceOver のローター）で、「入力していた画面を開く」「入力していた内容を消す」が単独で意味を成すかも確かめる
    6. 「入力していた内容を消す」: 5. の案内で押す。フォーカスが領域へ移り、「入力していた内容を消しました。」が読まれるか。次の Tab で main の先頭へ進むか
    7. 拡大: 拡大鏡 200〜400% と幅 320px で、知らせと期限の到来の案内（上端に留まる）がフォーカスを隠さないか（2.4.11）

    結果は「済み・問題なし」か「問題あり（項目と内容）」で返してほしい。問題があれば、この Bolt で直すか後の Bolt に送るかを諮る。
