    Bolt ゴール¶

    デモ環境と dev で、割り当てた経路が再設計要になった見積りを開いて、Bolt 37e3 で直した画面の理由と次の行動を見られるようにする。業務担当者がマニュアルで、再設計要の見積りの扱い（荷主は担当営業に相談、営業は本予約に進めず期限内は再見積りもできない、経路設計者は確定し直せない）を読めるようにする。この Bolt を終えると、W7 の評価の入口をつなぐ Bolt を始められる。

    確かめたい仮説¶

    # 仮説 この Bolt で分かること
    H1 見本は 0908 の前例の形で、経路版を再設計要の記録で入れ、見積りに印を付ければ、画面の判定は Bolt 37e3 のまま動く（本体のコードを変えない） DevSampleDataSmokeTest、dev（H2）での目視
    H2 キャプチャとデモは、Bolt 37e3 の画面の層のステップ（印を付ける手段）をそのまま使える manualScreenshots、demoVideo

    開始準備で確かめたこと¶

    • 開発データの前例（src/main/resources/db/dev-data/V20261020150900__seed_dev_sample_expired_after_approval.sql）: 見積りの側（輸送要求・版・審査・見積り・料金明細・割り当てた区間・identity.kpi_observation・業務番号の採番）と経路設計の側（案件・経路版・候補・候補の区間・確定・案件番号の採番）を、起動した日の 0 時からの相対の日時で入れる。イベントの発行記録は入れない。ID は 00000000-…-0009NN。最初の区間の出発は起動した日から 5 日後。この前例は routing_case.confirmed_route_version_no を入れている（INSERT :51・54、UPDATE :82-84）が、列は V20261022100000 で消えたので写さない。新しいファイルのバージョンは最新のマイグレーション V20261023100000 より後にする
    • 状態と制約: 輸送要求は荷主承認待ち AWAITING_APPROVAL（見本 1）・予約待ち READY_TO_BOOK（見本 2）、見積りは AWAITING_SHIPPER_APPROVAL・APPROVED（V20261007130000:17-22、V20261008100000:19-28）。経路版が REDESIGN_REQUIRED なら、確定の記録の 4 列（selected_candidate_no・判断根拠・承認者・承認時刻）と redesign_required_at・redesign_reasons（区分を空白で区切る）が要る（V20261022100000:10-16）。見積りの route_redesign_required_at は routing_case_number が要る（V20261023100000）
    • 採番と ID: 業務番号の採番は 908、案件番号は 905 まで。0909・0910、0906・0907 と ID の 909・910・919・920・939・940・946・947 は空いている
    • 見本の検査（DevSampleDataSmokeTest）: 0908 の検査の形（状態と版、時刻の順、荷主に見える最新、判定）と KPI の検査（:239-245）。見本を足すと既存の期待値（案件一覧の件数 hasSize(5) と中身、予約の確定待ちの並び containsExactly(908, 906, 907)、番号の後、Javadoc）が変わる。予約の確定待ちは有効期限の順（ORDER BY expires_at, request_number）
