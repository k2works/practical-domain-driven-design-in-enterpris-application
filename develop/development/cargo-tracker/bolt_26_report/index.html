    Bolt 26 終了報告 - 追跡管理者の入口（S-11 追跡一覧・S-12 追跡の詳細の最小の表示）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画の初版の報告の後に、人の指示（/goal Bolt26）で、計画を推奨のとおりに進め、承認ゲートで止まらずに進めた。計画の人の検証（verify）は、この報告の承認のときに行う。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 計画の確認ポイント 1〜15 の決定（すべて推奨のとおりで進めた）。とくに 1（Bolt 26 を 26 と 26b に分ける）、12（tracking から platform :: web への依存）、15（S-12 の予定区間を順序付きのリストにする） 計画の確認ポイントの表の推奨と理由。開始準備の 2 つの検証の指摘を反映した後の案 Bolt 26 計画 の確認ポイント
    2 認可のゲート（ステップ 1。CLAUDE.md の「確認必須」のセキュリティ）を事後に承認してほしい。/staff/tracking-records/** は追跡管理者だけ、追跡管理者はほかの役割の画面を開けない 範囲は確認ポイント 4 の推奨のとおりで、経路設計者（Bolt 17）と同じ形。役割ごとの 403 とナビの表示をセキュリティの統合テストで確かめた。開発レビューで「確認必須のゲートを AI の判断で通過したので、事後の承認を明示して受けること」と指摘された（プロセス・高） SecurityConfiguration、AuthenticationSecurityIntegrationTest
    3 モジュールの境界のゲート（ステップ 3）: tracking の allowedDependencies に platform :: web を足した 予約・経路設計と同じ形で、tracking.interfaces.web からだけ使う。ModularityTest・ArchUnit が通った tracking/package-info.java
    4 追跡状態の画面の表示名（確認ポイント 6。業務責任者の確認）。予約確定・集荷予定・集荷済み・出発地搬入済み・輸送中・積替え中・目的地到着・引渡し可能・引渡し済み・確認中。開発レビュー（ユーザー代表の観点）からの確認: (a) 追跡の「予約確定」と予約の状態「確定済み」（S-24）が近く、混同しないか、(b) 「目的地到着」と「引渡し可能」の違い（通関等の手続き中か）が荷主に伝わるか（UI 設計の C-10 は「目的地到着（通関等の手続き中）」と補う） ドメインモデルの候補の名前のまま出した。荷主の照会（Bolt 27）も同じ名前を使う予定 TrackingRecordViews、domain_model.md の追跡状態
    5 画面・Red／Green（照会）・開発レビューの判断のゲート（ステップ 2〜5） 画面の構成と文言、照会の置き場所と引き方は計画の S-11・S-12 の表と確認ポイント 9 のとおり 計画のステップ 2〜5 の結果
    6 計画からの変更: (a) S-12 の戻るリンクを「追跡一覧へ戻る」から「追跡一覧」にした（Bolt 25b の U-2 にそろえる）、(b) 追跡状態の表示名を switch から表（EnumMap）にした（循環的複雑度）、(c) S-11 の空の文言を「追跡記録はまだありません。営業担当者が本予約を確定すると、追跡が始まった貨物がここに出ます。」にした（レビュー U-2）、(d) 予定区間の表記の区切りを全角の空白から読点にした（SonarQube の S2479） 前例とレビューの指摘にそろえた 計画のステップ 3・5 の結果
    7 記録の確かめ方: 画面の層のテストの結果の XML は feature ごとに 2 つあり、片方は飛ばした扱いの複製（69 件）。途中で「全体が流れていなかった」と誤って読んだが、実行時間のある方で 69 本とも流れて失敗 0 だった。環境変数 CUCUMBER_FILTER_TAGS での絞り込みは効いておらず、毎回全体が流れていた（ステップ 2 の Red も全体の中で新しい 2 本だけが落ちたもの） XML の中身（実行時間と飛ばした扱い）を見て確かめた 計画のステップ 2・4・5 の結果

    仮説の結論¶

    # 仮説 結論
    H1 追跡一覧は追跡記録の要約の 1 本の SELECT で引け、N+1 にならない 成り立った。照会のサービスの単体テストで、追跡記録が 3 件でも要約の照会が 1 回、詳細の照会が 0 回であることを確かめた。マッパーの一覧の select は 1 つ

    開発レビュー¶

    プログラマー（テスター・アーキテクトの観点を含む）とインタラクションデザイナー（ユーザー代表の観点を含む）の 2 つの観点で行った（Bolt 25b と同じ）。マージの前に直すべき欠陥はなかった。

    # 指摘 重大度 対応
    懸念 確認必須の認可のゲートを AI の判断で通過した 高（プロセス） 人に諮る（議題 2）
    P-1 表示名を表にしたことで、追跡状態に値を足したときの抜けを拾えない 中 直した（すべての値の表示名を確かめるテスト、表にない値は例外）
    P-2 照合順序のテストが英字どうしの比較だけ 中 直した（数字と英字が分かれる追跡番号を足した。最初から通った）
    P-3 ナビの表示のテストに KPI 計測記録がない 中 直した
    U-1 予定区間の ol の list-unstyled でリストの意味が落ちるおそれ、S-06 と形が違う 中 直した（既定の形にした）
    U-2 空の状態に次に何が起きるかの案内がない、「追跡中」と「追跡記録」の用語が分かれる 中 直した
    U-3 一覧の到着の列が当初の予定だけ 中 後に回す（実績で見込みが動く Bolt 26b で決める）
    U-4 「→」がスクリーンリーダーで「右矢印」と読まれる 中 後に回す（S-06 と共通の決まりにする。Bolt 26b）
    P-5 追跡記録の 2 つの select の列の重複 低 直した（<sql> と <include>）
    P-9 Matcher の完全修飾名 低 直した
