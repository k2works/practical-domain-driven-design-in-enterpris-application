    Bolt 35c 終了報告 - 承認の後に失効した見積りの再見積りを社内の画面から操作する（D-85。S-02・S-04）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-19 に承認を受けた（1c37fef0c）。承認ゲートは計画と終了報告なので、ステップ 1〜7 は止めずに進めた。打ち切り（ステップ 4 の終わりで 3.5 時間、経路方針をサーバーで入れる形が検証と合わない、読み取りモデルの変更がスキーマの変更を要する）には当たらなかった。スキーマは変えていない（読み取りモデルの SQL だけ）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 開発レビューの後に人が決めたこと（2026-10-20、human:kakimomokuri）: (a) 再見積りできるかの判定を照会のサービスからドメインの規則 RequotePolicy に移す（開始準備の決定 (6) を改めた）。(b) 提示の前に失効した承認待ちの行のリンクを「… を再見積りする」にする。(c) 提示した見積りが DE-24 の受け取りの前に一覧から消える穴を 35c で直す（経路設計中・荷主承認待ちの表の SQL に、輸送要求が予約待ちで見積りが荷主承認待ちの行を足す） 指摘の表の 1・5・6 開発レビューの指摘と扱い
    2 計画からの変更（人に諮らずに変えた）: (a) AwaitingBookingSummary の不変条件に「状態は承認済みか承認待ち」を足し、controller の枝を承認待ちで分けた。(b) 判定の順から「見つからない」を外し、呼び手が先に見る形にした（規則は 2 つの集約と判定時刻を受け取る）。(c) S-02 のリンクは規則を通さず、見積りの状態と有効期限だけで出す（読み取りモデルで集約を組み立てない。開いた S-04 の GET が規則で判定する）と設計文書に書いた。(d) 画面の言葉を「承認済みの経路版と経路方針を引き継いで」にそろえ、「—」の見えない文字を「再承認の前」にした レビューの指摘への対応で、決定の趣旨（ボタン・GET・POST が同じ理由、新しい語を作らない）は変わらない 成果の表、ui_design の S-02・S-04
    3 支援技術による手動確認（計画の確認ポイント 10）: 35c で変えた S-02 の予約の確定待ちの表（承認待ちの行の「—」と凡例）と S-04 の再見積りのフォーム（読み取り専用の経路方針と経路版）は、画面の層のシナリオで axe を通した。スクリーンリーダーでの読み上げは人が確かめてほしい axe は見えない文字の意味までは確かめない requote_after_approval_ui.feature

    仮説¶

    # 結果
    H1 成り立った。判定を 1 か所（開発レビューの後はドメインの規則 RequotePolicy）に置き、S-04 のボタン・GET と POST が、期限内の承認済み・期限を過ぎた承認済み・予約確定済み・古い版で同じ理由を示す（WebMvc とサービスの単体）。置き場所は照会のサービスでは合わなかった（コマンドのサービスが照会のサービスを自分で作り、WebMvc はモックに本物の判定を呼ばせた）。判定は 2 つの集約を読むだけの純粋な関数なので、ドメインの規則が合う
    H2 成り立った。経路方針をフォームから受けず、POST で旧版の値をフォームに入れてから変換するので、QuotationInput.validate を変えずに読み取り専用にできた。正は集約の requoteInto（旧版の値で上書きする）で、controller の上書きは検証を通すため（Javadoc に書いた）

    判断と学び¶

    • 判定の置き場所は「何を読むか」で決める。リポジトリを読まず 2 つの集約と時刻だけで決まる判定はドメインの規則で、照会のサービスに置くと、コマンドのサービスがそれを呼ぶ向きとモックの細工という形で無理が出る。開始準備の段階で、判定が読むものの表を書いていれば、置き場所の決定を改めずに済んだ
    • 状態の表示（effectiveStatus）と操作のリンクを別々に作ると、時刻で状態だけが変わったときに食い違う。行の操作は表示する状態から作る
    • 一覧の表を「見積りの状態を正にする」と「輸送要求の状態を正にする」の 2 つの原則で作ると、非同期のイベントの間に行がどの表からも消える。表ごとの条件を並べて、状態の組み合わせを全部数えると穴が見える

    ふりかえり（KPT）¶

    • Keep
    • 3 つの観点の開発レビューが、同じ穴（失効した承認待ちの行、提示の後の消える行）を別の角度から見つけた
    • 経路方針は controller と集約の二重で守り、細工した要求のテストと再表示のテストで確かめた
    • Bolt 23b からの暫定の案内を、画面・7 章・付録 B の 3 か所から消した
    • Problem
    • 開始準備で決めた判定の置き場所を、実装の後のレビューで改めた（計画の段階で判定が読むものを書かなかった）
    • 一覧の表の条件を表ごとに見て、状態の組み合わせを数えなかった（提示の後の消える行を計画で「DE-24 の後に出る」として受け入れた）
    • キャプチャのデータの時刻の順（承認と有効期限）を撮った後に確かめなかった
    • Try
    • T-160: 判定・規則の置き場所を決めるときは、判定が読むもの（リポジトリ・集約・時刻）を書き、リポジトリを読まないならドメインの規則にする
    • T-161: 同じ画面の複数の表の条件を変えたら、状態の組み合わせ（輸送要求 × 見積り）の表を書き、どの表にも出ない組み合わせが非同期の間にないか確かめる
