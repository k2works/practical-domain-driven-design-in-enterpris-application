    Bolt 14 終了報告 - password によるログインと session（US-18 の一部）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt 14）により、計画の承認の後は承認ゲートで止まらずに進めた。次は AI の判断で通したもので、本報告の承認の場でまとめて確かめてほしい。

    # AI の判断で通したもの 根拠 却下・修正のときに戻す箇所
    1 ステップ 2 の業務のルールとスキーマのゲート（identity.company・app_user・user_role・audit_record、platform.spring_session、開発用の利用者の db/dev-data） 確認ポイント 4・5・7・12（承認済み）の範囲。計画からの変更は型の名前（User）と correlation_id を埋めないことだけ マイグレーション V20261006140000・V20261006140100・V20261006150000 と db/dev-data
    2 ステップ 3 のセキュリティのゲート（form login、認可、CSRF、session の固定化の防止、無操作 30 分と 8 時間、応答のヘッダーと Cookie、監査の同期の書き込み） 確認ポイント 6〜9・11 と ADR-012（提案）に沿う。計画からの変更はどれも守りを弱めない SecurityConfiguration と identity.infrastructure.security
    3 開発レビューの判断 D-49〜D-53（Bolt 14 のレビュー） 高・中の指摘をこの Bolt で直す（D-49）。無操作の期限の設定の鍵を直す（D-50）。役割とホームの対応を 1 か所にし画面のない役割は A-04（D-51） レビューの「対応結果」
    4 H2 のコンソールを外した（D-52） 使うにはその道筋だけ CSRF の確認を外す必要があり、SonarQube も脆弱性として止めた。手順書と README を直した build.gradle の spring-boot-h2console、application-dev.properties、手順書
    5 multipart の上限の超過の案内を /error の 413 の画面に移し、UploadLimitAdvice を消した（ステップ 3） CSRF の確認が送信の本体を読むため、超過は controller より前で起きる。荷主の見積依頼への送信のときだけ荷主向けの文言を出す templates/error/413.html
    6 画面の文言の「password」（人に確かめたい） 設計文書の用語に合わせた。レビューで、荷主には「パスワード」が自然と指摘された（D-53 で保留） A-01・A-03 のテンプレート

    計画からの変更¶

    • ステップ 3 で、既存のテストを緑に保つためにステップ 4 の一部を行った（画面の単体テストのフィルターを外す、画面の層のシナリオは A-01 からログインしてから開く、A-01・A-03 の最小の画面とルートの振り分け）。
    • コントローラーは @AuthenticationPrincipal を使わず、引数の型だけで AuthenticatedActor を受け取る（注釈も Spring Security の型のため。ADR-012 を直した）。
    • 準備中の画面に予定の週は出さない。代わりに荷主には「使えるようになるまでは、担当営業にご連絡ください。」を示す。
    • ログインの後は、元の URL がなければルート（/）を通り、役割のホームはルートの 1 か所で決める。画面のまだない役割は A-04（D-51）。
    • 発行から 8 時間を過ぎた session のままのログインの送信も A-03 へ移す。session に CSRF のトークンがない古いフォームの送信も A-03 へ移す（トークンが誤っていれば 403）。
    • multipart の上限の超過の案内を /error の 413 の画面に移した（議題 5）。H2 のコンソールを外した（議題 4）。
    • 開発用の設定の守りは identity.devlogin に置き、Flyway の設定の組み立てで動かす（開発用の利用者がマイグレーションで入る前に止める）。
    • 無操作 30 分は spring.session.timeout で決める（D-50）。

    仮説の結論¶

    # 仮説 結論 根拠
    H1 主体の型を shared に置けば、quotation の差し替えは引数の変更だけで済み、モジュールの依存は増えない 成り立った 4 つのコントローラーの変更は引数とフィールドの削除だけ。Spring Modulith の検証と、identity の外が Spring Security に依存しない規則（ArchUnit）が通る。@AuthenticationPrincipal も Spring Security の型だったため、引数の解決にした
    H2 標準の部品で password の段を作り、失敗の記録を 1 つの listener に寄せれば、W5 で構成を作り直さずに済む 一部成り立った form login・DaoAuthenticationProvider・Spring Session はそのまま使える。ただし W5 で直す箇所が 5 つある（成功のイベントの分割、認可の要素の権限、request ごとの DB、引数の解決の要素の確かめ、ロックの置き場所）。ADR-012 の「W5 で見直すこと」に書いた
    H3 打ち切りの順を先に決めておけば、範囲を分けずに 1 つの Bolt にしてもセキュリティの規則は削らずに終えられる 成り立った（条件あり） 打ち切りの線を使わず、AC2・AC4・AC5・CSRF・session の固定化の防止・監査は削らなかった。条件: 開発レビューで fail-open の 3 か所と無操作の期限の設定の誤りが見つかった。範囲が広いほど、レビューで見つかる守りの穴が増えた

    既知の課題（W5 の US-18 の計画に持ち込む）¶

    課題 影響 扱い
    利用停止・権限の取消しは既存の session に反映されない（最長 8 時間） 止めた利用者が使い続けられる W5 で request ごとに DB を確かめる（SEC-12、AC6）。リスク台帳
    入力の保持と失効 5 分前の警告がない 失効で入力中の内容が失われる（レビューの利用者の懸念） W5 で入れる（ACC-06）
    権限外のアクセスの試行を監査記録に残していない（IA-INV-08） 試行を追えない US-16 の Bolt
    ステージング・本番に利用者を作る手段がない 荷主の受入の場を作れない US-16（W5）。W10 より前に荷主の受入を予定するなら先に決める
    画面の文言の「password」 荷主には「パスワード」が自然 本報告の議題 6 で人に確かめる
    未認証の request で session の行が増える 大量の request で DB が膨らむ W5 のロックか W10 の WAF（リスク台帳）
    session の直列化の互換 配備で既存の session が復元できない 配備の手順で session を消す（ADR-012、W10）
    狭い画面でヘッダーの利用者名が出ない、email の正規化の差、テストの補助の置き場所 小さい D-53
    デモの動画を AI が再生して確かめていない 録画が崩れていても気づかない 本報告の承認の場で人が再生する
    支援技術による手動確認を記録していない（#6 の完了の定義の 1 行） 読み上げでの A-01・A-03・A-04 の使い勝手が未確認 @ui と axe-core は通った。手動確認は人に依頼する（#6 の本文に残した）
