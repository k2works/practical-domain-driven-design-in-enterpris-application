    Bolt 21 終了報告 - KPI-01 の提示時刻とリードタイム（US-21 AC1）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt21）により、計画の承認から終了報告の前まで、すべての承認ゲートで止まらずに進めた。止まらなかったゲートごとの判断を、ここでまとめて確かめてほしい。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 計画の確認ポイント 1〜12 を推奨のまま採った 範囲（US-21 AC1）はリリース計画の W3 の残り。確認ポイントは設計文書と前の Bolt から導いた細部。開始準備の整合性検証と横断検証の結果も計画に反映した Bolt 21 計画
    2 D-11（人が決める事項）: KPI-01 の終点は、その輸送要求で最初に提示した見積りの提示時刻とし、荷主の条件変更・再見積りで出し直しても変えない。リードタイムは暦の経過時間で、営業時間に換算しない。誤りで取り消した見積りを数えない規則は、取消しを作るときに足す（見積りごとの提示時刻が残るので、そのときに出し直せる） Bolt 3 レビューの推奨のとおり。利用者代表のレビューも、荷主の体感と改善の効果の測りやすさから妥当と判断した。KPI-01 の責任者（営業責任者）の承認を得てほしい US-21 の「AI の判断」、ドメインモデル KPI-INV-01
    3 ステップ 2〜4 の Red・Green と、データベース・画面のゲート 列・CHECK・条件付きの更新・画面の列は、計画の設計とデータモデル・UI 設計のとおり。計画からの変更は設計文書に戻した（T-53） 計画の各ステップの結果
    4 開発レビューの判断 D-79〜D-83 を直し、D-84 を後に回した 直らない欠けの毒入りのメッセージ（D-79）、保存を確かめていないテストダブル（D-80）、未提示の行の経過時間（D-82）はこの Bolt で直した Bolt 21 のレビュー
    5 日時表示・期間表示の写しを 1 か所に集めるか、いつ、どこに置くか（D-84。計画の確認ポイント 7 の条件に達した） 推奨は次の Bolt の最初のリファクタリングで、platform の Web の部品に置く（共有カーネルを表示の関心で変えない）。この Bolt では移していない レビューの D-84 と矛盾事項 1
    6 開発戦略の「Bolt ごとのアプローチの決め方」を見直すか（計画の確認ポイント 12） この Bolt は規則どおりアウトサイドインで進め、不都合はなかった。Bolt 19・20 は同じ種類の Bolt をインサイドアウトと書いていた。推奨は、規則から外れるときに計画の「アプローチ」欄に理由を必ず書く形 開発戦略
    7 未完了の発行の件数を確かめる手段を、パイロットの計測（W9）の前に前倒しするか（D-84） 記録に失敗した輸送要求は「未提示」と見分けられず、KPI-01 の母集団から黙って欠ける。今は W10 の予定 レビューの D-84
    8 #9 をクローズし、US-21 の R0.1 の 2 SP を W3 で数えた。W3 は 11 SP（計画 10 SP）で締められる状態にした 計画の確認ポイント 1 #9
    9 運用のタスク sonar-local:scan の Windows の不具合を直した（.\gradlew.bat を使う） 手順書のタスクが Windows で動かず、品質ゲートを確かめられなかった。独自のスクリプトは作らず、既存のタスクを直した ops/scripts/sonar_local.js
    10 デモの動画は Bolt 21 の 2 本だけを足し、demoVideo が撮り直した過去の Bolt の動画は元に戻した。承認の後、人が DEMO_BOLT=bolt-21 DEMO_ISSUE=9 npx gulp issue:attach-demo で #9 に添付し、BOLT_ISSUES に bolt-21: 9 を足す 過去の画面で変えたのは KPI 計測記録の一覧だけ。ウォーキングスケルトンの動画（bolt-01・03・04）にも一覧が映るが、業務番号の確かめは変わらない docs/assets/demo/bolt-21/
    11 人に確かめてほしいこと: デモ環境の KPI 計測記録の一覧で、TR-2026-0903〜0905 に最初の提示時刻とリードタイムが、0901・0902 に「未提示（提出から …）」が出ること。あわせて、一覧をスクリーンリーダーで操作して #9 の完了の定義の手動の確認を記録する AI はデモ環境に届かない。同じサンプルの値はスモークテストで、画面の表示は uiTest で確かめた —
    12 別のクラウドのセッションが、この Bolt の前（2026-10-08 12:16〜12:20 JST）に同じ US-21 AC1 を develop に push していた（23359f9f D-11 の決定、bf7c05f Red、d605f5d3 Green。CI #127 は check が失敗）。それらはこの Bolt の作業を始めたときには develop から外れており、本 Bolt はそれらを含まない 気づいたのは終了報告の前（CI の一覧）。中身は読むだけにし、取り込みも消去もしていない。並行して作業していたのか、残すべきものがあるかを確かめてほしい git show d605f5d3

    デモ項目¶

    デモ項目 受入条件 動画
    荷主が提出し、営業担当者が見積りを提示すると、KPI 計測記録の行に提出時刻・最初の提示時刻・KPI-01 リードタイムが出る US-21 AC1 kpi-01-lead-time.webm
    見積りを提示する前の行は「未提示（提出から …）」と示され、リードタイムを算出しない US-21 AC1 kpi-01-not-presented.webm

    AI は Playwright に同梱の ffmpeg（ms-playwright/ffmpeg-1011）で動画を 1 秒ごとの画像にし、通して確かめた。リードタイムの動画（8 秒）は、荷主の提出 → C-04 → 営業の審査・見積りの算出と提示 → KPI 計測記録の一覧の順に映っている。一覧では、TR-2026-0008 の行に提出時刻と最初の提示時刻（日本時間と UTC の併記）とリードタイム「0 時間 0 分」が出る。未提示の動画（5 秒）は、TR-2026-0009 の行に「未提示（提出から 0 時間 0 分）」と「—」が出る。画面の層のテストは実際の時計で数秒のうちに流れるため、リードタイムと経過時間はどちらも 0 分になる。値の大きい例（「26 時間 30 分」など）は、デモ環境のサンプル（TR-2026-0903〜0905）で見られる（議題 11）。

    ふりかえり（KPT）¶

    • Keep
    • 開始準備の横断検証で、開発戦略の規則（既存の集約に足す Bolt はアウトサイドイン）とのずれを着手前に見つけた。規則どおり受入シナリオから下りて、やり直しがなかった
    • Try T-58 のとおり、listener の拒否の経路と警告のログを単体テストの Red に入れた
    • 表の制約と条件付きの更新で、集約の規則を並行性に強い形でも守った
    • Problem
    • テスト用のメモリのリポジトリが実体を返していたため、listener の保存の呼び出しをどのテストも守っていなかった（レビューで見つかった）
    • 「提出の記録がない」と「提出時刻より前」を同じ扱いにした。後者は再配信しても直らない（ADR-014 の考え方に反した）
    • 確認ポイント 7 で自分が決めた「3 つ目で集める」を、その 3 つ目で守らなかった
    • 運用のタスク（sonar-local:scan）と documentationTest が Windows の作業ツリーで動かなかった
    • Try
    • T-61: テスト用のメモリのリポジトリは、読み出しで写しを返す（保存しなければ変わらない）。新しく作るときも既存のものを触るときも、保存を外すとテストが落ちることを確かめる（AI、次の Bolt から）
    • T-62: listener が処理できないときは、計画の確認ポイントで「再配信で直るか」を欠けごとに分けて書く（直るものは例外で残し、直らないものは理由を残して捨てる。ADR-014）（AI、次の Bolt から）
    • T-63: 計画で「N 個目になったらこうする」と決めた規則は、その N 個目の Bolt の計画の確認ポイントに入れる（AI、すぐ）
