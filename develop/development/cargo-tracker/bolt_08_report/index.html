    Bolt 8 終了報告 - UI の骨格と見積依頼の段階入力のプロトタイプ（#36）¶

    基本情報¶

    項目 内容
    Bolt 第 8 回
    期間 2026-10-03 11:24 JST（計画の承認のコミット e34f132）〜 終了報告のコミット。開始準備は 11:16〜11:24
    対象 技術タスク #36（SP 0）。UI-HO-04（C-03 の段階入力の操作性）
    計画 Bolt 8 計画
    ゴール すべての画面が共通レイアウトと Bootstrap 5.3 の部品で表示され、画面ごとのスタイルが共通の CSS に移る。荷主は見積依頼の作成と編集を 4 段階で入力し、キー操作だけで提出できる
    進め方 業務のルール・スキーマ・セキュリティに関わるステップがないので、承認ゲートは計画（確認ポイント 1〜4、外部ライブラリの導入を含む）と本報告（段階入力の操作性を人が確かめる）の 2 回

    成果¶

    ステップ 状態 コミット 誤りの検出と修正（検出の手段）
    1. 決定を設計文書に反映する 完了 e21e6f4 —
    2. UI の骨格 完了 328f6a1 3 件（下の「見つけて直した問題」）
    3. C-03 の段階入力のプロトタイプ 完了 a9c6c69 1 件
    4. 検証と終了報告 完了（2026-10-03 に人が承認。変更依頼 0） 本報告 SonarQube の品質ゲートは 1 回で PASS

    打ち切りの線（編集の画面の段階入力、確認のまとめ、社内業務 Web のレイアウト）は使わなかった。

    計画からの変更¶

    • 入口の一覧はテンプレートにせず、静的なファイルのまま Bootstrap と共通の CSS を読むようにした（コントローラを足さずに済む。AI の仮定からの変更）。
    • 既存の C-03 のシナリオ（キー操作の提出、誤りの直し、特殊貨物、書類、出し直し）は、期待する結果を変えずに、段階を進める操作を足した。特殊貨物のシナリオで「提出ボタンが使えない」ことは、提出ボタンのある確認の段階まで進んでから確かめる。

    見つけて直した問題¶

    ステップ 問題 検出の手段 対応
    2 スクリプトのないページで、フラグメント ~{::script} が解決できずに画面が描けなかった 画面の単体テスト スクリプトのないページは空のフラグメント ~{} を渡す。レイアウトの説明に書いた
    2 Bolt 4 のキー操作のシナリオが、ヘッダーとナビの分の Tab を想定していなかった 画面の層 最初の入力（荷受人）に届くまで Tab を進める。キー操作だけの期待は変えない
    2 ナビの移動の途中でアクセシビリティの検査を走らせた 画面の層（axe の注入の失敗） 移った先の URL を待ってから検査した
    3 提出ボタンが確認の段階にあるため、貨物の段階では見えず、特殊貨物のシナリオが提出ボタンを見つけられなかった 画面の層 確認の段階まで進んでから確かめた

    UI-HO-04 の所見（AI の観察。合否は本報告の承認の場で人が触り、この形で残すと決めた）¶

    • 1 つのフォームの中で段階を切り替えるので、選んだ書類は段階を行き来しても残る（シナリオ「確認の段階から前の段階に戻って直しても選んだ書類が残っている」）。
    • 段階を移ると見出しへフォーカスが移り、次の Tab で段階の最初の入力に届く。キー操作だけで 4 段階を進めて提出できた。
    • 提出の誤りは、エラー要約のリンクで誤りのある段階が開く。ただし、提出した直後に開くのは最初の誤りの段階だけで、2 つの段階に誤りがあると、もう 1 つの段階はリンクから開く必要がある。
    • 確認の段階の入力のまとめは、ファイル名と選んだ選択肢の表示名を出す。値は textContent で入れ、HTML として解釈しない。
    • 段階ごとの検証はしないので、誤りは確認の段階から提出するまで分からない（確認ポイント 3 の決定どおり）。

    デモ項目の結果¶

    # デモ 結果

    2 見積依頼の作成で 4 段階を進み、書類を選んで確認の段階から提出する @ui で、段階を行き来しても入力と書類が残り、C-04 に版 1 が出ることを確かめた。操作性は承認の場で人が bootRun で確かめる
    3 営業の受付一覧と審査画面を開く @ui で、社内業務 Web のナビと、キー操作でのナビの移動を確かめた
    4 ./gradlew uiTest 画面の層 28 本（うちレイアウト 4 本、段階入力 3 本）が通り、axe-core の違反は 0 件

    仮説の結論¶

    # 仮説 結論 根拠
    H1 Thymeleaf のフラグメントだけで 2 つのレイアウトを作れる（Layout Dialect を足さない） 成り立った（制約あり） layout(title, content, scripts, active) の 1 つのフラグメントで 7 つの画面を移せた。スクリプトのないページは空のフラグメント ~{} を渡す必要がある（使い方をレイアウトの説明に書いた）
    H2 段階入力をパネルの切り替えにすれば、ファイル・サーバーの検証・エラー要約を変えずに、JavaScript がなくても動く 成り立った コントローラ・検証・エラー要約は変えていない。選んだ書類は段階を行き来しても残った。JavaScript がないときは段階の一覧と「次へ」が hidden のままで全段階を示すことを、単体テストで確かめた
    H3 Bootstrap 5.3 に移しても、既存のシナリオ（文言とキー操作）と axe-core を変えずに通せる 成り立った（キー操作の手順は足した） 既存の 21 本は、文言と期待する結果を変えずに通った。axe-core の違反は 0 件。キー操作の手順は、ヘッダーとナビの分と、段階を進める分を足した

    判断と学び¶

    設計への反映（反映済み）¶

    • UI 設計: 「ナビゲーションとレイアウト」に実装（フラグメント、WebJars、共通の CSS、いまある画面だけのナビ、仮のヘッダーと窓口の案内）、C-03 の段階入力の行にパネルの切り替えの方式
    • リリース計画: W1 に Bolt 8

    人の決定（本報告の承認の場で）¶

    • 段階入力の操作性（UI-HO-04、確認ポイント 4）: 人が bootRun で見積依頼の作成を触り、この段階入力の形で残すことに決めた（2026-10-03、human:kakimomokuri）。段階ごとの検証は R1.0 の下書き保存のときに決める

    既知の課題¶

    課題 影響 扱い
    段階ごとの検証がない 誤りは確認の段階から提出するまで分からない R1.0 の下書き保存のときに、段階ごとの保存と検証を決める
    2 つの段階に誤りがあると、提出の直後に開くのは最初の段階だけ もう 1 つの段階はエラー要約のリンクから開く 承認の場で今の形のまま残すと決めた。段階ごとの検証とあわせて R1.0 の下書き保存の Bolt で見直す
    表を狭い画面で時系列のリストに切り替えていない 狭い画面では表を横にスクロールする 一覧が増えてから（UI 設計「画面幅」）
    ログアウト、役割に応じたナビ、利用者のタイムゾーンでの窓口の案内 仮の表示 認証（US-18）と利用者管理（US-16）
    htmx は読み込むだけで、まだ使っていない — 一覧の絞り込みなどを作る Bolt で使う

    Try 結果
