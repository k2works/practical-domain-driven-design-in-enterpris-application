    仮説の結論¶

    # 仮説 結論 根拠
    H1 決めた構成で動く骨格を、承認ゲートの変更依頼 1 回以内で作れる 成り立った（人の変更依頼 0。終了報告のゲートを変更依頼なしで通過） 実装中の誤りは版・API・設定の違いで、AI がテストの失敗から直した。ただしレビューで、設計の約束（受信側の冪等性、Clock の精度、イベントの直列化の契約）を実装が満たしていないことが見つかった。「設計の判断の誤りは 0」とは言えず、それを検出する仕組み（AT-02、受信側の冪等性のテスト）がなかった
    H2 同じマイグレーションで H2 の起動と PostgreSQL 18 の統合テストが通る 成り立った 実装中は手動の bootRun で確かめた。レビューの対応で H2 のスモークテスト（dev プロファイル）を足し、起動・マイグレーション・冪等な保存の SQL を自動で確かめるようにした
    H3 イベント配信を統合テストと受入シナリオの両方で確かめられる 成り立った 受入シナリオは発行と配信をステップに分けたテスト用の同期の配信で、統合テストは非同期の配信と発行記録の完了を、自分の輸送要求 ID で待って確かめる
    H4 1 Bolt を 4 時間以内に収められる 成り立った 実装とレビューの対応で約 72 分。ただし人のレビューの時間を含まない

    ふりかえり（KPT）¶

    Keep¶

    • 受入シナリオ（Red）→ 内側の TDD → シナリオが通る、の順で縦割りを通せた。ステップごとにコミットし、ビルドが通る状態を保った
    • テストが一度で通ったときに、わざと壊して失敗することを確かめた（AT-01、配信テスト）
    • 5 視点のレビューを並列に回し、実装の欠陥 5 件をクローズの前に直せた
    • 契約テスト（メモリ上・PostgreSQL・H2 の 3 実装で同じテスト）で、テストダブルと本物のずれを機械的に防げるようにした

    Problem¶

    • 設計にある約束（ARCH-HO-01 の受信側の冪等性、ADR-007 の Clock の精度）を、Bolt 計画のステップに落とさなかった。ウォーキングスケルトンの「入れないもの」に書いていなかったため、黙って抜けた
    • テストダブルを本物より緩く作り、本物の欠陥を隠した
    • 配信テストの待ち条件を緩く書き、他のテストの行で満たされうる形にした
    • 依存の向きの誤りをテストでなく目視で見つけた（AT-02 がない）
    • 画面の文言（見積依頼の併記、エラーの直し方）を UI 設計の横断ルールと突き合わせなかった

    Try¶

    # 改善 担当 期限 期待する効果
    T-1 Bolt 計画を作るとき、対象の設計（ARCH-HO・ADR の決定表・UI 設計の横断ルール）の約束を「入れる／入れない」の表に必ず書く AI Bolt 2 の計画 約束の抜けを計画の時点で人が見つけられる
    T-2 AT-02（層の向き。合成ルートの例外つき）と、@DomainEvent の配置の ArchUnit を Bolt 2 で入れ、それまでは各ステップでゲートを置く AI Bolt 2 依存の誤りを目視に頼らない
    T-3 テストダブルを作るときは、本物と同じ契約テストを同時に書く AI 次にテストダブルを作るとき 本物より緩いテストダブルを防ぐ
    T-4 コミットする統合テストは、自分が作ったデータの ID で待ち、絞り込む AI 次の統合テスト テストの順序と共有データへの依存を防ぐ
    T-5 CI・JaCoCo・Spotless・SonarQube のスキャンを Bolt 2 で揃え、SONAR_TOKEN を人が発行する AI・人 Bolt 2 クローズの品質ゲートを満たす

    判断と学び¶

    設計への反映（反映済み）¶

    • UI 設計: 画面ごとの URL の決まりと、仮の画面の逸脱（UTC だけの表示、エラー要約なし）を追記した
    • バックエンドアーキテクチャ: 次を追記した
    • domain.events を名前付きインターフェースで公開する
    • 技術的な部品を platform モジュールに置く
    • サービスを infrastructure.config（合成ルート）で組み立てる。その理由と、依存の規則の例外であること
    • allowedDependencies を宣言する
    • イベントの進化の規則
    • データモデル: マイグレーションを凍結する時点の規則を追記した
    • 開発戦略: 品質チェックのコマンドを、実際のものにした

    人の判断が必要なこと¶

    # 事項 AI の提案
    D-1 共有カーネルの DomainEvent インターフェースと注釈 @DomainEvent の重複 注釈に一本化する。条件は次の 3 つ（レビュー D-1）。
    1. 配置を ArchUnit で両方向に固定する
    2. 各イベントが業務キーを持つ
    3. ドメインモデルの図を承認つきで直す
    D-2 以降の Bolt のゲート密度 下の「ゲート密度の判断」
    D-3 KPI-01 の開始時刻 版 1 を最初に提出した時刻を開始とし、差戻し・再提出・新しい版で時計を戻さない
    D-4 荷主に見せる業務番号の形式 TR-年-連番。採番の単位と版の表記を決め、US-01 の Bolt でデータモデルに入れる
    D-5 infrastructure.config を依存の規則の例外（合成ルート）とする 例外として明記した（バックエンドアーキテクチャ）。AT-02 でこの例外だけを許す
    D-6 出発地と目的地が同じ輸送要求を拒否するか 拒否する。US-01 AC2 の必須条件に加える

    ゲート密度の判断（ステップ 10）¶

    レビューで、設計の約束の抜けが見つかった。それを検出する AT-02 と受信側の冪等性のテストは、Bolt 2 までそろわない。このため AI の提案を次のとおりに改める（レビュー R-38、C-2）。

    • Bolt 2 までは各ステップでゲートを置く（2026-10-01 に人が承認）
    • AT-02 と CI が入った後に、自律実行へ移るかをもう一度判断する。移った後も、次の Bolt では各ステップでゲートを置く
    • U2・U3 の中核の集約を作る Bolt
    • 認証・認可（US-18）
    • スキーマの変更
    • docs/design/ と食い違う判断

    意図的に持ち越した負債¶

    負債 持ち越し先 根拠
    再配信（起動時・定期）と、完了済みの発行記録の掃除が未設定 運用準備（ShedLock と合わせて）。冪等性は Bolt 1 で入れた レビュー R-18
    追記専用の表を DB の権限で守っていない（afterMigrate のコールバックがない） Bolt 2（DB 利用者 DA-02 と合わせて） レビュー R-17
    AT-02・AT-06 がない Bolt 2 レビュー R-15・R-16
    認証がなく、ID が分かれば誰の輸送要求でも表示できる（IDOR）。CSRF の対策がない US-18 の Bolt。「荷主企業の一致を確かめる」テストを最初に書く レビュー R-35
    起動の手順書がない Bolt 2（operating-setup） レビュー R-11
    状態の表示名、save の追加と更新、一覧のページング、入力の誤りの専用の例外 状態や入力項目を増やす Bolt レビュー R-34
