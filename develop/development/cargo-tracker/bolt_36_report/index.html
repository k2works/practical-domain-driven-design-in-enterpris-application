    Bolt 36 終了報告 - CI の画面の層のシナリオの揺らぎを直す（#50）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-20 に承認を受けた（343548974）。承認ゲートは計画と終了報告なので、ステップ 1〜4 は止めずに進めた。打ち切り（保留しても落ちない、画面の JS を直さないと通らない）には当たらなかった。画面の JS・テンプレート・スキーマは変えていない。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 計画からの変更（人に諮らずに変えた）: (a) 待ちの置き場所。計画では「CSRF の拒否のステップの側だけ」としたが、開発レビューの指摘で、共通のステップ「権限がない画面が表示される」にも 403 の画面の load の待ちを入れた（控えの中身は見ない）。認可の 403 のシナリオの否定の確かめ（「とは示されない」）も、script の処理の後に見ないと遅いマシンで偽の緑になり得るため。認可の 403 のシナリオの条件（控えの理由が違う）には触れていないので、計画の注意（条件が成り立たず時間切れになる）には当たらない。(b) 待ち方。計画は「控えの印を待つ」としたが、waitForFunction ではなく、load を待ってから印を 1 回確かめる形にした（失敗したときに「控えなし」と「印なし」を見分けられる） 開発レビューのテスターの指摘 1・3 SessionTimeoutUiSteps の差分
    2 #50 の閉じ方: 計画の確認ポイント 3 のとおり、#50 の「CI の揺らぎ」の項目は、W6 の残りの Bolt の CI の ui ジョブで揺らぎが出ないことを見てから印を付ける。今は Issue にコメントだけを残す 揺らぎは 1 回の緑を証拠にしない（Bolt 32 の学び） #50

    成果¶

    ステップ 結果 コミット
    1. 再現（Red） 一時の差し込み（Playwright の page.route で 403 の画面の /js/session-input.js の応答を控えて保留し、2 回目からの読み込みは通す）で、session_timeout_ui.feature の 2 つのシナリオ（:147-153・:155-164）が 5 回中 5 回落ちた。落ちたとき、移る前の控えは passedPublic: false で、一覧の画面に移った後は控えが捨てられていた（H1 のとおり）。認可の 403 のシナリオは通った （記録だけ）
    2. 写しを数える 公開の画面を経た直後に次の画面へ移る形は、画面の層の feature の全体で :150・:159 の 2 つだけ。:80・:102（session の失効の控えで、古いとして捨てる判定の対象外）、:95（移らない）、:123・:141（印の後に書かれる「入力を戻す旨」を待つ）、:174（認可の 403。理由が expired）は該当しない （記録だけ）
    3. 直し（Green） 共通のステップで 403 の画面の load を待ち、CSRF の拒否のステップで控えに印があることを確かめる。見出しの時点で保留し 300 ms 後に応答を返す差し込みで 10 回、差し込みなしで 10 回、3 つのシナリオが通った。差し込みと一時の tag・build.gradle の変更は消した 44d8b60d4
    4. 品質ゲートと開発レビュー 開発レビュー（テスター）の指摘を直し、変異（403 の画面で常に印を付ける）で認可の 403 のシナリオが落ちることを確かめた（T-164）。CI を 2 回流した 44d8b60d4、この報告のコミット

    仮説¶

    # 結果
    H1 成り立った。CI の成果物の失敗（案内が 5 秒の間に一度も出ない）と、保留したときの控え（印なし、移った後に捨てられる）が一致した。待ち方を直すと、保留しても通った

    開発レビューの指摘と扱い¶

    # 観点 重大度 指摘 扱い
    1 テスター 中 認可の 403 のシナリオは「印を付けないこと」を否定で確かめるが、共通のステップが見出しだけを待つので、script の前に移ると退行を見逃す（T-106） 共通のステップに 403 の画面の load の待ちを入れた。変異で落ちることを確かめた（議題 1 (a)）
    2 テスター 低 もし のステップの中で ならば の確かめを呼び、同じ確かめを 2 回する load の待ちを共通のステップに移し、CSRF の側は印の確かめだけにした（見出しの確かめは load を待つ前提として残る）
    3 テスター 低 控えが Map でないと ClassCastException で落ち、失敗の文言が読めない AssertJ の asInstanceOf(MAP).containsEntry にした
    4 テスター 低 メソッド名と Javadoc の「待つ」が実際の動き（load を待って 1 回確かめる）とずれる 名前を「公開の画面の読み込みを待ち印を確かめる」にし、Javadoc をそろえた
    5 テスター 低 控えの内部の名前 passedPublic に依存する 診断として残し、JS の名前を変えるときに直すことを Javadoc に書いた

    デモ項目¶

    判断と学び¶

    • 揺らぎは、遅らせ方を「時間で待つ」でなく「応答を保留する」にすると決まって再現できた。Playwright Java の route の handler はテストのスレッドで呼ばれるので、handler の中で待つと窓が縮む（検証の指摘のとおり）。また、handler はテストのスレッドが Playwright を呼んでいる間にしか呼ばれないので、送信の直後にはまだ応答を控えていない。保留を返す処理は、次に Playwright を呼んだ後に置く
    • 途中で waitForFunction が 30 秒で時間切れになったのは、差し込みが保留した応答を返していなかったためだった。偽の時計が原因だと早合点して、確かめていない理由をコメントに書きかけた。原因の候補を書くときは、確かめたかどうかを分ける
    • 見出しが見えることは、画面の script が終わったことを意味しない。テストは、画面が自分で書く状態か、文書の lifecycle（load）を待ってから次へ移る

    • 「とは示されない」の否定の確かめ（SessionTimeoutUiSteps の「… とは示されない」）は、知らせが 500 ms 遅れて出る間にすぐ通る。今は後ろの「入力の控えが残っていない」の待ちが守っている（計画の確認ポイント 6。#50 の開き直すループの共通化と一緒に見直す）
