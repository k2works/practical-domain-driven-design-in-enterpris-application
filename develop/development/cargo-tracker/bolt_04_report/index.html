    仮説の結論¶

    # 仮説 結論 根拠
    H1 年ごとのカウンター表を H2 と PostgreSQL の共通の SQL で更新すれば、同時に提出しても業務番号が重複も欠番もせずに振られる 成り立った（手順を直して） 年の最初の採番を 8 スレッドで同時に行っても 1〜8 が重複なく振られ、ロールバックしても欠番が出なかった（3 回続けて通った）。ただし、計画の「同じトランザクションで INSERT して違反ならやり直す」手順は PostgreSQL では成り立たず、年の行を別のトランザクションで用意する手順にした
    H2 提出の検証の結果をドメインの戻り値で表せば、画面のエラー要約と業務ルール層の受入シナリオが同じ規則を共有できる 成り立った ドメインは項目と理由の種類だけを返し、業務ルール層のシナリオはそれを、画面の層は文言を確かめた。形式の誤り（UN/LOCODE・日時・数値）は画面の層に残した。形式の誤りがあると業務の規則の違反は出さないため、2 段階で直す場合がある（既知の課題）
    H3 受入条件の番号を付けた業務ルール層のシナリオを外側のループにし、画面の層は主成功と画面に固有の条件だけにする構成で、業務のストーリーが回る 成り立った 業務ルール層 26 本（@US-01-AC1・AC2・AC4）と画面の層 5 本で、受入条件を両方の層に重ねずに済んだ。画面の層は実際の時計で動くため、業務番号の値は決め打ちせず、形式と画面の間で同じであることを確かめた

    判断と学び¶

    設計への反映（反映済み）¶

    • D-10: ドメインモデルの用語集（業務番号、業務番号の採番、輸送条件の入力、提出の検証結果、貨物、荷姿）、Q-INV-12（期限の境界と数量の値）、Q-INV-13（業務番号を変えない・重複させない）、DE-01 の表示用の業務番号
    • データモデル: 業務番号の列と一意制約、年ごとの採番の表（number_year。year は H2 の予約語）と採番の手順、KPI 計測記録の業務番号の列（null を許す）
    • ユーザーストーリー: US-01 の決定（D-10、期限の境界、AC2 をこの Bolt でどう読むか）
    • UI 設計: C-03 の Bolt 4 の形（1 画面、ラジオボタン、希望到着期限のテキスト入力）、完了画面の URL のキーを業務番号にすること
    • 手順書: 完了画面の UUID の負債の記述を消し、仮の荷受人の設定を書いた
    • 前提の違い（R-09）: マイグレーションは「既存の行はない」前提で列を NOT NULL で足した（行があるのはローカルの H2 と Testcontainers だけで、どちらも起動のたびに作り直す。作り直しの手順は要らない）。一方、DE-01 と KPI 計測記録の業務番号は、イベントの進化の規則に従い「業務番号のない古いイベントがある」前提で null を許す。後者は、発行記録に残った未完了のイベントを再配信する場合に備えるためである

    既知の課題¶

    課題 影響 扱い
    AC2 の必要書類がまだない（Q-INV-01 の一部） #2 を閉じられない。AC2 は完了していない 次の Bolt で、ファイルの保存（ローカルのファイルシステムのアダプター）と合わせて入れる
    受入条件の数との照合（テスト戦略、Bolt 2 R-17）がまだない 受入条件のシナリオの抜けを機械で検出できない 次の Bolt。必要書類を入れて AC2 を完了させるときに入れる
    形式の誤りがあると、業務の規則の違反は出さない 形式を直した後に、別の誤りが出ることがある（2 段階） 様子を見る。段階入力（#36）を作るときに見直す
    完了画面は業務番号を知っていれば開ける 他社の輸送要求の状態が見えうる（認証がないため、いまは全員が同じ仮の荷主） US-18（認証）と US-01 AC3（別企業の拒否）の Bolt で確かめる。計画の確認ポイント 5 で承認済み
    年の最初の提出では、採番の行を作るために別のトランザクション（もう 1 本の接続）を使う 接続の数が少ない環境で、年の最初の提出が待たされうる 運用準備（W10）の性能テストで確かめる
    社内の KPI 計測記録の一覧が UTC だけを表示する BR-10 と違う（Bolt 3 から継続） S-22 の本実装で直す
    荷受人は設定の仮の一覧（3 社） 実在の荷受人を選べない US-16（利用者と権限の管理）の Bolt で企業マスターに置き換える
    支援技術（VoiceOver）による手動確認 自動の検査（axe-core）では読み上げの順や内容を確かめられない 人がデモ 2 で確かめる（DoD）

    Bolt 3 の Try の結果¶

    Try 結果
    T-8 品質ゲートを足したら不合格の入力で失敗することを確かめる 実施した。業務番号の一意制約が同じ番号の 2 件目を拒否することを統合テストで確かめた
    T-10 設計文書やソースを読むテストを足したら Gradle のタスクの入力に宣言する 対象なし（新しくそうしたテストは足していない）

    T-12 権限や設定の保護を足したら、最小の権限で確かめる 実施した。アプリケーション利用者で採番の表を作って更新できることを統合テストで確かめた
    T-13 終了報告の時刻は計画の承認と報告のコミットを根拠にする 実施した。ただし承認の待ち時間を分けられないことが分かった

    ふりかえり（KPT）¶

    • Keep:
    • 開始準備の 2 つの検証（詳細・横断）で、重大度「高」の 3 件（イベントにドメインの型を入れる、SQL の方言を分ける、KPI 一覧の UUID）を実装の前に直せた
    • ドメインが「項目と理由の種類」だけを返し、文言を画面の層に置いたので、業務ルール層と画面の層のシナリオがそれぞれの関心だけを確かめられた
    • 画面の部品の選び方（select かラジオボタンか）を、AI が決めずに人に選択肢と理由を示して決めてもらった
    • Problem:
    • ステップ 3 で型を変えたため、ステップ 4 まで check が赤、ステップ 5 まで ui が赤になり、2 つのステップの間 push できなかった
    • 環境の差（H2 の予約語、.properties の文字コード、macOS と Linux の select のキー操作、PostgreSQL のトランザクション中の制約違反）が、実装の後半で次々に見つかった
    • 承認の待ち時間が報告の時間に混ざり、計画の目安（230 分）と比べられなかった
    • Try:
    • T-14: ステップの区切りは、終わりに check が緑になる単位にする。型の変更が層をまたぐときは、永続化の型合わせと SQL を同じステップに入れるか、ステップの順を内側から外側にする（AI、次の Bolt の計画）
    • T-15: マイグレーションを書いたら、統合テストより先に H2 のスモークを回す。設定値に ASCII 以外の文字を入れるときは .properties の文字コードを確かめる（AI、すぐ）
    • T-16: ステップの開始と完了をコミットのメッセージか計画に時刻で残し、承認の待ち時間と AI の実行時間を分けて測る（AI、次の Bolt）
    • T-17: コマンドの cd には絶対パスを使う（AI、すぐ）

    レビューとクローズ¶

    Bolt 4 開発成果物レビュー の指摘を、クローズの前に直した（R-01〜R-24。詳細はレビューの「対応結果」）。主なものは次のとおり。

    • 時計に依存するテスト（R-01）: 実際の時計で動くテストが固定の期限 2026-11-02 の見本を使い、その日を過ぎると落ちる状態だった。見本の期限を 2099 年にした
    • 他社の番号の照会（R-02）: 完了画面は業務番号（連番）を URL のキーにしたのに荷主企業で絞っていなかった。リポジトリから画面まで荷主企業で絞り、他社の番号は見つからない（404）ようにした。認証（US-18）では主体を差し替えるだけで済む
    • 採番の接続の枯渇（R-03、D-13）: 起動時に今年と来年の年の行を用意し、接続のプールの大きさ（10）を超える 16 本の同時の採番でも止まらないことを確かめた。提出の中の別のトランザクションは、年をまたいで動き続けた場合の予備として残した
    • 検証と変換の時間的結合（R-04）: 輸送条件の入力の検証が、輸送条件か違反のどちらかを返す形にした
    • 文言の網羅（R-06）: 項目と理由のすべての組で文言を確かめるテストを足し、特殊貨物の文言が「直し方」で終わっていない（「（手動窓口）」で終わる）ことを見つけて直した

    対応の後も、check（235 件）、uiTest（5 シナリオ）、CI（a348f15、check・ui）、SonarQube の品質ゲート（PASS、指摘 0 件、カバレッジ 98.1%）は緑。GitHub の #2 は、AC2 の必要書類が残るため開いたまま In Progress にし、進み具合をコメントした。

    業務責任者に確かめる事項（D-14〜D-20）は、レビューの「人の判断事項」に記録した。必要書類の Bolt の計画の前に、少なくとも D-20（必要書類の扱い）を決める必要がある。
