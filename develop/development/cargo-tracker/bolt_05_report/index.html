    見つけて直した問題（ステップ 3）¶

    問題 検出の手段 対応
    審査の結果をフラッシュ属性で渡した最初のリダイレクトの URL に ;jsessionid=... が付き、セッション ID が履歴やログに漏れうる 画面の層の待ち時間切れを、アプリを起動してリダイレクト先を確かめて特定した セッションの追跡を Cookie だけにした（server.servlet.session.tracking-modes=cookie）
    受付一覧の表が、幅 320 CSS px でページ全体を横にスクロールさせた 画面の層（320 CSS px） 表だけを横スクロールさせる囲み（フォーカスでき、名前を持つ）に入れた
    入口の一覧の縦に並べたリンクが、Linux では押せる範囲が 24 CSS px に届かない（WCAG 2.2 の 2.5.8） CI の ui ジョブ（手元の macOS では通った。CI の成果物の axe-core の結果で特定） リンクの高さを 24 px 以上にし、間隔を取った
    Playwright の正規表現で Java の Pattern.quote（\Q...\E）を使った 画面の層 正規表現はブラウザ（JavaScript）で評価されるため、文字列で比べた
    汎用のステップ「営業担当者が{画面}を開く」と、明示のステップが同じ文言に一致した 画面の層（ambiguous） 明示のステップを外した

    仮説の結論¶

    # 仮説 結論 根拠
    H1 審査の対象の版番号をコマンドに持たせ、集約の現在の版番号と照合すれば、古い版の審査の確定を集約の規則だけで拒否できる 成り立った 集約の単体テストと業務ルール層の @US-02-AC3 で、差戻し・再提出で版 2 ができた後の版 1 の確定・差戻しが「古い版」として拒否され、最新の版番号が返ることを確かめた。ARCH-HO-01 の期待版（集約の version）は、同時の更新を楽観ロックで 1 人だけ成功させる別の仕組みとして入れた
    H2 状態を変える集約の保存を、楽観ロック付きの UPDATE と審査記録の INSERT で、H2 と PostgreSQL に共通の SQL で書ける 成り立った UPDATE ... WHERE version = ? と INSERT ... SELECT ... WHERE NOT EXISTS で書き、PostgreSQL の統合テストと H2 のスモークで確かめた。同じ集約の版を 2 つ読んで更新すると、後の更新が競合で失敗した（R-27）
    H3 ステップの区切りを「終わりに check が緑になる単位」にすれば、どのステップの終わりにも push できる（T-14） 成り立った（課題あり） ステップ 1・2a・2b・3 の終わりに check を緑にして push できた。ただしステップ 3 では、手元の macOS で緑だった ui が CI（Linux）で赤になり、同じステップの中で直した

    判断と学び¶

    設計への反映（反映済み）¶

    • ドメインモデル: 審査記録・審査の判断の用語、集約の操作（再提出・確定・差戻し）、Q-INV-04 の照合、Q-INV-14・15、DE-02（判断時刻、判断は文字列）、社内用の照会
    • データモデル: review_record（判断の制約、追記専用）、楽観ロックの更新
    • ユーザーストーリー・UI 設計・要件定義: US-02 の決定、S-02・S-03 の URL と振る舞い、見積り作成中の状態
    • 実装の取り決め: 楽観ロックの競合はドメインの例外 ConcurrentTransportRequestUpdateException（リポジトリのポートを技術の例外に依存させない）。セッションの追跡は Cookie だけ

    既知の課題¶

    課題 影響 扱い

    • T-20: 計画に書く時刻は、date で確かめた値だけを書く（AI、すぐ）

    レビューとクローズ¶

    Bolt 5 開発成果物レビュー の指摘を、クローズの前に直した（R-01〜R-21。詳細はレビューの「対応結果」）。主なものは次のとおり。

    • 判断の取り違え（R-01）: 審査の POST で、APPROVED 以外の値がすべて差戻しになっていた。判断を解釈し、知らない値やないときは 400 にした
    • 1 つの版に判断は 1 つ（R-02）: 楽観ロックだけで守っていた規則を、審査記録の一意制約で DB でも守る
    • 審査記録の書き戻しと並び（R-03）: 更新のたびに全件を書き戻していた。新しい審査記録だけを追加し、版番号の順に返す
    • 本当の同時実行（R-04）: 楽観ロックのテストが 1 つのトランザクションの中で順に更新していた。別々のトランザクションを同時に動かして確かめた
    • 受付一覧（R-05・R-09・R-13）: 差し戻して出し直した版が最後に回っていた。集約を組み立てない読み取りモデルにし、最初の提出時刻の古い順に並べ、貨物種別と待っている時間を出した
    • 審査の履歴（R-06・R-11）: 版 2 の審査で前の判断が見えなかった。審査記録の履歴を示し、古い版で拒否したら根拠・理由を空にする
    • CSRF のつなぎ（D-21）: Cookie に SameSite=Lax を付けた。Spring Security の CSRF の防御と認証は US-18

    対応の後も、check（285 件）、uiTest（11 シナリオ）、CI、SonarQube の品質ゲート（PASS）は緑。GitHub の #3 は、AC1〜AC3 がそろったため閉じた。業務責任者に確かめる事項（D-24: 差戻しの荷主への知らせ方、出し直しの期限、不足事項の形、仮の営業担当者の記録と監査）は、レビューの「人の判断事項」に記録した。
