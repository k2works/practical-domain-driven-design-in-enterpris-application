    # AI の判断で通したもの 根拠 却下・修正のときに戻す箇所
    1 計画の承認（確認ポイント 1〜16。とくに 2 の見積りの公開 API、6・7 の仮の航海データと SGSIN 8 時間、9 の規則のない港を除外、11 の認可） 範囲（US-06 AC1〜AC3）は人が決めた。確認ポイントはどれも既存の決定（ADR-001・003・012、R-INV-10、D-4・D-10）の延長 計画 の確認ポイントと、設計文書の「Bolt 17 で決めたこと」
    2 ステップ 2 の Red（境界の表）と Green のゲート 境界の表は R-INV-01・02 と確認ポイント 9 の文言どおり。Golden dataset（W6）が届くまでの BR-11 の仕様になる ConstraintEvaluatorTest、RouteCandidateFinderTest

    計画からの変更¶

    • routing_case に業務番号の写しと依頼時刻、route_version に候補の判定時刻、candidate_leg に航海の採用情報版と取得時刻の列を足した。created_by・updated_by は US-07 で足す（データモデルに反映した）。
    • DE-16 の経路設計の購読は、見積りの購読と別の名前（RoutingCaseOpeningEventHandler）にした。同時の再配信で一意制約に当たったら、例外で全体を戻し（案件番号も戻る）、再起動の後の再配信で何もしない。
    • 画面のまだない役割の例（セキュリティの統合テスト）を、経路設計者から追跡管理者に変えた。
    • 社内のナビを役割ごとの項目だけにした（営業は見積依頼・予約・KPI 計測記録、経路設計者は経路設計）。
    • レビューの対応で、目的地を通り過ぎて戻る積替えを列挙しない（D-60）、S-06 の文言を比較の決め手が分かる形にした（D-61）。

    見つけて直した問題¶

    問題 見つけた手段 対応
    画面の層のテストの航海が DB に残り、シナリオが 4 本を超えると候補の上限で除外の候補が切られる 開発レビュー（tester） シナリオの後に航海を消し、使うシナリオだけで入れる（D-62）
    候補の上限のテストが「適合を先に」を確かめていなかった 開発レビュー（tester） 除外が先に着く並びと 19・20・21 件で確かめる（D-63）
    規則のない港の「接続できない」が、物理的に接続できないと誤読される 開発レビュー（user-representative） 「接続を判定できない（規則が未登録。接続 1 日）」にした（D-61）
    示す順の説明（「到着予定の遅いものを示していません」）が事実と違った（適合を先に並べるため） 開発レビュー（programmer） 「適合を先に、到着予定の早い順に 20 件まで示しています」にした
    候補探索の認知的複雑度、テストのラムダ、Javadoc の置き場所 SonarQube（Code Smell 7 件） 直した（e5c8b70）
    ローカルの SonarQube が起動しない（この環境のファイル記述子の上限 20000 で Elasticsearch の起動の検査に落ち、web の heap 256 MB で規則の登録に落ちた） 起動のログ スクラッチパッドの上書きの compose で、起動の検査を外し web の heap を 1 GB にした（リポジトリは変えていない。Try T-52）

    仮説の結論¶

    # 仮説 結論
    H1 制約適合判定と候補探索を純粋な関数にし、境界を 3 点の表で先に固めれば、W6 の Golden dataset はテストのデータを足すだけで済む 判定については成り立つ見込み。判定はリポジトリを呼ばず、入力（経路条件・区間・規則・判定時刻）だけで決まる。ただし W6 で変える箇所が 2 つ残る。候補の並びと上限は集約にあるため、Golden dataset が候補一覧を期待値に持つなら集約の単位のテストが要る。規則を判定時刻で選ぶ決定（確認ポイント 9）を接続の時刻に変えるなら、判定の入力が変わる（D-65）
    H2 経路条件を見積りの公開 API から ACL 越しに取れば、routing は quotation の domain に依存しない 成り立った。依存は quotation :: api・events だけで、公開 API は共有カーネルの型と文字列だけを返す（ArchUnit で固定）。残る課題は、公開 API が「現在の版」に結びつくため、依頼の後の再提出で経路条件が得られないこと（D-65）
    H3 新しいコンテキストの立ち上げと AC1〜AC3 を 1 つの Bolt にしても、打ち切りの順を決めておけば削らずに終えられる 成り立った。打ち切りは使わず、約 2 時間（目安の 6 時間を大きく下回った）。目安を外した主な理由は、既存のコンテキスト（見積り・アクセス監査）の型と規約をそのままなぞれたこと。逆に、ローカルの SonarQube の起動の問題に約 30 分を取られた
