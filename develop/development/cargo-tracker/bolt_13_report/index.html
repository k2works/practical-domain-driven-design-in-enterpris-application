    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt13）により、計画の承認の後は承認ゲートで止まらずに進めた。次の 3 つは AI の判断で通したもので、本報告の承認の場でまとめて確かめてほしい。

    # AI の判断で通したもの 根拠 却下・修正のときに戻す箇所
    1 ステップ 4 の方式の決定のゲート（ADR-011 の案） ADR は「提案」の状態で、採否は W5 の US-18 の計画で人が決める（確認ポイント 4）。本体のコードと依存は変えていない ADR-011 を却下にする
    2 案の段階で、技術スタック（多要素認証の行を java-otp の案、TS-01 をスパイク済み）とリスク台帳（TOTP の統合のリスクの発生確率を中から低）を更新した 確認ポイント 4 は TS-01 を「スパイク済み（ADR 011 の案）」に更新するとしていた。リスクの発生確率はスパイクの結果で下がった ADR が却下されたら、技術スタックの多要素認証の行を「未定」に、リスクの発生確率を中に戻す
    3 レビューの判断 D-45〜D-48（Bolt 13 のレビュー） 高の指摘をスパイクで直してから ADR に書く（D-45）、リスクで下げる列を直す（D-46）、時間箱を超える確認を W5 に回す（D-47）、認証の主体の型を shared に置く案（D-48） D-48 は W5 の US-18 の計画で人が採否を決める

    仮説の結論¶

    # 仮説 結論 根拠
    H1 Spring Security 7 の多要素認証の仕組みで、独自のフィルターの連鎖を書かずに、password の後に TOTP を求め、両方がそろうまで業務の画面を開かせない構成を作れる 成り立った（条件あり） 要素の要求と足りない要素の画面への誘導は枠組みに任せられた。条件: TOTP の認証のフィルター 1 つと最長 8 時間のフィルター 1 つは自分で書く。追加したフィルターは session の ID を変えず、結果のトークンが toBuilder() を宣言しないと要素が合わさらないなど、資料の少ない振る舞いを自分で設定する必要がある。期限の確認の置き場所を誤ると 8 時間を迂回できた（レビューで見つけて直した）
    H2 TOTP の検証は小さな部品で、試験ベクトルで正しさを確かめられる。保守されていないライブラリより、JDK の HMAC か保守されている小さなライブラリが安全 成り立った (a) JDK だけの実装も (b) java-otp も試験ベクトルを満たし、(c) は 2020 年が最後で依存とライセンスの記載に難がある。(b) は依存がなく 2026-08 に公開されている。(a) と (b) の差は小さい
    H3 再利用の拒否と 5 回の失敗のロックは、TOTP の検証の外（アプリケーションの記録）で持つ必要がある 成り立った どの候補も再利用と失敗の記録を持たない。利用者ごとの最後の時間の刻みと失敗の回数をアプリケーションで持ち、別の session からの再送とロックの境界で確かめた。本体では表を条件付きの UPDATE で原子的に更新する（ADR-011）

    開発レビューと対応¶

    確認ポイント 5 に従い、xp-architect と xp-tester の 2 つの視点でレビューした（Bolt 13 のレビュー）。

    重要度 件数 主な指摘 対応
    高 7 期限切れの session に TOTP を送って 8 時間延ばせる、TOTP の段で session の ID が変わらない、入力済みの守りが 1 層だけ、ロックと 8 時間の境界のテストがない、java-otp が流れで動いていない、identity への置き方がない スパイクで直しテストを足した（R-01 の一部、R-03〜R-07）。ADR に書いた（R-01 の残り、R-02）
    中 11 全体の注釈と初回の登録の関係、Spring Session JDBC、原子的な更新、ライブラリの根拠、リスク台帳の列、特性テスト テストを足すか ADR に書いた。特性テストなどは W5（D-47）
    低 5 成功の後の行き先、RequiredFactor の有効期間、SessionTimeoutTest の弱さ ADR に書いた

    ふりかえり（KPT）¶

    • Keep:
    • 本体と分けたプロジェクトの学習テストで確かめ、ADR の根拠を後から再現できる形で残した
    • tester のプローブとミューテーションが、テストの数では分からない穴（期限の迂回、境界の抜け）を見つけた
    • Spring Security の振る舞いを、推測でなく jar の公開 API とバイトコードで確かめた（RequiredFactor、要素を合わせる条件）
    • Problem:
    • ADR に「確かめた」と書いた範囲が、学習テストの裏付けより広かった（8 時間、java-otp、既定の A-02）
    • 境界のテストを「同時刻」の 1 点だけで書いた。プロジェクトのテスト戦略の 3 点の規則をスパイクに当てはめなかった
    • Red の記録で、失敗の理由が本命のアサーションか前提かを分けなかった
    • リスク台帳で下げる列を誤った
