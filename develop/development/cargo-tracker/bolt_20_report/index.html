    Bolt 20 終了報告 - 確定した経路の割当てと荷主の承認（US-24 AC4・AC5）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    人の指示（/goal Bolt20）により、計画の承認から終了報告の前まで、すべての承認ゲートで止まらずに進めた。止まらなかったゲートごとの判断を、ここでまとめて確かめてほしい。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 計画の確認ポイント 1〜12 を推奨のまま採った 範囲（US-24 AC4・AC5）と D-71 の形は人が決めていた。確認ポイントはその形から導いた細部 Bolt 20 計画
    2 ADR-014 の文面（下流から上流への通知。DE-05・DE-06・DE-07 に適用、イベントの発行の仕方の基準、技術の失敗は起動のときの再配信）。ステータスは「提案」にしてある。承認なら stable にする D-71 で人が採った推奨の形をそのまま書いた。レビューで、再配信が起動のときだけであることを書き直した（D-77） ADR-014
    3 ステップ 2〜4 の Red・Green と、データベース・モジュールの境界・画面のゲート 列・CHECK・表・公開 API・画面の文言は、計画の設計とデータモデル・UI 設計・ADR-014 のとおり。計画からの変更（C-17、輸送要求の状態の値、C-17 の補足の文言）は設計文書に戻した（T-53） 計画の各ステップの結果
    4 開発レビューの判断 D-73〜D-77 を直し、D-78 を後に回した 欠陥（遅れて届いたイベントの偽の警告）と荷主の画面の矛盾（承認の後の失効）はこの Bolt で直した Bolt 20 のレビュー
    5 荷主と営業の画面の文言（C-17 の「承認は本予約の確定ではありません」「有効期限（…）までに承認してください」、C-04 の承認の前後と失効の案内、S-02 の「経路設計中・荷主承認待ち・予約待ち」、S-07 の「確定した経路は見積りに割り当てられ、荷主の承認に進みます」、荷主の画面の状態の表示名） UI 設計の C-17 の行と、利用者代表・テクニカルライターのレビュー UI 設計、テンプレート、動画
    6 期限を過ぎた詳細設計依頼済みの見積りにも割り当て、承認で失効として拒否する（荷主承認待ちのまま新しい見積りの依頼を案内する） 計画の確認ポイント 3。レビューで出口がないと指摘があり、出口（経路設計の途中の再見積り）は US-05・US-08 で決めると記録した レビューの矛盾事項 2
    7 #5 をクローズした（R0.1 の範囲。AC2・AC3 は既存の #26。計画の確認ポイント 1 の「新しい Issue」は作らなかった） #26 がすでにあった #5
    8 デモの動画は Bolt 20 の 1 本だけを足し、demoVideo が撮り直した過去の Bolt の動画は元に戻した。承認の後、人が DEMO_BOLT=bolt-20 DEMO_ISSUE=5 npx gulp issue:attach-demo で #5 に添付する 過去の画面のうち変えたのは S-02 の見出しと S-07・S-06 の文言だけ docs/assets/demo/bolt-20/
    9 人に確かめてほしいこと: デモ環境で経路設計者として RC-2026-0902 を確定し、荷主 A で TR-2026-0905 の見積りと経路を承認する。あわせて、C-17 をスクリーンリーダーで操作して #5 の完了の定義の手動の確認を記録する デモ環境はセッションのネットワークの方針で接続が拒否される。同じ dev プロファイルとサンプルのデータで手元に起動して、同じ流れが通ることは AI が確かめた（デモ項目の節） —

    基本情報¶

    項目 内容
    Bolt 第 20 回
    期間 2026-10-08 10:10 JST（計画のコミット 14b9174）〜 11:55 頃（本報告の初版）
    対象 U1 見積り。US-24 見積りと経路に回答・承認する（AC4・AC5）。#5（R0.1 の残り）。Bolt 19 レビュー D-71
    計画 Bolt 20 計画
    ゴール 経路設計者が経路を確定すると、経路設計の中の listener が見積りの公開 API で依頼元の見積りに経路版を割り当て、見積りと輸送要求が荷主承認待ちになる。荷主担当者が C-17 で見積りと確定した経路を確かめて承認すると、承認が記録され輸送要求は予約待ちになる。失効・置換済みの見積りへの承認は拒否される
    進め方 /goal Bolt20 で承認ゲートを止めずに進めた（上の議題）

    デモ項目¶

    デモ項目 受入条件 動画
    荷主がキー操作だけで確定した経路と見積りを確かめて承認する US-24 AC4 approve-quotation-and-route.webm

    AI は動画（19.5 秒）を 1 秒ごとのフレームで通して確かめた。提出 → 見積りの算出と提示 → 回答 → 経路設計者の算出と S-07 の確定（「確定した経路は見積りに割り当てられ、荷主の承認に進みます。」）→ C-04 の「見積りと経路の承認待ち（お客様の対応待ち）」→ C-17 → 承認の後の C-04（「…の見積りと経路を承認しました。担当営業が本予約を確定します。」、状態「予約待ち（A 社の対応待ち）」）の順に映っている。キー操作の細部（フォーカスの移り）は、uiTest のキー操作のステップが確かめている。

    デモ環境（Heroku）は、このセッションのネットワークの方針で接続が拒否される（connect_rejected）。代わりに、デモ環境と同じ dev プロファイルとサンプルのデータ（db/dev-data）で手元にアプリケーションを起動し、ブラウザで、経路設計者として RC-2026-0902 の候補 1 を確定し、荷主 A として TR-2026-0905 の見積りと経路を C-17 で承認した。S-06 の結果の文言、C-04 の状態の移り（見積りと経路の承認待ち → 予約待ち）、C-17 の確定した経路（RC-2026-0902 経路版 1、DEMO-101、到着予定）、S-02 の「荷主承認済み（予約待ち）」を確かめた（2026-10-08）。デモ環境そのものでの確かめは人に依頼する（議題 9）。支援技術（スクリーンリーダー）による手動の確認はこのセッションではできず、#5 の完了の定義のその項目は未確認のまま残す（axe-core の自動検査は 0 件）。

    仮説の結論¶

    # 仮説 結論
    H1 下流から上流への通知を「下流の listener が上流の公開 API を呼ぶ」形にすれば、依存は routing → quotation :: api のままで、DE-06・DE-07 も同じ形で足せる 成り立った。routing の依存は増えず、見積りは経路設計を参照しない（ApplicationModules と ArchUnit）。ただし公開 API に「操作」が入り、理由の契約・不正な依頼の扱い・再配信の時期（起動のとき）を決める必要があった（D-75・D-77）
    H2 割当ての時に経路の情報を写せば、見積りは経路設計に問い合わせずに C-17 を描ける 成り立った。C-04・C-17 は見積りの写し（案件番号・経路版・確定の時刻・区間）だけで描いている。写しを後で書き直す（W6 の経路版の差し替え）規則は D-78
    H3 割当てを冪等にすれば、DE-05 の再配信は再配信だけで済む 成り立った。受入シナリオ（再配信）と統合テストが通った。ただし、輸送要求の側では、新しい状態を足したことで既存の listener の「済んでいるか」の判定が古くなり、遅れて届いたイベントで偽の警告が出ていた（D-73。hasReached にそろえた）
