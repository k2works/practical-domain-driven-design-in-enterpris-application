    Bolt 38g 終了報告 - 経路設計と追跡の担当範囲の絞り込みと、US-16 の締め¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    経路設計と追跡の社内の 9 つの入口を、業務担当者の担当企業で絞りました。範囲の外は 404 にし、状態を変える POST（候補の算出・確定・マイルストーンの登録）だけで「担当範囲の外の試行」を記録します。これで US-16 の AC1〜AC5 がそろいました。この報告の承認の後に #14 を閉じます。

    # 確かめてほしいこと 見る場所
    1 スキーマ: routing.routing_case.shipper_company_id を 3 段で足した。common で null 可で足して索引 ix_routing_case_shipper (shipper_company_id, quotation_expires_at) を付け、dev-data で輸送要求の荷主企業から埋め、common で SET NOT NULL にした。H2 と PostgreSQL の両方で通る。リスク: 本番・ステージングに案件の行があると 3 段目で起動が止まる（今は profile がなく、デモは 2 段目で埋まる）。W10 の運用準備の手順書に「配備の前に行数を確かめる」と「失敗したときの戻し方」を足す V20261029100000・V20261029100900・V20261029101000、data_model
    2 公開 API: 見積りの RouteConditionView に荷主企業（CompanyId）を足した。主体ではなく値。新しい ADR にせず、ADR-014 の改訂（改訂の経緯の節）で記録した（確認ポイント 2 の承認の範囲） ADR-014、architecture_backend
    3 認可の順: POST は値を読む前に、ロックしない照会で範囲を確かめ、範囲の外なら記録して 404。コマンドの中は「読み出し → 範囲 → 版の照合・登録済み・発生時刻」の順。経路設計の型の誤り（数でない版・候補番号）は範囲によらず 400 で記録しない。GET は記録しない RoutingCaseController・TrackingRecordController、RoutingCaseScope・TrackingRecordScope
    4 記録の部品と ArchUnit: 部品は 4 つ（見積り・予約・経路設計・追跡）。呼び手とトランザクションの規則を名前の規則 ..interfaces.web..*OutOfScopeResponder に変え、閉じる規則（4 つの FQN のどれかで、トップレベル・@Component）と FQN ごとの実在の見張りを足した。経路設計と追跡の部品は種類を中で固定した（開発レビュー） LayerArchitectureTest
    5 画面の文言（計画の表にない文。承認をお願いします） 下の表
    6 SpotBugs の除外を 1 つ足した: RoutingCaseLookup$Found の EI_EXPOSE_REP・EI_EXPOSE_REP2。見つかった集約をそのまま呼び手に渡す入れ物で、38f の StaffTransportRequestLookup$Found と同じ理由でこのクラスに限って抑止した。手元で check を流さず test だけで push したため、CI の check で初めて見つかった config/spotbugs/exclude.xml

    議題 5 の文言¶

    場面 文言 理由
    停止の確認で、選べる担当がなく変えられない企業だけを担当しているとき 担当企業: この画面で変えられない企業 {N} 社を担当しています。 計画の表のとおりに組み合わせると「担当企業: なし。この画面で変えられない企業 {N} 社も担当しています。」と食い違うため
    担当範囲の割り当ての確認の「影響」の欄とマニュアル 11.8（38e の「今後の更新から」を外した後の文） この利用者の担当企業が変わります。業務の画面では、次の操作から変更後の担当企業で絞られます。 計画は「今後の更新から」を外すだけだったが、外すと意味が足りなくなるため、request ごとに担当企業を読み直す今の振る舞いを書いた
    詳細の担当企業がないときの案内 担当企業はまだありません。担当企業は、業務の画面で扱える企業を絞るために使います。 同上
    停止の確認の行（直すかを諮る） 見出し（dt）「担当企業」に続けて、本文（dd）が「担当企業: 荷主 北。」になる スクリーンリーダーでは「担当企業」と 2 度読まれる（開発レビューの低 11）。推奨は、本文から接頭の「担当企業: 」を外すこと。承認を受ければ次の Bolt で直す

    計画は 2026-10-29 に承認を受けた（e126da0f2。約 12.7 時間を分割の規則の例外として受け入れる）。打ち切りの点検は 2 回とも「続ける」にした（3a の後で約 35 分、5 の後で約 65 分）。計画から外れた点は次のとおりです。

    • 新しいテストのファイル RoutingCaseCommandServiceScopeTest: 計画の一覧になかった。行 5c・5d（コマンドのサービスの単体）を置ける既存のテストがなかったため
    • UI のシナリオの準備: 経路設計案件と、AC5 の確定した案件はリポジトリに直接保存する（38f2 の前例）。ステップは既存の StaffAssignedScopeUiSteps と UserAdministrationUiSteps に足した
    • 担当企業のない主体の一覧の案内: controller の単体では書けない（@WithAuthenticatedActor が担当企業を必ず与える）ので、セキュリティの統合テストの行 6 だけで確かめた
    • 輸送要求の前例の規則は写していない: 「範囲を確かめない読み出しは判定の部品だけが呼ぶ」は、主体を持たない読み出し（confirmedLegs・evaluateConfirmedRoute）が同じ口を使うため、経路設計には置いていない
    • 確認ポイント 19 の UI のシナリオ: 計画の行 8 は AC に結び付かないので、AC のタグを付けずに manage_user_status_ui.feature に足した
    • 38f の記録の部品: 見積依頼と見積りの 2 つの種類を使うので、種類を引数で受ける形のまま残した

    判断と学び¶

    • 公開 API に足すのが「値」なのか「主体」なのかを分けると、ADR の扱い（改訂か新規か）を決めやすい。38f2 は主体（操作者）、38g は値（荷主企業）だった
    • 文言の表は場合を組み合わせて読み、矛盾した文ができないかを計画の段階で確かめる。今回は実装の段階で「なし。…も担当しています。」に気づいた
    • テストの準備でリポジトリに直接保存するときは、本番のコマンドと同じ口（save と update）を使う。違う口を使うと、外部キーや一意の制約で準備が落ちる
