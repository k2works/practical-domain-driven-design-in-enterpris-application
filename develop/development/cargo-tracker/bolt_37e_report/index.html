    Bolt 37e 終了報告 - US-07 AC5 の見積りの側（割り当てた経路の再設計要の印、荷主の承認と本予約の判定、見積りの公開 API）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    経路設計が経路版を再設計要にしたことを、見積りの公開 API で伝えられるようにしました。その経路版を割り当てた見積りすべてに印が付き、荷主の承認と本予約の照会を拒否します。本番で印を付ける入口（DE-06 の listener）は Bolt 37e2 なので、利用者に見える振る舞いはまだ変わりません。

    1 回目の終了報告の承認の場で「直してから」と指示を受け、次の 4 点を直しました。

    # 確かめてほしいこと 見る場所
    1 荷主承認待ちの出口を作った（決定の変更）。印のある荷主承認待ちは、承認済みと同じく有効期限の後に再見積りできるようにした。旧版は失効し、新しい見積りは経路と印を引き継ぐ。提示しても荷主の承認は再設計要で拒む。期限内と、印のない荷主承認待ちは今のまま。前の決定 D-86（荷主承認待ちは再見積りできない）を、印のある場合だけ変えた（human:kakimomokuri。台帳・ドメインモデル・US-07 に書いた） Quotation.requoteRejectionAt、集約のテストの行 14b・14c、受入シナリオ「荷主承認待ちの…有効期限の後に再見積りでき」
    2 照会のキャッシュをテストで確かめた。経路版で見積りを引く照会は MyBatis のセッションのキャッシュを使わない（flushCache）。同じトランザクションで照会し直すと、ほかのトランザクションが後からコミットした見積りが当たることを、PostgreSQL の統合テストで確かめた MyBatisRouteRedesignQueryIntegrationTest
    3 Red を見直した。開発レビューの後に足したテストと、この直しで足したテストは、テストが守る本体の文を一時的に戻して、期待した理由で落ちることを確かめてから戻した（下の「Red の確かめ」）。行 20 のテストは今の穴を固定する特性テストで、落ちる形がない。Bolt 37e2 で穴を塞ぐときに期待値を反転させ、その Red として使う 下の表
    4 報告の書き方を直した。議題を短くし、表を要るものだけにした この報告

    計画は 2026-10-22 に承認を受けた（ebba74d61。データベースのマイグレーション 1 つを含む）。開発レビューを受けて計画から変えたのは、照会のキャッシュ（議題 2）と、荷主承認待ちの出口（議題 1。1 回目の報告では既知の制限として書き分けただけだった）の 2 点。

    Red の確かめ¶

    テスト 戻した本体の文 落ちた理由
    印のある見積りの再見積りで新しい見積りが印を持って保存される（統合） INSERT から印の列を落とす 新しい見積りの印が null
    同じトランザクションで照会し直すと後からコミットした見積りが当たる（統合） 照会の flushCache を外す 2 度目の照会がキャッシュから最初の 1 件だけを返す
    印のある荷主承認待ちは有効期限の後に再見積りできる（集約）、同じ受入シナリオ 出口の判定がない今のコード（テストを先に書いた） 再見積りが ROUTING_REQUESTED で拒まれる、見積り 1 が荷主承認待ちのまま

    ステップ 2〜5 のはじめのテストは、まずテストのコンパイルの失敗（型と操作がない）で落ちることを見た。次に型と空の操作だけを作り、期待の値の誤りで落ちることを見てから中身を作った。

    直しの途中で check が 3 回落ちた。1 回目は、キャッシュのテストがコミットした業務番号（2085 年）がほかの統合テストとぶつかった（空いている 2094 年に変えた）。2 回目は、裏で流していた SonarQube と同じビルドの場所を同時に使った（SonarQube はほかの Gradle が終わってから流す T-147 を守れていなかった）。3 回目は sed で改行が変わったファイルの整形の検査だった。

    判断と学び¶

    • 事実の写し（印）を集約の値に持たせると、写す操作（再見積り）を増やさずに済んだ
    • 照会し直しで正しさを守ると、永続化の層のキャッシュに頼ることになる。メモリ上のリポジトリのテストでは見えず、データベースで別のトランザクションを挟むテストが要った
    • 出口のない状態を「既知の制限」と書くだけでは足りなかった。状態の組み合わせの表に「その後どう動けるか」の列を置けば、計画の段階で出口を決められた

    ふりかえり（KPT）¶

    • Keep: Bolt を 3 つに分け、出発済みの判定を 37e3 に移して、利用者に見える変化を出さずに契約を固めた。型と空の操作を先に作り、期待の値の Red を見てから作れた
    • Problem: 入力ポートを組み立てに足し忘れた。保存の列を落とす変異を計画に入れていなかった。出口のない状態を既知の制限で済ませ、承認の場で直すことになった
    • Try:
    • T-180: 新しい入力ポートやアダプターを作ったら、同じステップで組み立てに足し、統合テストを 1 本流す
    • T-181: 列を足す Bolt の変異には、挿入・更新・読み戻しから列を落とす変異を入れる
    • T-182: 状態の組み合わせの表に「その後に取れる操作（出口）」の列を置き、出口のない行は計画の確認ポイントにする
