    仮説の結論¶

    # 仮説 結論 根拠
    H1 @ui を CI の中でアプリを起動して毎回動かせ、E2E の目標（10 分以内）に収まる 成り立った ui ジョブは約 2 分（Playwright のブラウザのキャッシュあり）。check と並行して動く
    H2 業務ルール層と画面の層の受入シナリオを、別のスイートとして共存させられる 成り立った（課題あり） グルーを分け、タグで振り分けた。check では画面の層は動かない。ただし uiTest では業務ルール層のシナリオと ArchUnit のテストも重ねて動く（下の「既知の課題」）
    H3 用語集とクラス・Javadoc の整合を、テストで機械的に確かめられる 成り立った Red で用語集の欠落 5 件を検出し、用語集を直して Green。Javadoc の食い違いも検出する（入力の宣言の後）
    H4 追記専用の表の UPDATE・DELETE を、PostgreSQL の権限で拒否できることを確かめられる 成り立った 統合テストで 42501 を確かめた。REVOKE を外すと更新・削除のテストだけが失敗した

    判断と学び¶

    設計への反映（反映済み）¶

    • D-1: ADR-003 に補足の決定と改訂の経緯を書き、ドメインモデルの共有カーネルの図からインターフェースを外した
    • D-3: 要件定義の KPI-01、KPI-INV-01、US-21 に、開始時刻（版 1 の最初の提出、差戻し・再提出で戻さない）を書いた
    • D-4: 用語集と輸送要求の集約に業務番号を書いた。データモデルの列と採番は、US-01 AC2 の Bolt で設計する（「注」として残した）
    • D-5: ADR-001 のコンプライアンスから、合成ルートの例外を参照した
    • D-6: US-01 AC2 と Q-INV-01 に、出発地と目的地が同じ依頼を誤りとすることを書いた
    • Spotless: 技術スタックの「承認待ち」を外した。D-7: Dependabot を有効にした
    • 用語集の表に、共有カーネルの 4 つの型と輸送要求 ID を足した
    • テスト戦略に、ステージングができるまで E2E を CI の中で動かすことを書いた
    • 開発戦略のコマンドの表に、設計ドキュメントの生成と画面の層の受入シナリオを書き、手順書を参照した

    既知の課題¶

    課題 影響 扱い
    uiTest で、業務ルール層のスイート（シナリオ 1 本）と ArchUnit のテストも動く。Gradle のクラス名のフィルターが、JUnit Platform Suite の子と ArchUnit のエンジンに効かないため 数秒の重複。結果に関係ないテストが混ざる 次に受入シナリオを増やす Bolt で、スイートをタグかソースセットで分ける
    プラグインが Configuration.setVisible（Gradle 11 で削除）を使う警告 なし（Gradle 11 まで） プラグインの更新（Dependabot）で追従する
    Dependabot がまだ動いていない 既定ブランチ（main）にある設定だけを読むため、develop を main にマージするまで動かない main へのマージの時期とブランチ保護の必須チェックは人の判断（D-12）
    完了画面と画面の層のシナリオが内部の ID（UUID）を表示・検証する D-4（画面に UUID を出さない）と食い違う意図的な負債 US-01 AC2 の Bolt で、業務番号の採番と合わせて直す（R-03）。手順書にも書いた
    社内の KPI 計測記録の一覧が UTC だけを表示する BR-10（JST を主、UTC を括弧で併記）と違う 仮の画面。S-22 の本実装で直す

    Bolt 2 の Try の結果¶

    Try 結果
    T-6 【要確認】を計画の承認でまとめて確認する 実施した。実行中に人の判断を待つことはなかった
    T-8 品質ゲートを足したら不合格で失敗することを確かめる 実施した。axe-core（ラベルを外す）、用語集の整合（用語集にない型、Javadoc の食い違い）、権限（REVOKE を外す）。用語集の整合テストの検査の穴（UP-TO-DATE で飛ばされる）を、この確認で見つけた
    T-9 手順書の差分がないうちはステップを完了にしない 実施した。手順書を書き、書いたコマンドを実際に動かしてから完了にした

    ふりかえり（KPT）¶

    • Keep:
    • 開始準備の突き合わせで設計の欠落（用語集の 5 つの型）を予測し、整合テストの Red がそのとおりに出た
    • 不合格の側を確かめて、検査そのものの穴を見つけた
    • 【要確認】を前もってまとめて確認したので、実行が止まらなかった
    • Problem:
    • テストの入力（ソースの Javadoc、設計文書）を Gradle に宣言しておらず、検査が黙って飛ばされうる状態を一度作った
    • uiTest のフィルターが思ったように効かなかった
    • コマンドを && でつないだため、途中の grep -c が 0 件で後ろの okf:check が飛ばされた（コミットの後に確かめ直した）
    • Try:
    • T-10: ビルドの成果物以外（設計文書、ソースの文字）を読むテストを足したら、Gradle のタスクの入力として宣言する（AI、次にそうしたテストを足すとき）
    • T-11: 検証のコマンドを && でつなぐときは、件数を数えるだけの grep -c を途中に置かない（AI、すぐ）
    • T-12: 権限や設定の保護を足したら、本番と同じ最小の権限でアプリを起動するテストを同時に足す（所有者で動かすと、設定の誤りが黙って通る。Spring Modulith の自動初期化の例）（AI、次に権限を変えるとき）
    • T-13: 終了報告の時刻は、計画の承認と報告のコミットの時刻を根拠にする（AI、次の報告）

    レビューとクローズ¶

    Bolt 3 開発成果物レビュー の指摘をクローズの前に直した（詳細はレビューの「対応結果」）。主なものは次のとおり。

    • 最小の権限で動かす（R-01）: 画面の層のアプリを、アプリケーション利用者（最小の権限）で接続して動かすようにした。Flyway だけを所有者で動かす。これで、Spring Modulith 2.1 が既定で起動時に CREATE SCHEMA を実行し、最小の権限では起動に失敗することが分かった。所有者で接続していた間は黙って成功していた。スキーマの自動初期化を無効にし、本番で起きる前に直した
    • 追記専用の保護（R-02・R-09）: 名指しの REVOKE をやめ、表の定義の印（COMMENT ON TABLE ... IS 'append-only'）で選ぶ形（fail-closed）にした。ステージング・本番では、アプリケーション利用者がなければマイグレーションを失敗させる
    • axe の検査（R-06）: すべての @ui のシナリオで違反を必ず確かめるフックにし、WCAG 2.2 AA の基準を明示した
    • テストのコード（R-11〜R-19）: 次の点を直した
    • Playwright を Spring の部品にした
    • 待ちを、間隔を置いて同じスレッドで読み直す形にした
    • ラベルで要素を取るようにした
    • Tab のたびにフォーカスを確かめる
    • 用語集の整合テストを別のタスクにし、@Entity も対象にした
    • タグでスイートを振り分けた
    • ステージングへ移すための継ぎ目を作った
    • 失敗した画面を残す

    コードの修正の後も、CI（41ec8d2、check と ui）と SonarQube の品質ゲート（コマンドの成否で PASS）は緑。
