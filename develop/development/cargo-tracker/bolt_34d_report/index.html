    Bolt 34d 終了報告 - 利用者の利用停止と再開（US-16 の一部）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-17 に承認を受けた（73f824317）。/goal の下で、ステップ 1〜6 の承認ゲートで止まらずに進めた。層・モジュールの規則には当たらず、打ち切りの条件にも当たらなかった。開発レビューの後に 2 点を諮った（議題 2）。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 止まらなかった承認ゲート: ステップ 1（設計文書）、2（Red・Green、セキュリティ）、3（セキュリティ）、4（画面・セキュリティ）、5（文書）、6（終了報告の前の直し） 各ステップで Red を確かめてから実装し、check を緑にして push した。スキーマは変えていない。認可の守りはセキュリティの統合テストを先に書いてから入れた 成果の表、UserStatusChangeSecurityIntegrationTest
    2 開発レビューの後に人が決めたこと（2026-10-17、human:kakimomokuri）: (5) 停止の確定で、相手の未使用の password の再設定のトークンを無効にする（確認ポイント 13 を改めた）。(6) 再開の確定の後に、相手の前の session をすべて消す（停止ではすぐ消さない決定 2 は変えない） セキュリティ（中）: 緊急停止の後 30 分以内に再開すると、漏れたリンクで password を設定し直せる。アーキテクト（中）: 相手が 1 度も操作しないうちに停止して再開すると、前の session を使い続けられる UserStatusChangeService、domain_model の IA-INV-04・IA-INV-12
    3 計画からの変更（人に諮らずに変えた）: (a) 確認の領域のボタンを「確定する」から「停止する」「再開する」に（役割の変更の確認の「変更する」に合わせた）。(b) 完了の知らせに影響を添えた（「利用を停止しました。相手の次の操作から使えなくなります。」）。(c) 同じ状態の拒否のときは詳細のフォームを最新の版で示す。(d) 確定の POST は、状態と版の値を管理範囲の判定の後に解釈する（範囲外の利用者への値の誤った確定も試行を記録してから 404）。(e) 監査の変更前の状態を判定に使った利用者から渡し、変わっていない変更は記録しない。(f) 詳細のエラー要約を役割と利用状態で 1 つにした。(g) controller の文言の単体テスト UserStatusErrorMessageTest を新しく作った（計画の新しいファイルの一覧の外。前例は KpiObservationControllerTest） どれも約束の範囲を変えない守りと文言の直し。開発レビューの指摘への対応 UserAdministrationController、AuditRecord、ui_design の S-20
    4 ほかの Bolt の動画とキャプチャを戻した: demoVideo と manualScreenshots は全部を撮り直すが、ほかの Bolt の差分は日時と乱数の違いだけなので、新しい 2 本（bolt-34・bolt-34d）と 11 章のキャプチャだけを残した 差分を意味のある変更だけにする docs/assets/demo/bolt-34・bolt-34d、docs/manual/assets/11-*

    開発レビューの指摘と扱い¶

    # 観点 重大度 指摘 扱い
    1 セキュリティ 中・要判断 停止しても未使用の再設定のトークンが残り、30 分以内の再開で使える 人が決めた（議題 2 の (5)）。停止の確定で無効にする
    2 アーキテクト・セキュリティ 中・要判断 相手が操作しないうちに停止して再開すると前の session が残る。緊急停止でも処理中の request は止まらない 人が決めた（議題 2 の (6)）。再開の確定の後に前の session を消す。処理中の 1 回分の request は残る隙として既知の課題に
    3 アーキテクト・テスター 中・低 同じ状態の拒否の後、フォームの版が古く次の操作が必ず古い版で拒まれる 最新の版で示す
    4 テスター 中 updated_at の検証が空振り、過去の監査の行を件数で見ている 時計を進めて比べ、行の ID が残ることを確かめる形にした
    5 テスター 中 詳細を読んだ後に範囲から外れる枝と、拒否の文言が未テスト セキュリティの統合テスト（spy）と文言の単体テストを足した
    6 セキュリティ 低 版の誤った確定は範囲の判定の前に 400 になり、範囲外の試行が残らない 値の解釈を範囲の判定の後にした
    7 アーキテクト・セキュリティ 低 監査の変更前後を操作の向きで決め打ち 判定に使った利用者の状態を渡し、変わっていない変更は拒む
    8 テクニカルライター 中 停止の理由の違い、問い合わせを受けた管理者の手がかり、同じ状態の文言、00 章・用語集の追従、知らせに影響がない マニュアルと知らせの文言を直した
    9 テスター・アーキテクト・テクニカルライター 低 エラー要約の id の重複の恐れ、拒否のテストの 1 つにまとめた形、login の時計を進める写し 要約を 1 つにまとめ、テストを分け、使った刻みを戻す前例に合わせた
    10 アーキテクト・テスター 中・低 判定の前半の写し、controller の大きさ（579 行）、DetailForm の引数、利用状態の名前の写し、役割の領域の見出し 34c の行に送った（W6 の 3 つ目の操作の前に、詳細の描画を部品にして controller を分ける）
    11 テクニカルライター 中・低 詳細に停止の理由・停止した人・時刻が出ない、一覧のキャプチャに停止の例がない、担当の案件の引き継ぎ 既知の課題に送った（後の Bolt の候補）

    判断と学び¶

    • 「すぐ消さない」決定の副作用は、逆向きの操作（再開）で現れた。状態を 2 値で持つ操作では、往復（停止 → 再開）の後に何が残るかを計画の段で確かめる
    • 停止は「入れなくする」だけでなく、停止の前に配った鍵（再設定のリンク、既存の session）を無効にするかを同時に決める必要があった
    • 値の検証（400）を範囲の判定より先にすると、範囲外の試行が記録から漏れる。記録を伴う守りは、入力の解釈より先に置く

    既知の課題（後に持ち込む）¶

    • 停止の確定の時に相手が処理中の request は最後まで動く（request ごとの確かめの作り。隙は 1 回分）
    • 詳細に停止の理由・停止した人・時刻を示さない（監査記録にだけ残る）。一覧のキャプチャに停止の例がない
    • 停止する相手の担当の案件の引き継ぎ（W6 の担当案件と一緒に検討する）
    • 34c に送ったもの（Bolt 34c の開始準備で 34c・34e・34f に分けた）: 判定を通さずに呼べる changeRoles・changeStatus（→ 34e）、RoleChangeResult の共用（→ 34e）、判定の前半の写し（→ 34e）、controller の分割と詳細の描画の部品化（→ 34f）、利用状態の名前の写し（→ 34f）、役割の領域の見出し（→ 34f）、セキュリティの統合テストの login の写し（→ 34e）
    • Bolt 34b からの既知の課題（範囲外の POST の時間の差、テストの割り当ての暗黙の準備ほか）は変わらず。34d の確定にも同じ形がある
    • ffmpeg がない環境で、デモの動画のフレームを切り出して確かめられなかった（シナリオは緑で通った）
