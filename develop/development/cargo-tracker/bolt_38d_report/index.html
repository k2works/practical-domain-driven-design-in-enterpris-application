    Bolt 38d 終了報告 - TOTP の解除・登録・再登録を本人のメールで知らせる¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    管理者による TOTP の解除、解除や招待の後の A-07 の登録、回復コードの経路の再登録（A-08）の 3 つを、本人の登録メールアドレスに知らせるようにしました。#47 の AC9 の「本人へ通知される」と、SEC-10 の「解除と再登録を本人のメールで知らせる」を満たします。#47 は、残りの回復コードの案内（38d2）をそろえてから閉じます。

    # 確かめてほしいこと 見る場所
    1 セキュリティ（いつ送るか）: DE-26〜DE-28 を監査と同じトランザクションの中で出し、コミットの後に identity のハンドラーが ACL を通して通知の公開 API を呼ぶ。解除・登録・再登録が成り立たなかったとき（拒否・0 件・Unverifiable・Superseded ほか）と、監査が書けずに戻ったときは出さない。停止中の利用者にも送る（悪用に本人が気づくため）。送れなければ通知を失敗として記録し、警告のログだけを残す（解除などは戻さない） UserLoginCredentialService・TotpEnrollmentService・TotpReEnrollmentService、2 つのハンドラー、UserLoginCredentialRollbackIntegrationTest
    2 セキュリティ（何を残さないか）: 本文・Request と Command の toString・発行記録（event_publication）・ログ・失敗の理由に、メールアドレスを残さない。アドレスは正規表現の 1 つで伏せる（開発レビューで、同じ働きの明示の伏せ字を消した） MailDelivery、TotpMailRequestsTest、TotpNotificationIntegrationTest
    3 文面: 3 通の件名と本文は UI 設計の全文のとおり。件名は前例の「…のご案内」。解除のお知らせだけ「システム管理者が」と役割を書き、個人名・本人確認の手段・企業名・回復コードの値・リンクは書かない。連絡先は既存の文「荷主の方は担当営業に、社内の方はシステム管理者にお知らせください。」 resources/mail/totp-*.txt、NotificationMailAdaptersTest
    4 スキーマ: ck_notification_kind に TOTP_RESET_BY_ADMIN・TOTP_ENROLLED・TOTP_RE_ENROLLED を足すマイグレーション V20261027110000（前例 V20261026100000 と同じく DROP と ADD を別の文にする） マイグレーション、MyBatisNotificationRepositoryIntegrationTest（全部の種類の保存）
    5 構造: 共有の部品を LinkMailDelivery から MailDelivery に改め、リンクのないメールにも使う（伏せる文字列のリストを持つ 1 本の道）。公開 API は種類ごとの口のまま（TotpResetMail・TotpEnrollmentMail。登録と再登録は Request の reEnrolled で分ける）。ADR-017 の見直しは「種類ごとのまま」と記録した。再設定と招待の振る舞いは変えていない ADR-017、MailDelivery

    計画は 2026-10-27 に承認を受けた（1a5650d61）。計画から変えたのは次の点です。

    • 受入の Red の順: 計画は受入シナリオで Mailpit に届かない Red を先に見る順だったが、裏の実装を先に入れたので、受入で見えた Red は確認の画面の影響の文だった。お知らせの段は、変異 V1〜V3 を uiTest でも流して落ちることで補った。
    • DE-27・DE-28 の通しの確かめ: 統合テスト（TotpNotificationIntegrationTest）はハンドラーを直接呼ぶ。サービスがイベントを出しコミットの後に届くことは、サービスの単体テスト（発行の時点がトランザクションの中であることも照合する。開発レビューで足した）と受入シナリオ（A-07・A-08 の本物の流れ）で確かめた。計画の変異表は V2・V3 を統合テストで落とす見込みにしていたが、実際に落としたのは 2 つのサービスの単体テストと uiTest。
    • 招待の後の A-07 の登録: 登録の道は管理者の解除の後と同じなので、単体テストで確かめ、受入では管理者の解除の後だけを通した。
    • 伏せ字: 文字列のリストではなく Mask(text, placeholder) のリストにした（リンクは「[リンク]」）。空の文字列は拒む。
    • 付録 B: Q1-10（心当たりのないお知らせ）を新しく足した。登録・再登録のお知らせでは、すぐに password を再設定し（2.6）、そのうえでシステム管理者に登録の解除を頼む順にした。
    • ロールバックのテスト: 行 5 の確かめとして、UserLoginCredentialRollbackIntegrationTest に「解除のイベントの発行記録が残らない」を足した。
    • ACL: sendEnrolled・sendReEnrolled の 2 つの口にした（ハンドラーの真偽値の直書きをなくすため。開発レビュー）。

    Red の確かめ¶

    テスト 落ちた理由（中身を作る前）
    通知の記録の統合テスト（全部の種類） 新しい種類が ck_notification_kind に違反した
    MailDeliveryTest、解除・登録・再登録の新しいテスト 型がなく、コンパイルで落ちた
    解除のイベントの発行 UserLoginCredentialServiceTest が WantedButNotInvoked。TotpNotificationIntegrationTest の 2 本でメールが 0 通、発行記録が完了しない

    判断と学び¶

    • 打ち消しのない通知（お知らせ）でも、冪等の鍵とテンプレートの再現の鍵を監査記録の ID にそろえると、データモデルの「本文はテンプレートと対象から再現できる」の決まりを例外なしに守れる
    • 同じ働きの守り（明示の伏せ字と正規表現）を 2 つ重ねると、どちらかを外す変異が生き残り、テストで意図を示せない。守りは 1 つにする
    • イベントとハンドラーを統合テストで通すときは、ハンドラーを直接呼ぶとサービスの発行を見ない。発行の位置は単体（トランザクションの中かを記録する）と受入で見る
