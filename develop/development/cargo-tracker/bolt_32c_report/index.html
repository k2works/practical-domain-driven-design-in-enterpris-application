    Bolt 32c 終了報告 - request ごとの利用者の確かめ（US-18 AC6）¶

    承認の議題（T-36。先に確かめてほしいこと）¶

    計画は 2026-10-14 に確認ポイント 1〜10 を推奨のとおりで承認を受けた（77305d8）。/goal Bolt 32c の下で、ステップ 1〜6 の承認ゲートで止まらずに進めた。止めて諮る条件（層の規則の新しい例外、4.5 時間を超える見込み）には当たらなかった。

    # 確かめてほしいこと AI の判断の根拠 見る場所
    1 止まらなかった承認ゲート: ステップ 1（設計文書）、2（データベース: 読み出しの形、構造: ポートとサービス）、3（セキュリティ・認可: フィルターと主体の差し替え）、4（画面の層）、5（マニュアル）、6（レビューと報告） 振る舞いを足すステップは Red を確かめてから Green にした（T-83）。骨組みのクラスを置いて層の規則が緑のままであることを先に確かめた（T-101）。読み出し 1 回の見張りは、利用者と企業を別々に読む書き方を入れて 3 本落ちることを確かめた（T-112） 「ステップの結果」「指標」
    2 開発レビューで直した計画からの外れ: 公開の URL でも読んでいた。計画は「公開の URL では呼ばない」と約束していたが、フィルターは URL を見ず、認証済みの session の静的な資源（/css/** など）でも読み出していた。止められた利用者では、並行の資源の request が SESSION_REVOKED を重ねて書きえた。テストは cookie のない /login しか確かめていなかった 認証済みの session で静的な資源と A-03 を開いても読まないテストを先に足して落ちることを確かめ、公開の URL（SecurityConfiguration の PUBLIC_PATHS）をフィルターから外した（bcc605d）。計画どおりの形に戻しただけなので、設計の判断は変えていない SessionRevalidationFilter#shouldNotFilter、統合テストの「認証済みのsessionでも公開のURLと静的な資源では読まない」
    3 受け入れたこと（ADR-012 の決定 3 に書いた）: ①止められた利用者のログアウトの送信も確かめるので A-03 で終わり、監査記録は LOGOUT でなく SESSION_REVOKED になる。②同じ session の業務の request が同時に取り消されると SESSION_REVOKED が 2 行以上になることがある。③フィルターの順序の値は UsernamePasswordAuthenticationFilter と同じになり、登録の順で前に来る（並びは統合テストで見張る） ①止められた利用者の操作はすべて取り消しで扱う形がいちばん単純。②排他を入れると request ごとの確かめが重くなる。監査は欠けず、重なるだけ。③順序の値を明示する API がないので、並びを見張るテストで守る ADR-012 の決定 3
    4 計画からの変更: 500 のときのエラーのログ。計画（ステップ 3）は「エラーのログが残る（LogCapture）」としていた。フィルターでログを書いて同じ例外を投げ直すと、SonarQube の指摘（java:S2139、ログと投げ直しの二重）で Quality Gate が落ちた フィルターはログを書かず、利用者 ID を文言に足した例外に元の誤りを包んで投げ直す。エラーのログはコンテナが 500 にするときに残す。テストは元の誤りが原因にあり、文言に利用者 ID があることを確かめる形にした（03e24e2） SessionRevalidationFilter、統合テストの assertFailsWithContext
    5 画面の文言の提案（テクニカルライター）: A-03 の問い合わせ先の文を「ログインし直せない場合や、繰り返しログアウトされる場合は、荷主の方は担当営業に、社内の方はシステム管理者にお問い合わせください。」にする。止められた利用者は「繰り返しログアウト」でなく「ログインできない」になるので、今の文が症状に当たらない。止めたことは示さないので確認ポイント 2 と矛盾しない 画面の文言は計画の確認ポイント 2 で「変えない」と決めたので、変えずに諮る。採るなら画面・UI 設計・マニュアルの 2.4 を同時に直す（小さな直し）。マニュアルと付録 B の Q1-1・Q1-2 には、ログインできないときの案内をこの Bolt で足した session-expired.html、マニュアルの 2.4
    6 IA-INV-04 とロックの関係（アーキテクト、スコープ外）: request ごとの確かめはロック（Bolt 32）を見ないので、ロックされた利用者の既存の session は通り続ける。ロックは「ログインの試行」の規則なので意図どおりと読めるが、明文化されていない この Bolt では変えない。ロックはログインの試行を抑えるもので、session の取消しは管理者の操作（利用停止）で行う、と ADR か IA-INV-04 に書くかを Bolt 34（利用者の管理）で決めることを提案する ドメインモデルの IA-INV-04、ADR-011 の決定 9
    7 後の Bolt に送るもの（下の「既知の課題」） 開発レビューの中・低のうち、この Bolt で直さなかったもの 「既知の課題」

    仮説の結論¶

    # 仮説 結論 根拠
    H1 認証済みの request ごとに利用者・役割・企業を 1 回の SQL で読み、主体を作り直して差し替えれば、ログインの時点の役割でなく今の役割で認可できる 支持 役割を外した次の request でその URL が A-04、残した役割の URL は開け、足した役割の URL とナビの項目が出る（統合テスト）。1 つの request の読み出しは 1 回で、利用者と企業のリポジトリは呼ばない（見張り）
    H2 差し替えは request の中だけにし、session に保存しなくても、毎回作り直すので古い役割が戻らない 支持 特性テストで、新しい文脈は明示的に保存しなければ session に残らないこと、toBuilder() で要素の権限が残ることを固定した。8 時間の起点は役割を変えても変わらない（8 時間の 1 秒前は開け、8 時間で A-03）

    開発レビュー¶

    プログラマー、アーキテクト、テスター、テクニカルライターの観点で読んだ（並行の 4 つの視点。T-90）。

    # 観点 重さ 内容 対応
    1 プログラマー・アーキテクト・テスター 高 認証済みの session の静的な資源でも読み、止められた利用者では取消しを重ねて書く。計画の「公開の URL では呼ばない」に反し、テストの名前も事実と違う 議題 2。失敗するテストを先に足して直した
    2 アーキテクト 中 フィルターの順序が暗黙の登録順に頼る 並びの見張りのテストと、組み立てのコメントを足した（議題 3）
    3 プログラマー 中 誤りのときの session の破棄が失敗すると、元の例外が失われる 破棄の失敗は抑制された例外として足し、元の誤りを必ず投げ直す
    4 プログラマー 中 サービスの分岐を 2 回追う ガード節と revoke に分けた（振る舞いは同じ）
    5 テスター 中 ナビの「ないこと」に、外す前の「あること」がない（T-106） 外す前にナビに経路設計があることを確かめた
    6 テスター 中 役割 0 件のテストにログの確かめがない。ログの確かめが利用者 ID の部分一致だけ 3 つの誤りを同じ補助で確かめる形にした（その後、議題 4 で例外の文言と原因の確かめに改めた）
    7 テスター 中 password の段の取消しを A-02 の認証コードでしか確かめていない 回復コードの送信も A-03 になり、回復コードを使わないことを足した
    8 テスター 中 契約テストの「次の読み出しに出る」は前に読んでいない（トランザクションの中の 1 次キャッシュ）。役割を足す場合がない 「今の役割の行だけを読む」にし、外すと足すの両方を入れた。読み比べは統合テストに任せる
    9 テクニカルライター 中 止められた利用者は A-03 の後に「ログインできない」になるが、付録 B の Q1-1 から案内が届かない Q1-1 に「直前に『もう一度ログインしてください』と示されていた」の行を足した
    10 テクニカルライター 中 A-03 の問い合わせ先の文が止められた利用者の症状に当たらない 議題 5
    11 プログラマー・アーキテクト 低 UserStanding が 2 つの集約を持ち、使わない password のハッシュも読む Javadoc に「読み取り専用で保存に使わない、ハッシュは User が欠かせないので読むが主体に写さない」を書いた
    12 プログラマー 低 「session には保存しない」の書き方が、後ろの認証のフィルターの保存と食い違って読める 「このフィルターは保存しない」にし、A-02・A-07 が通ったときの保存を書いた
    13 プログラマー 低 監査の操作者の企業は session の値で、利用者が企業を移らない前提が書かれていない サービスの Javadoc に前提と見直す時期（US-16）を書いた
    14 テスター 低 利用停止と無効な企業を同じ利用者で同時に変えている。SESSION_REVOKED の 1 行を contains で確かめている 1 つずつに分け、containsOnlyOnce にした
    15 テクニカルライター 低 2.4 の手順の「開いていた画面に戻ります」が止められた利用者に当たらない。「入力した内容は送信されません」が既存の文と紛らわしい 手順に「ログインできない場合は注意・補足」を足し、「止められた後に送った入力は保存されていません」にした
    16 プログラマー 低 SecurityConfiguration の Javadoc が 2 つ続き、公開の URL の説明が別の定数に付いていた 直した

    計画からの変更¶

    • 公開の URL を確かめから外すことを、開発レビューで実装に入れた（議題 2。計画の約束どおりに戻した）
    • 500 のときのエラーのログは、フィルターでなくコンテナが残す（議題 4）

    判断と学び¶

    • 「公開の URL では呼ばない」を設計の約束に書いたのに、テストは cookie のない request で確かめていた。「ないこと」の確かめは、その条件が成り立つ場面（ここでは認証済みの session）で書かないと空振りする。T-106 の「あること」と並べる形は、条件の側にも当てはまる。
    • Spring Security の addFilterAfter は相対の位置ではなく順序の値を決めるだけで、同じ値のフィルターは登録の順で並ぶ。位置に頼る設計は、並びを見張るテストで守る。
    • ログを書いて投げ直す形は、コンテナのログと二重になる。入口で足すのは文脈（利用者 ID）だけにし、ログは 1 か所で残す。

    既知の課題（後に持ち込む）¶

    • 議題 5（A-03 の問い合わせ先の文）・議題 6（ロックと IA-INV-04）の判断
    • sessionExists（Base64 の cookie と platform.spring_session の表に頼る補助）が 3 つの統合テストに重複する。32d のテストの整理でまとめる
    • SessionRevalidationSecurityIntegrationTest も独自の Spring のコンテキスト（@MockitoSpyBean 4 つと独自の時計）を作る。32d の「独自の Spring のコンテキスト」の整理に入れる
    • 500 の応答の画面（コンテナの /error）の状態と本文は、MockMvc の統合テストでは確かめていない（例外が外に出ることまで）。監査の書き込みの誤りのロールバックは単体テストの偽のトランザクションマネージャーでだけ確かめている
    • password_hash を request ごとに読む（User が欠かせないため）。ハッシュを持たない読み取りの射影にするかを、W10 の性能の評価か利用者の管理（Bolt 34）で検討する
    • 役割 0 件の検査がリポジトリ（IllegalStateException）と User.of（IllegalArgumentException）に二重にある。リポジトリの側はデータの不整合として区別するために残した
    • W10 の性能の評価で、request ごとの SQL の時間と接続プールの使用率を計測項目に入れる（アーキテクト）
    • 管理者向けのマニュアル（利用を止めると次の操作で効く）は、利用者の管理の画面を作る Bolt 34 で書く。2.4 の最初の箇条にない「ログインの手続きを時間内に終えなかった」は 33b の 2 章の書き直しで直す
