    Bolt 62 計画 - 本予約前の輸送要求の条件の変更¶

    W11 計画の Bolt 62（US-05 AC1。機能、SP 0。SP は US-05 を締める Bolt 67 で数える）。荷主が本予約の前に条件を変えると、旧版を残した新しい輸送要求版ができ、承認は要りません。

    状態: 承認済み（2026-11-28、human:kakimomokuri）。確認ポイント CP-62-1〜CP-62-6 はすべて推奨のとおりです。Bolt 62・62-1 の報告は 2026-11-28 に承認されました（human:kakimomokuri。「承認してコミット」）。

    検証（2026-11-28。承認の前に実施）:

    • validating-iteration-plan: US-05 AC1、domain_model.md の輸送要求の状態遷移と Q-INV-03・04・13・15・18、ui_design.md の C-02〜C-04、data_model.md と移行ファイル、今のコードを突き合わせました。W11 計画の「ゲートは計画・終了報告」では足りず、スキーマの変更（CP-62-2）が要ります。 設計の状態遷移図とは、CP-62-1 の 2 点が食い違います。
    • validating-design: A は、開発戦略の終盤・アウトサイドイン（受入シナリオから入る）に合わせます。B は、見積りの状態を足すので、domain_model.md・data_model.md・ui_design.md の更新が要ります。C は、再見積りの置換（Bolt 11）と同じく「旧版を先に退かせる」形にし、版の照合は審査の STALE_VERSION（Q-INV-04）にそろえます。見積りの有効な件数の規則（Q-INV-18）と部分一意インデックスは変えません。

    調べて分かったこと（2026-11-28。コードと移行ファイルを読んだ。実行はしていない）¶

    # 事実 影響
    F-1 TransportRequest.resubmit は下書き（差戻し）のときだけ使える。差戻しは審査の段階なので、見積りがある輸送要求の版が変わることは、今は起きない 版が変わる場面を、この Bolt が初めて作る
    F-2 見積りの回答（経路設計の依頼・辞退・相談）と荷主の承認は、見積りの状態だけで判定し、輸送要求の版を照合しない。経路の割当ても同じ 版だけを足すと、旧版の見積りを荷主が承認でき、経路も割り当たる
    F-3 本予約の照会は版を照合する（BookableQuotationQueryService）。コメントは「版が違うことは起きない」を前提にしている 版の違いは断るが、同時の実行は F-5
    F-4 見積りの算出は、有効な見積りがあると ALREADY_QUOTED で断る。旧版の再見積りは OUTDATED_VERSION で断る。PostgreSQL の部分一意インデックス ux_quotation_active は、輸送要求ごとに有効な見積りを 1 件に限る（H2 にはこのインデックスがない） 旧版の見積りを退かせないと、新しい版の見積りを作れず、行き詰まる
    F-5 本予約の確定は見積りの行をロックするが、輸送要求が予約確定済みになるのは、後で届く DE-07 の listener 条件の変更と本予約の確定が同時に走ると、変更の側は本予約を知らずに通る可能性がある（推測。再現していない）
    F-6 REPLACED（置換済み）は、制約 ck_quotation_replaced が置換先の見積り ID を必須にする 条件の変更の時点には置換先がないので、REPLACED は使えない
    F-7 C-03 の下書きの保存は、まだない（作るのは提出と出し直しだけ） 「下書きに戻す」と、中身を変えずに下書きになるだけの状態ができる

    確認ポイント（承認が要る判断）¶

    # 判断 推奨 ほかの案
    CP-62-1 【前の決定の変更】変更できる状態と、変更の後の状態 審査中・見積り作成中・見積提示済み・経路設計中・荷主承認待ち・予約待ちから変更でき、荷主が C-03 で新しい条件を送ると、新しい版ができて審査中になる（下書きの出し直しと同じ。DE-01 を出す）。取下げ済みと予約確定済みは変更できない。下書きは今の出し直しのまま。domain_model.md の図は「下書きへ」で、審査中と予約待ちからの線がないので直す 図のとおり下書きへ戻す案は、下書きの保存（F-7）がないので、新しい版の中身がないまま下書きになる
    CP-62-2 【スキーマの変更】旧版の見積りの扱い 見積りの状態に条件の変更で無効（値は仮に VOIDED）を足し、変更と同じトランザクションで、旧版の有効な見積り（作成中・承認待ち・提示済み・経路設計の依頼済み・荷主承認待ち・承認済み）をこの状態にする。移行は status の CHECK 制約に値を足すだけで、列は足さない。無効の見積りは、回答・承認・割当て・本予約・再見積りのすべてで断る ck_quotation_replaced を緩めて REPLACED を使う案は、置換先のない置換済みができて意味が崩れる。状態を変えずに版を照合する案は、F-4 のインデックスを版ごとに変える移行がやはり要り、照合を足す場所が多く漏れやすい
    CP-62-3 【業務の判断】進行中の経路設計 旧版の経路設計案件は変えない。確定しても、無効の見積りには割り当てない（今の「退いた見積り」と同じ扱い）。経路設計の画面に案内は足さず、#33（経路の再設計）に項目を足す。画面が確定の後に何を示すかは、実装の最初に確かめ、誤解を招くなら改めて諮る 経路設計の画面に「輸送条件が変更された」を出す案は、経路設計の画面とコンテキストの間の知らせが増える
    CP-62-4 【業務の判断】変更の理由 理由の欄は設けない（AC1 は理由を求めていない。取下げの AC2 と申請の AC3 は理由を求める） UC-05 の手順 1 は「変更または取消し理由を指定する」で、測定基準に「理由欠落 0 件」がある。理由を取るなら、版に理由の列を足す（スキーマの変更が増える）
    CP-62-5 本予約との同時の実行（F-5） 実装の最初に PostgreSQL の同時実行のテストで再現を試す。再現したら、そこで止まり、防ぎ方の選択肢（本予約の確定の中で、見積りの公開 API を同期で呼んで印を付けるなど。ADR-016 に関わる）を添えて改めて諮る。再現しなければ、テストを残して進める 防ぎ方を今決める案は、再現を確かめていないので推奨しない
    CP-62-6 Bolt の分け方 2 本に分ける。62: 集約・状態の移行・コマンド・旧版の見積りの無効化・同時の実行。62-1: C-03・C-04・C-02 の画面、受入シナリオ（@US-05-AC1・@ui）、マニュアル。W11 計画の 200 分は、F-2・F-4 を含まない見積りだった。分けた後の分数に実測の根拠はないので置かない 1 本のままにすると半日を超える見込み

    CP-62-1〜4 を変えないと決めた点: 変更の画面と URL は、今の出し直し（GET /customer/transport-requests/{業務番号}/edit、POST …/versions）を使います。認可は変えません（荷主は自社の輸送要求だけ。Q-INV-08）。送る版番号が現在の版と違うとき（別の人が先に変えた）は、上書きせず、最新版の確認を求めます（B-INV-09 と同じ形）。KPI-01 は版 1 の提出と最初の提示で測るので変わりません（KPI-INV-01。テストで確かめます）。
