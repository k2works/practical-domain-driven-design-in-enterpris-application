    戦略成果物レビュー（2026-09-29）¶

    レビュー対象¶

    • docs/strategy/business_case.md — A 社の企業事例。
    • docs/strategy/business_strategy.md — 環境分析、企業・事業・機能戦略、業務分析。
    • docs/strategy/BMC.svg — ビジネスモデルキャンバス。
    • docs/strategy/business_architecture.md — プリンシプル、価値、能力、組織、情報、シナリオ。
    • docs/strategy/inception-deck.md — 10 の問い、スコープ、リスク、概算、マイルストーン。

    レビュー方法¶

    以下の XP エージェント視点で独立レビューし、指摘を重要度と論点ごとに統合した。

    エージェント 主な視点
    xp-product-manager ビジネス価値、優先順位、MVP、KPI、投資仮説
    xp-architect 技術的実現性、責任境界、データ、外部連携、非機能・運用リスク
    xp-interaction-designer 心理モデル、チャネル、例外時 UX、現場入力、アクセシビリティ
    xp-tester テスト可能性、状態遷移、異常系、品質ゲート、トレーサビリティ
    xp-user-representative 実務適合性、変更・取消し、再手配、訂正、手動代替

    総合評価¶

    戦略成果物は、「複雑貨物への集中差別化」から「熟練知とデータを組織能力へ変換する」「予約・経路設計・追跡を段階導入する」という縦の論理が一貫している。顧客価値、バリューストリーム、ケイパビリティ、組織、情報、シナリオを接続し、品質優先、人と自動化の協働、スコープ外を明示した点は高く評価できる。

    一方、現状は戦略仮説を方向付ける品質には達しているが、投資承認と要件定義の契約に使うには具体性が不足する。特に、KPI と投資効果、MVP の対象範囲と検証仮説、基本追跡の情報源、予約・経路・追跡・例外の状態遷移、変更・取消し・訂正・障害時の業務、認証・監査・可用性等の横断要件を補う必要がある。

    改善提案（重要度順）¶

    高¶

    # 提案 指摘元 理由
    H-1 KPI に仮説値または目標レンジ、期限、母集団、測定方法、責任者を定める PM、Tester 「迅速」「速やか」「重大欠陥ゼロ」では投資・リリースの合否を判定できない
    H-2 費用と便益を接続し、年間便益、回収期間、投資上限、段階ごとの継続・中止条件を置く PM 約 7,650 万〜1 億 3,000 万円の投資に対する期待リターンが示されていない
    H-3 MVP の対象顧客、貨物種別、航路・港湾、利用部門、案件数、最小データ源を限定する PM、Architect 10 週間の見積りと学習仮説を成立させる境界が不足している
    H-4 MVP の「基本追跡」について、予定・実績の区別、情報源、更新担当、許容鮮度、手動補正責任、第 2 段階への移行条件を定める 全員 荷役管理・リアルタイム連携前に何を追跡できるかが不明で、顧客期待と検証結果を誤る
    H-5 予約、見積り、経路版、追跡状態、例外案件の状態遷移と、変更・取消し・再設計・訂正を定義する Architect、Tester、User 現状のシナリオが正常系中心で、国際物流の頻出業務と test oracle が不足する
    H-6 外部連携障害と手動代替について、timeout、再送、重複、順序逆転、長時間停止、復旧後照合を定義する Architect、Tester、User 連携先の品質に依存し、予約・追跡業務が停止または二重処理になるリスクがある
    H-7 役割別の心理モデル、顧客セルフサービスと有人支援の境界、チャネル横断ジャーニー、例外時 UX、現場入力制約を定義する Interaction、User アクター名だけでは権限、利用環境、失敗への不安、チャネル切替時の体験を設計できない
    H-8 認証・認可、企業間データ分離、監査、可用性、RPO/RTO、性能、データ鮮度等を品質ゲートへ追加する Architect、Tester 後付けしにくい横断責務と測定可能な非機能条件が概念アーキテクチャに不足する
    H-9 経路算出の代表案件を、入力、期待候補、除外候補、判断根拠とともに golden dataset 化する Tester、User 熟練者の期待だけでは判断差を統制できず、制約組合せの回帰検証ができない
    H-10 優先 ICP を定め、支払者、契約意思決定者、利用者、受益者を区別する PM、Interaction 製造業・卸売業・貨物種別・荷受人が同列で、MVP の顧客価値が分散している

    中¶

    # 提案 指摘元 理由
    M-1 与件に案件数、経路提示時間、成約率、問い合わせ、誤予約・再設計等の現状値または調査計画を追加する PM、Tester 戦略仮説と改善効果の基準値がない
    M-2 結果指標と安全・品質のガードレール指標を分ける PM、Tester 効率向上が制約違反、手動補正、苦情、現場負荷を悪化させる可能性がある
    M-3 業務上の正、外部原本、システム内 authoritative copy と採否責任を区別する Architect 外部訂正・競合・欠落時の責任が曖昧である
    M-4 予約 ID、追跡番号、貨物・荷姿 ID、外部 ID の発行主体と対応を定義する Architect 分割、混載、積替え、再手配を単一予約 ID だけで表現できない可能性がある
    M-5 競争優位上のコアサブドメインと、価値提供に不可欠なコアケイパビリティの用語を区別する Architect 独自開発・購入・標準化の判断を誤る可能性がある
    M-6 経路候補比較に安全性、接続余裕、費用、鮮度、遅延実績、除外理由を含める Interaction、User 経路設計者が候補を説明・選択する材料が不足している
    M-7 通知の重要度、購読、静穏時間、再通知、到達確認、配信失敗、重大通知の代替を定める Interaction、Tester、User 通知疲れと重大通知の見逃しを両方防ぐ必要がある
    M-8 WCAG、キーボード、色に依存しない表示、言語、時差、日時、単位系を体験原則にする Interaction、Tester 国際物流と多様な利用環境に必要な包摂性が未定義である
    M-9 継続的なユーザー・現場フィードバックを改善バックログへ戻す仕組みを定義する Interaction 初期調査だけでは定着後の代替作業や誤入力を把握できない
    M-10 カスタマーサポートを独立アクターとし、照会、代理操作、応対履歴、引継ぎを定義する User 与件上の主要利用者が営業担当者へ吸収されている
    M-11 PoC 後の再見積り、調達、データ移行、並行稼働、切替期間を計画へ加える PM、Architect 30 週の直列計画に外部依存と移行作業が反映されていない
    M-12 ビジネス目標 → シナリオ → 受入条件 → テスト → 品質ゲートの追跡表を作る Tester 価値・リスクと検証証跡の対応を追跡できない

    低¶

    # 提案 指摘元 理由
    L-1 段階ごとに North Star 指標 1 つと補助指標 2〜3 個へ絞る PM 優先順位判断を明確にする
    L-2 BMC の生成元・再生成手順と派生物であることを明記する Architect Markdown と SVG のドリフトを防ぐ
    L-3 BMC SVG の代替説明を内容要約または生成元への参照まで拡充する Interaction 画像単体でも主要内容へ到達できるようにする
    L-4 規制・場所・貨物・航海・イベントで標準採否を判断する領域を一覧化する Architect、Tester 標準準拠の検討範囲を明確にする
    L-5 過去の誤予約・追跡遅延・規制判断ミスの代表例を収集する Tester 探索的テストと回帰テストの優先順位に使える

    高重要度指摘への対応方針¶

    指摘 方針 対応時期 完了条件
    H-1 KPI 修正する 戦略補完・要件定義 仮説値または調査期限、算式、責任者を記録する
    H-2 投資効果 修正する 戦略補完 便益レンジ、回収期間、段階継続条件を経営レビュー可能にする
    H-3 MVP 境界 修正する 要件定義開始前 パイロット顧客・貨物・航路・データ・案件数を明示する
    H-4 基本追跡 修正する 要件定義 情報源、予定／実績、鮮度、更新・補正責任を合意する
    H-5 状態・変更業務 修正する 要件定義・ユースケース 状態遷移、変更・取消し・再設計・訂正の受入条件を定義する
    H-6 障害・代替 修正する 要件定義・非機能要件・運用要件 失敗モード、手動継続、復旧照合、二重処理防止を定義する
    H-7 UX・役割 修正する 要件定義・UI 設計 役割、権限、利用文脈、ジャーニー、例外・現場 UX を定義する
    H-8 横断品質 修正する 非機能要件・アーキテクチャ設計 セキュリティ、可用性、性能、復旧、監査の測定基準を定める
    H-9 golden dataset 修正する 要件定義・テスト戦略 複数専門家と規制根拠で承認した代表案件を版管理する
    H-10 優先 ICP 修正する 戦略補完・要件定義 支払者・意思決定者・利用者・受益者を分けて MVP 対象を決める

    高重要度の指摘はすべて「修正する」と判断する。ただし、現時点で根拠のない数値や業務ルールを埋めることはせず、戦略補完で仮説と調査計画を定め、要件定義以降でステークホルダー確認と測定を行う。

    矛盾事項¶

    # 視点 A 視点 B 論点 推奨判断
    1 PM：差別化仮説の検証には追跡・例外対応を早く含めるべき スコープ方針：荷役・リアルタイム追跡は第 2 段階 MVP の追跡範囲 MVP は特定データ源による予定・主要実績の基本追跡に限定し、顧客価値をパイロット検証する。リアルタイム荷役連携は第 2 段階とする
    2 User：複雑貨物には人的支援が不可欠 BMC：Web セルフサービスを成長チャネルとする 自動化と有人支援 下書き・標準条件はセルフサービス、規制・不足・例外条件は同一案件を営業へ引き継ぐ assisted service とする
    3 Architect：外部連携を後段化して MVP を分離する PM・Tester：航海・追跡データなしでは価値を検証できない 外部連携の時期 パイロット対象の最小データ源だけを MVP の明示的依存とし、その他はスタブまたは管理された手動取込にする
    4 戦略：経路設計・追跡は差別化領域 Architect：差別化領域でも技術基盤は購入・再利用可能 build vs. buy 差別化する業務ルール・判断根拠と、汎用的な通知・連携・実行基盤を分けて評価する

    推奨改善アクション¶

    1. 戦略補完として、優先 ICP、MVP パイロット境界、KPI 仮説、投資便益モデルを経営レビュー用に追記する。
    2. 要件定義で、基本追跡の情報契約、役割・権限、状態遷移、変更・取消し・再設計・訂正、手動代替を定義する。
    3. ユースケース分析で、正常系に加えて、例外、差戻し、部分失敗、offline、復旧後照合を受入条件へ落とす。
    4. 非機能要件で、性能、鮮度、可用性、RPO/RTO、セキュリティ、監査、保持、アクセシビリティを測定可能にする。
    5. テスト戦略で、golden dataset、デシジョンテーブル、状態遷移、契約テスト、障害注入、品質ゲートと証跡を定義する。
    6. 改善後に再レビューし、高重要度 10 件が成果物または後続成果物へトレースされていることを確認する。

    レビュー判定¶

    条件付き承認とする。戦略の方向性と分析フェーズ次工程への進行は妥当である。ただし、analyzing-requirements の開始時に H-3、H-4、H-5、H-7、H-10 を優先し、アーキテクチャ設計へ進む前に H-1、H-6、H-8、H-9 の測定・検証条件を確定する。H-2 は経営による投資承認前の必須事項とする。
