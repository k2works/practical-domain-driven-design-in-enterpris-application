    cargo-tracker Bolt 4 開発成果物レビュー（2026-10-02）¶

    レビュー対象¶

    • Bolt 4（業務番号と必須条件の検証、US-01 AC1・AC2・AC4）の変更: コミット 207ecfc〜46a5397
    • ドメイン: 業務番号、輸送条件の入力と提出の検証結果、貨物、MVP 受付範囲、採番のポート、DE-01 の業務番号
    • アプリケーション: 提出の結果（SubmissionOutcome）、コマンドサービス
    • 永続化: マイグレーション、年ごとの採番（REQUIRES_NEW と行ロック）、業務番号で探す操作
    • 画面: C-03 の 1 画面、エラー要約、ラジオボタン、完了画面と KPI 一覧の業務番号
    • テスト: 業務ルール層 26 本、画面の層 5 本、単体・統合・Web
    • 文書: Bolt 4 計画、Bolt 4 終了報告、ドメインモデル・データモデル・UI 設計・ユーザーストーリー・手順書の差分
    • 観点: xp-programmer、xp-tester、xp-architect、xp-technical-writer、xp-user-representative の 5 つ（並列に実施）

    総合評価¶

    業務番号・提出の検証・採番が、用語集どおりの名前の値オブジェクトとポートに分かれた（programmer、architect）。違反は戻り値、壊れた前提は例外という返し方の使い分けも揃っていると評価された。H2 と PostgreSQL に共通の SQL（ADR-007）、イベントの進化の規則、依存の向きも守られている。境界値（期限の同時刻、日本時間の年の区切り、桁上がり、末尾のゼロ）と、採番の同時実行のテストは高く評価された（tester）。利用者の視点でも、業務番号を電話で伝えられる完了画面と、「理由と直し方」の文言が受け入れられた。

    一方、次の 3 つが重大度「高」として挙がった。

    • 時計に依存するテスト: 実際の時計で動くテスト 2 本が、固定の期限 2026-11-02 の見本を使っている。その日を過ぎると提出が拒否され、CI が落ち始める（tester）。
    • 他社の輸送要求が見える経路: 完了画面の URL のキーを連番の業務番号にしたのに、荷主企業で絞り込んでいない（architect）。
    • 接続の枯渇: 年の行を作る別のトランザクション（REQUIRES_NEW）が、外側の接続を握ったまま 2 本目の接続を取る。年の最初の提出が接続のプールの大きさ以上に同時に来ると、止まりうる（programmer、architect）。

    利用者の視点からは、特殊貨物の案内に連絡先がないこと、貨物種別の境界（冷蔵・定温を含むか）が分からないことが、業務の判断として挙がった。

    改善提案（重要度順）¶

    高（クローズ前に対応すべき）¶

    # 提案 箇所 指摘元 対応方針
    R-01 実際の時計で動くテストの期限を固定の日付にしない ShipmentTermsFixture、H2DevProfileSmokeTest、TransportRequestSubmittedDeliveryIntegrationTest tester 修正: 見本の期限を十分に先（2099 年）にする。固定の時計で動くテストの境界値は、それぞれのテストが自分で期限を持っている
    R-02 完了画面を荷主企業で絞り込む TransportRequestController、TransportRequestQueryService、TransportRequestRepository architect、tester 修正: findByNumber(番号, 荷主企業) の形にし、いまは仮の主体の荷主企業で絞る。認証（US-18）を入れたら、主体を差し替えるだけにする。他社の番号は見つからない（404）ことを Web テストで確かめる
    R-03 年の行の作成で接続のプールが枯渇しうる MyBatisTransportRequestNumberIssuer programmer、architect 人の判断（D-13）。推奨: 起動時に、今年と来年（日本時間）の年の行を提出のトランザクションの外で用意する。いまの別のトランザクションの経路は、年をまたいで動き続けた場合の予備として残す。プールの大きさを超える同時提出のテストを足す

    中（クローズ前に対応する）¶

    # 提案 箇所 指摘元 対応方針

    R-05 画面の層の待ちを、POST の後の画面の移動が終わるまでにする SubmitTransportRequestUiSteps の submit tester 修正: waitForURL で待つ

    R-07 個数に 1.5 と入れたときの文言が「数字で入力してください」で、理由が分からない TransportRequestFormConverter technical-writer 修正: 「個数は 1 以上の整数で入力してください」にする
    R-08 用語集の「提出の検証結果」が「理由と直し方を持つ」になっていて、実装（項目と理由の種類だけ）と違う domain_model.md programmer、architect 修正: 文書を実装に合わせる
    R-09 マイグレーション（既存の行はない前提）と DE-01・KPI の列（Bolt 4 より前のデータがある前提）の前提の違いを書く bolt_04_report.md architect 修正: 報告に書く。ローカルの PostgreSQL は Testcontainers だけで、作り直しの手順は要らない
    R-10 計画の本文に、KPI の列を「NOT NULL で足す」が残っている bolt_04_plan.md technical-writer 修正: 変更の注記を添える
    R-11 UI 設計の S-22 の行が Bolt 1 の形のまま ui_design.md technical-writer 修正: 業務番号の列を書く
    R-12 報告の所要時間がコミットの時刻と合わない bolt_04_report.md technical-writer 修正: 11:19〜15:55（報告のコミット）の 4 時間 36 分に直す

    # 判断事項 AI の提案
    D-13 採番の年の行をどう用意するか（R-03） 決定（2026-10-02、human:kakimomokuri）: 起動時に今年と来年の行を用意し、いまの別のトランザクションの経路は予備として残す。プールの大きさを超える同時提出のテストを足す
    D-14 特殊貨物の案内に出す連絡先（電話・メール・受付時間）と、入力した内容を営業へ引き継ぐか 連絡先は業務責任者に確かめてから設定にする。引き継ぎは有人案件（US-11・US-20、W8）で扱う
    D-15 貨物種別の境界（「冷凍」に冷蔵・定温を含むか、「その他特殊」の例: 重量物・長尺物、リチウム電池、高額品） 業務責任者に確かめ、ラベルに例を添える
    D-16 希望到着期限を日付だけで受け付けるか、どの地域の日付として扱うか（荷主は期限を日付で、欧州着なら現地の日付で考える） 業務責任者に確かめる。決まるまでは、いまの日時の入力（日本時間）のままにする
    D-17 完了画面に提出内容の控えと回答の目安を出すか 控えは C-04（見積依頼の詳細）を作るときに入れる。回答の目安は業務責任者に確かめる
    D-18 総重量の小数点以下の桁（kg の 1 桁で足りるか） いまの 3 桁（データモデル NUMERIC(12,3)）のまま。業務責任者に確かめる
    D-19 荷受人が企業マスターにないとき（初めての相手）の扱い（自由入力を認めるか、営業へ登録を依頼するか） US-16 の前に業務責任者に確かめる
    D-20 必要書類（次の Bolt）: 見積りの段階で必須か任意か（インボイス・パッキングリストは見積りの段階では確定していないことが多い）、形式と容量、閲覧できる人、複製で再提出させるか 業務責任者に確かめてから次の Bolt を計画する

    エージェント別フィードバック詳細¶

    xp-programmer（高: 0 / 中: 2 / 低: 4） - 評価: 「動くきれいなコード」の水準。業務番号・提出の検証・採番が用語集どおりの名前の値オブジェクトとポートに分かれ、違反は戻り値、壊れた前提は例外で揃っている。採番は同時実行のテストつきで正しいと判断する - 中: `validate` と `toTerms` の時間的結合（R-04）、用語集と Javadoc の食い違い（R-08） - 低: 規則が検証とコンストラクタの 2 か所にある、`RuntimeException` をまとめて捕まえる（R-13）、コントローラーが変換器の `CUSTOMER_ZONE` を参照する、採番のポートの置き場所（R-25） - 懸念: `REQUIRES_NEW` による接続の枯渇（R-03）、READ COMMITTED の前提（R-23）、同じ年の採番の直列化（R-26）
    xp-tester（高: 1 / 中: 2 / 低: 3） - 評価: US-01 の AC1・AC2・AC4 を業務ルール層・画面の層・単体・統合に重ならずに割り振れている。境界値と同時実行のテストを評価 - 高: 実際の時計で動くテストの固定の期限（R-01） - 中: `click` の後の待ち（R-05）、文言の対応の網羅（R-06） - 低: 受け付ける側の境界の例（R-20）、拒否のときの採番の確認（R-21）、権限のテストの番号の形式と DELETE（R-22、C-1） - 懸念: 他社の番号の完了画面（R-02）、同時実行のテストが競合を確かめていない（R-27）、`withReuse` を有効にしたときの採番の残り
    xp-architect（高: 2 / 中: 2 / 低: 2） - 評価: ADR-007 と依存の向きを守り、採番の判断はデータモデルと一致する。接続の扱いと、連番の URL で他社の要求が見える経路に手当てが要る - 高: `REQUIRES_NEW` による接続の枯渇（R-03）、完了画面の荷主企業での絞り込み（R-02） - 中: マイグレーションとイベントの前提の違い（R-09）、用語集の食い違い（R-08） - 低: 採番のポートの置き場所、null を許す入力の `@ValueObject`（R-25） - 懸念: 採番による直列化とスループット（R-26）、`MvpAcceptancePolicy` の継ぎ目、`model.rules` と `model.valueobjects` の依存の向き（R-25） - スコープ外: Bolt 3 の残り（`afterMigrate` の付与の方式、Flyway とアプリの DB 利用者の分離）の点検が、更新する表が増えたことでより重要になった
    xp-technical-writer（高: 0 / 中: 4 / 低: 5） - 評価: 文書どうし・文書と実装はおおむね一致。採番の手順の変更は計画・データモデル・報告の 4 か所で同じ内容。テストの件数も実物と合う - 中: 計画の本文の `NOT NULL`（R-10）、S-22 の行（R-11）、所要時間（R-12）、個数の文言（R-07） - 低: 完了画面の見出し（R-16）、「一覧から選んで」（R-14）、ヒントの二重の括弧（R-15）、Javadoc（R-17）、報告の承認の表記（R-18） - 懸念: 手順書の `generated`（R-24）、VoiceOver の確認を追う場所がない
    xp-user-representative（高: 2 / 中: 2 / 低: 1） - 評価: 荷主が 1 画面で迷わず提出でき、業務番号を受け取れる。業務に出せる水準に近い。D-10、UUID、UN/LOCODE の正規化は解消を確認した - 高: 特殊貨物の案内の連絡先と引き継ぎ（D-14）、貨物種別の境界（D-15） - 中: 期限を日付で受け付けるか（D-16）、完了画面の控えと回答の目安（D-17） - 低: KPI 一覧の UTC 表示（Bolt 3 から継続） - 懸念: 荷受人がマスターにないとき（D-19）、必要書類の業務の決めごと（D-20） - スコープ外: 受入シナリオの荷受人の呼び名（R-19）、総重量の桁（D-18）
