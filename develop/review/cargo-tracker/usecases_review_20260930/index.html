    cargo-tracker ユースケース成果物レビュー¶

    レビュー結果¶

    レビュー対象¶

    • docs/requirements/cargo-tracker/requirements_definition.md — 上流要件との整合確認。
    • docs/requirements/cargo-tracker/business_usecase.md — BUC、アクター、業務目標、主成功シナリオ。
    • docs/requirements/cargo-tracker/system_usecase.md — UC、保証、主成功・拡張シナリオ。
    • docs/requirements/cargo-tracker/user_story.md — 17 ストーリー、53 件の受入条件。
    • docs/requirements/cargo-tracker/units.md — U1〜U5、依存 DAG、対応表、ストーリーマップ。
    • docs/requirements/cargo-tracker/usecase_plan.md — AI-DLC の作業計画と承認ゲート。

    レビュー種別は要件定義・ユースケースである。2026-09-30 に xp-product-manager、xp-architect、xp-interaction-designer、xp-tester、xp-user-representative の 5 視点で独立レビューした。

    総合評価¶

    RQ・BR・KPI から BUC、UC、ストーリー、Unit までの骨格、版・出典・鮮度・訂正履歴を保持する方針、正常系だけでなく外部停止・重複・順序逆転・並行更新を扱う点は高く評価できる。一方、予約確定と経路確定の順序が成果物間で矛盾し、OQ に依存する判定語、有人代替、状態・時刻境界、荷受人の参照許可が未確定である。

    したがって、現時点の成果物は「十分なレビュー材料を備えた契約候補」だが、ゲート 4 を契約として承認できる状態ではない。高重要度の修正事項を反映し、受入条件の oracle を一意にしてから再レビューする。

    改善提案（重要度順）¶

    高¶

    # 提案 指摘元 理由 対応方針
    H-01 予約確定と経路確定の順序、各時点のコミットメント、用語を一本化する 全 5 視点 BUC-02→BUC-03 に対し、BR-01・UC-04・US-04 は予約確定前の経路版を要求し、U1↔U2 の循環を生む 修正する。ゲート 4 再承認前に BUC、UC、BR、US、Unit を同時に整合させる
    H-02 OQ-03〜OQ-07 に依存する判定語を decision table または blocked by OQ-* へ分離する PM、テスター、ユーザー代表 「変更可能」「承認可能」「許可範囲」「二者確認」が入力から一意に判定できない 修正する。完了チェックを見直し、人が承認する暫定規則を明示する
    H-03 予約・見積り・経路・追跡の状態 × 操作の許可／拒否表と日時境界を定義する テスター、UX 禁止遷移、有効期限の <／<=、タイムゾーン、判定時点が未定義 修正する。状態遷移表と時刻規約を追加する
    H-04 MVP の有人引継ぎを受付番号、担当、期限、状態、回答返却を持つ閉ループにする UX、ユーザー代表 「手動引継ぎ」だけでは例外時に業務と顧客対応が止まる 修正する。MVP ストーリーと受入条件を追加する
    H-05 追跡異常時に、判明事実、未確定事項、次の行動、次回更新、担当窓口を示す UX、ユーザー代表 RQ-03 の価値が US-09、US-10 から脱落している 修正する。追跡ストーリーへ受入条件を戻す
    H-06 荷受人の招待、案件単位の参照許可、開示項目・期間、取消しを定義する ユーザー代表、テスター US-10 の事前条件を成立させる業務が存在しない 修正する。権限管理とは別の利用者価値として追加する
    H-07 外部原本の冪等性キー、同一 ID・異 payload の衝突、復旧照合の完了条件を定義する テスター、アーキテクト 重複判定と復旧完了の test oracle が一意でない 修正する。UC-15、US-14、US-15、U5 契約へ反映する
    H-08 前方・後方トレースの不整合を修正し、機械検査可能な対応表にする テスター、PM BUC-02 の BR-01／BR-03、UC-15 の RQ、US-14／15 の BUC が成果物間で欠落する 修正する。単一のトレース表を正として検査する
    H-09 MVP の Must を価値・リスク・代替可否で再選別し、ウォーキングスケルトンを薄くする PM、ユーザー代表、アーキテクト 17 件中 16 件が Must で優先順位が機能せず、基盤先行を誘発する 修正する。通常運行必須、事故防止、有人代替、本格展開前に分類する
    H-10 RQ-10、OQ-08 の継続・中止判断を KPI の母集団、基準値、観測期間とともに接続する PM 機能完成と商品価値検証を区別できない 修正する。検証ストーリーまたはプロダクト検証計画へ追加する
    H-11 Unit 間の整合性境界、期待版、冪等 command、部分成功、再処理、未完了表示を明示する アーキテクト、テスター U1〜U5 の最終的整合性と障害時の利用者表示が未定義 保留する。アーキテクチャ分析で決定し、ゲート 4 には必須引継ぎ制約を追記する
    H-12 アクセシビリティ、エラー回復、影響の大きい操作の事前確認を横断契約にする UX OQ-07 だけでは後続 UI 設計・受入試験で検証できない 修正する。機能横断の受入条件を追加し、具体値は非機能要件へ引き継ぐ
    H-13 品質要求を NFR ID 化し、UC・US・Unit・テスト戦略へ接続する アーキテクト、テスター SLA、RTO/RPO、監査、性能、鮮度の承認漏れを防げない 保留する。analyzing-non-functional で決定し、現成果物には引継ぎ表を追加する

    中¶

    # 提案 指摘元 理由
    M-01 US-05 を変更と取消し、US-15 を停止時縮退と復旧、US-16 を利用開始・役割変更・無効化に分割する PM、UX INVEST の Independent、Small、Testable を満たしにくい
    M-02 ストーリーへ相対見積り、主要依存、スパイク要否を付ける PM Estimable と 1 週間以内のサイズを評価できない
    M-03 U4 の認可契約と監査契約を論理的に分け、障害時の fail closed／後送を分類する アーキテクト 同期認可と監査記録で可用性・保持の性質が異なる
    M-04 U3 と U5 の実績書込責任、重複キー、authoritative copy、訂正入口を一本化する アーキテクト 同じ実績が手動・外部の二経路から二重採用され得る
    M-05 情報源別プロファイルに外部 ID、版、発生・受信時刻、順序、署名、再取得期間、rate limit を定義する アーキテクト 情報源追加時の変更を U5 に閉じ込めるため
    M-06 US-09〜US-11 に存在しない番号、権限外、無効化直後を配分し、外部向け応答を同一化する テスター、UX 企業境界の試験不足と番号存在の推測リスクがある
    M-07 追跡番号の一意性範囲、再利用、採番後の部分失敗を定義する テスター 予約確定と採番の統合テスト条件が不足する
    M-08 情報鮮度を発生、受信、確認、表示更新の時刻に分け、タイムゾーンを明示する UX、ユーザー代表 国際輸送の日付・時刻誤認を防ぐため
    M-09 営業・経路設計・追跡管理の作業待ち一覧と優先度をストーリー化する ユーザー代表 個別案件を開く前に期限切迫・再設計・確認中を発見できない
    M-10 RQ-01 の「一度入力」を、過去予約・契約・荷受人・貨物明細の再利用として受入条件化する ユーザー代表 反復業務の入力負担を検証できない
    M-11 カスタマーサポートの本人・対象確認、最小開示、引継ぎ完結を具体化する UX、ユーザー代表 誤選択・誤開示を防ぎ有人出口を成立させるため
    M-12 Unit 完了判定を fixture、Golden dataset 版、unit／integration／E2E の合格式にする テスター 「確認できる」「再現できる」では自動判定できない
    M-13 監査証跡の時刻源、安定順序、snapshot 境界、session 失効時点を定義する テスター 並行実行と権限無効化の期待値が定まらない

    低¶

    # 提案 指摘元 理由
    L-01 MoSCoW の定義、Must の条件、Could／Won't を追加する PM 優先順位の説明可能性を上げる
    L-02 複数結果を含む Given / When / Then を独立 assertion に分ける テスター 失敗原因を特定しやすくする
    L-03 利用者向け語彙と内部概念の対応を定義する UX 「予約版」「採用値」などによる認知負荷を下げる
    L-04 追跡番号以外の予約番号、発注番号、コンテナ番号からの探索を検討する ユーザー代表 実務では追跡番号が手元にない照会がある
    L-05 Unit 完了判定に情報源・規則・役割追加時の変更容易性を加える アーキテクト 変更容易性を fitness criteria として継続検証する

    矛盾事項¶

    # 視点 A 視点 B 論点 推奨判断
    C-01 PM は管理・外部復旧をウォーキングスケルトンから薄くする アーキテクト・テスターは認可、監査、外部障害を必須安全策とする MVP の薄さと安全性 UI や全機能を先行完成させず、固定利用者・承認済み手動データ・内部監査という最小契約で安全性を通す
    C-02 自動例外管理は第 2 段階 UX・ユーザー代表は MVP で例外の閉ループ対応が必要とする 例外管理の境界 自動検知・通知・高度な案件管理は後続とし、MVP に受付・担当・期限・回答返却の有人代替を含める
    C-03 US-11 は Should ユーザー代表は有人出口として Must とする サポートの優先度 自動例外管理を先送りする条件として、US-11 を MVP Must へ昇格する
    C-04 詳細 NFR は後続工程で決定する UX・テスターは現時点で検証可能な契約を求める 詳細化の時期 現段階で最低保証と引継ぎ ID を定義し、数値・方式は非機能要件とテスト戦略で確定する

    改善アクション¶

    1. H-01 の業務判断を行い、予約・経路・見積りの状態と用語を全成果物で統一する。
    2. OQ-03〜OQ-07 を decision table へ分解し、未決のストーリーを blocked としてゲート 4 の完了チェックを再評価する。
    3. 状態遷移表、時刻境界、外部原本・復旧の test oracle を追加する。
    4. 有人引継ぎ、異常時の次アクション、荷受人の案件別参照許可をストーリー化する。
    5. Must の再選別、ストーリー分割、薄いウォーキングスケルトンを行う。
    6. トレーサビリティ表を修正し、前方・後方の機械検査を追加する。
    7. 横断 UX・アクセシビリティ最低保証と、後続のアーキテクチャ・非機能要件・テスト戦略への引継ぎ表を追加する。
    8. 高重要度の修正後、5 視点の差分レビューを行ってゲート 4 を再判定する。
