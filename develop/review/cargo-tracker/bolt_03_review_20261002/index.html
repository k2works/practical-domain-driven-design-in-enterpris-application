    cargo-tracker Bolt 3 開発成果物レビュー（2026-10-02）¶

    レビュー対象¶

    • Bolt 3（E2E の基盤と生きたドキュメント）の変更: コミット 71eca59〜f09659d
    • 人の決定（D-1・D-3〜D-7）の反映: ADR-001・003、ドメインモデル、データモデル、要件、ユーザーストーリー、技術スタック
    • 画面の層の受入シナリオ（Playwright、axe-core）、用語集の整合テスト、JIG・Spring Modulith の生成
    • 追記専用の表の権限（afterMigrate）
    • アプリケーション開発環境の手順書、CI の ui ジョブ、Dependabot
    • Bolt 3 計画・Bolt 3 終了報告
    • 観点: xp-programmer、xp-tester、xp-architect、xp-technical-writer、xp-user-representative の 5 つ（並列に実施）

    総合評価¶

    人の決定は、日付と承認者付きで ADR・設計・要件に漏れなく反映された（architect、user-representative）。画面の層の 2 つのスイートの振り分け、シナリオごとのブラウザの分離、権限の否定側と肯定側のテスト、T-8 で見つけた検査の穴（Gradle の UP-TO-DATE）は高く評価された。

    一方、次の 2 つが構造上の穴として挙がった。

    • 最小権限の検証がない: アプリ本体と他のテストは PostgreSQL の所有者（superuser）で接続している。アプリケーション利用者の権限で動くのは、権限テストが手書きした SQL だけである。Flyway とアプリの DB 利用者を分ける構成（DA-02 の手順 2）が、まだコードで表せていない。
    • 保護が黙って外れうる（fail-open）: 追記専用の表は名指しで REVOKE する。新しい表で書き忘れると、保護が黙って外れる。

    あわせて、完了画面が内部の ID（UUID）を見せていることが、D-4（画面に UUID を出さない）と食い違っている。テストのコードの次の点も、シナリオが増える前に直すべきとされた。

    • 静的に起動するブラウザ
    • 読み直しを繰り返す待ちの書き方
    • DOM の位置への依存
    • Javadoc の解析
    • axe の検査がステップの書き忘れで空振りすること

    改善提案と対応方針¶

    方針の凡例: 修正 はこのクローズで直す。後の Bolt は担当の Bolt を決めて持ち越す。人の判断 は業務か構造か外部の設定の判断が要る。

    高¶

    # 提案 箇所 指摘元 方針
    R-01 アプリの DB 利用者と Flyway の利用者を分け、アプリケーション利用者の権限で主要な流れが通ることを確かめる application.properties、TestcontainersConfiguration、テストの組み立て architect、tester、programmer 修正（テスト）。画面の層のスイートは、データソースをアプリケーション利用者にし、Flyway だけを所有者で動かす。本番の構成（アプリの中で spring.flyway.user を分けるか、配備の前に別ジョブで Flyway を動かすか）は人の判断（D-9）
    R-02 名指しの REVOKE が fail-open afterMigrate__grant_app_user.sql、AppendOnlyGrantIntegrationTest architect、tester 修正。追記専用であることを表の定義（COMMENT ON TABLE ... IS 'append-only'）に持たせ、コールバックが印の付いた表をすべて REVOKE する。テストは、印の付いた表の集合と「アプリケーション利用者が UPDATE を持たない表」の集合が一致することを確かめる
    R-03 完了画面と画面の層のシナリオが内部の ID（UUID）を表示・検証しており、D-4 と食い違う submitted.html、walking_skeleton_ui.feature、手順書 user-representative、technical-writer、architect 後の Bolt（US-01 AC2）。業務番号の採番と合わせて画面とシナリオを直す。それまでは意図的な負債として報告と手順書に書く（修正: 文書）
    R-04 D-4 の細部（いつ番号を振るか、年の区切り、欠番、桁あふれ、版 1 の表記、複製）が決まっていない ドメインモデル、データモデル user-representative、architect 人の判断（D-10）。US-01 AC2 の計画の前に決める
    R-05 US-01 AC1 の Then に業務番号が入っていない user_story.md user-representative 修正（D-4 の帰結として AC1 に「業務番号が示される」を足し、承認待ちの印を残す）
    R-06 axe の違反を確かめるのが、違反のステップを書いたシナリオだけ WalkingSkeletonUiSteps、walking_skeleton_ui.feature tester 修正。@After("@ui") のフックで、表示したすべての画面の違反がないことを必ず確かめる。検査の基準を WCAG 2.2 AA のタグで明示する
    R-07 手順書の SonarQube の URL が作者の環境の値（9001） 手順書 technical-writer 修正（既定の 9000 と、変えるときの設定を書く）
    R-08 報告の期間の時刻に根拠がない（開始が計画のコミットより前、終了が報告のコミットより後） bolt_03_report.md technical-writer 修正

    # 事項 提案
    D-9 本番で Flyway とアプリの DB 利用者をどう分けるか アプリの中で spring.flyway.user・spring.flyway.password をマイグレーション利用者にし、データソースをアプリケーション利用者にする（配備の手順が 1 つで済む）。ADR-007 の補足に記録する
    D-10 業務番号の細部 版 1 を最初に提出したときに振る（下書きには振らない）。年は JST の提出日で区切る。欠番は許し使い回さない。9999 件を超えたら 5 桁に伸ばす。詳細画面では版 1 も「版 1」と書く。複製した下書きは新しい番号になる（user-representative の推奨）
    D-11 KPI-01 の終点の「有効な」の定義と、基準値の開始点 誤りで取り消した見積りは「有効な提示」に数えない。荷主の条件変更で出し直した見積りは、最初の提示を終点のままにする。基準値の開始点は、今の業務で最初の問い合わせ（メール・フォーム）を受けた時刻とする（営業責任者が W3 までに確認）
    D-12 ブランチ保護の必須チェックに check と ui を入れるか。develop を main にマージして Dependabot を動かす時期 両方を必須にする。main へのマージは W1 の終わり（Release 0.1 の途中の区切り）に行う
