    cargo-tracker 分析成果物レビュー（2026-10-01）¶

    レビュー対象¶

    • 要件: requirements/cargo-tracker/ の要件定義、ユーザーストーリー、Unit 定義
    • 設計: design/cargo-tracker/ のアーキテクチャ 3 本、技術スタック、ドメインモデル、データモデル、UI 設計、テスト戦略、非機能要件、運用要件
    • ADR: adr/cargo-tracker/ の ADR-001〜009
    • 開発ガイドライン: article/ の第 1〜3 章

    レビューは 5 つの視点（プロダクトマネージャー、アーキテクト、インタラクションデザイナー、テスター、ユーザー代表）で並列に行い、統合した。改善提案の ID は前回レビュー（ユースケース成果物レビュー）の H-01〜H-13 と区別するため R- で始める。

    総合評価¶

    パイロット中止の条件（PV-01）を守る仕組みは、アーキテクチャから運用まで一貫して設計に落ちている。予定・実績・確認中を分けて見せる UI、境界値の 3 点規則、テストレベルの責務分担も評価が高い。

    一方で、次の 3 種類の問題が見つかった。

    • 業務順序の誤り: 設計が要件の業務順序と逆になっている（R-01）。
    • 実装方式の矛盾: 追記専用の権限、Flyway の版番号、フレームワークの DDL、イベントの購読方式が互いに食い違っている。
    • 利用者の業務上の穴: 荷主への通知、欧州の利用者への対応、問い合わせの追跡が抜けている。

    開発に入る前に、重要度「高」の修正が必要と判断する。

    前回の保留事項の判定¶

    前回の指摘 判定 根拠
    H-11 Unit 間の冪等性・期待版・部分成功・再処理・未完了表示 一部解消 方式と表は設計された（ARCH-HO-01〜03、processed_command、予約サガ、処理中表示）。次が残る: 受信側の冪等性（DE-02）、同じ見積りからの重複確定、再試行の担い手の二重化、結果整合の間の B-INV-06、イベントの順序、復旧後の再処理（R-03、R-07、R-19、R-20）
    H-13 品質要求の NFR 化と接続 一部解消 NFR は測定可能な値と検証方法になった（非機能要件）。テスト戦略が「性能は後で加える」のままで、PERF・RCV・OBS・AUD・FRS・SVC・RTY のテストが接続されていない（R-21）

    プロダクトマネージャーは H-11 を「解消」と判定した。アーキテクトとテスターは、受信側の冪等性と重複確定の穴を根拠に「一部解消」とした。統合判定では後者を採る。

    改善提案（重要度順）¶

    高¶

    # 提案 指摘元 理由 対応方針（案）
    R-01 業務順序を要件に合わせる: 審査 → 根拠付き見積りと経路方針の提示 → 荷主の確認 → 詳細経路設計 → 本予約。ドメインモデル（DE-02 の契機、輸送要求の「審査済み」状態、予約サガの図）、UI 設計（遷移図・操作フロー・C-05 の内容）、テスト戦略（E2E のフロー）を直す ユーザー代表（確認済み） units.md は U2 の入力を「見積り済み輸送要求」とし、要件定義の業務フローも見積り提示 → 詳細経路設計の順。設計はこれと逆になっている 修正する
    R-02 KPI の計測を設計する。KPI-01 の 2 時刻（条件受付・最初の有効な経路と見積りの提示）を記録する列、KPI-02 の分母（照会の総数）と分子（Web で完結した照会）の記録方法、パイロット開始前 4 週間の基準値の取り方を決め、計測のストーリーを追加する プロダクトマネージャー PV-01 の継続・中止を判定できない 修正する（ストーリーの追加は要件の改訂として承認を得る）
    R-03 同じ見積り（または輸送要求版）からの予約の重複確定を防ぐ不変条件と一意制約を加え、別のコマンド ID による同時確定を統合テストで確かめる。受信側の冪等性（DE-02 で経路設計案件を作る処理など）に一意制約を加える テスター、アーキテクト 重複予約は PV-01 の中止条件。いまは同じ commandId の再送しか防げない 修正する
    R-04 追記専用の対象を見直す。経路版（状態が変わる）と輸送要求版（下書きの更新）は UPDATE が必要なため、状態を版の表から分けるか、列単位の権限にする アーキテクト データモデルの権限設計とドメインモデルの状態遷移が矛盾している 修正する
    R-05 Flyway の版番号の付け方を直す。コンテキストごとの版番号の帯と単一の履歴表は、後から小さい番号を足すと検証で失敗する。タイムスタンプの版番号にするか outOfOrder を使い、ADR-007 に記録する アーキテクト 最初のコンテキスト追加で破綻する 修正する
    R-06 フレームワークの DDL（Spring Modulith、Spring Session）は DB ごとに違うため、Flyway の {vendor} の置き場所で分ける。権限の付与も同じ仕組みで Flyway に入れ、表の作成と同じ配備で行う。Testcontainers でも同じ手順を使う アーキテクト、テスター ADR-007 の「共通部分の DDL」が最初のマイグレーションで破れる。権限付与が別タスクだと、配備中に表を使えないか保護が外れる時間ができる 修正する（ADR-007 を改訂）
    R-07 イベントの購読方式を @ApplicationModuleListener（非同期・新しいトランザクション）と明記する。複数インスタンスで再配信を 1 つに限る仕組み（ShedLock など）を技術スタックに加える。業務ルール層の受入シナリオでのイベント配信の方式（テスト用の同期配信）を決める アーキテクト、テスター 同期の AFTER_COMMIT では購読側の書き込みがコミットされない。メモリ上の受入シナリオでは AFTER_COMMIT が発火しない 修正する（ADR-003、技術スタック、テスト戦略）
    R-08 session と認可の検証レベルを直す。ロックは利用者集約のユニットテストで境界（4・5・6 回目、14:59・15:00）を確かめる。session の失効と「次の request から反映」は SpringBootTest と PostgreSQL のセキュリティ統合テストで確かめる テスター メモリ上の受入シナリオやモックの Web テストでは確かめられない 修正する
    R-09 荷主へのメール通知を MVP に入れる（見積りの提示、見積りの期限間近、本予約の確定、確認中への遷移）。件名と画面への導線だけの最小限とする ユーザー代表 法人の荷主担当者は毎日ログインしない。見積りを見落として失効し、電話の催促が残る 要判断（スコープの追加。通知は第 2 段階の範囲に置いていた）
    R-10 荷受人の画面（C-11、C-12）と招待メールを英語でも表示する ユーザー代表 荷受人は欧州にいる前提で、日本語だけでは使われない 要判断（US-10・US-19 は Could）
    R-11 欧州の顧客との時差に対応する。窓口の受付時間を顧客のタイムゾーンで表示する、優先度高の案件は営業時間外でも受付番号と次回更新日時を自動で返す、日本と欧州の祝日を含む営業日カレンダーを定義する。当番は業務案件を受けないことを明記する ユーザー代表 平日 9-18 JST は欧州の営業時間とほぼ重ならず、優先度高の「当日中」が実質 1 日遅れになる 修正する（値は運用責任者の判断）
    R-12 鮮度の閾値 FRS-02（予定から 12 時間）を、日次の手動取込に合わせて「最終取込から 24〜36 時間」などに改める。ファイル未着の通知を 18:00 から昼前に早める ユーザー代表 取込の周期より閾値が短いと、確認中が毎日大量に出る 修正する
    R-13 荷主が問い合わせの受付番号・進捗・回答を見て、未解決なら再開を依頼できる画面（問い合わせ一覧・詳細）を顧客 Web に加える インタラクションデザイナー、ユーザー代表 US-20 の再開は「顧客が未解決と回答」したときに起きるが、顧客側にその手段がない 修正する
    R-14 荷受人の流れ（招待メール → 受諾 → 照会）の遷移図と、未登録の荷受人の扱いを定める。password の再設定と TOTP の初回登録・再登録の画面を加える インタラクションデザイナー US-18 の「事前登録」と招待の流れが矛盾する可能性がある。SEC-08〜10 の画面がない 修正する
    R-15 session の失効の前に警告し、延長できるようにする。入力の途中で失効しても入力を失わないようにする インタラクションデザイナー WCAG 2.2.1（レベル A）に反する 修正する
    R-16 WCAG 2.2 で新しく加わった基準を共通部品の要件にする: 2.4.11 フォーカスが隠れない、2.5.7 ドラッグ操作の代替、2.5.8 ターゲットサイズ（24px 以上）、3.2.6 一貫したヘルプ、3.3.7 冗長な入力の回避、3.3.8 認証のアクセシビリティ（貼り付けの許可、autocomplete） インタラクションデザイナー BR-13 は WCAG 2.2 AA を目標としているが、2.2 の新しい基準が部品の要件に入っていない 修正する
    R-17 ウォーキングスケルトンの範囲を、一般貨物 1 件が主要な流れを通り KPI-01 の 2 時刻が記録されるところまでに絞る プロダクトマネージャー 38 画面・6 コンテキストのすべてを最初の Bolt に入れると重い リリース計画で扱う

    中¶

    # 提案 指摘元 対応方針（案）

    xp-user-representative（高: 4 / 中: 5 / 低: 0） - 評価: 予定と実績の分離、確認中の「わかっていること・まだわからないこと」、訂正の二者確認は事故をよく防ぐ。荷主が画面を見に来ないと何も分からず、欧州の顧客には窓口の時間帯と言語が壁になる。 - 高: 荷主へのメール通知（R-09）、荷受人画面の英語（R-10）、欧州との時差と営業日カレンダー（R-11）、鮮度と日次取込の不整合（R-12）。 - 中: 見積りの辞退・相談、輸送要求の複製、担当営業と対応待ちの表示、荷主承認後の失効への手当て（R-27）、問い合わせの履歴（R-13）。 - 懸念: 「本予約」と船腹確保の関係、当初予定と最新見込みの対比、通関中の表示、締切の表示（R-28）、少人数への依存と代行者（R-29）。 - スコープ外: 要件の業務フローと UI の操作フローの順序の食い違い（R-01。確認の結果、設計側の誤り）。
