    cargo-tracker Bolt 16 運用成果物レビュー（2026-10-07）¶

    レビュー対象¶

    • 範囲: 595d2b3b..70bb65ea（Bolt 16 のステップ 1〜4）
    • 内容: .github/workflows/cargo-tracker-ci.yml の deploy-demo と workflow_dispatch、ADR-013 の改訂、Heroku デモ環境セットアップ手順書、インフラストラクチャアーキテクチャの CI/CD の節、Bolt 16 計画
    • 視点: xp-architect、xp-tester、xp-project-manager の 3 つ（並列。operating-review）

    総合評価¶

    needs: [check, ui] と同じ github.sha で、テストを通ったコミットだけを配備する形は、手元の deploy:demo のガードより直接的だと 3 視点が評価した。キーを持つジョブは BuildKit のビルドだけを行い、check・ui にキーが渡らないこと、アクションの SHA の固定、応答の本文をログに出さないこと、古い dyno の 200 にだまされないスモーク、失敗を記録して手順書に戻したことも評価された。

    一方で、起動に失敗したときに前の release に戻らないこと（Eco は preboot がなく古い dyno は止まる）、release が 2 段で取り消し・失敗のときに DEMO_REVISION が実際のイメージとずれること、古い実行の再実行で古いコミットが出ること、スモークが自分の release を確かめず API の一時の失敗に弱いこと、キーの境界が「develop に push できるもの」であること、キーが global で期限 1 年・期限に気づく仕組みがないこと、キーの登録の手順が崩れやすいまま残っていることが指摘された。

    レビューの後に AI が確かめた事実: develop にブランチ保護も ruleset もなく、書き込めるのは k2works（admin）だけ。リポジトリの既定のブランチは main で、workflow_run で配備を別のワークフローに分けると main の定義で動くため使えない。

    改善提案と対応¶

    高¶

    # 提案 箇所 指摘元 対応
    R-01 スモークの失敗（起動の失敗）では前の release のまま動かない（Eco は preboot がない）。手順書と確認ポイント 12 の記述が誤り。直前の release に自動で戻す ワークフロー、手順書 アーキテクト、テスター この Bolt で直す（スモークが失敗したら POST /apps/{app}/releases で直前の release に戻し、ジョブを失敗にする。手順書を直す）
    R-02 release が 2 段（formation と config-vars）。ワークフロー全体の cancel-in-progress で間に取り消されると DEMO_REVISION がずれる ワークフロー 3 視点 この Bolt で直す（ワークフロー全体の concurrency を check・ui のジョブ単位に移し、deploy-demo を取り消されないようにする）。release を 1 回にする案は W10（D-59）
    R-03 キーの境界は「develop に push できるもの」。ワークフローを書き換えれば needs・if・Environment を通れる ADR-013 テスター、アーキテクト D-58: いまのまま。ADR-013 に境界と、ワークフローの変更は人がレビューすることを書く
    R-04 キーが global で期限 1 年、期限に気づく仕組みがない ADR-013、手順書 3 視点 D-57: いまのキーの作り方のまま、期限を 90 日にする。期日付きの Issue で更新を知らせる。専用のアカウントは W10 で検討する
    R-05 キーの登録・更新の手順が崩れやすいまま（2 回失敗した）。pipefail がなく空の secret を登録しうる 手順書 PM、テスター この Bolt で直す（Gulp のタスク deploy:demo:ci-key にする。空を拒み、説明に年月を入れ、新しいキーで配備が通った後に古いキーを失効させる）

    中¶

    # 提案 箇所 指摘元 対応
    R-06 古い実行の再実行で古いコミットが出る ワークフロー、手順書 テスター、アーキテクト この Bolt で直す（origin/develop で CI の対象のパスを最後に変えたコミットが github.sha でなければ配備を飛ばす）
    R-07 スモークが自分の release を確かめない（手元の配備・rollback と競合すると他人の release を合格にする） ワークフロー テスター この Bolt で直す（DEMO_REVISION が github.sha で、release が succeeded で、その版の dyno が up で、/login が 200）
    R-08 API の一時の失敗でスモークがすぐ止まる。latest が取れないときの案内が紛らわしい ワークフロー テスター この Bolt で直す
    R-09 ADR-008 のコンプライアンスの「GitHub Actions に長期のアクセスキーを置かない」が文面上 AWS に限らない ADR-008 アーキテクト この Bolt で直す（ADR-008 に注記）
    R-10 Environment の規則そのものは試していない（別ブランチで止めたのは if） 計画、報告 テスター 終了報告に「Environment の規則は API の読み返しで確かめた」と書く
    R-11 配備をワークフローの取り消しから切り離し、イメージを 1 回だけビルドして昇格させる構造へ 構造 アーキテクト W10 に回す（インフラストラクチャアーキテクチャに引き継ぎを 1 行）
    R-12 verified が改訂の前のまま（ADR-013、手順書） フロントマター PM、アーキテクト 終了報告の承認で付け直す
    R-13 手順書に「CI の取り消しで DEMO_REVISION がずれうる」がない 手順書 PM R-02 で取り消されなくなるため、手順書は直した後の振る舞いを書く

    低¶

    # 提案 対応
    R-14 type=gha のキャッシュに scope=demo を付ける この Bolt で直す
    R-15 アプリ名と URL の重複（ワークフローの env と environment の url） この Bolt で直す（ワークフローの中は env の 1 か所に寄せる。Environment の variables は使わない）
    R-16 キーが curl のコマンドの引数に入る この Bolt で直す（ヘッダーを標準入力から渡す）
    R-17 「同じコミットでは release が増えない」はキャッシュが当たることが前提 この Bolt で直す（手順書に注記）
    R-18 README に設計文書の変更でも配備・再起動が起きることと、デモの最中に push しない注意がない この Bolt で直す
    R-19 手順書の関連ドキュメントに Bolt 16 計画がない。運用の索引のコマンドの表に deploy:demo:* を足す この Bolt で直す
    R-20 漏えいの疑いのとき、Heroku のアカウントの操作の履歴を確かめる この Bolt で直す（手順書）
    R-21 スモークを .github/scripts/ に出して単体テストを書く W10 に回す
    R-22 スモークを 1 時点でなく 30 秒後にもう一度見る 対応しない（R-07 の条件で足りると判断。起動直後の R14 は週次のログで見る）
    R-23 runtime のイメージの検証（R-13 of Bolt 15）を W10 より前にするか W10 のまま（#28）

    人の決定¶

    ID 決定 日付
    D-57 いまのキーの作り方（人のアカウントの global の authorization）のまま、期限を 90 日にする。更新は Gulp のタスクで行い、期日付きの Issue で知らせる。専用の Heroku アカウントは W10 で検討する 2026-10-07、human:kakimomokuri
    D-58 develop の直接 push の運用は変えない。キーの境界が「k2works のアカウントで develop に push するもの（人と AI のセッション）」であること、ワークフローの変更は人がレビューすることを ADR-013 に書く 2026-10-07、human:kakimomokuri
    D-59 上の表の「この Bolt で直す」と「W10 に回す」の分け方 2026-10-07、human:kakimomokuri
