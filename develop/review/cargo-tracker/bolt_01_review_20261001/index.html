    cargo-tracker Bolt 1 開発成果物レビュー（2026-10-01）¶

    レビュー対象¶

    • Bolt 1（ウォーキングスケルトン）のコードとテスト: apps/cargo-tracker（コミット 8f736d2〜970fadf）
    • 設計への反映と報告: Bolt 1 終了報告、Bolt 1 計画、バックエンドアーキテクチャ・UI 設計・開発戦略の追記（1221679）
    • 観点: xp-programmer、xp-tester、xp-architect、xp-technical-writer、xp-user-representative の 5 つ（並列に実施）

    総合評価¶

    5 つの視点が一致して、ウォーキングスケルトンとしての出来はよいと評価した。4 パッケージの構成、domain のフレームワークからの独立、名前付きインターフェースでのイベントの公開、common・{vendor} のマイグレーション、developmentOnly の H2 は、ADR-001・003・007 と第 3 章に沿っている。縦割り（画面 → 入力ポート → 集約 → イベント発行記録 → 非同期の購読 → 画面）は、PostgreSQL 18 の上で実際に通っている。

    一方、骨格が確かめたのは「正常系で 1 回だけ配信される」場合に限られる。設計が約束している次の事項には、実装かテストの穴があった。最も重いのは、購読側に冪等性がないことである。再配信のたびに主キー違反が起き、配信が完了しない。

    • 少なくとも 1 回の配信と、受信側の冪等性
    • Clock のマイクロ秒への切り捨て
    • 層の向きの固定
    • イベントの直列化の契約

    業務の面では、次の 3 つを W1 の残りに入る前に決める必要がある。

    • KPI-01 の開始時刻の定義
    • 荷主に見せる業務番号
    • 下書きを正規の状態の流れにすること

    改善提案と対応方針¶

    方針の凡例は次のとおり。

    • 修正: このクローズで直す
    • 後の Bolt: 担当の Bolt を決めて持ち越す
    • 人の判断: 業務か構造の判断が必要

    高¶

    # 提案 箇所 指摘元 方針
    R-01 DE-01 の購読に冪等性がない。再配信で主キー違反になり、配信が完了しないまま残る（ARCH-HO-01 に反する） KpiObservationEventHandler、MyBatisKpiObservationRepository、KpiObservationMapper.xml programmer、architect、tester 修正。保存を「同じ輸送要求の記録があれば何もしない」にし、2 回配信しても 1 件になることを確かめるテストを先に書く
    R-02 メモリ上のリポジトリが上書きするため、本物の INSERT の重複エラーや並び順の違いを隠している InMemoryKpiObservationRepository、InMemoryTransportRequestRepository programmer、tester 修正。契約テストを、メモリ上の実装と MyBatis の実装の両方で走らせる
    R-03 ADR-007 の「Clock をマイクロ秒に切り捨てる」が実装されていない。ナノ秒を持つ時刻が保存の前後で変わる ClockConfiguration tester、programmer 修正
    R-04 配信の統合テストの待ち条件が「記録が 1 件でもある」で、他のテストの行で満たされてしまう。完了の記録も待たずに読んでいる TransportRequestSubmittedDeliveryIntegrationTest tester、programmer、architect 修正。自分の輸送要求 ID で待ち、完了の記録も待つ
    R-05 イベントの JSON の形（共有カーネルの record の部品名を含む）が暗黙の契約になっている。改名すると、未完了の発行記録を復元できなくなる TransportRequestSubmitted、CompanyId、UtcInstant architect 修正。固定した JSON から復元するテストを置き、イベントの進化の規則をバックエンドアーキテクチャに足す
    R-06 KPI-01 の開始時刻の定義（差戻し・再提出・新しい版で時計を戻すか）が業務で決まっていない US-21、要件定義 KPI-01 user-representative 人の判断（D-3）。提案は「版 1 を最初に提出した時刻を開始とし、時計を戻さない」
    R-07 荷主に UUID を見せている。電話やメールで伝えられる業務番号（UI 設計の TR-2026-0142）が必要 submitted.html user-representative、technical-writer 人の判断（D-4）。採番の形式を決め、US-01 の Bolt でデータモデルに入れる
    R-08 下書きを経ない提出のまま積み上げると、状態の流れを作り直すことになる TransportRequestController user-representative 後の Bolt（W1 の US-01）。「下書き → 提出 → 審査中」を最初から正規の流れとして作る
    R-09 小文字や前後の空白で形式の誤りになる。空欄と形式の誤りが同じ文言になる TransportRequestController、new.html technical-writer、user-representative 修正。Web の層で前後の空白を除いて大文字にそろえ、空欄の文言を分ける。ドメインの検証は厳格なまま
    R-10 荷主向けの画面で「輸送要求 ID」だけを表示しており、UI 設計の「見積依頼（輸送要求）」の併記に反する submitted.html technical-writer 修正
    R-11 起動の前提（JDK 25、Docker、開く URL、H2 コンソール、仮の主体）が 1 か所にまとまっていない — technical-writer 後の Bolt（Bolt 2）。operating-setup でアプリケーション開発環境の手順書を作り、README はその入口にする（新規作成のため確認必須）

    中¶

    # 提案 箇所 指摘元 方針
    R-12 受入シナリオの Clock とメモリ上のリポジトリがシナリオ間で共有され、順序に依存する AcceptanceTestConfiguration tester 修正。シナリオの開始時に初期化する
    R-13 テスト戦略は「イベントが配信される」をステップとして明示すると決めているが、同期の配信が組み立てに隠れている walking_skeleton.feature tester 修正。発行したイベントをためて、配信のステップで届ける
    R-14 AT-01 がアプリケーション全体への依存を許すため、domain から application・infrastructure への依存を検出できない。allowEmptyShould(true) が残っている DomainArchitectureTest tester、architect 修正
    R-15 AT-02 が未実装。サービスを infrastructure.config で組み立てる決定が、文字どおりの依存の規則（infrastructure → application を含まない）と矛盾する QuotationConfiguration、バックエンドアーキテクチャ architect、technical-writer 修正（文書）。config を合成ルートとして規則の例外に明記し、理由を書く。AT-02 は Bolt 2。構造の判断として人の承認を得る（D-5）
    R-16 H2 のスモークテスト（テスト戦略）がなく、仮説 H2 の根拠が手動の bootRun だけ。AT-06 も自動化されていない build.gradle tester、architect 修正（H2 のスモークテスト）。AT-06 は CI と合わせて Bolt 2
    R-17 追記専用の transport_request_version を DB の権限で守っていない（afterMigrate のコールバックがない） マイグレーション architect 後の Bolt（Bolt 2）。DB 利用者（DA-02）と合わせて入れ、「アプリの利用者では UPDATE できない」統合テストを書く
    R-18 再配信（起動時・定期）と、完了済みの発行記録の掃除が未設定で、設計との差が記録されていない application.properties architect、programmer 後の Bolt（運用準備）。R-01 の後に、ShedLock と合わせて有効にする。負債として終了報告に記録する
    R-19 KpiObservation.excluded を使う振る舞いがない（YAGNI） KpiObservation programmer 修正。列は DB の既定値に任せ、集約からは外す
    R-20 社内画面の時刻が UTC だけ、エラー要約がない。UI 設計からの逸脱が記録されていない list.html、new.html user-representative、technical-writer 修正（文書）。UI 設計の URL の表に、仮の画面の逸脱として明記する。S-22・C-03 の本実装で適用する
    R-21 完了画面に「次に何が起きるか」がない submitted.html user-representative、technical-writer 修正
    R-22 終了報告の記述が実態と食い違う。
    ・reconstitute を外したとだけ書いている
    ・誤りの内訳がずれている
    ・時刻にタイムゾーンがない
    ・H2 の根拠が手動であることを書いていない
    ・依存の向きは目視で見つけた    		 bolt_01_report.md technical-writer、architect、tester 修正
    R-23 KPI 一覧のテストの期待値が、テンプレートのプロトタイプの文字列と同じで空振りしうる KpiObservationControllerTest tester 修正
    R-24 合成ルートの決定に理由がない バックエンドアーキテクチャ technical-writer 修正（R-15 と合わせて）
    R-25 出発地と目的地が同じでも提出できる TransportRequestController user-representative、technical-writer 人の判断（D-6）。業務ルールとして US-01 AC2 の必須条件に加えるか

    R-36 開発戦略の「受入シナリオだけ」のコマンドで、ArchUnit のテストも一緒に走る development_strategy.md technical-writer 修正（注記）
    R-37 イベントの payload を小さく保つ規則と、マイグレーションを凍結する時点の規則がない バックエンドアーキテクチャ、データモデル architect 修正（文書）
    R-38 自律実行への移行は、AT-02 と受信側の冪等性のテストが入るまで待つべき 終了報告のゲート密度 architect 修正。提案を「Bolt 2 までは各ステップでゲート」に改める

    人の判断が必要なこと¶

    # 事項 提案
    D-1 共有カーネルの DomainEvent インターフェースと、注釈 @DomainEvent の役割が重なる 注釈に一本化する（architect も条件付きで賛成）。次の 3 つを条件とする。
    1. 「domain.events のクラスは @DomainEvent の付いた record」と「@DomainEvent は domain.events にだけある」の両方向を ArchUnit で固定する
    2. 各イベントは受信側の冪等のキーになる業務キーを持つ
    3. ドメインモデルの図を承認つきで直す
    D-3 KPI-01 の開始時刻 版 1 を最初に提出した時刻を開始とし、差戻し・再提出・新しい版で時計を戻さない。R-01 の修正で、版 2 以降の DE-01 では記録を変えない動きになる
