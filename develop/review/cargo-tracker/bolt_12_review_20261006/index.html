    cargo-tracker Bolt 12 開発成果物レビュー（2026-10-06）¶

    レビュー対象¶

    • Bolt 12 の変更: 計画の承認（7fa553b）から 3e80954 まで（apps/cargo-tracker の 50 ファイル、+1,964 行・-32 行と、文書）
    • ステップ 1: 決定を設計文書に反映する
    • ステップ 2〜4:
      • 荷主の回答（提示済み → 詳細設計依頼済み、回答者・回答時刻）と回答できない理由（responseRejectionAt）
      • DE-16（RouteDesignRequested）と、その受け取りによる輸送要求の経路設計中
      • 荷主の回答の入力ポート QuotationResponseService
      • 表の変更: quotation の ROUTING_REQUESTED・回答の 3 列・CHECK、ux_quotation_active の作り直し
      • 画面: C-05 見積りへの回答、C-04 の回答の入口と経路設計中、S-02 の経路設計中の表、S-04 の詳細設計依頼済み
    • 文書: Bolt 12 計画、設計文書・要件定義の差分
    • 観点: xp-programmer、xp-tester、xp-architect、xp-technical-writer、xp-user-representative の 5 つ（並列に実施）
    • 同じ時点の SonarQube の品質ゲート:
    • 1 回目は不合格（新しい Code Smell 3 件）。直して PASS にした（R-26）。
    • PASS の時点: Bug 0、Vulnerability 0、Security Hotspot 0、重複 0.0%、新しいコードのカバレッジ 94.4%。

    総合評価¶

    次の点は規律どおりで、5 つの視点とも評価した（programmer、architect、tester）。

    • 1 つのトランザクションでは見積りの集約だけを更新し、輸送要求の経路設計中への変更は DE-16 の受け取りで別のトランザクションに分けている（DE-03 と同じ形）。
    • 回答できるかを集約の responseRejectionAt の 1 か所で判定し、C-04 の入口・C-05 の表示・回答の拒否がそれを写している（H2）。
    • DE-16 が DE-03 より先に届いても輸送要求を経路設計中にし、遅れて届いた DE-03 では戻らない。
    • 境界値（1 秒前・同時刻・1 秒後）、再配信の冪等、楽観ロックの競合、他社・未提示の見積りの「見つからない」をテストしている。
    • Red を先にコミットする順序を、3 つのステップとも守っている。

    通常の回答の流れ（回答の前・直後・後）では、荷主も営業も迷わず進めると評価された（user-representative）。計画の「利用者の見え方」の表（T-32）が効いた部分である。

    一方、計画の表で「Bolt 11 と同じ文言」とした 経路設計中に見積りが失効した場面 で、荷主と営業がどちらも行き止まりになることが、4 つの視点から挙がった（重要度は高 3、中 1）。中身は次のとおり。

    • 荷主の C-04 で、進み具合は「経路設計者が詳細な経路を設計しています」のまま、見積りの節は「新しい見積りは担当営業にご依頼ください」と食い違う。
    • 依頼した事実の行が消える。
    • 営業は S-04 で「再見積りはできません」と示されるだけで、次の行動がない。
    • この組み合わせのテストが、どの層にもない（tester）。

    H3（計画の段階で利用者の見え方を確認ポイントにすれば、開発レビューで高・中の行き止まりの指摘が出ない）は、この場面については成り立たなかった。

    改善提案（重要度順）¶

    【見え方】は、荷主・営業が画面で行き止まる・誤解する種類の指摘（H3 の判定に数える）。

    高¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-01 【見え方】詳細設計依頼済みで失効した見積りの表示を分ける。荷主の C-04 は依頼した日時の行を残し、「有効期限を過ぎました。詳細経路設計は依頼済みのまま進めています。料金の扱いは担当営業からご連絡します。」と示す。営業の S-04 は「荷主と経路設計者に連絡し、扱いを決めてください（経路設計の途中の再見積りは今後の更新で入れます）」を足す。C-04・S-04 の単体テストを有効期限より後の時計で足す C-04 detail.html、QuotationViews、StaffQuotationController.expiredNotice user-representative、technical-writer、tester（programmer・architect は中） Bolt 12 で修正（文言は人の判断 D-42）

    中¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-02 【見え方】S-02 の経路設計中の表に状態の列（表示する時刻で失効なら「失効」）を足す。RoutingRequestedSummary の Javadoc の約束（失効は表示する側が決める）も守る list.html、TransportRequestReviewController user-representative、technical-writer、programmer、architect、tester Bolt 12 で修正
    R-03 【見え方】C-05 に「この回答は予約の確定ではありません。経路が決まったら、あらためて見積りと経路を確かめて承認していただきます。」と、押し間違えたときの連絡先（業務番号を添えて担当営業へ）を示す。辞退・相談の案内をボタンの前に置く response.html user-representative、technical-writer Bolt 12 で修正
    R-04 輸送要求が経路設計中になった後に DE-03 が届くと、誤った警告のログが出る。同じ版で経路設計中のときも「変えなくてよい」に含め、テストを足す QuotationPresentedEventHandler programmer、architect Bolt 12 で修正
    R-05 「時刻で失効し得る状態」と「Q-INV-18 で数える状態」の列挙が、集約・画面に重複している。QuotationStatus に述語を置き、集約と画面から使う Quotation.isExpiredAt・isActive、QuotationViews.effectiveStatus programmer、architect Bolt 12 で修正。部分一意インデックスの除外リスト化は AC4 の Bolt で検討
    R-06 計画からの変更を文書に戻す。具体的には、承認待ちなど荷主に見えない見積りへの回答は 404、DE-16 の受け取りは見積り作成中からも変える、S-04 は依頼者を出さない、入力ポートを QuotationResponseService に分けた US-24 の決定、UI 設計の C-05・S-04、ドメインモデルの DE-16・荷主の回答、計画 technical-writer、programmer、architect Bolt 12 で修正
    R-07 受入シナリオに、回答の直後（配信の前）に輸送要求がまだ見積提示済みであること（H1 の別のトランザクションの実証）を足す request_route_design.feature tester Bolt 12 で修正
    R-08 【見え方】経路設計中の輸送要求の C-04・C-02 の表示（「経路設計中（A 社の対応待ち）」と案内）の単体テストを、経路設計中の輸送要求で書く。今の C-04 のテストは審査中の輸送要求に詳細設計依頼済みの見積りを組み合わせている TransportRequestControllerTest tester Bolt 12 で修正
    R-09 ステップの引数の状態を対応表で変換し、定数と比べない。知らない呼び名は分かる例外にする QuotationResponseSteps tester Bolt 12 で修正
    R-10 荷主の回答の種類（PROCEED）がドメインになく、リポジトリが決めている。値オブジェクト ShipperResponse を集約に持たせる MyBatisQuotationRepository architect、programmer AC2（辞退）の Bolt の最初のリファクタリング
    R-11 ck_quotation_presented を、詳細設計依頼済みも提示時刻を持つ形に広げる マイグレーション architect AC4・AC5 で状態を足すマイグレーションでまとめる（スキーマの変更）
    R-12 計画のステップの状態の記号が凡例と承認ゲートに合っていない（承認ゲートを通らずにステップ 4 に入った） 計画 technical-writer 人の判断（D-43）。終了報告に、承認ゲートを後でまとめて受ける理由を書く

    低¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-13 【見え方】二重送信の「すでに回答しています」を、警告でなく結果として「すでに詳細経路設計を依頼しています」と示す QuotationResponseController user-representative、technical-writer 修正
    R-14 【見え方】荷主向けの競合の文言を「見積りが更新されました。最新の見積りを確かめてから回答してください」にする 同上 user-representative 修正
    R-15 【見え方】置換済みの見積りへの回答の文言を、新しい見積りがすでに提示されている場合にも合う形にする 同上 technical-writer 修正
    R-16 【見え方】「承認の準備ができたらお知らせします」は通知（US-22）ができるまで守れない。「担当営業からご連絡します」にする TransportRequestLabels user-representative 修正
    R-17 【見え方】回答の直後、DE-16 を受け取るまでの数秒、進み具合が「お客様の対応待ち」のまま C-04 user-representative、technical-writer 直さない（計画で受け入れた。見積りの見出しと結果の文言は正しい）
    R-18 荷主向けのテンプレートの開発の注記が、荷主のブラウザに届く HTML コメントになっている。Thymeleaf のパーサーレベルのコメントにする response.html architect 修正
    R-19 「荷主に見える見積り」（提示時刻がある）の判定が、照会と入力ポートの 2 か所にある。集約の問い合わせにまとめる QuotationResponseService、QuotationQueryService、C-05 programmer、tester 修正
    R-20 DE-16 の概算の出発・到着を確かめるテストを足す QuotationTest tester 修正
    R-21 MyBatisQuotationIntegrationTest の CHECK の CSV の「Bolt 11 でまだ使わない状態」の例が、別の理由で通り続けている。未使用の状態に替え、制約名まで確かめる 統合テスト architect 修正
    R-22 画面の層の待ちが回数を使い切ったら、分かる理由で失敗させる RouteDesignUiSteps tester 修正
    R-23 Javadoc の抜けと古い出典（selectRoutingRequested、InMemoryQuotationRepository の Bolt 11・12）、responseRejectionAt の判定の順の書き方 マッパー、テスト用のリポジトリ、集約 programmer、technical-writer 修正
    R-24 C-05 の画面イメージと注、S-02 の列の書き方、C-05 の「状態」の行が実装・設計とずれている UI 設計、response.html technical-writer 修正
    R-25 集約の復元の引数（16）、QuotationRejection の操作ごとの分割、View の肥大、イベントの受け取りの重複 集約、値、画面 programmer、architect 直さない（次に触る Bolt の候補として既知の課題に書く）
    R-26 SonarQube の新しい Code Smell 3 件（C-05 の URI の文字列、record パターン、テストのラムダ） C-05、統合テスト SonarQube 修正（レビューの前に直した）
    R-27 冪等の受入シナリオに、2 回目の配信で輸送要求の版が変わらないことと、審査中の輸送要求に DE-16 が届いても変わらない例を足す request_route_design.feature tester 修正

    人の判断事項¶

    # 判断事項 AI の提案
    D-42 経路設計中に見積りが失効したときの案内（R-01）。業務責任者の D-36-3 の回答までの仮の文言 荷主には「有効期限を過ぎました。詳細経路設計は依頼済みのまま進めています。料金の扱いは担当営業からご連絡します。」、営業には「荷主と経路設計者に連絡し、扱いを決めてください（経路設計の途中の再見積りは今後の更新で入れます）」
