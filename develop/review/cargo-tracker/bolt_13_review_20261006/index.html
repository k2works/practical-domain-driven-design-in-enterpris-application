    cargo-tracker Bolt 13 開発成果物レビュー（2026-10-06）¶

    レビュー対象¶

    • Bolt 13 の変更: 計画の承認から 4e0adb3 まで
    • スパイク spikes/ts-01-totp/（学習テスト 29 件）
    • ADR-011（提案）、技術スタックの多要素認証と TS-01、リスク台帳と引継ぎ
    • Bolt 13 計画
    • 観点: xp-architect、xp-tester の 2 つ（並列に実施）。本体のコードを変えないため、計画の確認ポイント 5 で 5 つの視点から縮めた
    • SonarQube とデモの動画は対象外（確認ポイント 5）

    総合評価¶

    次の点は 2 つの視点とも評価した。

    • 本体と分けた Gradle プロジェクトで学習テストを書き、本体の依存と CI に触れていない（確認ポイント 1・2）。
    • RFC 6238 の試験ベクトルで 3 つの候補を同じ入力のまま比べ、骨組みを先に置いて Red を記録した（T-37）。
    • 資料の少ない振る舞い（結果のトークンの型が toBuilder() を宣言しないと要素が合わさらない、要素の権限の発行時刻がシステムの時計で決まる）を見つけ、ADR に残した。
    • password と TOTP の失敗を AuthenticationFailureBadCredentialsEvent の 1 か所で数え、監査記録（IA-INV-08）を書く箇所とそろえた。
    • 時計を注入し、TOTP・ロック・最長 8 時間の判定を決定的に確かめた。
    • 「開発環境では TOTP を飛ばす」案を退け、開発と本番で認証の流れをそろえた。

    一方、ADR の主張のうち 3 つは、実装に穴があるかテストの裏付けがなかった（tester）。

    1. 最長 8 時間を、期限切れの session に TOTP だけを送って延ばせた（プローブで再現）。
    2. ロックと最長 8 時間の境界が「同時刻」の 1 点だけで、ロックの回数・期間・最長の時間・窓を変えるミューテーションがすべて残った。
    3. ADR が採る (b) java-otp が、2 段階のログインの流れで一度も動いていなかった（流れは (a) の実装の上）。

    加えて architect は、開発環境の入力済みの守りが「設定の値があるか」の 1 層だけであること、identity への置き方と仮の主体の置き換えの順が ADR にないこと、TOTP の段で session の ID を変えていないことを高とした。

    方式（Spring Security 7 の要素の権限で 2 段階のログインを組み、TOTP の生成は小さなライブラリに任せる）は 2 つの視点とも維持できると評価した。

    改善提案（重要度順）¶

    高¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-01 開発環境の入力済みを多層で守る。(1) 入力済みの部品を @Profile("dev") の bean にする (2) コードを作れるのは開発用の固定の秘密だけにする (3) dev の外で設定があれば起動を失敗させる (4) 開発用の利用者と秘密は dev だけの投入の場所に置く。本体の dev が「H2 で bootRun」の意味と相乗りすることも書く LoginController、DevLoginProperties、ADR architect (1)(3) はスパイクで直してテストを足す。(2)(4) は ADR の決定に書く（D-45）
    R-02 identity への置き方と仮の主体の置き換えの順を ADR の決定に書く。quotation → identity → quotation::events の循環を避け、認証の主体の型を shared に置く ADR architect ADR の決定の案に書く（D-48）
    R-03 TOTP の段で session の ID を変え、CSRF のトークンを作り直す（formLogin と同じ扱い） TotpAuthenticationFilter architect（高）、tester（中） スパイクで直し、テストを足す
    R-04 期限切れの session に POST /login/totp を送ると、TOTP の認証が期限の確認より先に動き、本人確認の時刻が書き直されて 8 時間延びる SecurityConfig、SessionLifetimeFilter、TotpAuthenticationFilter tester スパイクで直し、テストを足す
    R-05 ロックの境界のテストを足す（4 回ではロックしない、14 分 59 秒ではロック中、成功で数え直す、password の後にロックされたら正しい TOTP も拒否） MfaLoginTest tester テストを足す
    R-06 最長 8 時間の直前（7 時間 59 分 59 秒）のテストを足す MfaLoginTest tester テストを足す
    R-07 (b) java-otp を流れの中で使うか、6 桁と窓の照合を学習テストで確かめる。生成器のスレッドセーフも確かめる SpikeUsers、TotpCandidatesTest tester SpikeUsers を java-otp に切り替え、6 桁の試験ベクトルのテストも足す。スレッドセーフは未確認として ADR に書く

    中¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-08 全体に要素を求める注釈と、初回の登録（AC7）・再設定（SEC-08）の画面の認可の関係を、URL ごとに要素を求める案と比べる ADR architect ADR の選択肢と未確認の項目に書く（W5）
    R-09 Spring Session JDBC を前提にした確認（直列化、changeSessionId、30 分の設定の効き方、8 時間と即時失効の経路）を未確認に足す ADR architect ADR の未確認の項目に書く
    R-10 失敗の回数と再利用の拒否を原子的に更新する（条件付きの UPDATE の更新件数で判定する） ADR architect ADR の決定の案に書く
    R-11 ライブラリの選択の根拠を正確にする。java-otp が担うのは HOTP の切り詰めだけ。Base32 と otpauth:// は確かめておらず、出どころも未定。(a) の却下理由は弱く、後で替えられる判断と明記する ADR architect、tester（低） ADR を直す
    R-12 TOTP の生成をポートの裏に置き、ロック・再利用・回復コードの不変条件を分ける ADR architect ADR の「US-18 の Bolt で要るもの」に書く
    R-13 リスク台帳の更新が「影響度」を下げている。下がったのは発生確率 リリース計画 architect 影響度を中に戻し、発生確率を低にする（D-46）
    R-14 窓のテストを、刻みの開始・終了で ±1 を受け付け ±2 を拒否する形に分ける TotpCandidatesTest tester テストを足す
    R-15 ロック中の拒否を、LockedException で確かめる。ロック中に誤った password を送っても期限が延びないことも確かめる MfaLoginTest tester 前者はテストを足す。後者は W5 の統合テストに回す（D-47）
    R-16 toBuilder() の要否、既定のリポジトリ、issuedAt の時計を特性テストに固定する MfaLoginTest tester（architect の低「版を上げるときの守り」と同じ） W5 の統合テストに回し、ADR のコンプライアンスに書く（D-47）
    R-17 Argon2id が Bouncy Castle なしで符号化できないことを、実際の符号化で確かめる。bcrypt の強さも確かめる PasswordStorageTest tester テストを足す
    R-18 既定の設定で A-02 にコードが入らないことを確かめる DevLoginPrefillTest tester テストを足す

    低¶

    # 提案 箇所 指摘元 AI の提案する対応方針
    R-19 TOTP の成功の後の行き先を、保存した request にする（深いリンクから入ったとき） TotpAuthenticationFilter architect ADR の画面の行に書く（US-16 と一緒に決める）
    R-20 「最長の時間に既製の部品はない」を確かめる（RequiredFactor の有効期間） ADR architect 確かめて ADR を直す
    R-21 まだない文書（終了報告）へのリンク ADR architect 終了報告を書いて解消する
    R-22 SessionTimeoutTest は設定の値を読むだけ。ADR の「設定で守れる」を弱める SessionTimeoutTest、ADR tester ADR を「設定した」に直し、振る舞いは W5
    R-23 回復コード 10 個（SEC-09）とハッシュでの保存を確かめていない ADR tester 未確認の項目に書く

    懸念事項¶

    # 懸念 指摘元 対応
    K-01 利用者 A の session に利用者 B の password を送ったとき、A の FACTOR_TOTP が B に引き継がれないか architect テストを足した。Spring Security 7.1.1 の AbstractAuthenticationProcessingFilter は、主体の名前が同じときだけ要素を合わせる（バイトコードで確かめた）
    K-02 AC2（利用者の存在や失敗箇所を推測させない）と、2 段階の画面・ロックの表示の緊張。A-02 に進めば password が正しいと分かり、ロックの表示から利用者の存在が分かる architect、tester ADR に W5 で人が決める論点として書く
    K-03 ステージング・本番で dev プロファイルを付けないことが運用の手順にない architect ADR に書き、W5 で運用の手順と IaC に足す
    K-04 TOTP はサーバーの時計に依存する（NTP の前提） architect ADR に書く。非機能要件・運用要件への反映は W5
    K-05 方式の決定の承認ゲートを AI の判断で通し、技術スタックとリスク台帳は案の段階で更新した architect 終了報告の承認の議題の先頭に、ADR が却下されたときに戻す箇所として書く
    K-06 テストの共有の状態（singleton の利用者、時計）は並列実行で壊れる tester ADR に、本体ではテストごとにデータを分ける方針として書く
    K-07 T-37 の Red の記録が事実と違う tester 計画のステップ 3 の結果を直す（下の事実）
    K-08 ADR のテストの一覧に SpikeSetupTest がない tester ADR を直す

    K-07 の事実（tester が 8ba68bf を取り出して実行した結果）: 28 件中 9 件が失敗した（MfaLoginTest 7 件、DevLoginPrefillTest 2 件）。2 段階のログインの 9 件のうち 2 件（未認証で業務の画面を開く、password を経ずに TOTP だけを送る）は、枠組みの既定で骨組みの上でも通った。失敗した 7 件のうち 4 件（8 時間、ロック、回復コード、正しい TOTP）は、前提の段階（ログインできない）で落ち、本命のアサーションは Red を見ていない。Green の 7c02540 で、4 件の期待値を /login/totp から factor.type・factor.reason の付いた URL に書き換えた。SessionTimeoutTest は Green のコミットで足し、Red を経ていない。

    スコープ外の発見¶

    # 発見 指摘元 扱い
    S-01 本体の server.servlet.session.cookie.same-site=lax は「CSRF の防御は US-18」のつなぎ（D-21）。US-18 で CSRF の防御を有効にし、つなぎとの関係を整理する architect W5 の計画の確認ポイントにする
    S-02 複数の利用者に対する password の総当たり（password spraying）は、利用者ごとのロックでは防げない。送信元ごとの流量の制限は SEC-04〜10 にない architect 非機能要件で扱うかを W5 の計画で決める
    S-03 開発用の利用者の投入で、全員に同じ固定の秘密を使う形を写すと、利用者ごとの秘密が使われていないことにテストが気づけない tester ADR の開発環境の節に書く
    S-04 /staff を誤って permitAll にすると principal が null で 500 になる tester 本体では URL ごとの認可を Web テストで網羅する（ADR のコンプライアンス）

    対応結果¶

    判断（2026-10-06、Bolt 13 のステップ 5）¶

    # 判断 根拠
    D-45 高の指摘のうち、スパイクで直せるもの（期限の迂回、session の固定化、入力済みの守りの 1・2 層目、java-otp を流れで使う）は、ADR に「確かめた」と書く前にスパイクで直し、テストで確かめる ADR の主張を学習テストで裏付けるのがスパイクの目的。直さずに書くと、W5 に穴のある方式が渡る
    D-46 リスク台帳の「TOTP と Spring Security 7 の統合が想定より難しい」は、影響度を中に戻し、発生確率を中から低にする。ADR-011 が却下されたら中に戻す スパイクで下がったのは統合の難しさ（起こりやすさ）で、起きたときの影響は変わらない
    D-47 特性テスト（R-16）、ロック中の誤りで期限が延びないこと（R-15 の後半）、Spring Session JDBC（R-09）、Base32 と URI（R-11）、回復コード 10 個（R-23）、AC2 の緊張（K-02）は、W5 の US-18 の Bolt に回し、ADR の未確認の項目とコンプライアンスに書く スパイクの時間箱を超える。本体の表と Spring Session の上でないと意味のある確認にならない
    D-48 認証の主体の型を shared に置き、identity が利用者・TOTP の資格・回復コード・失敗の記録と認証の部品を持つ形を、ADR の決定の案に書く。置き換えの順も書く 今の依存のままでは quotation → identity → quotation::events の循環になる。採否は W5 で人が決める

    D-45〜D-48 は、人の指示（/goal Bolt13）で AI の判断のまま進め（T-36）、2026-10-06 に終了報告の承認の場で human:kakimomokuri がすべて承認した。

    改善提案ごとの対応（Bolt 13 計画 のステップ 5、2026-10-06）¶

    # 対応 コミット
    R-01 入力済みを @Profile("dev") の DevLoginPrefill に移し、controller はその有無だけを見る。DevLoginGuard で、dev の外（または staging・prod と併用）で設定があれば起動を失敗させる。(2)(4) と本体の dev の相乗りは ADR に書いた Red 8eef0c7、Green 0616c67
    R-02 ADR の決定 4（置き方と置き換えの順）に書いた ADR の更新のコミット
    R-03 TOTP のフィルターに ChangeSessionIdAuthenticationStrategy と CsrfAuthenticationStrategy を設定した。session の ID が変わるテストを足した Red 8eef0c7、Green 0616c67
    R-04 期限の確認を UsernamePasswordAuthenticationFilter の前（TOTP の認証より前）に置き、期限切れはログインの送信だけを新しい session で続けさせる。本人確認の時刻は、その session で初めて TOTP が通ったときだけ残す。迂回と送り直しのテストを足した 同上
    R-05 4 回ではロックしない、14 分 59 秒ではロック中、成功で数え直す、password の後にロックされたら正しい TOTP も拒否、のテストを足した（実装は変えずに通る特性のテスト） 8eef0c7
    R-06 7 時間 59 分 59 秒で開けるテストを足した 8eef0c7
    R-07 SpikeUsers の生成を java-otp（6 桁、HMAC-SHA1、30 秒）に切り替え、窓と一定時間の比較はアプリケーションで書いた。2 段階のログインの全テストが java-otp の上で通る。6 桁で先頭の 0 を保つ全試験ベクトルのテストを足した。スレッドセーフは未確認 Red 8eef0c7、Green 0616c67
    R-08〜R-12 ADR に書いた ADR の更新のコミット
    R-13 D-46 同上
    R-14 刻みの開始・終了で ±1 を受け付け ±2 を拒否する、パラメーター化したテストを足した 8eef0c7
    R-15 ロックの理由（LockedException）で拒否されることを確かめた。後半は D-47 8eef0c7
    R-16 D-47 —
    R-17 Argon2id の符号化が NoClassDefFoundError になること、bcrypt が $2a$10$（強さ 10）で保存することを確かめた 8eef0c7
    R-18 既定の設定で password の後の A-02 にコードが入らないテストを足した 8eef0c7
    R-19 ADR の画面の行に書いた ADR の更新のコミット
    R-20 Spring Security 7.1.1 に RequiredFactor の有効期間（validDuration）があり、判定の時計は AllRequiredFactorsAuthorizationManager.setClock で替えられることを確かめた（クラスの公開 API）。期限切れは要素の再入力を求めるもので session を終わらせないため、AC5 の再認証には session を捨てるフィルターを使う。どちらで組むかは W5 で比べる。ADR を直した 同上
    R-21 終了報告を書いた 本報告のコミット
    R-22 ADR を「設定した」に直し、振る舞いは W5 の統合テストに回した ADR の更新のコミット
    R-23 D-47 —

    修正の後、スパイクの学習テストは 57 件すべてが通る（Red 8eef0c7 では 57 件中 5 件が失敗: 起動の確認、利用者の取り違え、期限の迂回、session の ID、送り直しの時刻）。利用者の取り違えの失敗は、スパイクの利用者 STAFF の状態がなかったための前提の失敗で、枠組みの振る舞いは正しかった。
