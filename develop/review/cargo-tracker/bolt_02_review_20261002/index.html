    cargo-tracker Bolt 2 開発成果物レビュー（2026-10-02）¶

    レビュー対象¶

    • Bolt 2（CI と品質の安全網）の変更: コミット a5b9a1b〜48bb848
    • 主な対象: apps/cargo-tracker/build.gradle、config/checkstyle・config/spotbugs、アーキテクチャテスト（AT-02、ドメインイベントの配置）
    • そのほか: .github/workflows/cargo-tracker-ci.yml、ops/scripts/sonar_local.js、sonarqube.config.json、Bolt 2 計画・Bolt 2 終了報告、開発戦略とテスト戦略の追記
    • 観点: xp-programmer、xp-tester、xp-architect、xp-technical-writer、xp-user-representative の 5 つ（並列に実施）

    総合評価¶

    5 つの視点は、./gradlew check 1 本にまとめた安全網を、シンプルで意図のはっきりした構成と評価した。

    • ローカルと CI で入口が同じである
    • 抑止は理由つきで最小にしている
    • AT-06 の検査対象（productionRuntimeClasspath）を正しく選んでいる
    • ドメインイベントの規則が両方向である

    一方、品質ゲートには 偽の安心 を与える穴があった。中でも重いのは次の 2 つである。

    • sonar-local:gate が Quality Gate の FAIL でも成功で終わる。終了報告の「PASS」は人が出力を読んだ結果であって、仕組みが判定したものではなかった
    • JaCoCo の閾値は分母が 0 のとき黙って通る。application の分岐の閾値は、実際には何も検証していなかった

    このほか、次の 3 点も挙がった。

    • AT-02 は層の外（platform、ルートのパッケージ、技術への依存）を見ていない
    • CI のアクションが SHA で固定されていない
    • 運用スクリプトの変更が手順書に反映されないまま、ステップ 6 を「完了」としていた

    利用者の視点からは、技術の Bolt はここまでにし、次の Bolt を業務のストーリー（US-01 AC2）にすべきだという意見が出た。

    改善提案と対応方針¶

    方針の凡例: 修正 はこのクローズで直す。後の Bolt は担当の Bolt を決めて持ち越す。人の判断 は業務か構造か外部連携の判断が要る。

    高¶

    # 提案 箇所 指摘元 方針
    R-01 sonar-local:gate が Quality Gate の FAIL でも成功で終わる。スキャン直後は前回の結果を読むおそれがある ops/scripts/sonar_local.js tester、technical-writer 修正。スキャンに -Dsonar.qualitygate.wait=true を付けて反映を待ち、FAIL ならスキャンを失敗させる。gate も OK 以外で失敗させる（T-7 も同時に片づく）
    R-02 分母が 0 の JaCoCo の閾値は黙って通る。application の分岐は 0 件で、閾値が何も検証していない。include のパターンが何も拾わなくても緑になる build.gradle tester 修正。各層の検証の前に、対象のクラスが 1 件以上あることを確かめる。分岐のない層は報告で「対象なし」と書く
    R-03 GitHub Actions をタグで参照している。SHA で固定し、Dependabot で更新したい cargo-tracker-ci.yml architect、programmer、tester 修正（SHA の固定）。Dependabot の追加は、ボットが Pull Request を作る外部連携のため人の判断（D-7）
    R-04 AT-02 が層の外を見ない（consideringOnlyDependenciesInLayers）。application から Web・MyBatis への依存、platform との依存を検査しない LayerArchitectureTest architect、programmer、tester 修正。application は Web・MyBatis・Servlet に依存しない、platform はコンテキストから参照されずコンテキストに依存しない、の規則を足し、規則が見る範囲を Javadoc に書く
    R-05 計画のステップ 6 は「運用手順書にも書く」としたが、手順書の scanType の表が gradle sonar のまま。それなのにステップ 6 を「完了」とした docs/reference/SonarQubeローカル環境セットアップ手順書.md technical-writer 修正
    R-06 開発戦略が「Quality Gate を判定する」と書くが、コマンドは失敗しない development_strategy.md technical-writer 修正（R-01 の後の実際の挙動に合わせて書き直す）
    R-07 技術の Bolt はここまでにし、次の Bolt は US-01 AC2 にする。Bolt 3 の項目は、必要になるストーリーの Bolt に寄せて分ける — user-representative 人の判断（D-8）。AI も賛成する
    R-08 D-3・D-4・D-6 が「提案」のまま。US-01 の Bolt の計画の前に人の決定として記録し、D-6 はユーザーストーリーの受入条件に入れる bolt_01_report.md、user_story.md user-representative 人の判断（D-3・D-4・D-6。D-4 は採番の単位と版の表記まで）

    中¶

    # 提案 箇所 指摘元 方針
    R-09 AT-06 の照合が座標の完全一致で、旧グループ（org.hibernate:hibernate-core、javax.persistence）をすり抜ける。禁止のリストをタスクの入力にしていない build.gradle programmer、architect、tester 修正。グループの接頭辞で照合し、org.hibernate.validator は許す
    R-10 カバレッジの閾値が build.gradle とテスト戦略の表の 2 か所にある build.gradle、test_strategy.md programmer 修正。CI の閾値の正は build.gradle とし、テスト戦略からは参照する
    R-11 domain.events の規則が、イベント専用の enum や入れ子の値を置けなくする DomainEventArchitectureTest architect 修正。規則の対象をトップレベルのクラスに限り、イベントが持つ値は入れ子にする方針を書く
    R-12 「イベントは UUID と共有カーネルの型だけで表す」が機械化されていない DomainEventArchitectureTest architect 修正
    R-13 D-1 は ADR-003 の改訂、D-5 は ADR-001 からの参照で記録したい。infrastructure.config は @Configuration のクラスに限りたい ADR、architecture_backend.md、domain_model.md architect、technical-writer 修正（@Configuration の規則）。ADR と設計文書への反映は、D-1・D-5 の承認の後
    R-14 sonar_local.js が check sonar を動かすため、check が失敗すると解析が走らない。トークンがコマンドラインに出る sonar_local.js architect、programmer 修正。test jacocoTestReport sonar にし、トークンは環境変数 SONAR_TOKEN で渡す（Gradle の分岐）
    R-15 カバレッジが受入シナリオ・統合テストを含む単一の実行データで、ユニットテストの不足を隠す build.gradle tester 後の Bolt（Bolt 3 以降。テストの実行を分ける）
    R-16 AT-02 が interfaces → domain を無条件に許し、Controller がリポジトリを直接使って application を迂回しても検出できない LayerArchitectureTest tester 修正。interfaces はリポジトリ（送信ポート）に依存しない、の規則を足す
    R-17 テスト戦略の「受入条件の数との照合」が未実装 CI tester 後の Bolt（US-01 の Bolt。Bolt 2 計画で意図的に先送りしたもの。受入条件のシナリオができてから入れる）
    R-18 @wip の検出が規約（必須の実行から外す・残したまま Bolt を完了しない）と食い違う。部分一致で誤検出し、ディレクトリがないと黙って通る cargo-tracker-ci.yml tester、programmer、architect 修正。@wip をタグとして厳密に照合し、develop と Pull Request では警告、main への push では失敗にする。grep の終了コード 2 は失敗にする
    R-19 計画のステップ 8 を承認の前に [x] にした bolt_02_plan.md technical-writer 修正（[?] に）
    R-20 Spotless と Checkstyle・SpotBugs の実際の版が技術スタックにない。D-5 は「承認待ち」のまま tech_stack.md、architecture_backend.md technical-writer、architect 修正（実際の版を書き、Spotless は「承認待ち」として載せる）。D-5 の確定は承認の後
    R-21 開発戦略の「check の後にスキャンし」が、先に check を流す必要があるのか読み取れない development_strategy.md technical-writer 修正（R-06 と合わせて）
    R-22 次の Bolt を業務にし、UI-HO-04（C-03 のプロトタイプ）に実際の利用者が触る場を W1 に取る。週次の見直しで技術の Bolt の時間を業務 SP と分けて記録する リリース計画 user-representative 人の判断（D-8 と合わせて）。週次の見直しの記録の項目は W1 の見直しで足す
